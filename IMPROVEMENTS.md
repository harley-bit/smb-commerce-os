# Improvements (not acted on mid-card, per CLAUDE.md build protocol)

- **[D037]** `packages/domain/src/auth/rbac.ts`'s `MerchantRole` type (`"OWNER" | "ADMIN" | "STAFF" | "READ_ONLY"`) is structurally identical to, but declared independently of, `packages/db`'s `MerchantUserRole` (`packages/db/src/repositories/MerchantUserRepository.ts`) — domain code can't depend on `packages/db`, so this is a real duplicate source of truth for the same four literals (also inlined a third time as the `enum` array in both `schema/sqlite.ts` and `schema/pg.ts`). Not unified here since the card's job was the RBAC matrix itself, not a cross-package role-type refactor. Future cleanup: `packages/db`'s `MerchantUserRole` could just be `import type { MerchantRole as MerchantUserRole } from "@smb-os/domain"` since `packages/db` already depends on `packages/domain`.
- **[D037]** `packages/db/src/services/ListingService.ts`'s `assertCanManageCatalog` (D023) and `VariantService`/`ProductListingService`'s reuse of it predate this card's `assertCan(ctx, action, resource)` and duplicate its own small role check (`actingRole !== "OWNER" && actingRole !== "ADMIN"`) instead of calling it. Migrating those three call sites to `assertCan(ctx, "catalog:manage")` would give the codebase the single enforcement point `docs/design/07` calls for, but that's a refactor of already-shipped, already-tested service code, not something this card's acceptance criteria required.
- **[D055]** `packages/domain/src/reservations/reservationStateMachine.ts`'s `ReservationState` type is structurally identical to, but declared independently of, `packages/db/src/repositories/ReservationRepository.ts`'s pre-existing `ReservationState` (from D049) — the same duplicate-type pattern as the `MerchantRole`/`MerchantUserRole` case above. `packages/db` already depends on `packages/domain`, so `ReservationRepository.ts` could `import type { ReservationState } from "@smb-os/domain"` instead of declaring its own; not done here since it's a refactor of already-shipped repository code outside this card's acceptance criteria. No service layer yet calls `applyReservationEvent` to actually persist a transition — D050–D054 only ever insert new `HELD` rows.
- **[D066]** `RentalReservationService.createRentalReservation` allocates across *every* `AVAILABLE` unit for a variant regardless of `locationId` — if a merchant's fleet for one variant is split across multiple pickup locations, this card doesn't filter candidates to the requested location before running the free-interval/allocator narrowing. Not addressed here since the card's acceptance criteria ("conflict rejected", "allocator picks a free unit") don't require location-awareness and no prior card established a location-scoped allocation policy to follow. Future card should add an optional `locationId` filter to the candidate query before it's a real bug for a multi-location merchant.
- **[D067]** `ProductSaleService.sellProduct`'s new `isSubjectCurrentlyBlocked` check (invariant I3) reads outside any transaction shared with the sale's own stock-decrement/unit-status writes, so it is best-effort against a reservation being created for the same unit concurrently with the sale — unlike the reservation write path itself (`ReservationRepository.createGuarded`), which serializes via `BEGIN IMMEDIATE`. Not closed here since the card's acceptance criterion ("selling a currently-rented unit is rejected") only requires the sequential case. Worth revisiting alongside D068 (the mirror invariant, sold unit cannot be reserved) if the pair ever needs a genuine cross-write-path concurrency guarantee rather than two independent read checks.
- **[D068]** Invariant I4 ("sold unit cannot be reserved") is already fully enforced by D066's `RentalReservationService` candidate filter (`unit.status === "AVAILABLE"`) — a SOLD/RETIRED unit is never in the candidate set, so `selectUnitForAllocation` throws `NoAvailableUnitError` the same way it would for a pure scheduling conflict. This card added regression tests (`RentalReservationService.test.ts`, "invariant I4") rather than new production code. The cross-write-path concurrency gap flagged in the D067 entry above is unaffected: this filter reads unit status outside `ReservationRepository.createGuarded`'s `BEGIN IMMEDIATE` transaction, so it remains best-effort against a concurrent sale of the same unit rather than a serialized guarantee.
- **[D069]** `ProductSaleService.sellProduct`'s future-reservation override path (`findFutureBlocking` check, `cancel` calls, notifier callback) has the same cross-write-path concurrency shape as I3/I4 above: the check and the cancellations happen outside a shared transaction with the sale's own stock-decrement/unit-status writes, so a reservation created for the unit concurrently with an override sale could theoretically be missed. Not closed here since the card's acceptance criterion (cancel affected bookings and notify) only requires the sequential case, same reasoning as D067/D068. Also: `FutureReservationCancelledNotifier` is a pure in-process callback with a default no-op — no real notification channel (email/SMS) exists anywhere in the codebase yet; wiring one in is future work, not something this card's scope covers.
- **[D123]** `apps/web/src/app/m/[slug]/l/[listingSlug]/page.tsx` fetches `GET /v1/m/{slug}/listings/{listingSlug}` once just to read `mode` and pick `ProductDetailView` vs `ServiceDetailView`, then each of those self-contained components fetches the same detail again for its own fields — a deliberate duplicate request to keep D122's `ProductDetailView` (and its existing test contract) untouched rather than refactoring both views into fetch-once presentational components. Worth collapsing into a single fetch-and-dispatch if a third mode (D124's RENTAL) makes the pattern feel worse.
- **[D123]** `ServiceDetailView.tsx` only ever books against `resourceIds[0]` — a SERVICE listing assigned to more than one resource (`docs/design/03` "which resources can fulfil a service") has its other resources' availability silently ignored on the storefront slot picker, same documented single-resource deviation `docs/logs/D058.md`/`docs/logs/D059.md` already flagged for `AvailabilityService.getResourceAvailability`/`BookingService`. Not resolved here since resolving the `listing_resources` fan-out (union free intervals across every assigned resource, or let the customer pick a specific staff member) was explicitly called out as out of scope in those same logs and this card's estimate didn't budget for it.
- **[D124]** `RentalDetailView.tsx` only ever checks/books `variants[0]` of a rental listing — same single-variant deviation category as D123's `resourceIds[0]`; a rental listing with more than one variant (e.g. two tent sizes) has every variant but the first invisible on the storefront. Not resolved here for the same reason as D123's equivalent entry — out of this card's scope/estimate.
- **[D124]** Clicking "Reserve" on `RentalDetailView` only toggles local `selected` state — there is still no rental-line checkout/cart endpoint anywhere in this codebase (`CartService` remains PRODUCT-only, the gap D108's log already flagged and left open), so a storefront visitor can prove a date range is free and see the deposit, but cannot actually place a hold from this page yet. A future Phase 7 card (cart/checkout) is the natural place to wire this button to a real reservation-creating endpoint.
- **[D124]** `GET /v1/m/{slug}/listings/{listingSlug}/rental-availability`'s rate limit (3/60s, same tight budget as `./availability.ts`) means a visitor dragging a date-range picker or retrying quickly will see 429s with no client-side retry/backoff or debounce on `RentalDetailView`'s date-change effect. Worth a debounce if real usage shows this budget is too tight for a two-input date picker's natural interaction pattern.
- **[D125]** `RentalDetailView.tsx` (D124) still uses a single free-text start/end date-range picker with no calendar UI of its own — `availabilityWindow.ts`'s month-paging pattern was only wired into `ServiceDetailView`'s slot picker this card, since the card's literal deliverable ("free-interval display with month navigation") describes the SERVICE `free: Interval[]` list, not a rental date-range check. Extending the same pattern to `RentalDetailView` is a natural follow-up.
- **[D127]** This card's countdown/expiry closure lives entirely on the merchant-dashboard confirm path (`CalendarView.tsx`'s new "Hold" column, `POST /bookings/:id/confirm`) because that is the only place in this codebase where a real `HELD` reservation can currently be confirmed at all — `POST /bookings` (and its confirm counterpart) still asserts `bookings:manage` (staff-only, per `apps/api/src/routes/bookings.ts`'s own comment: "a future public/anonymous checkout endpoint" doesn't exist yet), and the storefront's `ServiceDetailView`/`RentalDetailView` "Reserve" buttons still only toggle local selection state (D124's log, unchanged since). A customer visiting the storefront today never sees a real hold or its countdown — that requires an anonymous/customer-authenticated hold-creation endpoint, which is natural scope for D128–D131 (checkout) rather than this card. The countdown UI (`HoldCell`) and the server-side `HoldExpiredError` guard (`ReservationRepository.confirm`) are both mode-agnostic and reusable once that endpoint exists.
