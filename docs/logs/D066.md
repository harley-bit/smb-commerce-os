## What happened

Implemented rental reservation creation as `RentalReservationService` (`packages/db/src/services/RentalReservationService.ts`), the `RENTAL`-mode counterpart to D059's `BookingService` for `SERVICE`-mode — same relationship, different subject-selection problem. `BookingService` occupies a `RESOURCE` the caller already names; a rental instead has to *pick* which of the variant's serialized `inventory_units` to occupy, since the caller only knows the variant, not a specific unit. `createRentalReservation` loads the variant (rejecting non-`RENTAL` variants via `VariantNotRentalError`), lists its `AVAILABLE` inventory units, narrows them to ones with no blocking reservation over the requested interval (`ReservationRepository.findBlocking`, `subjectType: "INVENTORY_UNIT"`), derives each survivor's `lastReturnedAt` via a new `ReservationRepository.lastReturnedAt()` method (most recent `endsAt` among that subject's `COMPLETED` reservations, `null` if never completed one), and hands the resulting candidate set to D065's `selectUnitForAllocation`. The winning unit becomes the reservation's `subjectId`, written through `ReservationRepository.createGuarded` (D050's guarded conflict check, D064's buffer expansion using the variant's `bufferMinutes`, D059's idempotent-replay-by-key) exactly like every other reservation subject — no new write path, no duplicated conflict logic. An empty candidate set surfaces as `selectUnitForAllocation`'s existing `NoAvailableUnitError`, satisfying this card's "conflict rejected" criterion without inventing a second error type for the same condition.

## Acceptance criteria check

- "Conflict rejected" — **Met.** `RentalReservationService.test.ts`: with a 2-unit fleet, once both units are HELD/CONFIRMED for a window overlapping a third request, `createRentalReservation()` throws `NoAvailableUnitError` (domain package, re-exported through `@smb-os/domain`).
- "Allocator picks a free unit" — **Met.** Two tests: (1) a happy-path reservation lands on one of the variant's two units in state `HELD`; (2) once the first unit is occupied for an overlapping window, a second concurrent request is allocated the *other* free unit, proving the free-unit filter (not just the allocator's tie-break) is actually wired to real overlap data, not a stub.

## Security check answer

"Idempotency-Key required" — yes, enforced identically to D059's `BookingService`: `createRentalReservation` throws `MissingIdempotencyKeyError` before doing any unit-selection work if `input.idempotencyKey` is falsy, and a genuine retry (same key, same or later `createdAt`) short-circuits inside `createGuarded`'s `BEGIN IMMEDIATE` transaction to the already-created row rather than re-running allocation — proven directly by a dedicated retry test asserting the second call returns the same reservation id as the first rather than allocating (and holding) a second unit. Unlike `BookingService`, a rental retry's chosen `subjectId` is decided fresh on every call (unit selection happens before the idempotency short-circuit), but that's harmless: `createGuarded` ignores whatever `subjectId` a replay computes once it finds the existing row by key, so a retry can never double-allocate even if it happens to reselect a different unit than the original attempt.
