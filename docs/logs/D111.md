## What happened

D110's `InventoryUnitsView` already listed every unit with its own `status` column, but that column can never show a rental in progress: `inventory_units.status` stays `AVAILABLE` for the entire life of a rental (D065's design decision — "currently rented" is derived from `reservations`, never stored on the unit itself, so a later change to reservation state can't desync a separately-maintained unit flag). This card's gap was that nothing computed or surfaced that derived state anywhere.

New `ReservationRepository.findActiveBlocking` (`packages/db/src/repositories/ReservationRepository.ts`) is the read primitive: same zero-width-instant technique as D067's `isSubjectCurrentlyBlocked` (and the same `blockingStatePredicate` that already enforces invariant I3 on the sale path — `CONFIRMED`/`IN_USE`/unexpired-`HELD` only, so an unswept expired hold still doesn't count), but returns the actual blocking row instead of a boolean, so its `endsAt` can be read off as the unit's return date.

`InventoryUnitService` gained an optional `ReservationRepository` constructor argument (every one of the half-dozen existing call sites across `packages/db`/`apps/api` construct it with only two arguments and keep working unchanged) and a new `listWithRentalStatus(ctx, actingRole, variantId, asOf)` method: for each of the variant's units, looks up `findActiveBlocking` and reports `rentalStatus: "OUT_ON_RENTAL"` with `returnDueAt` set to that reservation's `endsAt`, or `rentalStatus: "AVAILABLE"` with `returnDueAt: null` otherwise. `GET /listings/:listingId/variants/:variantId/units` (`apps/api/src/routes/inventoryUnits.ts`) now calls this instead of the bare repository listing, passing `new Date().toISOString()` as `asOf`. `packages/contracts/src/inventoryUnit.ts` gained `inventoryUnitWithRentalStatusSchema` documenting this response shape.

`InventoryUnitsView.tsx` is the actual demo-moment deliverable: a new "Rental status" column renders "Out on rental — due back {returnDueAt} — unavailable for sale" for any unit currently blocked by a reservation, and "Available" otherwise — this card's deliverable, a unit list that shows out-on-rental with its return date. The same `outOnRental` flag also disables that row's "Retire" button (previously gated only on `status !== SOLD/RETIRED`), so an operator can't retire a unit that's physically out with a customer — this card's acceptance criterion, made concrete: a rented unit is visibly (and, for this one action, actually) unavailable, not just cosmetically labeled.

Wrote failing tests first throughout: `ReservationRepository.test.ts` (4 new cases for `findActiveBlocking`, including the cross-tenant isolation case the D021 generator requires — confirmed the whole suite still finds zero isolation-coverage gaps across every real repository afterward); `InventoryUnitService.test.ts` (4 new cases for `listWithRentalStatus`, including a tenant-isolation case); `apps/api/test/inventoryUnits.test.ts` (2 new cases proving the HTTP response carries the right `rentalStatus`/`returnDueAt` for both an out-on-rental unit and an available one); `InventoryUnitsView.test.tsx` (3 new cases, confirmed red — `getByText(/unavailable for sale/i)` and the disabled-Retire assertion both failed against the pre-change component — before implementing the column and the retire-gate).

Proven at the repository, service, HTTP, and component layers (`ReservationRepository.test.ts`, `InventoryUnitService.test.ts`, `apps/api/test/inventoryUnits.test.ts`, `InventoryUnitsView.test.tsx`), not asserted only at the top of the stack.

## Security check answer

**"THE demo moment — shared inventory made visible"** — the property this card makes visible is that one physical unit cannot be simultaneously "available to sell" and "out with a rental customer" without the dashboard showing it: `findActiveBlocking` reads the exact same `blockingStatePredicate` (`CONFIRMED`/`IN_USE`/unexpired `HELD`) that D067's `isSubjectCurrentlyBlocked` already uses to reject a sale of a currently-rented unit (invariant I3) — this card doesn't introduce a second source of truth for "is this unit rented," it surfaces the one the sale path already trusts. A unit's `inventory_units.status` column is never touched by this card; rental status is computed fresh on every read from `reservations`, so it can never drift out of sync with what the sale-blocking check itself sees.
