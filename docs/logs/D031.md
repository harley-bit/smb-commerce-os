## What happened

Added `packages/domain/src/utils/lineTotal.ts` on top of D016's existing `Money` class: `computeLineTotal(unitPrice, quantity)` (rejects non-integer/non-positive quantity, then reuses `Money.multiply`, which already refuses a non-integer factor) and `assertLineTotal(unitPrice, quantity, claimedLineTotal)`, which implements invariant I8 (`docs/design/03`: "Order line totals equal quantity × unit price, in minor units" — "Domain invariant, asserted on write") by throwing if a caller-supplied line total doesn't match the computed one, including a currency mismatch. Test-first via `packages/domain/src/utils/lineTotal.test.ts` (8 cases, confirmed failing with `Cannot find module` before `lineTotal.ts` existed), including the card's named property test (quantity × unit price == line total for randomized integer inputs) and a second property test proving any tampered claimed total is always rejected. Exported from `packages/domain/src/index.ts`.

## Acceptance criteria check

- "Property test: qty x unit price equals line total, in minor units" — **Met.** `lineTotal.test.ts`'s `"property: quantity x unit price equals line total, in minor units"` case (fast-check, randomized `unitPriceMinor`/`quantity` integers) asserts `lineTotal.minorUnits === unitPriceMinor * quantity` and that the result stays an integer.

## Security check answer

"No floating point anywhere in money paths" — true by construction, not by convention. `computeLineTotal` takes a `Money` (already integer-only, enforced by `Money.of`) and an integer `quantity`, and returns `unitPrice.multiply(quantity)`, which throws on any non-integer factor before it can touch a money value. `assertLineTotal` never divides or averages — it only compares two already-integer `Money.minorUnits` values for exact equality, so no rounding step exists anywhere in the line-total path. Verified beyond the single-case tests by a fast-check property run over randomized integer inputs asserting `Number.isInteger` holds on every computed result.
