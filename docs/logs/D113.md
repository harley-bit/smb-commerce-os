## What happened

`AvailabilityExceptionRepository`/`ResourceService.createAvailabilityException`/`listAvailabilityExceptions`/`updateAvailabilityException`/`removeAvailabilityException` (D058) and `applyAvailabilityExceptions`/`subtractIntervals` (`packages/domain/src/utils/availabilityExceptions.ts`) already existed with full BLACKOUT/EXTRA semantics and were already exercised end-to-end through `AvailabilityService.getResourceAvailability`, but had zero HTTP surface or dashboard UI — this was D112's log's explicitly called-out open gap and this card's named deliverable. Closed the HTTP gap with two additions to `apps/api/src/routes/resources.ts`, mirroring D112's `availability-rules` route exactly: `GET`/`POST /resources/:resourceId/availability-exceptions`, forcing `resourceId` from the URL (never trusting a body-supplied value, same "path is the source of truth" posture as `variants.ts`/the availability-rules routes) and re-resolving the resource under the acting tenant's own `ctx` via `resourceService.findResourceById` before either verb touches an exception row.

`ResourceAvailabilityEditor.tsx` (already routed at `/dashboard/catalog/resources`) got a new "Exceptions" section between the weekly-rules form and the "Upcoming availability" list: a table of the selected resource's existing exceptions (kind, starts, ends, note) and a form to add one (kind select, ISO start/end text fields, optional note). Adding an exception reuses the same `loadRulesAndAvailability` refetch the weekly-rule form already calls, which now also fetches `GET /resources/:id/availability-exceptions` alongside rules and availability, so the "Upcoming availability" list picks up the exception's effect immediately without a page reload.

## Acceptance criteria check

- **"Exception blocks or opens the expected window"** — Met. `apps/api/test/resources.test.ts`'s new test configures a Sunday 09:00–17:00 weekly rule, adds a BLACKOUT exception for 13:00–17:00 on one occurrence of that Sunday and an EXTRA opening 08:00–09:00 on an otherwise-closed Monday, then reads back `GET /resources/:id/availability` and asserts: the base Sunday window is trimmed to exactly 09:00–13:00 (the blacked-out tail is gone), and the Monday EXTRA opening appears verbatim even though no base rule covers Monday at all — proving both exception kinds actually reshape the returned free intervals, not just that the exception row was saved. `ResourceAvailabilityEditor.test.tsx`'s new test proves the dashboard form correctly posts a BLACKOUT exception and renders it back in the exceptions table.

## Security check answer

**"Merchant-scoped only"** — Both new routes call `resourceService.findResourceById(request.auth!.tenant, request.params.resourceId)` before doing anything else, exactly like the pre-existing availability-rules routes; that lookup runs through `ResourceRepository`'s `TenantScopedRepository` predicate, so a resource id belonging to another merchant resolves to `undefined` and the route 404s before `AvailabilityExceptionRepository` (itself also `TenantScopedRepository`-backed, scoped on `availability_exceptions.merchant_id`) is ever touched. Verified with two new tests, not just inferred from the shared base class: "404s creating an exception against another merchant's resource" (POST) and "never lists another merchant's exceptions, even for a resource id that exists under this merchant's own connection" (GET) — both use a resource id that genuinely exists, under a different merchant, on the same SQLite connection as the acting tenant's session, so a bypass would show up as a 200/201 leaking or writing cross-tenant data rather than a plain not-found id.
