## What happened

Wired up `drizzle-kit` for real, per `docs/design/04`'s "matching pair per dialect" migration rule. Added two schema files, `packages/db/src/schema/sqlite.ts` and `schema/pg.ts`, each defining a single smoke-test table (`migration_smoke_test`) — deliberately not a real domain table, since the actual tenancy schema is D018's job; this card is the tooling only. Two `drizzle-kit` configs (`drizzle.config.sqlite.ts`, `drizzle.config.pg.ts`) point at each schema and its own `migrations/{sqlite,pg}` output folder; ran `drizzle-kit generate` for real against both, producing genuine SQL migration files and journal/snapshot metadata (`packages/db/db:generate:sqlite`/`:pg` scripts added for future regeneration).

`src/migrate.ts` adds `runSqliteMigrations`/`runPgMigrations`, thin wrappers around `drizzle-orm`'s per-dialect migrators pointed at the generated folders. Test-first via `src/migrate.test.ts`: confirmed failing (`Cannot find module './migrate.js'`) before the file existed. Four cases: SQLite migrations apply to a fresh in-memory DB and create the real table (verified via `sqlite_master`, not a mock); running them twice is idempotent (forward-only in practice, no duplicate tables); and two `describe.skipIf(!process.env.DATABASE_URL)`-gated PostgreSQL cases — migrations apply to a real PostgreSQL 16 instance (same local Homebrew install from D014) and, critically for this card's acceptance criterion, a deliberately PG-incompatible migration (`CREATE TABLE ... (id INTEGER PRIMARY KEY AUTOINCREMENT)` — SQLite-only syntax, no PostgreSQL equivalent) is applied via the real `drizzle-orm/node-postgres` migrator against the real database and asserted to reject. Ran this locally with `DATABASE_URL` pointed at the D014 `smb_os_test` instance — all 4 cases passed for real, including the incompatible-migration rejection. One bug caught while doing this: the test's cleanup originally dropped `public."__drizzle_migrations"`, but node-postgres's migrator actually tracks applied migrations in a `"drizzle"` schema, so a second run silently no-op'd the migration (already "applied" per stale tracking state) instead of recreating the table — fixed by dropping the whole `"drizzle"` schema between test runs; reran three times back-to-back to confirm it's now stable, not a fluke.

A second test file, `src/migrations-policy.test.ts`, operationalizes the forward-only policy itself rather than just restating the design doc's prose: for both dialects, it asserts no file with `down`/`rollback`/`revert` in its name exists under `migrations/`, and that each dialect's `_journal.json` only ever has densely-appended `idx` entries (0..n-1 in order) — a structural guard against a hand-edited or reordered migration history, since `drizzle-kit` itself never generates a down migration but nothing stops one being added by hand later.

No CI workflow changes were needed — D014 already added the `test-postgres` job (`pnpm --filter @smb-os/db test` against a real `postgres:16` service container), and this card's new tests run as part of that same package's suite, so the "both-dialect migration check in CI" deliverable is satisfied by composition: the existing job now exercises real migration application on both dialects, and the fixture test proves a PG-incompatible migration genuinely fails there rather than being asserted by inspection.

## Acceptance criteria check

- **"A PG-incompatible migration fails CI"** — met. `src/migrate.test.ts`'s "fails to apply a PG-incompatible migration" case plants a real SQLite-only migration (`AUTOINCREMENT`) and applies it via the real PostgreSQL migrator against a real PostgreSQL 16 database; the promise rejects, as asserted. This exact test runs inside `test-postgres`'s `pnpm --filter @smb-os/db test` step in CI, so a genuinely PG-incompatible migration written into this repo would fail that job today — verified locally against a real database, same constraint as D013/D014 (no live GitHub Actions run available in this sandboxed session; first real push should confirm the job is green in the GitHub UI, per the standing note carried since D005).

## Security check answer

**"Migration review is part of the security review triggers"** — this card doesn't add a new security-review policy document (that's `docs/compliance/policies/secure-development-policy.md`, already in place since D011); it makes the existing "every migration is reviewed for portability against P1–P10 before merge" rule (`docs/design/04`) mechanically enforceable rather than a code-review-only convention: (1) the branch-protection PR-required rule from D009 means no migration reaches `main` without a PR existing, and (2) `migrations-policy.test.ts` plus the PG-incompatible fixture test mean a reviewer (or CI) doesn't have to manually re-derive portability by reading SQL — a P1–P10 violation that breaks PostgreSQL compatibility fails the build automatically, and a down/rollback migration slipped in by hand fails the forward-only structural check. Human review is still the primary gate per `docs/design/17`'s PR-required policy; these tests are what make that review's job tractable rather than trust-based.
