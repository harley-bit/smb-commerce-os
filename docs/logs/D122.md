## Security check answer

"Stock state never reveals exact competitor-sensitive counts" — **met**. `InventoryMovementRepository.sumStock`'s raw integer never leaves `toPublicVariant` (`apps/api/src/routes/publicStorefront.ts`) — it is consumed only to pick one of two enum members, and the function's return type (`PublicVariant`) has no numeric stock field at all. This is enforced at three layers: (1) the contract schema `publicVariantSchema` (`packages/contracts/src/publicStorefront.ts`) defines only `stockStatus: publicStockStatusSchema` (`"IN_STOCK" | "OUT_OF_STOCK"`), no quantity field, proven by `publicStorefront.test.ts`'s "rejects a payload carrying a raw stock quantity" (a `quantityOnHand` field fails `.strict()` parsing); (2) the API route test "never exposes the raw stock count, merchantId, or listingId on a variant" asserts the live HTTP response has no `quantityOnHand`/`stock` property; (3) the web view (`ProductDetailView.tsx`) renders only `STOCK_STATUS_LABEL[variant.stockStatus]` ("In stock"/"Out of stock"), never interpolates a number, proven by `ProductDetailView.test.tsx`'s "never renders a raw stock count" (asserts no `/\d+ in stock/i` or `/units? available/i` text appears). Same posture as `InventoryUnitService`'s merchant-facing `RentalStatus` enum (`packages/db/src/services/InventoryUnitService.ts`, D111) — a bucket, never a count — applied here to an unauthenticated public surface where the stakes are higher (a competitor, not a teammate, could otherwise scrape exact reorder points).
