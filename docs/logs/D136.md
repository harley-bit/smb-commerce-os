## What happened

Built the first real, browser-driven E2E suite this codebase has ever had — five Playwright specs (`e2e/`, new workspace package) driving a real Chromium instance against a real, listening `apps/api` process and a real `next build && next start` `apps/web`, sharing one SQLite file. Getting there required fixing three previously-undiscovered, real gaps that only a real cross-origin browser run could surface (every test in this repo before this card was either `app.inject()` or a jsdom component test, neither of which exercises a real network stack): (1) `apps/api` had no real process entrypoint at all (`index.ts` was a placeholder marker, `dev`/`start` were `echo` stubs) — new `apps/api/src/serve.ts` opens one real migrated connection and wires a real `DbMerchantMembershipResolver` to it; (2) no CORS response headers existed anywhere, so every one of `apps/web`'s cross-origin `fetch(..., {credentials: "include"})` calls was silently blocked by the browser — fixed with `@fastify/cors`, reflecting the same `allowedOrigins` allowlist the CSRF check already uses; (3) the strict CSP's `connect-src 'self'` blocked the same cross-origin fetches at the browser's CSP layer too — `buildCspHeader` now takes an optional `apiOrigin`, wired from `middleware.ts`'s existing `API_URL`. Also fixed a `next dev`-vs-CSP `unsafe-eval` conflict (switched E2E to `next build && next start`) and a genuinely subtle bug in the E2E harness itself (Playwright re-evaluates `playwright.config.ts` in each worker process, so an unconditional `mkdtempSync` at module scope minted a second, disconnected SQLite path in the worker — fixed with a `??=` guard). Also added a "Cancel" button to `OrderHistoryView.tsx` — D133 built cancellation at the service/HTTP layers only with no UI, and a pilot-capable storefront needs a customer to actually be able to cancel through the product. All five specs pass through the real `pnpm test:e2e` command.
