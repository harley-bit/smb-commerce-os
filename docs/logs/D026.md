## What happened

Added `reservations` (`packages/db/src/schema/{sqlite,pg}.ts`) per `docs/design/03`'s "The reservation — services and rentals" section — `docs/design/03` calls this table "the correctness centre of the system." Columns: `id`, `merchant_id`, `order_line_id` (nullable while `HELD` in a cart), `subject_type` (`RESOURCE | INVENTORY_UNIT`), `subject_id` (polymorphic — no single FK can span both `resources` and `inventory_units`, so it's a plain column, enforced at the service layer per invariant I4, not the DB), `starts_at`/`ends_at` (half-open `[start, end)`, UTC), `quantity`, `state` (`HELD | CONFIRMED | IN_USE | COMPLETED | CANCELLED | EXPIRED`), `expires_at`, `created_at`, `released_at`. Two indexes per `docs/design/03`'s "Indexing" section: `reservations_subject_interval_idx` on `(merchant_id, subject_type, subject_id, starts_at, ends_at)` for the overlap query, and `reservations_state_expires_idx` on `(state, expires_at)` for the hold sweeper. Real `drizzle-kit`-generated migrations for both dialects (`packages/db/migrations/{sqlite,pg}/0005_*`). Test-first via `packages/db/src/schema/reservations.test.ts` (7 cases, confirmed failing with `Cannot read properties of undefined` / no-such-table errors before the schema existed), including a real local PostgreSQL 16 run that checks `pg_indexes` for both index names directly, not just SQLite `PRAGMA index_info`. No overlap-prevention constraint, no service layer, no allocator — this card is schema only, same split as D022→D023, D024, and D025 before it. The PostgreSQL GIST exclusion constraint and SQLite `BEGIN IMMEDIATE` serialization that actually enforce invariant I2 (`docs/design/05` C1) are gate-G3 work, tracked in `D053`/`D062`, not this card.

## Acceptance criteria check

- "Index present" — **Met.** Both `reservations_subject_interval_idx` (`merchant_id, subject_type, subject_id, starts_at, ends_at`) and `reservations_state_expires_idx` (`state, expires_at`) exist on both dialects, verified directly: `PRAGMA index_info` on SQLite, `pg_indexes` on a real local PostgreSQL 16 instance.
- "Blocking-state filter works" — **Met.** A test inserts one reservation in each of the six states and confirms a `state IN ('HELD','CONFIRMED','IN_USE')` query returns exactly the three blocking rows and excludes `COMPLETED`/`CANCELLED`/`EXPIRED`, matching `docs/design/03`'s "Blocking states are `HELD`, `CONFIRMED`, `IN_USE`" rule and `docs/design/05`'s state machine.

## Security check answer

**"The correctness centre — see 05."** This card makes the reservation's shape and its two query-critical indexes durable; it does not yet make double-booking impossible. `docs/design/05`'s C1 property (two blocking reservations for the same subject never overlap) is enforced by a PostgreSQL GIST exclusion constraint and, on SQLite, `BEGIN IMMEDIATE` transaction serialization — neither exists yet. Today, nothing stops two concurrent inserts for the same `subject_id`/overlapping interval from both succeeding; the schema is deliberately permissive at this layer because the DB-level guarantee (the actual fix) is Gate G3 scope, tracked at `D053`/`D062`, and a same-process check written now (e.g. an app-level "select then insert") would be a race condition that gives false confidence — worse than an honest gap. Flagged the same way D025 flagged `resources.capacity` enforcement as deferred, not silently assumed.
