## What happened

Built the real parallel-transaction concurrency harness for reservations on both dialects, closing the gap D050/D051's notes both flagged: prior "concurrency" proof was either hand-interleaved single-thread SQLite connections (D050) or a single raw insert with no concurrency at all (D051).

**SQLite:** `packages/db/src/repositories/reservationRaceWorker.mjs` (plain JS, imports built `dist/` output — same pattern as D040's `guardedDecrementWorker.mjs` — so each worker is a genuinely separate `worker_threads` isolate with its own `better-sqlite3` connection to one shared on-disk file) plus `ReservationRepository.concurrency.test.ts`: 10 real worker threads, released simultaneously off a `SharedArrayBuffer` start-gate, all attempt to book the identical overlapping interval on the same resource. Parameterized on `guarded: boolean` so the same harness drives both arms.

**PostgreSQL:** `ReservationRepository.pg-concurrency.test.ts`: 10 real `pg.Pool` client connections (each `pool.connect()`, not shared `pool.query`, so all 10 are genuinely open and inserting at once — real separate backend processes on the server, not same-thread simulation) racing the identical overlapping raw insert, first with D051's exclusion constraint dropped, then restored.

Both dialects prove the acceptance criterion the same way: the "no fix" arm (SQLite's plain `create()`; Postgres with the constraint dropped) lets more than one of the 10 real concurrent attempts land — an actual on-disk/on-server double-booking, not a hypothetical one — while the "fix" arm (`createGuarded()`; constraint restored) resolves the identical race to exactly one winner every time, with the rest failing with the expected typed error (`ReservationConflictError` / PostgreSQL `23P01`).

## Security check answer

"A test that isn't actually concurrent proves nothing": this is exactly why neither harness uses `Promise.all` over same-thread calls or hand-interleaved statements. SQLite's race uses real OS `worker_threads` — separate V8 isolates, separate connection handles, released at the same instant via `Atomics.wait`/`Atomics.notify` — so SQLite's actual file-locking behavior is under test, not Node's cooperative event loop. PostgreSQL's race uses 10 real dedicated pool connections (separate backend processes), so the database engine's own concurrency control is under test. The direct proof this isn't theater: pointed at the *unguarded* write path, both harnesses produce a real double-booking (more than one row for the same overlapping interval, persisted on disk / in the database) — a harness that wasn't actually concurrent would either always produce exactly one winner (sequential execution hides races) or would need to be trusted rather than demonstrated. The unguarded-arm test explicitly asserts `> 1` for this reason, not just "not exactly 1".

Carried-over gap, unchanged from D050/D051: `capacity > 1` fungible-resource sum-of-quantities case is still not implemented or exercised by this harness — both arms use `capacity: 1` STAFF resources. D053 (concurrency suite: identical reservations) is the next card in this epic and can reuse this harness's worker/race helpers directly rather than rebuilding them.
