## What happened

This codebase has no OIDC identity provider anywhere (confirmed by investigation before writing any code: `AuthProvider`/`NativeAuthProvider` are a native, in-house email+password+TOTP-MFA system per ADR-002, with plain 24h opaque session tokens and no refresh-token concept at all — grep for PKCE/OIDC/OAuth across the repo only hit design docs discussing it as a *future* alternative provider, never implemented code). Rather than silently reinterpreting the card or inventing a fictitious third-party IdP, built the literal deliverable — OAuth 2.0 Authorization Code + PKCE (RFC 7636) — as new first-party endpoints layered on the existing `authenticate()` password/MFA logic: `packages/domain/src/auth/AuthProvider.ts` gained `createAuthorizationCode`/`exchangeAuthorizationCode`/`refreshMobileSession`/`revokeMobileSession` plus `MobileTokenPair`/`AuthorizationCodeGrant` types and three new typed errors. `apps/api/src/auth/NativeAuthProvider.ts` implements all four (new `apps/api/src/auth/repositories.ts` in-memory `AuthorizationCodeRepository`/`RefreshTokenRepository`, same architecture as the pre-existing `SessionRepository`/`ResetTokenRepository` — this whole subsystem is still D010's in-memory placeholder, never migrated to `packages/db`, a pre-existing gap this card didn't touch). New `apps/api/src/routes/mobileAuth.ts` exposes `POST /auth/mobile/{authorize,token,refresh,logout}`; a new shared `apps/api/src/auth/sessionToken.ts` lets the existing `authenticate` middleware and `/auth/me` accept `Authorization: Bearer <token>` alongside the cookie, so a mobile access token (the same opaque token type a web session cookie carries) actually authenticates real protected routes, not just its own login flow. On the client, `apps/mobile/src/auth/` got `pkce.ts` (pure, dependency-injected — verified against RFC 7636 Appendix B's own worked example), `expoPkceAdapter.ts` (real `expo-crypto` wiring), `secureTokenStore.ts`/`expoSecureTokenStore.ts` (new `expo-secure-store` dependency — Keychain on iOS, Keystore on Android, one JS API), `authClient.ts` (orchestrates the PKCE handshake + refresh + sign-out against the new routes), and a minimal `SignInScreen.tsx` wired into `App.tsx`. Building this surfaced one real, unrelated bug in this sandbox: Metro (unlike plain `tsc`/vitest under this package's `moduleResolution: "bundler"`) does **not** remap an explicit `.js`-suffixed relative import to a same-named `.ts` file — every new mobile source file initially used the NodeNext `.js`-suffix convention copied from `apps/api`, which typechecked fine (bundler mode tolerates it) but silently failed to bundle; fixed by dropping the suffix on every relative import actually reachable from `App.tsx`, matching this package's pre-existing convention (`parseMerchantProfile`'s own import). Confirmed both platforms bundle clean afterward (`npx expo export --platform ios --platform android`, 744/742 modules, no errors) — this machine's iOS-simulator/Android-emulator tooling now works since D137's fourth session, but a live on-device manual click-through of the sign-in screen was not attempted this session (see Notes).

## Security check answer

"Never AsyncStorage for tokens — platform secure storage only." **Enforced two ways, not just by convention:** (1) `secureTokenStore.ts`'s `SecureTokenStorage` interface has exactly one real implementation, `expoSecureTokenStore.ts`, which only ever calls `expo-secure-store` (Keychain/Keystore) — no code path in this app writes a token anywhere else. (2) `apps/mobile/src/auth/noAsyncStorage.test.ts` is a static tripwire (same shape as D099's PCI SAQ A `pageCardFieldGuard.test.ts`) that scans every source file under `src/` for any reference to `AsyncStorage` or `@react-native-async-storage/async-storage` and fails the build if one appears — so the constraint can't quietly regress in a later card the way a code-review-only rule could. `@react-native-async-storage/async-storage` was never added as a dependency at all.
