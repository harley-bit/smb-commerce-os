## What happened

New `DepositHoldProvider` port (`packages/domain/src/payments/DepositHoldProvider.ts`), same seam shape as D089's `PaymentIntentProvider` but modeling Stripe's `capture_method: "manual"` — an authorize-only hold rather than an immediate charge. `SimulatedDepositHoldProvider` (`packages/db/src/payments/SimulatedDepositHoldProvider.ts`) is the only implementation (no live Stripe account provisioned, same precedent as every prior payments card): it derives `expiresAt` from a fixed 7-day authorization window run through D079's `recordProviderAuthorizationWindow`, so a misconfigured window above the 30-day product ceiling is rejected at the provider itself, not just by a caller who remembers to check.

`DepositAuthorizationService.placeHold` (`packages/db/src/services/DepositAuthorizationService.ts`) is the card deliverable. It reads the deposit amount exclusively from `OrderRepository.findLineById`'s server-recorded `depositMinor` — `PlaceDepositHoldInput` carries no amount field at all, mirroring `CheckoutPaymentService`'s "amounts computed server-side only" pattern — calls the provider to place the hold, then persists a `PaymentRepository` row (`kind: DEPOSIT_HOLD`, `status: PENDING`) and a `DepositAuthorizationRepository` row (`state: AUTHORIZED`) with `expiresAt` copied verbatim from the provider's response. If the provider response has a falsy `expiresAt`, `MissingHoldExpiryError` is thrown before either row is written — no half-persisted hold with a payment but no matching deposit-authorization row, and no deposit-authorization row that could ever be missed by a future expiry sweeper.

## Acceptance criteria check

- "Hold placed" — **Met.** `DepositAuthorizationService.test.ts`'s first test places a hold and confirms a `PaymentRepository` row (`kind: DEPOSIT_HOLD`, `providerRef` = the provider's `intentId`) and a `DepositAuthorizationRepository` row (`state: AUTHORIZED`) both exist and agree on amount/currency.
- "Expiry recorded from provider response" — **Met.** The same test asserts `deposit_authorizations.expiresAt` equals exactly the value `SimulatedDepositHoldProvider` returned (`2026-09-15T00:00:00.000Z`, 7 days after the injected `now`), not a value computed independently by the service. A second test proves the amount is read from the order line's own `depositMinor` even if a caller's raw payload tried to smuggle an `amountMinor` field in (`@ts-expect-error` on the conforming type, confirming no such field exists to begin with).

## Security check answer

**"expires_at mandatory — drives the auto-release job."** `deposit_authorizations.expires_at` is `NOT NULL` at the schema level (D028), but a service that silently coerced a missing provider expiry to some default would defeat that guarantee by construction — `DepositAutoReleaseJob` (D080) and any future hold-expiry sweeper can only find and release what's actually recorded. `DepositAuthorizationService.placeHold` enforces this one layer earlier than the schema: a provider response with a falsy `expiresAt` throws `MissingHoldExpiryError` before either the `payments` or `deposit_authorizations` insert runs, proven by a test using a stub provider that returns an empty-string `expiresAt` — confirming no `payments` row is left behind either (`paymentRepo.findByProviderRef` returns `undefined` for that intent afterward). A hold that can't be recorded with a real expiry is never persisted at all, rather than persisted with a placeholder that would let the auto-release job's coverage silently regress.
