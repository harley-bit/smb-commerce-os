## What happened

Added migration `packages/db/migrations/pg/0010_reservations_no_overlap.sql` (generated as an empty custom migration via `drizzle-kit generate --custom`, then hand-written — `EXCLUDE USING gist` has no representation in drizzle-orm 0.45's PostgreSQL schema builder, so this is real SQL, not schema-diff output): `CREATE EXTENSION IF NOT EXISTS btree_gist` followed by `ALTER TABLE reservations ADD CONSTRAINT reservations_no_overlap EXCLUDE USING gist (subject_type WITH =, subject_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&) WHERE (state IN ('HELD','CONFIRMED','IN_USE'))`, exactly matching `docs/design/05` C1. `btree_gist` supplies the equality operator classes gist needs for `subject_type`/`subject_id` (plain btree types) alongside the native range-overlap operator class for `tstzrange`.

Wrote the failing test first, in a new file `packages/db/src/schema/reservations-exclusion.test.ts` (kept separate from `reservations.test.ts`'s existing PG describe block, which covers structural/index concerns, not the overlap guarantee itself): four cases — (1) `btree_gist` extension is installed, (2) a second raw `INSERT` overlapping an existing blocking reservation for the same subject is rejected with PostgreSQL's exclusion-violation error code `23P01`, issued via `connection.pool.query` directly (no `ReservationRepository`, no app code at all — the "console session" scenario the card's security check asks about), (3) a back-to-back reservation at the exact boundary (`ends_at` of one == `starts_at` of the next) is allowed, proving the `[)` half-open interval semantics from `docs/design/05` are honored by the constraint itself, and (4) an identical overlapping interval with state `CANCELLED` is allowed, proving the `WHERE` predicate correctly excludes non-blocking states. Confirmed all four failing before the migration existed (extension check failed with 0 rows; the overlap-rejection case failed because the insert silently succeeded).

Real finding en route: confirming "the tree is green" against a real PostgreSQL database (`DATABASE_URL` set — the CI-equivalent invocation, not the SQLite-only default `pnpm test`) turned up a pre-existing, order-dependent bug across every real-PostgreSQL test in the package. Each `schema/*.test.ts` file's setup dropped only its *own* migration slice's tables (`DROP TABLE IF EXISTS "x", "y", ... CASCADE`) plus `DROP SCHEMA "drizzle"` (resetting migration tracking), then reran the *entire* migration chain. Tables created by a different file earlier in run order — outside that file's own narrower drop list — were left behind, so the full chain's `CREATE TABLE` statements collided with tables that already existed (`relation "X" already exists`, Postgres error `42P07`). Reproduced deterministically on a truly fresh database via `pnpm --filter @smb-os/db test` with `DATABASE_URL` set (CI's exact command): 8 of 9 real-PostgreSQL suites failed. This wasn't caused by this card — D047 through D050 were all SQLite-path cards, so `DATABASE_URL` was never set locally, and the failure only surfaces when the real-PostgreSQL describe blocks actually run. It's very likely the `test-postgres` CI job has been red since whichever earlier card introduced the second real-Postgres schema test file, unnoticed because no card since has needed to look at it. Fixed at the root: every affected file's cleanup now does `DROP SCHEMA IF EXISTS "public" CASCADE` + `CREATE SCHEMA "public"` (covers every table regardless of which file created it or in what order) instead of an enumerated, file-scoped table list; `DROP SCHEMA "drizzle"` is unchanged. Verified order-independence directly: ran the full package test suite against a fresh database twice, once with `vitest run` and once with `--sequence.shuffle`, both 41/41 files and 257/257 tests green. This fix is 10 files, ~34 lines changed (9 test-cleanup call sites + this card's own new test file), pure infrastructure — no assertions were changed, no test coverage was removed.

## Security check answer

"Makes double-booking impossible even from a console session": confirmed directly, not just asserted. The constraint is a database-level object (`ALTER TABLE ... ADD CONSTRAINT ... EXCLUDE USING gist`), enforced by PostgreSQL on every write path to the `reservations` table — there is no "guarded" vs. "unguarded" insert function the way SQLite's `BEGIN IMMEDIATE` requires (D050); a raw `INSERT` from `psql`, a migration script, or any future service that never goes through `ReservationRepository` is rejected identically. The test proves this literally: it issues the conflicting insert as a raw parameterized SQL string over `connection.pool.query`, with zero application logic in the call path, and the engine itself throws `23P01`. The one thing this constraint does *not* guard against — by design, per `docs/design/05`'s fungible-capacity section — is `resources` with `capacity > 1` (a class with several seats), where an exclusion constraint can't express "sum of overlapping quantities ≤ capacity" and a `SELECT ... FOR UPDATE` row lock is required instead; that's out of scope for this card (single-quantity subjects only, matching every prior card in this epic) and is called out below for D051+ visibility, consistent with D050's note.
