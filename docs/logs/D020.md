## What happened

Added `packages/db/src/repositories/{UserRepository,MerchantUserRepository}.ts`. `UserRepository` is a plain (non-tenant-scoped) repository over `users` — that table has no `merchant_id` column because a single identity can hold a role in more than one merchant, so tenant scoping doesn't apply at this layer; it exposes `create`/`findById`/`findByEmail`. `MerchantUserRepository` extends `TenantScopedRepository<merchantUsers.merchantId>` (`docs/design/07` Control #1) and enforces the card's acceptance criterion directly: `assignRole(ctx, actingRole, targetUserId, role, createdAt)` throws immediately if `actingRole !== "OWNER"`, before any write happens, matching `docs/design/07`'s role table ("`OWNER` — full merchant control including... role assignment"; "`ADMIN` — no... role changes"). `assignRole` upserts on the table's composite PK (`merchantId`, `userId`) so a repeat call changes an existing role rather than erroring. Both repositories exported from `packages/db/src/index.ts`.

## Acceptance criteria check

- **Role assignment restricted to OWNER** — Met. `MerchantUserRepository.assignRole` throws `Error(/OWNER/)` for `ADMIN`, `STAFF`, and `READ_ONLY` acting roles, verified by tests, and only an `OWNER` actor can create or change a `merchant_users` row through this repository.

Test-first via two new test files (12 cases total), confirmed failing (`Cannot find module`) before the repository files existed:
- `UserRepository.test.ts` (5 cases): create/find by id/find by email, unique-email rejection, real UUIDv7 id generation.
- `MerchantUserRepository.test.ts` (7 cases): OWNER-only assignment (positive case, three negative actor-role cases), upsert-on-repeat-assignment, and three cross-tenant isolation cases (list scoped to caller's merchant, `findRole` blind to another merchant's row for the same user, and an OWNER in merchant A cannot make their assignment visible inside merchant B's scope) — the last three double as Gate G1 evidence for this new table.

## Security check answer

**Card's question: "Role changes are audit-logged and notified."**

Not yet true, and this card does not close that gap — it is explicitly out of scope for it. `docs/design/03`'s `audit_log` table (hash-chained, append-only) is `D030`'s deliverable (`docs/cards/D030.md`: "audit_log with prev_hash/row_hash; verification job"), and no notification mechanism (e.g. "email all owners on a role change," `docs/design/07`'s threat-model row for `STAFF` escalating to `OWNER`) exists anywhere in the codebase yet. What *is* true today: role assignment is restricted to `OWNER` at the repository layer (this card's actual acceptance criterion), which is the precondition the audit/notify requirement builds on — you can't meaningfully audit-log or notify on a role change that any role could trigger. Recorded here rather than silently glossed over so `D030` (and whatever card ends up wiring owner notifications — not yet scheduled by name) can pick it up as a known, tracked gap rather than a surprise.

## Notes for next session

- `MerchantUserRepository.assignRole`'s upsert path uses Drizzle's `onConflictDoUpdate` targeting the table's composite PK (`merchantId`, `userId`) — the same pattern will likely be needed anywhere else a composite-PK tenant-scoped table needs "insert or update" semantics.
- `UserRepository` deliberately does **not** extend `TenantScopedRepository` — `users` has no `merchant_id` column at all (a user can hold roles in multiple merchants), so tenant boundary enforcement for user data lives one layer up, at `MerchantUserRepository`. Don't try to force `UserRepository` into the tenant-scoped base class later without re-checking this reasoning.
- Real audit logging (`audit_log`, hash-chained) and role-change notification to owners are still open gaps, tracked against `D030` and an as-yet-unnamed notification card — see the security check answer above.
