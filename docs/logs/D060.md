## What happened

Built the read side of the availability engine and its first HTTP route on top of D046-D059's already-existing rule/exception/reservation machinery. Added `AvailabilityCache` (`packages/db/src/cache/AvailabilityCache.ts`), an in-memory TTL cache keyed on `(merchantId, subjectId, from, to)` with an `invalidateSubject(merchantId, subjectId)` method, same in-process posture as `apps/api/src/auth/rateLimiter.ts`'s `SlidingWindowRateLimiter` — a shared store (Redis) is a later infra concern, not a reason to skip caching now. Added `AvailabilityService` (`packages/db/src/services/AvailabilityService.ts`), which composes `ResourceRepository`, `LocationRepository` (for `timezone`), `AvailabilityRuleRepository`, `AvailabilityExceptionRepository`, and `ReservationRepository.findBlocking` into `packages/domain`'s already-built `expandAvailabilityRule`/`computeFreeIntervals`, enforces the 90-day window cap (`AvailabilityRangeTooLargeError`), clips each rule to its own `validFrom`/`validTo` bound (a gap flagged but left unwired by D058), and reads/writes through the cache. Cache invalidation is wired at the actual write layer, not the service layer: `ReservationRepository`'s constructor now takes an optional `AvailabilityCache`, and `create`/`createGuarded`/`confirm` call `cache?.invalidateSubject(ctx.merchantId, subjectId)` immediately after their write commits — a purely additive, post-commit side effect that doesn't touch the guarded transaction's conflict-check or locking logic (G3 untouched), and is a no-op for every existing caller that doesn't pass a cache.

Added the actual public route: `GET /v1/m/:slug/availability` (`apps/api/src/routes/availability.ts`), registered in `apps/api/src/app.ts` via `registerAvailabilityRoutes`. This is the first unauthenticated, tenant-data-serving route in `apps/api` — it resolves `{slug}` to a `merchantId` via a new `MerchantRepository.findBySlug(slug)` (declared as a plain method, not a `RepositoryMethod` arrow-function class property, so Gate G1's isolation-coverage scanner correctly excludes it — same exemption pattern `ReservationRepository.explainFindBlocking` already established for "not a tenant-scoped access path"), then builds a `TenantContext` from the result. It carries its own `SlidingWindowRateLimiter`, per-IP only (no account to key on), defaulting to 3 requests/60s — strictly tighter than `app.ts`'s existing `loginLimiter` (10/60s) and `resetLimiter` (5/60s), satisfying this card's security check. The query takes `resourceId`, not `docs/design/06`'s literal `variantId`: no `listing_resources` join exists yet to resolve a listing/variant to the resource(s) that fulfil it (flagged as a carryover gap in `docs/logs/D058.md` and `docs/logs/D059.md`); `BookingService` (D059) already made the identical documented deviation for its own create-booking input, so this isn't a new gap, just the same one surfacing again at the HTTP layer.

Test-first throughout: `AvailabilityCache.test.ts`, `AvailabilityService.test.ts`, the new `MerchantRepository.findBySlug` cases, and `apps/api/test/availability.test.ts` were all written and confirmed failing (`Cannot find module`) before their implementation files existed. 5 cache tests, 9 service tests (including a direct cache-hit-count assertion via `vi.spyOn(reservations, "findBlocking")` and a cross-tenant isolation test), 2 new `MerchantRepository` tests, and 8 HTTP-level tests (200 unauthenticated happy path, no-leak-who-booked-it assertion on the raw response body, 90-day cap → 400, unknown slug → 404, unknown resource → 404, missing query params → 400, end-to-end cache-invalidation-on-write, and the rate-limit-to-429 case) — all green. ## Acceptance criteria check

- **GET availability with 90-day cap, caching, invalidation** — Met. `AvailabilityService.getResourceAvailability` throws `AvailabilityRangeTooLargeError` for any `(from, to)` window exceeding 90 days (`AvailabilityService.test.ts` "rejects a window wider than 90 days" / "accepts a window of exactly 90 days", and the HTTP-level `availability.test.ts` "rejects a window wider than 90 days with 400"); a second identical call is proven not to recompute (`AvailabilityService.test.ts` "caches the computed result" — `vi.spyOn(reservations, "findBlocking")` called exactly once across two calls).
- **Cache invalidated on any reservation write for that subject** — Met. Proven at two layers: `AvailabilityService.test.ts`'s "acceptance criterion" test (service-layer, calling `reservations.createGuarded` directly between two `getResourceAvailability` calls on the same window and asserting the second reflects the new blocking reservation) and `apps/api/test/availability.test.ts`'s identically-named end-to-end test (HTTP-layer, same shape but going through `app.inject`). Both assert the *changed* free-interval result after the write, not just "the cache was cleared" — the strongest form of this acceptance criterion, since a bug that invalidated the wrong key or failed silently would still leave the stale (wrong) result in either test.

## Security check answer

**Unauthenticated — tightest rate limit in the system.** `GET /v1/m/:slug/availability` has no `preHandler: app.authenticate` (unlike every other route in `apps/api` — a storefront visitor checking availability has no session), so its only defense against scraping/DoS is `registerAvailabilityRoutes`'s own `SlidingWindowRateLimiter`, instantiated per-IP (no account to key on for an anonymous caller) with a default of 3 requests/60s. This is deliberately stricter than every other limiter in the codebase: `app.ts`'s `loginLimiter` (10/60s) and `resetLimiter` (5/60s) both key on `ip:` *and* `account:` and gate an action a legitimate user does rarely; this endpoint is the single cheapest-to-scrape, most-expensive-to-compute read in the system per `docs/design/06`/`docs/design/07`/`docs/design/14` (risk T13), so it gets the smallest budget, proven by `availability.test.ts`'s "tightest rate limit in the system" test (2 requests succeed, the 3rd returns 429 with the default limiter). Beyond rate limiting, the response body is also proven not to leak who booked a slot — `AvailabilityService` only ever passes bare `{start, end}` `Interval`s into `computeFreeIntervals` (never a full `Reservation` row), and both `AvailabilityService.test.ts` and `availability.test.ts` assert the serialized response never contains `subjectId`/`orderLineId`/`customer` — the privacy requirement `docs/design/06`'s "It never reveals who booked a slot" names explicitly.
