## What happened

Added `packages/db/src/services/ProductListingService.ts`, a PRODUCT-mode-locked facade over D023's `ListingService`. `create()` never trusts a caller-supplied `mode` — it is hardcoded to `"PRODUCT"` regardless of what a raw payload contains — and both `create()` and `update()` reject any payload carrying a service/rental-only field (`durationMinutes`, `ratePeriod`, `depositMinor`) before `ListingService`/the repository ever run. The `listings` table itself has no mode-specific columns (those live on `listing_variants`, D033's job), so this validation guards the boundary where an untyped client payload first reaches a PRODUCT-scoped call, ahead of D033's variant-level DB CHECK constraint. `assertCanManageCatalog` was exported from `ListingService.ts` (previously a private function) so `ProductListingService` can assert authorization first, before its own field validation and before delegating. Test-first via `packages/db/src/services/ProductListingService.test.ts` (12 cases, confirmed failing on `Cannot find module` before the file existed): create/update/archive happy paths, the mode-hardcoding proof (a tampered payload claiming `mode: "SERVICE"` still stores as `PRODUCT`), all three forbidden fields rejected on both `create()` and `update()`, and two authorization-ordering cases (STAFF rejected outright, and STAFF rejected even when the payload also carries a forbidden field, proving auth runs first). Both new exports (`ProductListingService`, `CreateProductListingInput`) and `assertCanManageCatalog` added to `packages/db/src/index.ts`.

## Acceptance criteria check

- "Mode-specific validation rejects service/rental fields" — **Met.** `ProductListingService.test.ts`'s three `it.each` cases per method (`durationMinutes`, `ratePeriod`, `depositMinor`) assert `create()` and `update()` throw `PRODUCT listings cannot carry service/rental-only field: <field>` for each one.

## Security check answer

"Authorization asserted before any write" — `ProductListingService.create()` and `.update()` both call `assertCanManageCatalog(actingRole)` as their first line, before the field-validation guard and before `ListingService`/`ListingRepository` are ever reached, so an unauthorized caller is rejected without any write happening and without even the field-validation logic running against their payload. Proven directly by the test "authorization is checked even when the payload also carries a forbidden field" — a STAFF-role call with a `durationMinutes` field present still fails with the authorization error, not the field error, confirming the check order at runtime rather than just by reading the source.
