## What happened

`@smb-os/contracts`'s `updateVariantInputSchema` (D034) already existed — a `.strict()` schema with no `mode`/`listingId` fields and the same `Money.of`-backed price validation as `createVariantInputSchema` — but nothing in the codebase called it: no HTTP route exposed a variant update, and no merchant-facing UI existed to edit a variant at all. This card's gap, mirroring D106–D108's precedent, was purely the missing route + UI. Added `PUT /listings/:listingId/variants/:variantId` to `apps/api/src/routes/variants.ts`, which looks up the parent listing (404 if missing/cross-tenant), then the variant (404 if missing or if it belongs to a different listing than the one in the URL), then runs the patch through `updateVariantInputSchema` before calling the existing, unmodified `VariantService.update` (D033). New `apps/web/src/app/dashboard/catalog/VariantTable.tsx` (routed at `/dashboard/catalog/[listingId]/variants`, linked from each `CatalogView` row via a new "Manage variants" link) is the deliverable: fetches every variant on a listing, renders one editable row per variant (SKU/name/price/currency), tracks which rows were actually changed, and saves all dirty rows in one "Save changes" action — issuing one `PUT` per changed row, then re-fetching and rendering the server's own read-back. This card's acceptance criterion ("bulk edit works; prices validated") is proven by editing two variants on the same listing in one save action (`apps/api/test/variants.test.ts`) and by a dedicated client-side rejection test (`VariantTable.test.tsx`) showing an invalid price blocks the whole batch with zero PUT requests fired, mirroring `ProductEditor`'s existing client-schema-mirrors-server-schema pattern (same `node:crypto`-via-`@smb-os/domain` bundling reason documented there — this table's client schema is a small local Zod object, not an import of the real contract schema).

## Acceptance criteria check

- **Bulk edit works** — met. `apps/api/test/variants.test.ts`'s new test edits two variants' price/attributes in one save action through the new `PUT` route and confirms both persisted via a subsequent `GET`. `VariantTable.tsx`'s "Save changes" button issues one `PUT` per dirty row and is disabled until at least one row is actually edited.
- **Prices validated** — met, at both layers. Server-side: `updateVariantInputSchema`'s existing `Money.of`-backed `superRefine` rejects a non-integer `priceMinor` with 400, proven by a dedicated test showing the stored price is unchanged after the rejected request. Client-side: `VariantTable.tsx`'s local `rowEditSchema` blocks the save action (zero fetches) on an invalid price, proven by `VariantTable.test.tsx`.

## Security check answer

**"Price changes do not affect historical orders"** — true structurally, and now proven directly, not just asserted. `packages/db/src/schema/sqlite.ts`'s `order_lines` table (`docs/design/03`) copies `unit_price_minor`/`line_total_minor` from the listing/variant **at checkout write time** — the column comment has said as much since the schema was built, but no test in this codebase had actually exercised "reprice after checkout" until this card. `apps/api/test/variants.test.ts`'s new dedicated security-check test creates a real order line referencing a variant's current price (1999), reprices that same variant to 9999 through this card's own new `PUT` route, then re-reads the order line via `OrderRepository.listLines` and confirms `unitPriceMinor`/`lineTotalMinor` are still 1999 — proving the new mutation path this card adds cannot regress a historical order, not merely that the schema is shaped that way.
