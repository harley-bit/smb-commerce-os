## What happened

Built `OrderRepository` (`packages/db/src/repositories/OrderRepository.ts`) on the existing `orders`/`order_lines` schema (present since a Phase 1 schema card but never given a repository, per D042's note) — `create` (initializes a cart-status order with totals zeroed), `findById`, `addLine`, `listLines`, and `updateTotals`, all merchant-scoped. On top of it, `CartService` (`packages/db/src/services/CartService.ts`) implements the card's deliverable: `createCart` opens an order in `CART` status, and `addProductLine` looks up the variant server-side (`VariantRepository.findById`), rejects non-`PRODUCT` variants and currency mismatches (via `Money.add`'s built-in currency assertion), inserts the order line using `computeLineTotal` (domain's I8 helper), then **unconditionally recomputes the cart's `subtotalMinor`/`taxMinor`/`totalMinor` from `listLines` and overwrites the stored totals via `updateTotals`** — never an incremental update — which is this card's acceptance criterion. `AddProductLineInput` has no price field, so a conforming caller cannot supply one. Test-first: both `OrderRepository.test.ts` and `CartService.test.ts` were written before their implementation files existed (confirmed failing on `Cannot find module`), then implemented to green — 5 and 8 cases respectively, including a case that directly corrupts a cart's stored total to 999999 via `updateTotals` and proves the next `addProductLine` call overwrites it back to the correct recomputed value, and a case injecting `unitPriceMinor`/`lineTotalMinor` into the input (`as never`) that confirms the server-computed price wins. Both new repositories/services exported from `packages/db/src/index.ts` alongside their types, matching the existing pattern.

## Acceptance criteria check

- **Totals recomputed server-side on every mutation** — Met. `"recomputes cart totals server-side after every mutation, not just the first"` adds two lines in sequence and asserts the stored subtotal/total after each one; `"ignores a client-supplied cart total even when it disagrees with the recomputed value"` corrupts the stored total directly, then proves the next `addProductLine` overwrites it from a full recompute over `listLines`, not an incremental add onto the (possibly tampered) stored value.

## Security check answer

**"Cart is server-authoritative."** Answered directly: `AddProductLineInput` carries no price or line-total field, so a conforming caller cannot influence what gets written — `addProductLine` reads `unitPriceMinor`/`currency` exclusively from `VariantRepository.findById`'s row, computes `lineTotalMinor` via the domain's `computeLineTotal`, and recomputes the order's `subtotalMinor`/`taxMinor`/`totalMinor` from a fresh `listLines` read on every call rather than trusting or incrementing any previously stored value. Verified by a test that injects `unitPriceMinor: 1`/`lineTotalMinor: 1` into a raw payload (`as never`, modeling a tampered HTTP body) and asserts the real server price (2500) is what's returned and stored, and by a second test that corrupts the stored cart total directly and confirms the very next mutation overwrites it with the correct recomputed value rather than trusting or building on the corrupted figure.
