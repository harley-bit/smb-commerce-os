## What happened

Added `fulfillment_events`, `condition_reports`, `condition_media`, and `damage_claims` (`packages/db/src/schema/{sqlite,pg}.ts`) per `docs/design/03`'s "Rental lifecycle" section. `fulfillment_events`: `id`, `merchant_id`, `order_line_id` (FK `order_lines`), `kind` (`PICKED_UP | RETURNED | NO_SHOW | COMPLETED | CANCELLED`), `occurred_at`, `actor_user_id` (FK `users`), `note` — append-only, the reservation's state transitions are driven by these events rather than set directly. `condition_reports`: `id`, `merchant_id`, `order_line_id` (FK `order_lines`), `inventory_unit_id` (FK `inventory_units`), `phase` (`CHECKOUT | CHECKIN`), `condition_grade`, `notes`, `created_by` (FK `users`), `created_at`. `condition_media`: `id`, `merchant_id`, `condition_report_id` (FK `condition_reports`), `storage_key`, `content_type`, `bytes`, `sha256`, `captured_at` — the card's security check. `damage_claims`: `id`, `merchant_id`, `order_line_id` (FK `order_lines`), `amount_minor`, `state` (`DRAFT | FILED | CUSTOMER_NOTIFIED | RESOLVED_CAPTURED | RESOLVED_WAIVED | DISPUTED`), `filed_at`, `resolved_at`, `resolution_note` — financial record, never deleted, no `archived_at` column. Real `drizzle-kit`-generated migrations for both dialects (`packages/db/migrations/{sqlite,pg}/0008_*`). Test-first via `packages/db/src/schema/rental-lifecycle.test.ts` (7 SQLite cases, confirmed failing with `TypeError: Cannot read properties of undefined (reading 'Symbol(drizzle:Columns)')` before the schema existed), including a real local PostgreSQL 16 run (`smb_os_test`) inserting a full fulfillment-event/condition-report/condition-media/damage-claim chain and confirming a condition-media row referencing a non-existent condition report is rejected. Full local gate green. No repository/service layer yet — same schema-only split as every prior D02x card; the reservation-state-transition logic these events drive, and the "checkout report required before `IN_USE`" invariant, are future service-layer work.

## Security check answer

**"`condition_media.sha256` present for tamper evidence."** Confirmed by construction: `condition_media` has a `sha256` column, `NOT NULL`, alongside `storage_key`/`content_type`/`bytes`/`captured_at`. This is schema-only — nothing at this layer yet computes the hash from the uploaded bytes or verifies it on read; that belongs to the future media-upload service. The honest gap: a caller could currently insert an arbitrary string into `sha256` without it matching the actual file content, since no service-layer code exists yet to compute or verify it. The column's presence and non-nullability is what this card's acceptance criterion asks for — actual hash computation/verification is deferred, same pattern as prior schema-only cards (e.g. D024's inventory-movement actor/note columns, D026's overlap-prevention deferral).
