## What happened

Built the customer-initiated cancellation flow, wiring three domain/service pieces that already existed but had never been connected to a customer-facing entry point: D084's `CancellationPolicySet`/`computeCancellationRefund` (per-mode refund math), D094/D095's `DepositAuthorizationService.releaseHold` (deposit release), and D071's `ReservationRepository.cancel` (reservation cancellation). New `packages/db/src/services/CustomerCancellationService.ts` is the orchestrator: `cancelOrder(ctx, customerUserId, orderId, input)` checks ownership first — returning `undefined` on any mismatch, the exact same outcome as a nonexistent order id, the same IDOR-safe pattern D132's `CustomerOrderHistoryService.getOrderDetail` established — then, for every line on the order, computes the mode-correct refund via the existing policy math, issues it through `RefundProvider.createRefund` if positive, cancels the line's reservation if one is still blocking (`HELD`/`CONFIRMED`), and releases the line's deposit hold if one is still `AUTHORIZED`, before finally marking the order `CANCELLED` via a new `OrderRepository.cancel` (the first writer of the `orders.status`/`cancelled_at` columns' `CANCELLED` value). An order already `CANCELLED`/`REFUNDED` throws a new `OrderAlreadyFinalizedError` rather than silently double-refunding. New `POST /v1/m/:slug/account/orders/:orderId/cancel` (`apps/api/src/routes/customerOrders.ts`) requires an `Idempotency-Key` header (same convention as `./checkoutPayment.ts`) and the same session-cookie check as D132's two GET routes. `apps/api/src/app.ts` now shares one `DepositHoldProvider` instance between `registerCustomerOrderRoutes` and `registerDamageClaimRoutes` (previously each route file that needed one instantiated its own default `SimulatedDepositHoldProvider`, which is stateful — a hold placed under one instance can't be released under another) and gained `refundProvider`/`cancellationPolicySet` options with simulated/placeholder defaults, since no merchant-configurable policy storage exists yet (a gap flagged since D084/D096 and still open).

## Acceptance criteria check

**"Correct refund and deposit release per policy"** — Met. `CustomerCancellationService.test.ts` proves per-mode correctness directly: a `PRODUCT` line refunds 100% via the provider; a `SERVICE` line cancelled 30 hours before start lands in the policy's 24h tier (50%) and its `CONFIRMED` reservation flips to `CANCELLED`; a `RENTAL` line cancelled 30 hours before start lands in the rental policy's own (different) tier (25%) and its `AUTHORIZED` deposit hold transitions to `RELEASED` — proving both that refund math is genuinely per-mode (the same 30-hours-before-start input prices differently under `SERVICE` vs `RENTAL`) and that reservation/deposit side effects only fire when a reservation/deposit actually exists for that line. `apps/api/test/customerOrders.test.ts`'s first cancel case proves the same over real HTTP for a charged `PRODUCT` order, and confirms the order's `status` becomes `CANCELLED` only after every line's refund/reservation/deposit step has already run.

## Security check answer

**"Cancellation authority verified against ownership"** — Met, and answered by the same construction D132 used for reads: `CustomerCancellationService.cancelOrder` re-checks `order.customerUserId !== customerUserId` and returns `undefined` on a mismatch — indistinguishable from the order id simply not existing — so the route always answers `404`, never a distinguishable `403`. Proven at both layers: `CustomerCancellationService.test.ts`'s dedicated case cancels as `userB` against an order owned by `userA` and asserts the result is `undefined` **and** that the order's status and payments are completely untouched (no partial refund leaked out before the ownership check failed); `apps/api/test/customerOrders.test.ts`'s matching HTTP case asserts a `404` for another customer's order and that its status stays `CONFIRMED`, plus a separate case proving a genuinely nonexistent order id returns the identical `404`.
