## What happened

New `packages/db/src/jobs/DownstreamConflictAlerts.ts`, implementing steps 3-4 of `docs/design/05`'s "Late returns" section: "3. Detect downstream conflicts — reservations on the same unit starting soon. 4. Alert the merchant with a specific list of affected bookings and contact details." Builds directly on D081's `LateReturnDetector` — the same "overdue = `IN_USE` and `ends_at` passed" definition — but instead of stopping at "this item is late," it asks "who else is affected."

`detectDownstreamConflictsSqlite(conn, asOf, notifiers?)` is a **read-only** self-join query: every overdue reservation (`state = 'IN_USE' AND ends_at < asOf`) is joined against every other reservation on the *same* `merchant_id` + `subject_type` + `subject_id` that is still `HELD` or `CONFIRMED` and starts in the future (`starts_at > asOf`) — left-joined through `order_lines` → `orders` → `users` to resolve the affected booking's contact email. One alert row per (overdue, affected) pair, never collapsed into a single "unit N is overdue" notice, because the acceptance criteria is that the merchant learns exactly which booking and which customer to call, not just that a conflict exists somewhere. `detectDownstreamConflictsPg` is the PostgreSQL twin (`$1` placeholder), same precedent as every prior job in this family.

`onConflictAlert` is a single injected notifier callback (default no-op), fired once per alert — deliberately not split into merchant/customer variants like D081's notifiers, since this alert's whole point (per the card's acceptance criteria) is informing the *merchant* who to call; the affected customer's own outreach is a merchant action taken after seeing the alert, not an automated notification this job sends directly.

Wrote the failing test first (`DownstreamConflictAlerts.test.ts`, 5 cases, confirmed failing on `Cannot find module` before the file existed): no overdue reservation → no alert; overdue reservation with no future booking on its unit → no alert; overdue reservation with a `CONFIRMED` future booking on the *same* unit → exactly one alert, asserted to `toMatchObject` the specific `overdueReservationId`, `affectedReservationId`, `affectedStartsAt`, `affectedCustomerUserId`, and `affectedContactEmail` (not just a count) — this is the test that actually proves the acceptance criteria, "alert names the specific affected booking and contact"; a future booking on a *different* unit → no alert (same subject required); and a future booking that was subsequently `CANCELLED` (via `ReservationRepository.cancel`, D071's transition path) → excluded, since only `HELD`/`CONFIRMED` states genuinely block the unit.

## Acceptance criteria check

- "Alert names the specific affected booking and contact" — **Met.** The one-alert-per-pair test asserts the alert object carries the affected reservation's own id (`affectedReservationId`) and the affected customer's actual email (`affectedContactEmail`), resolved through the real `order_lines` → `orders` → `users` chain, not a generic "unit is double-booked" message.

## Security check answer

**"A late return is a double-booking that already happened."** Made operational, not just stated: the query treats an overdue `IN_USE` reservation as *already* conflicting with any `HELD`/`CONFIRMED` reservation on the same subject that starts after `asOf` — there is no grace period or "wait and see if it comes back late" logic, because by the time the second customer's `starts_at` arrives, the first customer already has the unit and hasn't returned it. The alert fires the instant both facts are true (overdue + a future claim on the same subject), same call, same read, no separate confirmation step, matching the design doc's framing that this is "a future double-booking that has already happened," not a probabilistic risk. What is **not yet closed**: no scheduler invokes this on an interval yet (same gap every job in this family carries since D062); the notifier is still a default no-op with no real delivery channel; and — deliberately, per the card split — this job does not decide what the merchant *does* about the conflict (rebook, call the second customer, waive a fee) or apply any late fee itself (`D083`).
