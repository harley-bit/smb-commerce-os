## What happened

Added the HTTP surface over D059's `BookingService` (`apps/api/src/routes/bookings.ts`): `POST /bookings` (create a `HELD` booking), `GET /bookings/:id`, and `POST /bookings/:id/confirm` (HELD → CONFIRMED). These are staff-authenticated routes (`app.authenticate` + `bookings:manage`, OWNER/ADMIN/STAFF — same RBAC action `BookingService` already enforces, checked again at the route per `./listings.ts`'s defense-in-depth precedent), not a public storefront endpoint — matches D059's finding that booking a resource is a routine staff operation. `Idempotency-Key` is read from its own request header (per `docs/design/06`'s conventions table), not the JSON body; `createServiceBookingInputSchema` (D059, `packages/contracts`) is reused for the body via `.omit({ idempotencyKey: true })` since this route is the schema's first HTTP caller and the header is now the source of truth for that field. `BookingService` and `MissingIdempotencyKeyError` weren't exported from `packages/db`'s public entrypoint yet — added both to `packages/db/src/index.ts` and rebuilt the package (`pnpm --filter @smb-os/db build`), otherwise `apps/api` resolves against the stale `dist/`.

This card's acceptance criterion drove the 409-conflict handling specifically: `ReservationConflictError` is caught and translated to a generic Problem Details body ("This resource is not available for the requested time.") that deliberately never forwards `error.message` or looks up the conflicting reservation's id/`orderLineId` — the only fields that could identify who else holds the slot. `GET`/`confirm` reuse `ReservationRepository.findById`'s existing tenant scoping (`TenantScopedRepository`), so a booking created under another merchant returns 404, not 200/403, exactly the IDOR-safe shape `./listings.ts` already established. Test-first throughout: `apps/api/test/bookings.test.ts` was written before the route file existed (confirmed failing — `Cannot find module`), then iterated through two real bugs the tests caught: the body schema initially still required `idempotencyKey` (double-submission with the header), and `BookingService`/`MissingIdempotencyKeyError` weren't actually resolvable from `@smb-os/db` until the export + rebuild.

## Acceptance criteria check

- **Booking routes + privacy test** — Met. `apps/api/src/routes/bookings.ts` adds the three routes; `apps/api/test/bookings.test.ts` (16 tests, all green) covers role-based authorization (OWNER/ADMIN/STAFF can create, READ_ONLY forbidden), idempotent replay, invalid-payload/missing-resource 400s, illegal-transition 409, and the specific "acceptance criterion" cases: **response never contains another customer's identity** — proven both for cross-tenant IDOR (`GET`/`confirm` on another merchant's booking → 404, body excludes `orderLineId`) and for same-tenant conflicts (a second booking on an already-held resource → 409, body excludes the first booking's id, `orderLineId`, or the string `customer`).

## Security check answer

**THREAT: information disclosure via availability response.** Applied to booking creation: a 409 conflict response tells an attacker a slot is taken, but must not tell them *who* holds it. `ReservationConflictError` (thrown inside `BookingService.createServiceBooking` → `ReservationRepository.createGuarded`) carries only `subjectType`/`subjectId` — the *resource*, not a person — and the route handler intentionally discards even that, returning a fixed generic detail string rather than `error.message` or a lookup of the conflicting row. Proven by `bookings.test.ts`'s "a conflicting booking never reveals the other reservation's identity" test: creates booking A, then attempts a second overlapping booking as the same tenant, and asserts the 409 body contains neither booking A's id, `orderLineId`, nor the string `customer`. Cross-tenant reads/confirms are the second half of the same threat model — proven by the two IDOR tests returning 404 (not 200/403) for another merchant's booking.
