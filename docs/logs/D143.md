## What happened

Built the mobile service listing detail screen and slot picker, Phase 8's seventh card, replacing D142's "not available yet" placeholder for SERVICE-mode listings. New `apps/mobile/src/merchant/fetchServiceDetail.ts` mirrors D142's `fetchProductDetail.ts` — calls the existing unauthenticated `GET /v1/m/{slug}/listings/{listingSlug}`, checks the response's own `mode` field before validating against `@smb-os/contracts`'s `publicServiceDetailSchema`, and returns `not-found`/`wrong-mode`/`invalid`. New `fetchServiceAvailability.ts` calls the existing `GET /v1/m/{slug}/availability?resourceId=&from=&to=` (`apps/api/src/routes/availability.ts`, already used by the web storefront's `ServiceDetailView.tsx`) and passes the `{ free: Interval[] }` response through verbatim. New `serviceAvailabilityWindow.ts` is a pure fixed 14-day window from "now" — the same starting window D123 originally shipped on web before D125 added month navigation there; month navigation is out of this card's scope. New `ServiceDetailScreen.tsx` (no test of its own, same thin-glue boundary as `ProductDetailScreen.tsx`) renders the listing's name/description, then every entry of the `free` array as a labeled "Book" button — nothing else on the screen is selectable. Tapping "Book" calls `onBook(interval)`, which `App.tsx` wires to push the `Checkout` screen, same navigation-only posture D124's log documented for the web storefront's "Reserve" buttons (`CartService`/booking-creation still has no HTTP route reachable from here).

Closed a real routing gap while wiring this in: `App.tsx`'s `ListingDetail` case previously rendered `ProductDetailScreen` unconditionally for every mode, relying on that screen's own internal `wrong-mode` detection to show the "not available yet" notice for SERVICE/RENTAL. That approach can't scale to a second real mode-specific screen (SERVICE now needs its own real screen, not a notice). New `resolveListingMode.ts` is a lightweight probe (fetch the listing, read only its `mode` field) and new `ListingDetailScreen.tsx` dispatches to `ProductDetailScreen`/`ServiceDetailScreen` based on that probe, still showing the "not available yet" notice for RENTAL (D144's scope) — each mode-specific screen still performs its own complete fetch-and-validate against `@smb-os/contracts`; the probe never substitutes for that. `App.tsx` now renders `ListingDetailScreen` instead of `ProductDetailScreen` directly, wiring both `onBuy` and `onBook` to push `Checkout`.

## Acceptance criteria check

"Only free slots selectable" — met by construction, verified by test. `fetchServiceAvailability.test.ts` proves the helper passes the server's `free` array through verbatim (no client-side filtering, no invented entries) and reports `{ ok: false }` on any non-ok response or a malformed body. `ServiceDetailScreen.tsx` renders exactly one "Book" button per entry of that `free` array and nothing else is selectable on the screen — there is no code path to select a slot the server didn't report as free. `serviceAvailabilityWindow.test.ts` proves the request window itself is a bare 14-day range from "now", with no user-suppliable offset.

## Security check answer

"Free/busy only" — answered by construction and verified by test. `apps/api/src/routes/availability.ts`'s response shape (`{ free: Interval[] }`) never carries a reservation id or customer name — only bare `start`/`end` ISO instants — a fact already established by D123/D125's web implementation of the same route. `fetchServiceAvailability.ts` reads only that `free` field off the response and passes it through unmodified (`fetchServiceAvailability.test.ts` asserts the exact array round-trips), so this mobile client has no busy-slot or booking-identity data to leak even if a future change wanted it to — there is nothing to redact because nothing sensitive was ever fetched.
