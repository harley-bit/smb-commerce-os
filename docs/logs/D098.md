## What happened

New pure domain function `mapDeclineToCustomerMessage` (`packages/domain/src/payments/declineHandling.ts`) maps a provider's raw `DeclineCode` (`insufficient_funds | expired_card | incorrect_cvc | processing_error | card_declined | lost_card | stolen_card | fraud_suspected`) to a `DeclineOutcome` — a customer-facing `customerMessage` plus a `retryableWithSameMethod` flag telling the caller whether prompting an immediate retry with the identical payment method is worth it (a transient `processing_error` or a mistyped `incorrect_cvc`) versus steering the customer to a different one (`insufficient_funds`, `expired_card`, or anything fraud-adjacent). The card's security check is structural here: `card_declined`/`lost_card`/`stolen_card`/`fraud_suspected` all collapse onto the exact same generic message text — a caller cannot distinguish "this card was reported stolen" from a plain decline by inspecting the output. `PaymentIntentProvider`'s `PaymentIntentStatus` gained a `DECLINED` member and `PaymentIntentResult` gained an optional `declineCode` (`packages/domain/src/payments/PaymentIntentProvider.ts`) — documented as an internal-only signal that must be routed through the mapper before reaching a customer. `SimulatedPaymentIntentProvider` (`packages/db/src/payments/SimulatedPaymentIntentProvider.ts`) gained test-only `simulateDeclineForOrder`/`clearDeclineForOrder` seams (no real Stripe account exists to actually decline a card, same "native/simulated now" precedent as every other provider in this codebase) — a decline persists across idempotency-key retries until explicitly cleared, modeling a customer retrying the same bad card versus switching methods. `CheckoutPaymentService.createCheckoutIntent` (`packages/db/src/services/CheckoutPaymentService.ts`) is the card deliverable: when the provider returns `DECLINED`, it runs `mapDeclineToCustomerMessage` and throws a new `PaymentDeclinedError` carrying only the mapped `customerMessage` and `retryableWithSameMethod` — there is no field on the error a caller could accidentally surface that leaks the raw decline code or any other payment-method detail. 6 new domain tests (`declineHandling.test.ts`, incl. one proving all four fraud-adjacent codes produce the identical message and none of "lost"/"stolen"/"fraud" appear in any customer-facing text), 2 new provider tests, 3 new service tests (a declined checkout produces `PaymentDeclinedError` with the right message/flag, a fraud-adjacent decline's error text is checked against leaking, and a `processing_error` decline is proven retryable — clearing the simulated decline and retrying with a fresh idempotency key succeeds).

## Security check answer

**"Error text reveals nothing about the payment method."** `mapDeclineToCustomerMessage` collapses `card_declined`, `lost_card`, `stolen_card`, and `fraud_suspected` onto one identical generic message string (`declineHandling.test.ts`'s "collapses every fraud-adjacent decline onto the exact same generic message" test asserts the four outputs produce a `Set` of size 1) — a caller receiving a `PaymentDeclinedError` cannot tell a plain decline apart from a card flagged lost, stolen, or fraudulent, which matters both ways: it doesn't tip off an actual card-tester probing which decline reason they hit, and it doesn't wrongly alarm or accuse a legitimate cardholder whose card was misflagged. None of the four messages contain the substrings "lost", "stolen", or "fraud" (asserted directly). `PaymentDeclinedError` itself has no field beyond the mapped `message` and `retryableWithSameMethod` — there is no raw `declineCode` or provider detail attached to the error for a caller to accidentally log or display. The provider-level `declineCode` field on `PaymentIntentResult` is explicitly documented as internal-only in `PaymentIntentProvider.ts`'s doc comment, precisely so a future caller doesn't bypass the mapper and surface it directly.
