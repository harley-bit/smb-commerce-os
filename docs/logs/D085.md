## What happened

New pure domain module `packages/domain/src/media/mediaRetentionPolicy.ts` — `evaluateMediaRetention(input, now)` implements exactly the two-rule policy `docs/design/08` names: 90 days after rental completion (`CHECKIN`) when no damage claim was ever filed, or 2 years after a filed claim's resolution, with claims that are still `LIVE` (filed, unresolved) or `DISPUTED` never eligible regardless of elapsed time. Deadlines are computed calendar-wise (`setUTCDate`/`setUTCFullYear`) so a 2-year deadline lands on the same month/day two years later across leap years. Wrote the failing test first (`mediaRetentionPolicy.test.ts`, confirmed failing on `Cannot find module` before the file existed) — 8 cases covering before/at/after the 90-day boundary, before/at the 2-year boundary, live claims, disputed claims, and that a resolved claim's clock keys off resolution date, not rental completion. 100% statement/branch/function coverage on the new file.

New `packages/db/src/jobs/MediaRetentionJob.ts` — the I/O wrapper, same shape as `DepositAutoReleaseJob.ts` (D080): `runMediaRetentionSqlite` and `runMediaRetentionPg`. Each run fetches every `condition_media` row joined to its order line's earliest `CHECKIN` `condition_reports` timestamp, and every `damage_claims` row for those order lines; `combineClaimStatus` folds multiple claims on one line into the single `MediaRetentionClaimStatus` the domain function needs (a disputed claim always wins over a live one, which always wins over a resolved one, on the same line); `evaluateMediaRetention` then makes the actual eligibility call per media row. `dryRun: true` returns the candidate list and touches nothing. `dryRun: false` deletes each eligible `condition_media` row, calls an optional injected `MediaObjectDeleter` for the underlying storage object (same optional-callback shape as `DepositReleaseCustomerNotifier`), and appends one hash-chained `audit_log` entry per deletion via the existing `AuditLogRepository` (SQLite) or equivalent raw SQL against the same hash-chain algorithm (`computeRowHash`) for PostgreSQL. A second real run against the same data is a no-op (delete-then-check-`changes`/`rowCount` guards re-processing), and a dry run followed by a real run deletes exactly the set the dry run reported.

Wrote the failing test first for the job too (`MediaRetentionJob.test.ts`, 8 cases against real SQLite via `better-sqlite3`): dry run lists without deleting; media less than 90 days old is excluded; a live claim excludes regardless of age; a disputed claim excludes regardless of age; a resolved claim becomes eligible once its own 2-year clock elapses; a real run deletes and writes exactly one audit record with `action: CONDITION_MEDIA_RETENTION_DELETED` whose `beforeJson` carries the storage key and reason; idempotency on a second real run (no further deletions, no further audit rows); dry-run/real-run agreement. The PostgreSQL path (`runMediaRetentionPg`) mirrors the SQLite query and audit-append logic in raw SQL but has no test exercising it in this session — same as every other job's `*Pg` counterpart in this codebase (`describe.skipIf(!process.env.DATABASE_URL)`), it's untested here because no real PostgreSQL instance is available in this environment.

## Acceptance criteria check

- "Dry run lists correctly" — **Met.** `runMediaRetentionSqlite(conn, { dryRun: true, now })` returns exactly the eligible candidates (id, order line, storage key, reason) and performs no writes — proven by a test that asserts the media row is still present via `ConditionMediaRepository.findByStorageKey` after a dry run, and by a test that dry-run and a following real run delete the identical id set.
- "Deletion writes an audit record" — **Met.** A real run (`dryRun: false`) appends one `audit_log` row per deleted `condition_media` row, hash-chained through the existing `AuditLogRepository`/`computeRowHash` machinery — verified by asserting `auditLogRepo.list(ctx)` has exactly one new entry with the correct `actorType: SYSTEM`, `action`, `entityType`, `entityId`, and a `beforeJson` capturing the storage key and the specific retention reason that triggered the deletion.

## Security check answer

**"Retention set when the feature ships, not deferred."** Addressed the same way `docs/design/08`/`docs/design/14` (risk T12) require: this card lands in Phase 4 alongside the condition-media feature itself (D073–D076), not as a later cleanup task, and the retention clock has exactly the two values the design doc specifies — 90 days with no claim, 2 years after a filed claim resolves — with no default/fallback path that could silently apply a shorter or longer window, and no way for a live or disputed claim's media to be deleted (the domain function's `LIVE`/`DISPUTED` branches both return `{ eligible: false }` unconditionally, before any date arithmetic runs). What is **not yet closed**: this job is not wired to any scheduler yet (`docs/design/11` names EventBridge Scheduler → ECS as the eventual production trigger) — it is invokable, tested, and idempotent, but nothing currently calls it on a cadence, matching the same "domain/job built, wiring deferred" split every prior sweeper/detector card in this phase (D057, D080–D082) has left open. There is also no real cloud object-storage deletion yet — `MediaObjectDeleter` is an injected optional callback (mirroring `HmacMediaUploadProvider`'s "native now, real provider later" stub pattern from D073), so a real run today deletes the `condition_media` database row and audit-logs it correctly, but actually removing bytes from a storage backend depends on whichever concrete provider composition wires in that callback — not a gap introduced by this card, since `HmacMediaUploadProvider` itself has no delete capability to call yet.
