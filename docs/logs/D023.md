## What happened

Closed the mode-immutability gap D022 flagged. Added `ListingRepository` (`packages/db/src/repositories/ListingRepository.ts`), the first `TenantScopedRepository` subclass for `listings`, scoped conventionally on `listings.merchant_id`; its `UpdateListingInput` type deliberately omits `mode` — the compile-time half of the immutability guarantee. On top of it, added `ListingService` (`packages/db/src/services/ListingService.ts`), the repo's first service-layer class: `create`/`update`/`archive` each call `assertCanManageCatalog(actingRole)` first (restricted to `OWNER`/`ADMIN`, per `docs/design/07`'s role table treating catalog management as an "Operations" action — `STAFF`/`READ_ONLY` denied), and `update` additionally calls `assertModeUnchanged(patch)`, which throws if the patch object carries a `mode` key at all — the runtime half of immutability, covering a caller that hands the service a plain object with an extra `mode` field bypassing the `UpdateListingInput` type (exactly what a future controller deserializing a client JSON body would need to be protected against). Test-first via two new files (confirmed failing on `Cannot find module` before either class existed): `ListingRepository.test.ts` (7 cases, including the standard cross-tenant `ctxA`/`ctxB` coverage D021's generator requires) and `ListingService.test.ts` (10 cases: role-gated create/update/archive for all four `merchant_users` roles, the mode-immutability rejection itself, a clean update with no `mode` key succeeding normally, and cross-tenant isolation flowing through from the repository). Both classes exported from `packages/db/src/index.ts`.

## Acceptance criteria check

- "Attempt to change mode after creation is rejected" — **Met**. `ListingService.test.ts`'s "attempt to change mode after creation is rejected" case creates a `PRODUCT` listing, then calls `service.update(ctx, "OWNER", id, { name: "Retagged", mode: "SERVICE" })` (the `mode` key injected via a cast past `UpdateListingInput`, simulating a tampered payload) and asserts it throws `/mode is immutable/i`, then re-reads the listing and confirms `mode` is still `PRODUCT`.

## Security check answer

"Authorization asserted at service layer, not controller" — **by construction**. `ListingRepository` has no role concept at all — it only ever enforces tenant scoping (`docs/design/07` Control #1). The `OWNER`/`ADMIN`-only check for `create`/`update`/`archive` lives entirely in `ListingService`'s `assertCanManageCatalog` helper, called at the top of each of those three methods, before the repository is ever touched — matching `docs/design/07`'s stated pattern of "a single `assertCan(ctx, action, resource)` call at the top of each service method." There is no controller/route for listings yet (that's a later Phase 2 card); when one is added, it will call `ListingService`, never `ListingRepository` directly, so the authorization check cannot be bypassed by a controller that forgets to ask — proven today by `ListingService.test.ts`'s four role-matrix cases (`OWNER`/`ADMIN` allowed, `STAFF`/`READ_ONLY` rejected) exercising the service directly with no controller in the loop at all.
