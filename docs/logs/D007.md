## Security check answer

**Q: SBOM is the dependency-inventory evidence for control ID —**
A: This maps to SOC 2 CC7.1 / CC9.2 (vulnerability and third-party risk management — maintaining an inventory of components to identify and respond to vulnerabilities) and NIST SSDF PW.4 / RV.1 (maintain provenance and a software bill of materials for produced software). The CycloneDX SBOM generated by `syft` in the "Generate SBOM (CycloneDX)" CI step and retained for 90 days as a build artifact is the machine-readable inventory of every dependency (279–280 components as of this run) shipped in a given build — the evidence an auditor or incident responder would pull to answer "was package X, at version Y, present in production" for any release. Paired with the `pnpm audit --audit-level=high` gate (which blocks known-vulnerable dependencies with a fix from merging at all), the SBOM covers the complementary case: *proving*, after the fact, exactly what shipped, including transitive dependencies not visible from `package.json` alone. No live control framework has been formally adopted for this project yet (Phase 0), so this is process/evidence groundwork, not a response to an actual audit request.
