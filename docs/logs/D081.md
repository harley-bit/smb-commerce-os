## What happened

New `packages/db/src/jobs/LateReturnDetector.ts`, implementing step 1-2 of `docs/design/05`'s "Late returns" section: "A rental whose `ends_at` has passed with no `RETURNED` event is overdue... 1. Mark the reservation overdue (derived, not a stored state). 2. Notify merchant and customer." Steps 3-5 (downstream conflict detection/alerting, late fees) are explicitly out of scope for this card — they land in `D082` and `D083` per `docs/BUILD_CALENDAR.md`.

`detectOverdueReservationsSqlite(conn, asOf, notifiers?)` is a **read-only** query: `SELECT ... FROM reservations WHERE state = 'IN_USE' AND ends_at < asOf`, left-joined through `order_lines` → `orders` to surface `customerUserId` for the notification payload. There is no `overdue` column anywhere in the schema and this function contains no `UPDATE` statement — overdue is recomputed fresh from `state` and `ends_at` on every call, so it can never drift out of sync with reality the way a cached/stored flag could. `detectOverdueReservationsPg` is the PostgreSQL twin (same query, `$1` placeholder), added for symmetry with the other scheduled jobs (`HoldExpirySweeper`, `DepositAutoReleaseJob`) even though no PG-specific test exists yet, matching the precedent `DepositAutoReleaseJob` (D080) set of a SQLite-only test suite for this style of job.

"Notify merchant and customer" is two injected `OverdueReservationNotifier` callbacks (`onMerchantNotify`/`onCustomerNotify`, both optional/default no-op), same shape as `DepositReleaseCustomerNotifier` (D080), `DamageClaimCustomerNotifier` (D076), and `FutureReservationCancelledNotifier` (D069) — each fires once per overdue reservation found, on every call, since there is nothing to mark "already notified" without introducing the stored state field the acceptance criteria explicitly forbids. Deduping actual notification delivery (so a customer isn't emailed every minute the scheduler ticks) is a job for whatever real delivery-channel/scheduler wiring lands later, the same gap every prior notifier-shaped job in this repo has carried.

Wrote the failing test first (`LateReturnDetector.test.ts`, 5 cases, confirmed failing on `Cannot find module` before the detector file existed): an `IN_USE` reservation whose `ends_at` is still in the future is not detected; an `IN_USE` reservation whose `ends_at` has passed is detected, both notifiers fire exactly once with the right payload (including `customerUserId` resolved through the order-line join), and `reservations.state` is unchanged (still `IN_USE` — nothing was written); a `COMPLETED` reservation past its `ends_at` is not detected (it was returned); a `HELD` reservation past its `ends_at` is not detected (it was never checked out, so nothing is late); and calling the detector twice in a row returns the same overdue reservation both times, demonstrating the "derived, not stored" behavior directly rather than just asserting the absence of a column.

## Acceptance criteria check

- "Overdue detected without a stored state field" — **Met.** No new column was added to `reservations` (or anywhere else); overdue-ness is computed each call from the existing `state`/`ends_at` columns. The "second call still detects the same reservation" test proves this isn't silently caching a result anywhere.

## Security check answer

**"Overdue is derived — no state drift."** Enforced structurally: `detectOverdueReservationsSqlite`/`Pg` are pure `SELECT` queries with no accompanying `UPDATE`, so there is no persisted "overdue" value that could ever fall out of sync with the underlying `state`/`ends_at` truth — there is nothing to drift because nothing is stored. Every call re-derives the answer from current data, verified by the test that calls the detector twice and gets the identical result both times purely from re-reading `state`/`ends_at`, not from any cached flag. What is **not yet closed**: no scheduler invokes this on an interval yet (same gap `HoldExpirySweeper`/`DepositAutoReleaseJob` still carry), no real notification delivery channel exists behind the two callbacks (default no-op), and — deliberately, per the card split — this job does not yet detect the downstream double-booking conflict a late return can cause (`D082`) or apply any late fee (`D083`).
