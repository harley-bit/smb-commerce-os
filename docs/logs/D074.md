## What happened

Built the confirm step D073's log flagged as this card's job: verifying the uploaded bytes' `sha256` and actually writing the `condition_media` row. Added a real unique index (`condition_media_storage_key_unique`, both dialects, new migrations `sqlite/0014` and `pg/0016`) on `condition_media.storage_key` — the database-level guarantee that a storage key can never be silently reused. `ConditionMediaRepository` (`packages/db/src/repositories/ConditionMediaRepository.ts`) is the first `TenantScopedRepository` subclass for that table: `create`, `findByStorageKey`, `listByConditionReport`. `ConditionMediaConfirmService.confirmUpload` (`packages/db/src/services/ConditionMediaConfirmService.ts`) is the card's deliverable — it takes the condition report ID, the `storageKey` `ConditionMediaUploadService.requestUpload` (D073) minted, the actual uploaded `bytes` (a `Buffer`), and the client's `declaredSha256` (computed on-device before upload). It re-runs D073's role/report-ownership/content-type/size checks (reusing `ConditionReportNotFoundError`, `UnsupportedMediaTypeError`, `MediaTooLargeError` from `ConditionMediaUploadService.ts` rather than duplicating them), then computes `sha256` itself from the real bytes with Node's `crypto` — never trusting the caller's hash — and throws `ConditionMediaHashMismatchError` without writing anything if it disagrees with the client's declared value. It also pre-checks `findByStorageKey` and throws `ConditionMediaStorageKeyReusedError` on a second confirmation against the same key, with the new unique index as a real backstop if that application-layer check is ever bypassed (same belt-and-suspenders pattern D030 documents for its audit log).

## Acceptance criteria check

- **SHA-256 recorded at upload** — Met. `confirmUpload()` always stores the server-computed hash of the actual bytes (never the caller's claim) in `condition_media.sha256`; proven directly (`confirmUpload() allows role %s and records the server-computed sha256`) and via the DB-bypass test that inserts through the repository directly.
- **Keys never overwritten** — Met, two layers deep. Application layer: a second `confirmUpload()` call against a `storageKey` already recorded throws `ConditionMediaStorageKeyReusedError` without touching the first row (`confirmUpload() rejects a second confirmation against the same storage key`). Database layer: `condition_media_storage_key_unique` rejects a duplicate `storage_key` insert even when the repository's `create()` is called directly, bypassing the service's pre-check entirely (`the database itself rejects a duplicate storage_key even bypassing the application-layer check`).
- **Hash mismatch detected** — Met. A `declaredSha256` that doesn't match the server's own hash of the real bytes throws `ConditionMediaHashMismatchError` and writes no row (`confirmUpload() detects a hash mismatch and does not write a row`).
- **Overwrite attempt rejected** — Met, same evidence as "keys never overwritten" above.

## Security check answer

**THREAT: tampering with dispute evidence.** Two independent tampering vectors are closed. (1) Corrupted-or-swapped-in-transit bytes: the server never trusts a caller-supplied hash for what it stores — it recomputes `sha256` from the actual bytes it received and only persists that value, and if the client's own declared hash (computed before upload) disagrees, the whole confirmation is rejected rather than silently recording a hash that doesn't match the evidence. This means a `condition_media.sha256` value in the database is always provably the hash of the bytes actually stored under that key, not a value an attacker or a buggy client could inject to make tampered evidence look clean. (2) Post-hoc evidence swap: once a `storageKey` has been confirmed, it's permanently closed to further writes — enforced first at the application layer (a clear domain error, checked before any DB call) and then, as real defense-in-depth against a race or a bypass of that check, by a genuine unique index at the database layer, proven by a test that calls the repository directly and confirms the constraint fires. Together these mean neither "swap the photo after the fact" nor "claim a hash that doesn't match what's stored" is possible through this service — which is the property a financial dispute over rental condition actually needs. One honest limit carried from D073: no real cloud object storage is provisioned yet, so `confirmUpload` receives bytes directly rather than fetching them from a bucket after upload — the hash-verification logic itself doesn't change when a real `MediaUploadProvider` implementation lands, but the caller wiring that fetches bytes from storage before calling `confirmUpload` is still future work, same "native now, real provider later" situation as D010/ADR-002.
