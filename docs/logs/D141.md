## What happened

Extended `GET /v1/m/{slug}/listings` (`apps/api/src/routes/publicStorefront.ts`) with opt-in cursor-based pagination — a new `ListingService.listPublishedPage` (`packages/db`) sorts published listings by their own `id` (a UUIDv7, monotonically increasing with creation time), and, when the request supplies a `?limit=`, returns at most that many and an `X-Next-Cursor` response header carrying the last item's own `id` (present only when more remain). When `limit` is omitted the route behaves exactly as it did before this card (the whole catalog, one array, no header) — every existing caller (the web storefront's `MerchantPageView.tsx`, the mobile app's prior D140 `Home` fetch) is unaffected; this was a deliberate backward-compat choice so the change is additive, not a breaking response-shape migration. On mobile: new `apps/mobile/src/merchant/fetchCatalogPage.ts` (DI'd `fetchFn`, reads the `X-Next-Cursor` header, validates the body against `@smb-os/contracts`'s `publicListingSchema`) and `catalogFilter.ts` (pure `CatalogFilter` type/`filterToMode`, an `ALL`/`PRODUCT`/`SERVICE`/`RENTAL` tab list), both unit-tested. `HomeScreen.tsx` was rewired: it previously fetched the entire mixed catalog unbounded via `fetchMerchantHome` and grouped it into three always-present sections; now it fetches 20 listings at a time per filter tab via `fetchCatalogPage`, with a "Load more" button appending the next page using the server's own cursor. `fetchMerchantHome.ts` was narrowed to just the profile fetch (its listings-fetching responsibility moved to `fetchCatalogPage`) — updated its own test accordingly. `merchantCatalog.ts`/`groupListingsByMode` (D140) became dead code once `HomeScreen` stopped grouping a full unbounded list into fixed sections, so it and its test were deleted rather than left unused. Confirmed the Metro `.js`-suffix bug class D138/D139/D140 all hit doesn't recur here — no new suffixed imports were added — via a real `npx expo export --platform ios --platform android` bundle (753/753 iOS modules, 427/427 Android modules, zero errors), not just typecheck.

## Acceptance criteria check

- "All three modes browsable" — **met**. `CATALOG_FILTERS` exposes `ALL`/`PRODUCT`/`SERVICE`/`RENTAL` tabs; each fetches its own paginated catalog via `fetchCatalogPage`'s `mode` parameter, proven server-side by `publicStorefront.test.ts`'s "combines the mode filter with pagination" case and client-side by `catalogFilter.test.ts`.

## Security check answer

"Pagination cursor-based, no offset leakage" — answered by construction on both layers. Server: `GET /v1/m/{slug}/listings` accepts only `mode`, `cursor`, and `limit` query parameters — there is no `offset`/`page` parameter anywhere in the route's typed querystring, so an extra `?offset=1` is simply ignored (proven by `publicStorefront.test.ts`'s "has no offset/page query parameter at all" case, asserting an offset-shaped request returns the identical body to one without it). The cursor itself is opaque — the last-seen listing's own `id` — never a numeric position, so a caller can only walk forward from a page it was actually handed, never jump to or infer a position in the catalog (`ListingService.listPublishedPage`'s doc comment states this explicitly; `ListingService.test.ts`'s "walking the cursor forward visits every listing exactly once" case proves the walk is gapless and duplicate-free). Client: `fetchCatalogPage.ts` only ever forwards the `cursor` value the server's own `X-Next-Cursor` header handed back in a prior page — nothing in `HomeScreen.tsx` computes or accepts an offset/index of its own.
