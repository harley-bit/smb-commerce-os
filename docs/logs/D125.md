## What happened

Added month navigation to the service listing detail page's slot picker (`apps/web/src/app/m/[slug]/l/[listingSlug]/ServiceDetailView.tsx`, D123). Previously it fetched one fixed 14-day window from `GET /v1/m/{slug}/availability` (`apps/api/src/routes/availability.ts`) on load with no way to look further ahead. New pure module `availabilityWindow.ts` exports `computeMonthWindow(now, monthsAhead)`, which pages forward one calendar month at a time (page 0 starts at `now` itself, not the 1st of the current month, so today's remaining slots aren't hidden) and `monthLabel(date)` for the header. `ServiceDetailView` now holds a `monthsAhead` counter, refetches availability whenever it changes, and renders "Previous month"/"Next month" buttons around a month/year label. "Previous month" disables at `monthsAhead === 0`. `computeMonthWindow` clamps `to` at `now + 90 days` — the same cap `AvailabilityService` (`packages/db/src/services/AvailabilityService.ts`) enforces server-side via `AvailabilityRangeTooLargeError` — and reports `canGoNext: false` the instant a further page's natural end would cross that cap, which the UI uses to disable "Next month" before ever issuing an over-wide request. Wrote failing tests first: `availabilityWindow.test.ts` (5 cases — page-0 starts at `now`, later pages align to calendar-month boundaries, `to` never exceeds the 90-day cap across 12 simulated pages, `canGoNext` goes false exactly once the window is clamped, `monthLabel` formatting) and three new `ServiceDetailView.test.tsx` cases (renders month nav and refetches on "Next month" click; "Previous month" disabled on the initial page; "Next month" disables itself once navigating further would cross the cap). One pre-existing test ("shows no selectable slots when nothing is free") had to be narrowed from `queryByRole("button")` to a name pattern matching only slot buttons (`/–.*UTC/`), since month-nav buttons are now legitimately present even with zero free slots.

## Acceptance criteria check

- "Matches server availability exactly" — **met**. `free` is rendered verbatim from the `GET /v1/m/{slug}/availability` response for the currently-selected month window, never filtered, recomputed, or merged with a previous page's results — proven by the existing "renders only the free intervals as selectable slots" case (unchanged assertion) still passing against the new month-scoped fetch, and the new "refetches availability for the navigated month" case asserting a second, distinct `/availability` call fires on "Next month".

## Security check answer

"90-day request cap respected by the client" — **met**. `computeMonthWindow` computes `cap = now + 90 days` and clamps every page's `to` at that cap (`availabilityWindow.test.ts`'s "never lets `to` exceed 90 days from `now`, however far the client navigates forward" — asserted across 12 simulated forward pages, well past where the real cap is hit). `canGoNext` is derived from the same clamp check (`naturalEnd >= cap`), so the "Next month" button disables itself in the same render pass that would otherwise produce an over-cap window — proven by `ServiceDetailView.test.tsx`'s "disables Next month once navigating further would exceed the 90-day cap," which clicks forward until the button reports `disabled`. The client never depends on the server's `AvailabilityRangeTooLargeError` to catch an over-wide request; it structurally can't construct one.
