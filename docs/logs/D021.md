## What happened

Built `packages/db/src/tenancy/isolation-coverage.ts`, a generator that scans every repository source file in a directory (via the TypeScript compiler API, same pattern D017 used for compile-time diagnostics), finds every class extending `TenantScopedRepository`, and lists its public `RepositoryMethod`-typed members. For each method it then parses that repository's sibling `.test.ts` file and checks for at least one `it()` block that both calls the method and references two distinct tenant-context identifiers (e.g. `ctxA`/`ctxB`) — real evidence the method was exercised across two merchants, not just declared to take a `TenantContext`. A method with no such evidence is reported as an `IsolationCoverageGap`. Ran this generator against `packages/db/src/repositories` (the four real tenant-scoped repositories built in D019–D020) and it reports zero gaps — every existing method already has genuine cross-tenant test coverage. Two fixture repositories (`GoodFixtureRepository`, fully covered; `BadFixtureRepository`, with an `archive` method added but never isolation-tested — the "new method lands untested" scenario) prove the generator both passes clean code and catches the gap.

## Acceptance criteria check

- "New repository method without a test fails the build" — **Met**. `isolation-coverage.test.ts`'s `findIsolationCoverageGaps` runs against the real `packages/db/src/repositories` directory as part of `pnpm test`; if a future card adds a method to any `TenantScopedRepository` subclass without adding a matching cross-tenant `it()` block, that assertion (`expect(gaps).toEqual([])`) fails and the build fails. Proven directly with the `BadFixtureRepository` fixture, whose untested `archive` method is reported as exactly one gap.

## Security check answer

"THE critical control. Never waivable" — read as: does this generator actually enforce Gate G1 (tenant isolation) going forward, or just check today's state? Answered honestly: it enforces it going forward for `TenantScopedRepository` subclasses specifically, because it's now a permanent assertion in `pnpm test` (not a one-time audit) — any new method on `MerchantRepository`, `LocationRepository`, `MerchantUserRepository`, or any future tenant-scoped repository that lacks cross-tenant test evidence breaks CI immediately. Two known limits, tracked rather than hidden: (1) it can only see repositories that actually extend `TenantScopedRepository` — a new repository class that should be tenant-scoped but isn't (e.g. forgets to extend the base class) is a gap this generator cannot detect, since it never enters its scan; that failure mode is Control #1's type-system layer's job (`RepositoryMethod`'s `ctx`-first signature), not this generator's. (2) the "isolation evidence" heuristic (two distinct `ctx*` identifiers in the same `it()` block that also calls the method) is a structural proxy, not a semantic proof the assertions inside actually check isolation — a badly-written test that merely *mentions* two contexts without asserting cross-tenant behavior would still count as covered. Given the existing test suite's actual assertion patterns (verified by inspection: every real `it()` block flagged as covered genuinely asserts one merchant's data is invisible to or unmodified by the other), this gate stays non-waivable in practice, but it is not a substitute for reviewing new isolation tests' assertions by hand.
