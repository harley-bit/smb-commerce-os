## What happened

`ResourceService`/`AvailabilityRuleRepository`/`AvailabilityService` (D058) already had full weekly-rule CRUD and a DST-correct read path (`packages/domain/src/utils/availabilityRule.ts`'s `expandAvailabilityRule`) with zero merchant-facing HTTP surface or dashboard UI. Closed the HTTP gap with three additions to `apps/api/src/routes/resources.ts`: `GET`/`POST /resources/:resourceId/availability-rules` (forces `resourceId` from the URL, never trusts a body-supplied value — same "path is the source of truth" posture `variants.ts` uses for `listingId`/`mode`) and an authenticated `GET /resources/:resourceId/availability` that wraps the already-tested `AvailabilityService.getResourceAvailability`, sharing the same `AvailabilityCache` instance `app.ts` already threads through `./availability.ts`'s public route and `./bookings.ts` so a reservation write's cache invalidation is visible here too. Also added a small new `GET /locations` route (`apps/api/src/routes/locations.ts`) — no route had ever listed a merchant's own locations before this card, and the editor needs a resource's location `timezone` to render anything in merchant-local time. New `packages/contracts/src/location.ts` (`locationSchema`/`Location`) mirrors `LocationRepository`'s row shape for the web client's type-only import, same pattern as every other contracts schema.

`apps/web/src/app/dashboard/catalog/resources/ResourceAvailabilityEditor.tsx` (routed at `/dashboard/catalog/resources`, linked from `CatalogView.tsx`) is the actual deliverable: a resource picker, a form to add a weekly rule (weekday + HH:MM start/end), a table of the resource's existing rules, and an "Upcoming availability" list for the next 14 days. The acceptance criterion — "Availability renders correctly in merchant timezone" — is delivered by a new pure function, `formatIntervalInZone.ts`, which converts each returned UTC interval into the *selected resource's own location* timezone via `Intl.DateTimeFormat` with an explicit IANA zone (never the browser's local zone), never a hardcoded offset.

## Acceptance criteria check

- **"Availability renders correctly in merchant timezone"** — Met. `ResourceAvailabilityEditor` fetches `GET /resources/:id/availability`, which returns raw UTC instants, and converts every one through `formatIntervalInZone(interval, selectedLocation.timezone)` before display — proven end-to-end in `ResourceAvailabilityEditor.test.tsx` (adds a Monday 09:00–17:00 rule for a resource in `America/New_York`, asserts the rendered list shows "9:00 AM – 5:00 PM" from a UTC interval that is *not* 9–17 in UTC) and at the route/domain layer in `apps/api/test/resources.test.ts` (a real weekly rule expanded across a US spring-forward boundary returns the correct UTC instants on both sides of the transition, driven through the resource's own location row, not a fixed offset).

## Security check answer

**"Timezone handling verified across DST"** — Answered at two layers, neither of which changed this card (both pre-date it and are exercised again here, not newly built):
1. **Expansion (write→read) side**, unchanged: `packages/domain/src/utils/availabilityRule.ts`'s `expandAvailabilityRule` resolves each interval endpoint's local-to-UTC offset independently at its own local date/time (`zonedTimeToUtcMs`), so a window spanning a DST transition reflects the actually-elapsed UTC duration rather than a naive wall-clock diff. This card's own `apps/api/test/resources.test.ts` case drives that function through the new HTTP route with a real 2027 US spring-forward date (`2027-03-14`), confirming `09:00`–`17:00` local resolves to `14:00`–`22:00Z` the week before (EST, UTC-5) and `13:00`–`21:00Z` the week of/after (EDT, UTC-4) — a genuine DST-in-effect check, not a mocked clock.
2. **Display (read-side) conversion**, new this card: `formatIntervalInZone.ts` is the first piece of code in this repo that converts a UTC instant back to merchant-local wall-clock text for display. Its own test file (`formatIntervalInZone.test.ts`) proves the same configured local window (9am–5pm) renders identically from two different UTC interval pairs that straddle the March 2027 spring-forward, and separately proves the November 2027 fall-back transition doesn't shift the displayed time either — both directions of the DST boundary are covered, plus a cross-timezone sanity check (same UTC interval renders as 9am in New York and 6am in Los Angeles).

Neither layer trusts the browser's/server's local system timezone at any point — every conversion takes an explicit IANA zone from the resource's own `locations.timezone` row.
