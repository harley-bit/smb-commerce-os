## What happened

Implemented `docs/design/05`'s "Turnaround buffer" rule: a rental variant's `buffer_minutes` (D063) is applied by **expanding the interval at write time**, not by complicating the overlap predicate — `effective_start = requested_start`, `effective_end = requested_end + buffer_minutes` — and the buffer is stored on the reservation row itself, not re-derived from the variant on read. Added a pure domain function `expandIntervalForBuffer(startsAt, endsAt, bufferMinutes)` (`packages/domain/src/reservations/bufferExpansion.ts`) that returns the expanded interval (or the input unchanged when there is no buffer) and rejects a negative/non-integer buffer. Added a nullable `buffer_minutes` column to `reservations` on both dialects (real `drizzle-kit`-generated migrations — plain `ALTER TABLE ... ADD COLUMN` on both, no table-recreate bug this time since `reservations` carries no CHECK constraint). Wired the domain function into both real write paths: `ReservationRepository.createGuarded`/`create` (SQLite) and `PgReservationRepository.createGuarded` (PostgreSQL) now expand `input.endsAt` by `input.bufferMinutes` *before* the overlap/capacity check runs and before the row is inserted, and always persist a concrete `bufferMinutes` value (`null` when none was supplied) rather than leaving it undefined. No dedicated rental-booking service exists yet (that's D065's unit allocator / D066's rental reservation creation) — this card is infrastructure the generic `ReservationRepository` now provides for those future callers, plus proof that the SERVICE-mode `BookingService`'s existing bookings (which never pass `bufferMinutes`) are entirely unaffected.

## Acceptance criteria check

- "Later variant buffer change does not alter existing bookings" — **Met.** Proven directly in `ReservationRepository.test.ts`'s new "buffer expansion (D064)" suite: a reservation created with `bufferMinutes: 15` is re-read after a second, unrelated reservation is created with `bufferMinutes: 60` for the same subject-type, and the first reservation's stored `endsAt`/`bufferMinutes` are unchanged — the buffer is a per-row snapshot at write time, not a live lookup against the variant. Also proven for real against PostgreSQL 16 in `PgReservationRepository.test.ts` (`DATABASE_URL`-gated), including the buffer-expansion-creates-a-conflict scenario the design doc's own test table names explicitly ("Buffer expansion creates a conflict | Second rejected | G4").

## Security check answer

"Stored buffer prevents retroactive schedule mutation" — yes, by construction, not by convention: `bufferMinutes` and the already-expanded `endsAt` are written once, at `createGuarded`/`create` time, onto the `reservations` row itself. Nothing in the reservation read path (`findById`, `findBlocking`, the overlap/capacity check on a *later* booking) re-joins back to `listing_variants` to re-fetch a "current" buffer — every consumer of a reservation's interval sees only what was persisted on that row. Changing a variant's `buffer_minutes` later (D063's column) therefore has zero effect on any reservation already written; it only affects bookings created after the change, which is the intended behavior per `docs/design/05`. The one gap, honestly flagged: nothing yet calls `createGuarded` with a real `bufferMinutes` sourced from a variant, since the rental booking service itself doesn't exist until D065/D066 — this card proves the storage/expansion mechanism is correct and immutable, not that it's wired to a live rental checkout flow yet.
