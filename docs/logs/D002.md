## What happened

D001's scaffold had already put `strict: true` (plus `noUncheckedIndexedAccess`, `noImplicitOverride`) into the shared `packages/config/tsconfig.base.json`, and every package already had a `typecheck` script running `tsc -p tsconfig.json --noEmit`. `pnpm typecheck` was already green across all 6 packages before this card started — but nothing regression-tested that guarantee, so a future edit could silently weaken the base config with no test failing. D001's own log flagged this explicitly ("D002 should own hardening/auditing that config properly rather than treating this as done"), so this card's real job was to lock the guarantee in with a test, per the test-first rule.

Added `packages/config/test/strict-config.test.ts`, a Vitest suite that loads the real `tsconfig.base.json` via `ts.readConfigFile`/`ts.parseJsonConfigFileContent` (not a re-declared copy of its options) and type-checks small in-memory fixtures against it using `ts.createProgram`. It asserts: an implicitly-typed parameter is rejected (`noImplicitAny`, TS7006), unguarded access on a possibly-null value is rejected (`strictNullChecks`, TS18047), unchecked array indexing produces a diagnostic (`noUncheckedIndexedAccess`), and the null-safe equivalent compiles clean. Wrote the test first, confirmed it failed by temporarily flipping `strict`/`noUncheckedIndexedAccess` to `false` in the base config (3 of 4 assertions failed as expected), then restored the config (clean `git diff`) and confirmed all 4 assertions pass against the real, unmodified base config. Wired `@smb-os/config` with a `test` script and the `typescript`/`vitest` devDependencies needed to run it; `lint`/`test:isolation` echo stubs added for consistency with the other packages' convention.
