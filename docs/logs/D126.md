## What happened

Closed the gap D108's and D124's logs both flagged: `CartService` (`packages/db/src/services/CartService.ts`) only ever had `addProductLine` — no way to put a SERVICE or RENTAL line in a cart at all, so a merchant selling all three catalog modes had no single cart that could hold a mix. Added `addServiceLine` and `addRentalLine`, both following `addProductLine`'s existing server-authoritative pattern exactly: quantity is fixed at 1 for both (a service booking is one slot, a rental line is one item-over-a-date-range, neither is a countable quantity), price is read exclusively from `VariantRepository.findById` (never the caller), and `addRentalLine` copies `depositMinor` onto the order line from the variant's own record, never from caller input. Extracted the shared cart/variant/currency/status validation (previously duplicated inline in `addProductLine`) into a private `resolveCartAndVariant(ctx, cartId, variantId, expectedMode)`, reused by all three `add*Line` methods, so mode-mismatch and currency-mismatch checks are identical across all three line types rather than three independently-maintained copies. Rental line pricing stays flat (`variant.priceMinor`, not multiplied by the number of days/rate-periods in the requested range) — no design doc or existing code path in this repo computes that multiplication anywhere yet (confirmed by search; `RentalDetailView`, D124, discloses the same flat rate), so multiplying here would be new, unscoped math rather than closing a gap this card asks for. `OrderRepository`/`AddOrderLineInput` (`packages/db/src/repositories/OrderRepository.ts`) already supported `mode: "SERVICE" | "RENTAL"` and optional `depositMinor`/`startsAt`/`endsAt` from earlier schema work — no schema or repository change was needed, only the service-layer methods that had never been written.

## Acceptance criteria check

- "All three line types coexist and total correctly" — **met**. New `CartService.test.ts` case "holds product, service, and rental lines together and totals them correctly, recomputed server-side" adds one PRODUCT line (qty 2 @ 2500 = 5000), one SERVICE line (9000), and one RENTAL line (5000) to the same cart, asserts `orderRepo.listLines` returns all three modes present, and asserts the cart's `subtotalMinor`/`totalMinor` both read back as 19000 — the sum across all three, computed by the existing `recomputeTotals` (unchanged, mode-agnostic — it already summed `lineTotalMinor` across whatever lines exist).

## Security check answer

"Totals always recomputed server-side" — **met**, and now proven across all three modes, not just PRODUCT. `addServiceLine`/`addRentalLine` call the same `recomputeTotals` `addProductLine` always has, which reads every line back fresh via `orderRepo.listLines` and writes `subtotalMinor`/`totalMinor` from that read — never incrementally, never trusting a caller-supplied total. New test "adds a rental line carrying the server-side deposit amount, ignoring any client-supplied deposit" passes a tampered input (`depositMinor: 1`) cast past the type system the same way the pre-existing PRODUCT tampered-price test does, and asserts the persisted line's `depositMinor` is 20000 (the variant's real deposit), not 1 — the deposit, like price, is never read from caller input. Price itself is proven the same way for both new methods: `unitPriceMinor`/`lineTotalMinor` in both new tests match the variant's own `priceMinor` exactly, never a caller-supplied value (neither `AddServiceLineInput` nor `AddRentalLineInput` even has a price field, so a conforming caller cannot supply one; a raw HTTP body could still carry extra keys, which is exactly what the tampered-input tests simulate).
