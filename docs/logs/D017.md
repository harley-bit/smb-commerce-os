## What happened

Added `TenantContext` (`packages/domain/src/tenancy/TenantContext.ts`) — an interface holding a validated `merchantId` (UUIDv7 only, via `createTenantContext`, which throws on anything else, reusing D016's `isUuidV7`) — and `TenantScopedRepository`/`RepositoryMethod` (`packages/db/src/tenancy/TenantScopedRepository.ts`), the base every tenant-scoped repository will extend per `docs/design/07` Control #1. `TenantScopedRepository` holds only a table's `merchant_id` column (never the table or db handle), and its one protected method, `scope(ctx)`, is the sole place a `merchant_id = ?` predicate can be built — there is no path to that predicate that doesn't require a real `TenantContext`. `RepositoryMethod<TArgs, TReturn>` is the named type from the design doc's own language: `(ctx: TenantContext, ...args: TArgs) => TReturn`.

Found and fixed a naming collision before writing anything new: `packages/domain/src/auth/AuthProvider.ts` already declared a `TenantContext` interface from D010 (`{ userId, email, roles }` — the identity a verified session resolves to). That's a different concept from this card's tenant/merchant scope, so it was renamed to `AuthIdentity` (and its three call sites — `AuthProvider.ts`, `AuthProvider.test.ts`, `apps/api/src/auth/NativeAuthProvider.ts` — updated) to free the name `TenantContext` for its real meaning per `docs/design/07`.

Test-first throughout, confirmed failing before implementation existed (module-not-found on both new files). `packages/domain/src/tenancy/TenantContext.test.ts` covers construction from a real UUIDv7, rejection of a non-UUID and of a UUIDv4 (wrong version nibble), and that the resulting value is a plain, I/O-free structural type. `packages/db/src/tenancy/TenantScopedRepository.test.ts` has two layers: a runtime layer (real in-memory SQLite via D013's `createConnection`, two merchants seeded into a fixture `widgets` table, asserting `scope(ctx)` returns only the calling merchant's rows and never leaks the other's), and a type-system layer using the same real-tsc-diagnostics pattern as `packages/config/test/strict-config.test.ts` — a fixture repository method missing `TenantContext` as its first parameter is compiled against the actual `RepositoryMethod` type from the real source file and asserted to produce real diagnostics, while the same method with `ctx` first compiles clean (`[]` diagnostics). Full local gate green (lint, typecheck, `pnpm build`, `pnpm test` — domain 100% coverage — `pnpm test:isolation`, `pnpm audit --audit-level=high` clean at the high threshold, `semgrep scan --config p/security-audit --error` 0 findings on the new files).

## Acceptance criteria check

- "Repository method without ctx is a compile error" — **Met.** Verified with real `ts.createProgram` diagnostics (not a manual read of the type signature): a `RepositoryMethod`-typed method literal omitting `TenantContext` as its first parameter produces non-empty diagnostics; the same method with `ctx` first produces zero diagnostics, against the actual `packages/db/src/tenancy/TenantScopedRepository.ts` file and `packages/db`'s real `tsconfig.json`.

## Security check answer

**Control #1 — tenant isolation, layer 2 (type system):** `docs/design/07` requires "every repository method takes `TenantContext` as its first parameter — a missing scope is a compile error." That contract now exists as the named `RepositoryMethod` type, and `TenantScopedRepository` makes the runtime side of layer 2/3 (`docs/design/04`/`07`: "repository base class injects the `merchant_id` predicate; raw query construction is banned outside `/packages/db`") the only path to a merchant-scoped `WHERE` clause — `scope(ctx)` has no unscoped overload, and the column it closes over is private. This card does not yet add the generated cross-tenant test suite Gate G1 depends on (no real domain tables exist until D018) — that's explicitly future work for the schema cards, not a gap in this card's own acceptance criterion.
