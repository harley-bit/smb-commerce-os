## What happened

Added three core utilities to `packages/domain/src/utils/`, each mapping directly to a `docs/design/04` portability rule (P4–P6): `uuid.ts` (`generateUuidV7`/`isUuidV7`, a hand-rolled RFC 9562 UUIDv7 — Node core's `crypto.randomUUID()` only produces v4, so the 48-bit big-endian millisecond timestamp plus version/variant bits are constructed manually from `crypto.randomBytes(16)`), `money.ts` (`Money`, an immutable value object over integer minor units with a private constructor forcing all instances through `Money.of()`, which rejects non-integers, `NaN`/`Infinity`, and empty currency codes; `add`/`subtract`/`multiply` all re-validate through the same constructor so no code path can produce a float-backed instance), and `time.ts` (`nowUtcIso`/`toUtcIso`/`isUtcIso`/`parseUtcIso`, built on `Date.toISOString()` which is always UTC by spec, plus a regex+`Date.parse` validator that explicitly rejects offset-bearing timestamps like `+02:00`).

Added `fast-check` as a new dev dependency to `packages/domain` (not previously used anywhere in the repo) to write real property-based tests for the card's two named acceptance criteria, not just example-based ones: "no float money" is checked by generating random integers (must always survive `Money.of` and stay `Number.isInteger`) and random non-integer doubles (must always throw), plus a property that `add`/`subtract`/`multiply` never emit a non-integer result; "all timestamps UTC" is checked by generating random `Date`s across a wide range and asserting `toUtcIso` always ends in `Z`, always passes `isUtcIso`, and round-trips exactly through `parseUtcIso`. All three new test files were confirmed failing (`Cannot find module`) before their implementation files existed. Domain package coverage is 100% across all metrics after adding one more example test for `toUtcIso`'s invalid-`Date` guard branch, which the property tests alone didn't reach (property generators only produce valid `Date`s).

## Acceptance criteria check

- **"Property tests: no float money"** — met. `money.test.ts` has two `fast-check` properties: every `Money.of(integer, currency)` holds an integer, and every non-integer double is rejected with a message matching `/integer/i`; a third property confirms `add`/`subtract`/`multiply` never produce a non-integer `minorUnits`. 200+ generated cases per run, all passing.
- **"all timestamps UTC"** — met. `time.test.ts`'s property generates random `Date`s (1990–2100) and asserts `toUtcIso` always ends in `"Z"`, always satisfies `isUtcIso`, and round-trips through `parseUtcIso` to the exact same instant.

## Security check answer

**"Money as integer minor units — floats are unacceptable for money"** — enforced structurally, not just by convention: `Money`'s constructor is private, so the only way to obtain an instance is `Money.of(minorUnits, currency)`, which calls `Number.isInteger()` and throws before construction if the value isn't a true integer (this also catches `NaN` and `±Infinity`, both of which fail `Number.isInteger`). Every arithmetic method (`add`, `subtract`, `multiply`) routes its result back through `Money.of()` rather than constructing directly, so there is no code path inside this class that can produce or return a float-backed `Money`. `multiply` additionally rejects a non-integer factor for the same reason — multiplying by e.g. `0.5` would be a disguised way to reintroduce fractional minor units. The property test suite exercises this against hundreds of random doubles per run rather than a handful of hand-picked examples, per the card's own acceptance criterion.
