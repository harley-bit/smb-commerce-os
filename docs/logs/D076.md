Session 2 (this run) closed that gap:

- `packages/domain/src/index.ts`: exported `damageClaimStateMachine.js`, so `applyDamageClaimEvent`, its types, and `IllegalDamageClaimTransitionError` are now part of the public domain API (same as `reservationStateMachine.js`).

## Acceptance criteria check

- "Claim states transition legally" — **Met.** `applyDamageClaimEvent` is the only path from one state to another (domain, 22 tests, unchanged from session 1); `DamageClaimRepository.transition()` is now the only path a persisted row's state can change through, and it routes every call through that same function — a resolve attempt on a terminal claim throws `IllegalDamageClaimTransitionError` rather than silently writing (tested).
- "Customer notified" — **Met.** `DamageClaimService.notifyCustomer` is the only path that moves a claim into `CUSTOMER_NOTIFIED`, and it fires the injected `DamageClaimCustomerNotifier` exactly once with the claim's new state after the write succeeds (tested with a mock notifier; also tested that omitting the notifier defaults to a no-op rather than throwing).

## Security check answer

**"Customer can see and respond to a claim against them."** `DISPUTE` is the only event reachable from `CUSTOMER_NOTIFIED` that isn't a merchant unilaterally resolving the claim, and `DamageClaimService.disputeClaim` deliberately has no `assertCan`/merchant-role gate — it models the customer's own action, not a merchant permission. This is now operational, not just structural: `notifyCustomer` is the one path into the state the customer can act on, and it is guaranteed (by the repository's single-transition write path plus the service's notifier callback) to actually inform the customer when a claim reaches that state — a claim can no longer become customer-visible without the customer being told. What's still out of scope for this card: an actual customer-facing HTTP endpoint/UI to submit a dispute, and a delivery-channel implementation (email/SMS) for the notifier — those are wiring concerns for later API-surface cards in this phase, consistent with `ProductSaleService`'s notifier (D069), which is also still a default no-op pending real delivery-channel work.
