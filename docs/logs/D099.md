## What happened

`apps/web` had no test runner wired at all (`test` script was a placeholder `echo`) and no pages yet — Phase 8 hasn't built any UI. This card's job is a structural tripwire, not a page: a static scanner, `scanSourceForCardFields` (`apps/web/src/security/cardFieldScanner.ts`), that walks a source file line by line and flags any `<input>` carrying a card-data `autocomplete` token (`cc-number`, `cc-csc`, `cc-exp`, etc.) or a card-shaped `name`/`id` (`cardNumber`, `cvc`, `cvv`, `card-expiry`, `pan`, ...). `apps/web/src/security/pageCardFieldGuard.test.ts` is the enforcement test: it recursively scans every `.ts`/`.tsx`/`.html` file under `apps/web/src` (excluding test files themselves, so the scanner's own fixture strings can't trip the repo-wide check) and asserts zero violations — this is the deliverable, "test fails if a card input is added to our pages." Wiring `vitest` into `apps/web` (new `vitest.config.ts`, `test` script, `vitest`/`@types/node` devDependencies) surfaced a pre-existing broken lockfile entry: `pnpm-lock.yaml`'s `apps/web` importer had recorded `vitest: 3.2.7` with no peer-dependency suffix, a version for which no matching snapshot/store directory existed, so `vitest` never linked into `apps/web/node_modules/.bin` no matter how many times `pnpm install` ran. ## Security check answer

**"Preserves SAQ A eligibility — change requires an ADR."** The scanner and its test are additive-only guardrails; nothing in this card touches how card data is collected (still nothing — no checkout UI exists yet) or introduces any new field, endpoint, or dependency capable of handling a PAN/CVC. The test enforces `docs/design/07`'s existing rule ("card data never touches our servers... any change that puts a card field on our own page... requires an ADR, not a pull request") as an automated, unbypassable-by-oversight CI gate: a future page adding a raw `<input>` for card data will fail `pnpm test` before it can merge, forcing the ADR conversation the design doc already requires rather than letting a card field slip in silently. The scanner deliberately does not flag a bare `<div id="card-element">`-style mount point, since that is exactly what Stripe Elements/Checkout hosted fields legitimately need — the tripwire is scoped to `<input>` elements, not "any mention of the word card."
