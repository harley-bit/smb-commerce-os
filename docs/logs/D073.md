## What happened

Built the signed-upload-URL step for condition media, on top of D029's `condition_media` schema and D072's `ConditionReportRepository`. A new `MediaUploadProvider` port (`packages/domain/src/media/MediaUploadProvider.ts`) — same object-storage seam shape as `AuthProvider` (D010/ADR-002): callers depend on the interface only, so a real cloud-storage-backed implementation can swap in later without touching any consumer. Its first (and, for now, only) implementation is `HmacMediaUploadProvider` (`packages/db/src/media/HmacMediaUploadProvider.ts`) — no cloud object-storage account has been provisioned for this project yet, so it mints a time-limited, HMAC-signed upload URL using only Node's built-in `crypto`, upholding the same properties a real presigned S3/R2 URL would (short expiry, a signature the client can't forge or widen) rather than faking the interface with an unsigned URL.

`ConditionMediaUploadService` (`packages/db/src/services/ConditionMediaUploadService.ts`) is the actual card deliverable: `requestUpload(ctx, actingRole, { conditionReportId, contentType, bytes })` asserts `bookings:manage` (same permission `FulfillmentEventService` already gates rental-lifecycle operations on), looks up the condition report via the tenant-scoped `ConditionReportRepository.findById` (new method, added this card) to confirm it belongs to the caller's merchant, rejects any `contentType` outside `["image/jpeg", "image/png", "image/webp"]` and any `bytes` that isn't a positive integer `<= 15_000_000`, then generates a randomized `storageKey` (`condition-media/{merchantId}/{conditionReportId}/{uuidv7}`, never accepted from the caller) and asks the provider to sign it. This card mints the upload grant only — it does not write a `condition_media` row, since the actual bytes' `sha256` isn't known until the upload completes and D074 ("Condition media integrity") is the card that verifies and persists that.

## Acceptance criteria check

- **Oversized and wrong-type uploads rejected** — Met. `ConditionMediaUploadService.test.ts` proves `UnsupportedMediaTypeError` for `application/pdf`, `MediaTooLargeError` for a 50MB request and for a `0`-byte request, both confirmed thrown before any signed URL is produced (permission and report-lookup checks run first, then type, then size).

## Security check answer

**Private bucket, randomized keys, no public access.** `storageKey` is always server-generated (`condition-media/{merchantId}/{conditionReportId}/{uuidv7}`) — the caller never supplies or influences it, so a key can't be guessed or chosen to collide with another merchant's media; a dedicated test (`requestUpload() generates a different storage key on every call`) proves two calls for the same report never reuse a key. "Private bucket, no public access" is upheld at the `MediaUploadProvider` implementation boundary: `HmacMediaUploadProvider` signs every URL with an HMAC over `storageKey:contentType:maxBytes:expiresAt`, so a client cannot widen its own declared size limit or reuse a URL for a different object without invalidating the signature (proven directly: tampering `maxBytes` on an already-issued URL leaves a signature that no longer matches, `HmacMediaUploadProvider.test.ts`), and every URL carries a short expiry (default 15 minutes) rather than being a durable, indefinitely-reusable link. The one honest limit: since no real cloud object-storage account is provisioned yet, there is no actual bucket ACL to verify "private" against — that verification is real once a concrete `MediaUploadProvider` backed by real object storage exists behind this same interface; today's implementation only proves the URL itself carries no standing access beyond what its signature and expiry allow.
