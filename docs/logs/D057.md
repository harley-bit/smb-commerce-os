## What happened

`docs/design/05` "Hold expiry and the sweeper" names the active half of the belt-and-braces pair the lazy filter (D049/D050/D056) already satisfies: "a scheduled job transitions expired holds to `EXPIRED` and releases any associated authorization. Runs every minute; idempotent; must be safe to run concurrently with itself." Built `packages/db/src/jobs/HoldExpirySweeper.ts`: `sweepExpiredHoldsSqlite(conn, asOf)` and `sweepExpiredHoldsPg(pool, asOf)`, both system-level jobs (not `TenantScopedRepository` methods — they legitimately scan across every merchant, which is why they live outside the repository layer the D021 isolation-coverage scanner walks) that find `HELD` reservations whose `expires_at <= asOf`, flip them to `EXPIRED`, then release (`AUTHORIZED` → `RELEASED`) any `deposit_authorizations` row for the same order line that's still outstanding. SQLite reuses D050's `BEGIN IMMEDIATE` lock discipline (select-then-update inside one `sqlite.transaction(...).immediate()`), so a second concurrent sweeper blocks until the first commits, then finds nothing left to expire. PostgreSQL uses a single `UPDATE ... WHERE state = 'HELD' AND expires_at <= $1 RETURNING id, order_line_id` — no explicit row lock needed, since under READ COMMITTED a losing concurrent transaction's `WHERE` re-evaluates against the winner's committed row and matches zero rows, the same "second caller sees nothing to do" property SQLite's lock gives directly. Test-first via `packages/db/src/jobs/HoldExpirySweeper.test.ts` (9 cases, confirmed failing with `Cannot find module` before the file existed): expiry + deposit release, "not yet expired" is left alone, a non-`AUTHORIZED` deposit is left alone, sequential idempotency (rerun is a no-op), `CONFIRMED`/`IN_USE` reservations are never touched, and — the card's literal acceptance criterion, not just asserted but proven — a real 10-worker-thread concurrent race (`holdSweeperWorker.mjs`, same `SharedArrayBuffer` start-gate pattern as D052) against one on-disk SQLite file, where exactly one worker's result carries the expired reservation and released deposit and the other nine return empty. Three more cases (`DATABASE_URL`-gated) prove the same three properties — expiry+release, "not yet expired" untouched, and idempotency/concurrency (10 real concurrent `pg.Pool` connections racing the same row) — against real local PostgreSQL 16.

## Acceptance criteria check

- "Idempotent" — **Met.** `HoldExpirySweeper.test.ts`'s "is idempotent: running it again after a successful sweep is a no-op" (SQLite, sequential rerun) and the PostgreSQL "...and is idempotent on rerun" case both prove a second call after a successful sweep returns empty result arrays and leaves the data unchanged.
- "Safe under concurrent runs" — **Met.** Proven with real concurrency, not simulated timing, on both dialects: 10 genuine `worker_threads` (SQLite, one on-disk file) and 10 genuine separate `pg.Pool` connections (PostgreSQL) racing the identical expired hold; across all 10 results combined, the reservation is expired exactly once and the deposit authorization released exactly once — no double-expiry, no double-release, no dropped row.

## Security check answer

"Releases customer money promptly rather than letting holds lapse" — the sweeper's second responsibility (the first, `state` bookkeeping, is a formality now that D056 made the write path itself independent of it) is exactly this: for every hold it expires, it looks up the same order line's `deposit_authorizations` row and flips `AUTHORIZED` → `RELEASED` in the same transaction as the reservation's own expiry, so a customer's card is never left holding an authorization for a booking that silently lapsed. Two honest gaps, not glossed over: (1) this only updates our own database's record of the authorization's state — no payment provider (Stripe) integration exists yet in this repo, so there is no outbound API call actually releasing funds at the provider; that's future payments-integration work, and this job's job is to be the trigger point that call will hang off of. (2) nothing in this repo yet invokes `sweepExpiredHoldsSqlite`/`sweepExpiredHoldsPg` on an actual "every minute" schedule (cron/queue/worker process) — this card built and proved the job function itself, per the card's literal deliverable ("scheduled expiry of holds"), but wiring it to a real scheduler is a separate, not-yet-scoped operational task, consistent with how D030's audit-log append and D039's inventory receipts were built as callable functions before anything called them in production.
