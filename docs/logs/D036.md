## What happened

Built `apps/api/src/auth/authenticate.ts`: a reusable Fastify `preHandler` (`app.authenticate`, decorated onto every `buildApp()` instance) that verifies the session cookie via the existing `AuthProvider.verifySession` (401 if missing/invalid/expired/revoked), then resolves a `TenantContext` by reading an `X-Merchant-Id` header (400 if missing or not a well-formed UUIDv7) and checking real merchant membership via a new `MerchantMembershipResolver` seam — `DbMerchantMembershipResolver` (backed by `packages/db`'s `MerchantUserRepository.findRole`) is the real implementation, injectable via a new `BuildAppOptions.merchantMembershipResolver` for tests, defaulting to a lazily-migrated in-memory-SQLite-backed resolver otherwise. On success it populates `request.auth = { identity, tenant, role }` per `docs/design/06`'s "every authenticated request resolves to a TenantContext before reaching a controller" rule. `packages/db`'s `Connection` type wasn't previously exported from the package's public `index.ts` — added, since the resolver needs it.

Along the way, found and documented a real architecture gap rather than papering over it: `NativeAuthProvider`'s session-subject user ids (D010, in-memory) and `packages/db`'s `users.id` (the actual FK target of `merchant_users.user_id`) are not unified — no card has wired API registration to write through `packages/db`'s `UserRepository`. The final test proves the middleware's own contract (verify session → resolve membership → populate `request.auth`) against a real `packages/db`-created user id and a minimal fake `AuthProvider` standing in for that not-yet-built link, rather than routing through `/auth/register` and pretending the two id spaces already match. Flagged as follow-up, not fixed here — out of this card's scope (middleware, not identity unification).

Also corrected a stale line in `docs/design/07`'s threat table: "Session hijacking via stolen token" still named the pre-ADR-002 mitigation ("short-lived tokens; refresh rotation with reuse detection") that the doc's own "Authentication" section had already marked superseded elsewhere but this row hadn't been updated to match. Now points at ADR-002's actual mitigation (revocable server-side session, httpOnly Secure `SameSite=Strict` cookie) with a cross-link, instead of describing a control that was never built and isn't the ratified design.

## Security check answer

Card's stated check: "Short-lived tokens; refresh rotation with reuse detection." This exact mitigation was the **pre-ADR-002** design (`docs/design/07`'s "Authentication" section, struck through) and was explicitly superseded by ADR-002 (2026-09-07, decision D4): native auth, session-table-backed, opaque revocable token in an httpOnly/Secure/`SameSite=Strict` cookie — deliberately **not** a JWT and **not** refresh-token pairs, because ADR-002's whole rationale was avoiding the "how do we revoke it" problem a refreshed-JWT model reintroduces. Building refresh-token rotation with reuse detection for this card would silently reverse an already-ratified blocking decision (D4, `docs/BUILD_STATE.md`'s "Open decisions" table), which `CLAUDE.md` says not to do without surfacing it first — and there's no signal this needs revisiting.

What's actually true today, as the real mitigation for "session hijacking via stolen token": the session token is opaque (unforgeable without server state), revocable server-side (`revokeSession`), transported only in an httpOnly/Secure/`SameSite=Strict` cookie (never readable by JS, never sent cross-site), and this card's own middleware never trusts a client-declared identity or merchant — a stolen token still only grants exactly the roles/merchants the underlying session already had. Corrected `docs/design/07`'s threat table (see above) so the documented mitigation matches what's built instead of a design that was intentionally not built. Genuine, tracked gap: the session TTL (24h, set in D010) is not "short-lived" by a strict reading of the old language — no card has revisited that TTL since ADR-002 replaced the mitigation strategy it came from, and it isn't this card's job to silently change it.
