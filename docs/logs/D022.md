## What happened

Added the catalog schema per `docs/design/03`: `listings` (`id`, `merchant_id`, `mode`, `name`, `slug`, `description`, `status`, `created_at`, `archived_at`, unique `(merchant_id, slug)`) and `listing_variants` (`id`, `merchant_id`, `listing_id`, `sku`, `name`, `attributes_json`, `price_minor`, `currency`, `duration_minutes`, `rate_period`, `deposit_minor`, `archived_at`), in both `packages/db/src/schema/{sqlite,pg}.ts`, with real `drizzle-kit`-generated migrations for both dialects. `listing_variants` also carries a denormalized `mode` column (copied from the parent listing at write time, same rationale the design doc gives for `order_lines.mode`) purely so the mode-specific-field CHECK constraint can be evaluated locally — a CHECK constraint in either SQLite or PostgreSQL can only see the row being written, not a joined parent row. The CHECK (`listing_variants_mode_fields_check`, via `drizzle-orm`'s `check()` builder, identical shape on both dialects) enforces: `PRODUCT` variants must have `duration_minutes`, `rate_period`, and `deposit_minor` all NULL; `SERVICE` variants must have `rate_period` and `deposit_minor` NULL (`duration_minutes` is theirs to use); `RENTAL` variants must have `duration_minutes` NULL (`rate_period`/`deposit_minor` are theirs to use). Test-first via `packages/db/src/schema/catalog.test.ts` (confirmed all 8 SQLite-side cases failing with `Cannot read properties of undefined` before the schema/migrations existed — `sqliteSchema.listings`/`listingVariants` didn't exist yet). Covers: migration applies, a clean PRODUCT round-trip, duplicate-slug rejection, an FK-violation rejection (variant referencing a non-existent listing), three CHECK-violation cases (one per mode, each carrying a field that belongs to a different mode), and a clean RENTAL accept case. A `DATABASE_URL`-gated real-PostgreSQL case (run directly against a local Postgres 16 instance for this session, not just SQLite) proves the same CHECK is real on that dialect too, not a SQLite-only accident.

## Acceptance criteria check

- "Mode CHECK constraints reject invalid mode-specific fields" — **Met**. Proven on both dialects: SQLite (`PRODUCT` variant carrying `duration_minutes`, `SERVICE` variant carrying `rate_period`, `RENTAL` variant carrying `duration_minutes` — all three rejected) and a real PostgreSQL 16 instance (`SERVICE` variant carrying `rate_period` rejected). A clean same-mode insert for each of PRODUCT and RENTAL is also proven to succeed, so the constraint isn't accidentally rejecting everything.

## Security check answer

"Mode immutability prevents capacity-strategy confusion" — answered honestly as a **tracked gap, not yet closed by this card**. This card is schema-only: `listings.mode` has no DB-level immutability guard, because a CHECK constraint evaluates only the row being written and cannot compare it against the row it replaces (no `OLD`/`NEW` comparison without a trigger, which the portability rule in `docs/design/04` avoids in favor of dialect-portable constructs). `docs/cards/D023.md` ("Service: listings") is explicitly the card that adds the create/update/archive service layer and its acceptance criterion is "attempt to change mode after creation is rejected" — that is where mode immutability actually gets enforced and tested, as a repository/service-layer guard rather than a schema constraint. Until D023 lands, nothing in this repo prevents a raw UPDATE from flipping a listing's `mode` and silently invalidating any reservations or CHECK-guaranteed variant data that assumed the old mode — this schema card only guarantees that *variants* stay internally consistent with whatever mode a listing currently has, not that a listing's mode itself is stable over time.
