## What happened

Built mobile's "Order history and upcoming" screen, mirroring `apps/web/src/app/m/[slug]/account/orders/OrderHistoryView.tsx`'s two-section (Upcoming/Past) layout against the same already-existing `GET /v1/m/{slug}/account/orders` route (D132's `CustomerOrderHistoryService`). Along the way, found and fixed a real, pre-existing bug that would have made this card impossible to actually use from a device: `apps/api/src/routes/customerOrders.ts` read the session token only from `request.cookies["session"]` — but `apps/mobile` has no cookie jar; it authenticates via `Authorization: Bearer <accessToken>` (D138's PKCE flow, stored in Keychain/Keystore). `apps/api/src/auth/sessionToken.ts`'s `extractSessionToken` already exists precisely to resolve a token from either source and is already used by the merchant-staff `authenticate` middleware — `customerOrders.ts` was just never wired to it. Fixed by swapping all three handlers (`GET .../account/orders`, `GET .../account/orders/:orderId`, `POST .../account/orders/:orderId/cancel`) from the raw cookie read to `extractSessionToken(request)`; the cookie path (web) still works identically since `extractSessionToken` checks the cookie first. New mobile `apps/mobile/src/account/fetchOrderHistory.ts` (DI'd `fetchFn`/`accessToken`, same convention as every other mobile fetch helper since D140) presents the access token as a Bearer header, sends no customer identifier of any kind, and short-circuits to `unauthenticated` with zero network calls when there is no stored token. New `AccountOrdersScreen.tsx` (thin RN glue, no test of its own — same boundary as `HomeScreen.tsx`) reads the access token via `authClient.ts`'s existing `getAccessToken`/`ExpoSecureTokenStore` and renders both buckets the server already partitions. `App.tsx`'s `AccountOrders` case (route already typed since D139, previously falling through to `PlaceholderScreen`) now renders this real screen.

## Acceptance criteria check

- "Only own orders returned" — **Met.** `fetchOrderHistory` sends no customer identifier at all (not even implicitly filterable) — the server derives the customer entirely from the bearer token's session identity. Proven at the HTTP layer by the new `apps/api/test/customerOrders.test.ts` case (see security check below) and, unchanged from D132, by `CustomerOrderHistoryService.test.ts`'s cross-customer isolation cases.

## Security check answer

"Ownership enforced server-side, not by client filter." Yes, unchanged in kind from D132 but newly *reachable* from a real mobile client: `customerOrders.ts` resolves `identity.userId` from the verified session token (now via `extractSessionToken`, accepting either the web cookie or the mobile Bearer header) and passes it into `CustomerOrderHistoryService.listOrderHistory`/`getOrderDetail`, which filter/compare against `customerUserId` inside the query itself — there is no step where a client-supplied id or filter parameter is trusted. `fetchOrderHistory.ts` sends no such parameter for there to be a client-side filter to bypass. New test: `apps/api/test/customerOrders.test.ts` — "D147: accepts an Authorization: Bearer session token, not just the session cookie" — written first, confirmed failing (401) against the pre-fix route, passing after the `extractSessionToken` swap.
