## Acceptance criteria check

- "provider_ref unique constraint enforced" — **Met.** `payments_provider_provider_ref_unique` is a real unique index on `(provider, provider_ref)`, proven three ways in `payments.test.ts`: a duplicate `(STRIPE, pi_123)` insert is rejected on SQLite; the same `provider_ref` under two *different* providers is accepted (the constraint is scoped to the pair, not `provider_ref` alone, matching `03`'s "unique per provider" wording); and the constraint is confirmed present in `pg_indexes` plus a real rejected duplicate insert against local PostgreSQL.

## Security check answer

**"No PAN, CVV, or track data anywhere in the schema."** Confirmed by construction: `payments` and `deposit_authorizations` carry only `provider` (a string identifier like `"STRIPE"`), `provider_ref` (the provider's own opaque reference to a charge/authorization/refund), amounts in integer minor units, currency, status/state enums, and timestamps. `raw_event_json` stores the provider's webhook payload for audit/debugging — this is the one column worth flagging honestly: a provider's raw event payload is not expected to contain card data (Stripe's own webhook events never include PAN/CVV, only tokenized references), but nothing in this schema-only card enforces that at write time. That enforcement (validating or redacting `raw_event_json` before it's persisted) belongs to the future service layer that actually calls the provider API and writes these rows, not this table definition. No column here is capable of holding a full card number, CVV, or magnetic-stripe track data by design — the architecture (`07`) never routes card data through our servers in the first place, so there is no code path that could populate such a column even if one existed.
