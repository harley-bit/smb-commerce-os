## What happened

Built the merchant onboarding flow end to end: a new `POST /merchants` route in `apps/api` (`src/routes/merchants.ts`) that a session-authenticated (but not yet merchant-scoped) caller hits once, and a new `apps/web` page (`src/app/onboarding/page.tsx`) that collects the form and posts to it. The route deliberately does not use `app.authenticate` — that decorator requires an `X-Merchant-Id` the caller is already a member of, which by definition doesn't exist yet for a brand-new merchant — so it re-derives identity the same way `GET /auth/me` already does (verify the session cookie directly), matching `docs/design/06`'s narrower "session-authenticated, not yet tenant-scoped" case.

On a valid request the route: generates a new `merchantId` (UUIDv7) and builds a `TenantContext` from it; creates the `merchants` row (now including seller-identity columns — see security check); finds-or-creates a `@smb-os/db` `users` row for the caller via `users.external_auth_id` (bridging the still-separate id space between `apps/api`'s native in-memory auth store, a documented D010 placeholder, and the real `users` table `merchant_users.user_id` actually references — this bridge only exists inside the onboarding route, it changes no other route's identity resolution); assigns that user `OWNER` via `MerchantUserRepository.assignRole` (a legitimate self-bootstrap: no prior member exists to have granted the role, so the acting role and the target role are the same first assignment); and creates the first `Location`. Slug uniqueness is enforced with a `findBySlug` retry loop (the same public, unscoped lookup D060 already added). Wrote the failing test first in `apps/api/test/merchants.test.ts` (confirmed 404 against the not-yet-registered route, then a `TypeError` from an unbuilt `@smb-os/contracts` export, before the real implementation went green) covering: full onboarding success (merchant row, seller-identity fields, OWNER role, location all persisted), 401 with no session, 400 with seller identity omitted, and — the Gate G1 spirit-check for this card, since two brand-new merchants necessarily start as strangers to each other — two separate onboarding calls landing in two distinct merchants neither can see into the other's row.

Seller-identity capture required a schema change: `merchants` gained eight nullable columns (`legal_name`, `tax_id`, four business-address fields, state, country) via `drizzle-kit generate` for both dialects (`migrations/sqlite/0017_violet_whistler.sql`, `migrations/pg/0019_dashing_emma_frost.sql`), matching `docs/design/08` line 11's already-stated data-category table ("Business name, address, tax ID... `merchants`") that the schema hadn't caught up to yet. Columns are nullable rather than `NOT NULL` — dozens of existing fixtures across `packages/db` and `apps/api` tests create bare merchant rows purely to satisfy an FK, not to exercise onboarding, and forcing all of them to supply seller identity would have been unrelated churn on this card. The actual requirement lives at the contract boundary instead: a new `packages/contracts/src/onboarding.ts` zod schema (`onboardMerchantInputSchema`) makes `legalName`, `taxId`, and the business address non-optional, so `POST /merchants` 400s if they're missing regardless of what the DB column itself allows.

On the web side, `apps/web/src/app/onboarding/page.tsx` is a client form (business name, legal name, tax ID, currency, business address, first location name/timezone) built from the existing `Button`/`TextField` components (D102), posting `credentials: "include"` to `${API_BASE_URL}/merchants` and redirecting to `/dashboard` on success — same shape as the existing `login/page.tsx`. `routeRules.ts` gained a new rule for `/onboarding` requiring only an authenticated session (no merchant role — there isn't one yet), with a new test in `routeRules.test.ts`. Verified live: started `next dev`, confirmed an unauthenticated request to `/onboarding` redirects to `/login` (middleware correctly enforcing the new rule), then confirmed with a stub `/auth/me` responding as a session'd user that the page renders 200 with all expected form fields and labels present.

One honest scope note: `apps/api` still has no bootable `listen()` server anywhere in this repo (`src/index.ts` is a marker function only, unrelated to this card) — a pre-existing gap, not something D103 introduces or was asked to close — so the full register → login → onboard → dashboard path could only be verified as two separate pieces: the API path via Fastify's `.inject()` (real route, real DB, no real socket) and the web path via a live `next dev` server against a stub `/auth/me`. Both prove the card's acceptance criterion; neither required standing up new API server infrastructure that's genuinely a different card's job.

## Security check answer

**Seller identity captured at onboarding (DAC7/DSA readiness).** `onboardMerchantInputSchema` (`packages/contracts/src/onboarding.ts`) requires `legalName`, `taxId`, and a full business address as non-optional fields — `POST /merchants` returns 400 (proven by a dedicated test) if any are missing, so onboarding cannot complete without them. The values are persisted on the `merchants` row itself (`legal_name`, `tax_id`, `business_address_*` columns, migrations 0017/0019) rather than dropped, matching `docs/design/08` line 11's stated data-category mapping. Per that same doc's line 84, this is deliberately *readiness*, not the DAC7/EU platform-reporting or DSA trader-traceability features themselves — those remain out of scope until an EU launch is real; today's job was making sure the data a future compliance feature would need is actually being collected and stored now, not retrofitted later.
