## What happened

Built the repository/service layer for `inventory_units` (D024's schema — serialized vs fungible tracking, `AVAILABLE/SOLD/MAINTENANCE/RETIRED/LOST`) which existed only as a table until this card. `InventoryUnitRepository` (`packages/db/src/repositories/InventoryUnitRepository.ts`) is a standard `TenantScopedRepository` subclass: `create` (always starts a unit `AVAILABLE`), `findById`, `listByVariant`, `updateStatus` (sets `retiredAt` only when the new status is `RETIRED`). `InventoryUnitService` (`packages/db/src/services/InventoryUnitService.ts`) is where the actual enforcement lives: a `Record<InventoryUnitStatus, ReadonlySet<InventoryUnitStatus>>` state machine makes `SOLD` and `RETIRED` terminal — no entry in either status's allowed-transitions set — so any attempted transition out of them throws `InvalidUnitStatusTransitionError` before the repository is ever touched, satisfying the card's acceptance criterion directly. `AVAILABLE` can reach `SOLD`/`MAINTENANCE`/`RETIRED`/`LOST`; `MAINTENANCE`/`LOST` can still move (back to `AVAILABLE` or on to `RETIRED`), only `SOLD`/`RETIRED` are dead ends. `transitionStatus` gates on `inventory:manage` via D037's `assertCan` (same posture as `InventoryService.receiveStock`), looks the unit up first (404-equivalent `Error` for an unknown or cross-tenant id, since tenant scoping means "not mine" and "doesn't exist" are indistinguishable — same IDOR posture as D038's listing routes), validates the transition, updates the row, and only then appends a hash-chained `audit_log` entry (D030) carrying before/after status and the caller's note — a rejected transition writes no audit entry, verified directly by a dedicated test.

## Acceptance criteria check

- **SOLD/RETIRED transitions enforced** — Met. `InventoryUnitService.test.ts` proves both terminal states directly: a transition out of `SOLD` throws `InvalidUnitStatusTransitionError` and leaves the row's status unchanged; same for `RETIRED`; and a same-unit `SOLD` → `RETIRED` attempt (an unrecognized edge, not just "any transition") is also rejected.

## Security check answer

**"Unit status changes audit-logged."** Answered directly, not deferred: every successful `transitionStatus` call appends an `audit_log` row (`action: "inventory_unit.status_changed"`, `entityType: "inventory_units"`, `entityId` = the unit id) with `beforeJson`/`afterJson` capturing the prior and new status plus the caller's reason — hash-chained per D030, so it's tamper-evident the same way D039's receipt logging is. Verified by a dedicated test asserting the entry's shape and contents, and by a second test proving a *rejected* transition (out of a terminal state) writes zero audit entries — the log reflects only transitions that actually happened, not attempts.
