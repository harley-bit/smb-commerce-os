## What happened

New `packages/domain/src/orders/cancellationPolicy.ts` — per-mode cancellation policy configuration, one policy per `FulfillmentMode` (`PRODUCT | SERVICE | RENTAL`, the same three-way split as `docs/design/03`'s listing `mode`). A `CancellationPolicy` is `{ mode, tiers }`, where each `CancellationTier` is `{ minHoursBeforeStart, refundPercent }`; `computeCancellationRefund(policy, hoursBeforeStart, amountMinor)` finds the first tier whose notice threshold is met and returns that tier's refund percentage applied to the amount, or zero if no tier matches (e.g. cancelling after the start has already passed with no zero-hour tier defined).

The card's real requirement is the *separation*, not the arithmetic: `CancellationPolicySet` is `{ product, service, rental }`, all three required — there is no shared/default policy field a caller can set once and have it apply to every mode. The sole constructor, `defineCancellationPolicySet`, additionally cross-checks that each policy's own `mode` tag matches the key it's registered under, so passing the rental policy under the `service` key (an easy copy-paste mistake) is rejected at construction rather than silently governing the wrong mode. `resolveCancellationPolicy` is an exhaustive `switch` over `FulfillmentMode` with no `default` case, so there is no fallthrough branch that could apply one mode's rule to another.

Wrote the failing test first (`cancellationPolicy.test.ts`, confirmed failing on `Cannot find module` before the file existed): product policy refunds in full up to fulfillment; service policy applies tiered refunds by notice given (100% / 50% / 0%) with thresholds different from the rental policy's own tiers (100% / 75% / 25%), proving the two aren't sharing logic; zero refund with no matching tier; invalid policies rejected (empty tiers, out-of-range `refundPercent`, non-descending tier order, non-finite `hoursBeforeStart`/negative amount); `defineCancellationPolicySet` accepts three independently-shaped policies and rejects a policy registered under the wrong key (tested for each of product/service/rental individually so all three cross-checks are exercised); and a TS-level proof (`@ts-expect-error`) that the type requires all three modes, not a partial/default set. 15 test cases, 100% function coverage, meets the workspace's ≥95% branch-coverage gate. Exported from `packages/domain`'s `index.ts`.

## Security check answer

**"Three different policies, never forced into one rule."** Addressed structurally, the same way D083's late-fee module enforced its own invariant: there is no single "cancellation policy" type that all three modes read from, and no default/fallback path. `defineCancellationPolicySet` requires all three modes as separate arguments (TypeScript rejects a call missing any of them) and additionally validates at runtime that each policy's `mode` tag matches its key — so even a same-shaped object handed in under the wrong key is caught, not silently applied cross-mode. `resolveCancellationPolicy`'s exhaustive switch (no `default` branch) means there is no code path anywhere in this module that could resolve an unrecognized or shared rule for a given mode. What is **not yet closed**: no repository/service/route persists a `CancellationPolicySet` per merchant/listing or wires an actual cancellation event to `computeCancellationRefund` yet — same domain-only scope split as D077's deposit state machine and D083's late fee policy before their respective persistence/wiring cards. There is also no `cancellation_policy` column on `listings` or `listing_variants` yet (`docs/design/15` only shows it as a UI concept, not a schema field) — a future card would need to decide where this is stored per merchant/listing and connect it to the order-cancellation flow, including how a rental cancellation interacts with an already-held deposit (`depositStateMachine.ts`, D077) rather than just the line-item amount. No follow-on card in the current sequence (`D085`–`D086`) is scoped to close this gap, so it stays open until surfaced explicitly.
