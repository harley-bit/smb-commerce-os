## What happened

`ReservationRepository` (D050/D059/D066) already stored both service `RESOURCE` bookings and rental `INVENTORY_UNIT` reservations in one `reservations` table, distinguished only by `subjectType` — but nothing read across both together. Added `listInRange(ctx, rangeStart, rangeEnd)` (tenant-scoped interval-overlap query, no state filter — the read side decides what to show, not the repository), a new `CalendarService` (`packages/db/src/services/CalendarService.ts`) that merges the two subject types, resolves a human label for each row (`ResourceRepository.findById().name` for `RESOURCE`, `InventoryUnitRepository.findById().unitCode` for `INVENTORY_UNIT`), and flags `hasConflict` on any two rows for the same subject that overlap in time while both sit in a blocking state (`HELD`/`CONFIRMED`/`IN_USE` — the same set `blockingStatePredicate` uses at write time). A genuine double-booking can't occur through the normal write path (`createGuarded`, Gate G3) — the conflict flag is a defensive read-side check, proven by a test that deliberately bypasses the guard (`ReservationRepository.create`, the unguarded insert) to construct two overlapping `CONFIRMED` rows and confirms both come back flagged. New `GET /calendar` route (`apps/api/src/routes/calendar.ts`) takes `rangeStart`/`rangeEnd` query params, gated by `bookings:view` (granted to every merchant role including `READ_ONLY` — a read-only calendar view is legitimately staff-wide, not manager-only). `apps/web/src/app/dashboard/calendar/CalendarView.tsx` renders it as one table (Starts/Ends/Subject/Mode/State/Conflict badge) with a client-side mode filter (Bookings/Rentals/All) and from/to date inputs that re-fetch on change — both subject types visible together by default, this card's acceptance criterion. `CatalogView.tsx` gained a "Calendar" link alongside its other cross-links (same pattern D106–D113 established, no central nav shell exists yet). Conflict styling uses a new `.calendar-row--conflict` CSS class (`apps/web/src/styles/globals.css`, reusing the existing `--color-danger-bg` token) rather than an inline `style` prop — D102's CSP/no-inline-style convention, confirmed by grepping the rest of `apps/web/src` for any prior `style=` usage (none) before adding this one. Wrote failing tests first throughout: `ReservationRepository.test.ts` (3 new `listInRange` cases, red on `TypeError: repo.listInRange is not a function`); `CalendarService.test.ts` (5 cases, red on `Cannot find module`); `apps/api/test/calendar.test.ts` (8 cases across all four roles plus the security/tenancy/validation paths, red on 404 before the route existed); `CalendarView.test.tsx` (7 cases, red on unresolved import).

## Acceptance criteria check

- "All modes on one calendar; conflicts highlighted" — **Met.** `apps/api/test/calendar.test.ts`'s first case (run for all four roles) proves a `RESOURCE` booking and an `INVENTORY_UNIT` rental both appear in one `GET /calendar` response with their resolved labels; `CalendarService.test.ts`'s conflict tests prove overlapping same-subject blocking reservations are flagged `hasConflict: true` while a completed-then-later-confirmed pair is not; `CalendarView.test.tsx` proves the UI renders both subject types together and visually distinguishes the conflicting row from the clean one.

## Security check answer

"No customer data beyond what staff need" — a calendar entry (`CalendarEntry`, both at the service and HTTP layer) exposes `id`/`subjectType`/`subjectId`/`subjectLabel`/`startsAt`/`endsAt`/`state`/`orderLineId`/`hasConflict` only. It deliberately omits `createdByIp` and `createdByAccountId` — a raw IP address has no operational use on a shared calendar view, and the acting account id, if genuinely needed, is one click away by opening the reservation/order directly rather than being printed on every row a whole staff roster sees. `apps/api/test/calendar.test.ts`'s dedicated security test seeds a reservation with a real `createdByIp` and asserts neither field appears anywhere in the response. The route itself is staff-only (`app.authenticate` plus `bookings:view`), never reachable without a session — the calendar carries no anonymous/public path at all.
