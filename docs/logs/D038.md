## What happened

Built the first real HTTP routes in `apps/api`: `apps/api/src/routes/listings.ts` registers `GET /listings`, `GET /listings/:id`, `POST /listings`, `PATCH /listings/:id`, and `POST /listings/:id/archive`, all behind D036's `app.authenticate` preHandler (session + tenant resolution) plus an explicit `requireAction(request, reply, action)` call using D037's `assertCan` from `@smb-os/domain` (`catalog:view` for the two GET routes, `catalog:manage` for the three mutating routes) — every route gets its own visible authorization check rather than relying solely on `ListingService`'s internal `assertCanManageCatalog` (D023), which still runs too as defense in depth. Request bodies are validated through D034's `@smb-os/contracts` Zod schemas (`createListingInputSchema`, `updateListingInputSchema`) before ever reaching the service layer, returning `400` on a bad payload (including a patch carrying a `mode` key, proving mode immutability holds at the API boundary too). `PATCH`/`archive` look the row up via `service.findById` first and return `404` if the tenant-scoped lookup comes back empty — the same code path a genuinely-missing id and a cross-tenant id both take, so an IDOR probe can't distinguish "doesn't exist" from "exists but isn't yours."

`apps/api/src/app.ts` gained a new `connection?: Connection` option (defaults to a fresh in-memory SQLite connection, migrated lazily on first route call via a `createListingServiceFactory` closure mirroring `./auth/authenticate.ts`'s existing lazy-migration pattern for the membership resolver) and now calls `registerListingRoutes(app, connection)` during `buildApp()`. Same honest, already-precedented gap as the membership resolver's own default: unless a real, shared connection is passed in, the default `connection` and the default `merchantMembershipResolver` are two disconnected in-memory databases, so a from-scratch `buildApp()` with no options will never resolve any caller as a merchant member in the first place — not a regression, the same state D036 already documented, and real end-to-end DB wiring for `apps/api` is still a future card, not this one's job.

Test-first via `apps/api/test/listings.test.ts` (23 cases, confirmed failing — 404/`Not Found` on every route, `connection` option not yet accepted — before the implementation existed): every route tested against all four roles (`OWNER`/`ADMIN` allowed on manage routes, `STAFF`/`READ_ONLY` getting `403`; all four roles allowed on view routes), an unauthenticated request getting `401`, invalid payloads getting `400`, and a dedicated "cross-tenant isolation (IDOR)" block covering all four of read-by-id, list, update, and archive against a listing that belongs to a merchant the caller has no membership in at all.

## Acceptance criteria check

- **Authorization test per route** — Met. Each of the five routes has its own dedicated test(s) exercising the full role matrix (`OWNER`/`ADMIN`/`STAFF`/`READ_ONLY`), not one shared authorization test reused across routes.
- **Cross-tenant read returns 404** — Met. `GET /listings/:id` against another merchant's listing id returns `404`, not `403` or `200` with someone else's data; the same `404` behavior is also proven for `PATCH`/`archive` (whose repository-level scoped `UPDATE`/lookup would otherwise silently no-op) and the cross-tenant listing is proven absent from `GET /listings`'s result set.

## Security check answer

Card's stated check: "IDOR test: another merchant's listing ID is not readable." Verified directly and from four angles, not just the one named in the card: a listing created under merchant B, read by an authenticated `OWNER` of merchant A (a real member of A, zero membership in B) via `GET /listings/:id`, returns `404` — the exact same response a caller gets for an id that was never created at all, so the response gives no signal distinguishing "not yours" from "doesn't exist." The same real (not stubbed) tenant-scoped repository query (`ListingRepository.findById`'s `WHERE merchant_id = ? AND id = ?`, from D023) backs both the `GET` and the existence check inside `PATCH`/`archive`, so all three routes inherit the same guarantee from one code path rather than three independently-hand-rolled checks. `GET /listings` was also checked directly: merchant B's listing never appears in merchant A's list response.
