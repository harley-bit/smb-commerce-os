## What happened

D072 modeled `condition_reports` and gated the `IN_USE` transition on a CHECKOUT report's existence, but no service ever let staff actually *record* a report — `ConditionReportRepository.create` had no caller outside its own test (flagged in D074's carried-forward notes). This card closes that gap for the CHECKIN side and adds the comparison the card actually asks for.

New `packages/domain/src/rentals/conditionGrade.ts`: a fixed ordered scale (`CONDITION_GRADES = ["DAMAGED","POOR","FAIR","GOOD","EXCELLENT","NEW"]`, worst to best) and `computeConditionGradeDelta(checkoutGrade, checkinGrade)`, which validates both grades against the scale (`InvalidConditionGradeError` on an unrecognized value) and returns `{ checkoutGrade, checkinGrade, deltaSteps, deteriorated, improved, unchanged }`. `condition_reports.condition_grade` itself stays free-text at the schema level (D029) — this is a domain-layer scale the service enforces, not a DB constraint change, which was out of scope for this card.

New `packages/db/src/services/ConditionReportService.ts`: `recordCheckin(ctx, actingRole, input)` — gated on `bookings:manage` (same action `FulfillmentEventService`/`ConditionMediaConfirmService` already use for rental operations) — looks up the order line's CHECKOUT report via `ConditionReportRepository.listByOrderLine` (tenant-scoped, so a cross-tenant caller sees no reports and gets the same "no baseline" rejection as a real missing baseline, no distinguishing signal), throws the new `MissingCheckoutBaselineError` if none exists, otherwise writes the CHECKIN report and returns both reports plus the computed delta in one `RecordCheckinResult`.

Test-first throughout: `conditionGrade.test.ts` (6 cases, confirmed failing on `Cannot find module` before the file existed) covers ordering, comparison, deterioration/improvement/unchanged, and rejection of an unrecognized grade on either side. `ConditionReportService.test.ts` (4 cases, same failing-first pattern) covers: reject with no baseline, record + correct delta against a real baseline, role-gate rejection, and the cross-tenant case. Both exported from their package's barrel (`@smb-os/domain`'s `index.ts`, `@smb-os/db`'s `index.ts`).

## Acceptance criteria check

- **Grade delta surfaced to merchant** — Met. `recordCheckin` returns `delta: ConditionGradeDelta` (`deltaSteps`, `deteriorated`/`improved`/`unchanged`) alongside both the CHECKOUT and CHECKIN reports on every successful call, proven directly by `"recordCheckin() records the report and surfaces the grade delta against the CHECKOUT baseline"` (GOOD → FAIR yields `deltaSteps: -1, deteriorated: true`).

## Security check answer

**Both-phase evidence supports or defeats a claim fairly.** A CHECKIN report recorded with no CHECKOUT baseline on file is one-sided: it could be used to accuse a customer of pre-existing wear as if it happened during the rental, but it could never be used to *clear* a customer either, since there is nothing to compare the returned condition against. `recordCheckin` refuses to write a CHECKIN report at all — throwing `MissingCheckoutBaselineError` before any row is written — unless a CHECKOUT report already exists for the same order line, and when it succeeds it always returns both reports together with the delta, not just the new CHECKIN reading in isolation. That means the same response a merchant would use to *support* a damage claim (a real negative delta) is structurally the same shape that would *defeat* a false one (delta shows `unchanged`/`improved`) — the service can't be used to present one side's evidence without the other. Known gap, honestly not closed here: there is still no HTTP route calling `recordCheckin` (or the still-nonexistent CHECKOUT-recording service) — both phases remain service-layer only, same caveat D072/D073/D074 already carry forward for this whole rental-lifecycle area.
