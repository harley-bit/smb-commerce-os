## What happened

Built customer-facing order history end to end — the first customer route in this codebase to actually require a session, closing the "no `customerUserId` ownership check" gap every Phase 7 checkout card since D130 has carried forward. New pure-domain `classifyOrderTiming` (`packages/domain/src/orders/orderTiming.ts`) buckets an order as `UPCOMING`/`PAST` from its own lines' recorded `startsAt`/`endsAt` only, never from order status — a `PRODUCT`-only order (no dated lines) is always `PAST` once placed, while a `SERVICE`/`RENTAL` line with a date still ahead makes the whole order `UPCOMING`, including a rental still checked out. New `OrderRepository.listByCustomer(ctx, customerUserId)` filters by `customerUserId` at the query itself (never by fetching every order and filtering in application code). New `CustomerOrderHistoryService` (`packages/db`) composes both: `listOrderHistory` returns `{ upcoming, past }` summaries; `getOrderDetail` re-checks `order.customerUserId` even on an order already found by id, returning `undefined` — indistinguishable from a nonexistent order id — whenever it belongs to a different customer. New unauthenticated-by-membership-but-session-required routes `GET /v1/m/{slug}/account/orders` and `GET /v1/m/{slug}/account/orders/{orderId}` (`apps/api/src/routes/customerOrders.ts`): both verify the session cookie via the existing global `AuthProvider` (the same one D036/D101 built for merchant staff, reused here via `verifySession` exactly as `/auth/me` does) but deliberately skip `app.authenticate`'s merchant-staff membership check, since a customer is never a row in `merchant_users` — only identity is required, and the merchant itself is resolved from the URL slug like every other public storefront route. Both routes pass the verified session's own `userId` as `customerUserId`, never a client-supplied value. New web page `OrderHistoryView.tsx`, routed at `/m/[slug]/account/orders`, fetches with `credentials: "include"` so the session cookie travels, and renders two sections ("Upcoming" / "Past"), each order showing every mode present on it.

## Acceptance criteria check

**"Only the authenticated customer's orders are returned"** — Met. `OrderRepository.test.ts`'s new `listByCustomer()` case seeds four orders (two for the acting customer, one for a different customer at the same merchant, one for the acting customer at a *different* merchant) and proves only the acting customer's same-merchant orders come back, most recently placed first. `CustomerOrderHistoryService.test.ts` proves the same at the service layer (`listOrderHistory` for customer B returns empty buckets when only customer A has orders) and adds the merchant-isolation case (`is tenant-scoped`). `apps/api/test/customerOrders.test.ts`'s first case proves it over real HTTP: two customers each get one order at the same merchant; the session cookie for customer A returns exactly customer A's order, and it lands in the correct upcoming/past bucket.

## Security check answer

**"IDOR test: another customer's order ID returns 404"** — Met, and answered by construction rather than by a separate access-control layer: `CustomerOrderHistoryService.getOrderDetail` returns `undefined` whenever `order.customerUserId !== customerUserId`, the exact same return value as an order id that doesn't exist at all — the caller (`apps/api`'s route) maps both cases to a flat `404`, never a `403`, so a customer probing another customer's order id cannot learn from the response whether that id exists. Proven at both layers: `CustomerOrderHistoryService.test.ts`'s dedicated case ("this card's security check — IDOR") creates an order for customer A and asserts `getOrderDetail(ctx, customerB, orderId)` is `undefined`; `apps/api/test/customerOrders.test.ts`'s matching case asserts the real HTTP response is `404` when customer A's session requests customer B's order id, and a separate case proves a genuinely nonexistent order id returns the identical `404` — the two are indistinguishable from outside.
