## What happened

D049's `ReservationRepository.findBlocking` already lazily excludes an expired-but-unswept `HELD` row (`blockingStatePredicate`'s `expiresAt > asOf` clause), and D050's SQLite `createGuarded` write path reuses that same query — so on SQLite this card's acceptance criterion was already satisfied going in. The real, previously-undiscovered gap was on the PostgreSQL side: D051/D054's `reservations_no_overlap` exclusion constraint (migration 0011, scoped to `INVENTORY_UNIT` subjects) is a static index predicate (`state IN ('HELD','CONFIRMED','IN_USE') AND subject_type = 'INVENTORY_UNIT'`) that cannot compare `expires_at` against "now" the way an ordinary query can — exclusion-constraint predicates must be immutable, and "now" isn't. So an expired-but-unswept `HELD` row for an `INVENTORY_UNIT` subject correctly fell out of `PgReservationRepository.createGuarded`'s app-level sum check, but the immediately following raw `INSERT` still tripped the DB-level exclusion constraint against that same stale row — a real, reproducible false-conflict, confirmed first as a failing test (`conflicting key value violates exclusion constraint "reservations_no_overlap"`) before any fix existed. Fixed by having `createGuarded` eagerly close out exactly the caller's own subject's expired `HELD` rows (`UPDATE ... SET state = 'EXPIRED' WHERE subject_type = $x AND subject_id = $y AND state = 'HELD' AND expires_at <= $asOf`) inside the same transaction, before the sum check and insert — this only ever touches rows that are already, unambiguously expired (never an active hold), so it doesn't weaken the constraint's guarantee for genuinely overlapping reservations, and it makes the write path correct without depending on any background sweeper's timing (D057).

## Acceptance criteria check

- "Expired hold does not block before the sweeper runs" — **Met.** Pre-existing on SQLite (`ReservationRepository.test.ts`'s D049-era "security: a HELD reservation whose hold has expired must not block" case, still green). Newly proven on PostgreSQL by `PgReservationRepository.test.ts`'s new "D056: an expired-but-unswept HELD reservation on an INVENTORY_UNIT does not block a new overlapping request" case — confirmed failing (raw `23P01` exclusion violation) before the fix, passing after, run against a real local PostgreSQL 16 instance.

## Security check answer

"Lazy filter guarantees correctness independent of the job" — true on both dialects now, but by two different mechanisms worth being explicit about. On SQLite there is no DB-level overlap constraint at all; `findBlocking`'s `expiresAt > asOf` predicate is the *only* thing preventing a stale hold from blocking, and every overlap-sensitive read (`findBlocking`, `createGuarded`) goes through it, so correctness genuinely never depends on D057's sweeper having run. On PostgreSQL, the exclusion constraint's own predicate structurally *cannot* express "now" (immutable-expression requirement on index predicates), so a per-request lazy filter alone can't fully cover the write path — this card closes that gap by having `createGuarded` eagerly and narrowly expire just the caller's own overlapping-subject's stale rows inside the same transaction as the write, which has the same net effect (correctness independent of the background job) without weakening the constraint for real, active holds. The sweeper (D057) remains valuable for keeping `state` accurate for reads/reporting outside the write path (e.g. a merchant's dashboard listing "active holds"), but no overlap decision anywhere in the codebase depends on it having run.
