## What happened

Implemented the hold-exhaustion mitigation named in `docs/design/07`/`14` (risk T10): per-account and per-IP concurrent-hold caps, with a stricter cap for anonymous callers, plus an abandonment-monitoring hook on the hold-expiry sweeper.

`reservations` gained two nullable columns on both dialects (`created_by_account_id`, `created_by_ip` — real migrations generated via `drizzle-kit`, `packages/db/migrations/{sqlite,pg}`), each backed by its own `(merchant_id, state, holder)` index. `ReservationRepository` gained `countActiveHoldsByAccount`/`countActiveHoldsByIp` (`packages/db/src/repositories/ReservationRepository.ts`), using the same lazy-expiry predicate (`state = 'HELD' AND expires_at > asOf`) `findBlocking` already relies on — a cap frees up the instant a hold expires, with no dependency on the sweeper having run. `PgReservationRepository.createGuarded`'s INSERT was updated to persist the same two columns so both dialects stay in parity.

`BookingService.createServiceBooking` (`packages/db/src/services/BookingService.ts`) now takes an optional `HoldCapConfig` (`perAccountLimit: 5`, `perIpLimit: 20`, `anonymousLimit: 3` by default) and calls a new `assertUnderHoldCap` before creating a hold: an authenticated caller (has `createdByAccountId`) is checked against `perAccountLimit`; the IP check applies `perIpLimit` when there's an account and the stricter `anonymousLimit` when there isn't — matching `docs/design/07`'s "anonymous carts get a stricter concurrent-hold cap than authenticated ones." A new `HoldLimitExceededError` is thrown on either breach.

`POST /bookings` (`apps/api/src/routes/bookings.ts`) now passes `createdByAccountId: request.auth!.identity.userId` and `createdByIp: request.ip` into every booking it creates, and maps `HoldLimitExceededError` to a `429` Problem Details response with a fixed, non-numeric detail string (no cap value, no count — this card's security check). This route is always staff-authenticated (never anonymous — see `requireBookingsManage`), so only the account-cap and authenticated-IP-cap branches are exercised end-to-end today; the `anonymousLimit` branch is proven directly at the `BookingService` unit-test level and is ready for whatever future public/anonymous checkout endpoint needs it — a documented gap in the same spirit as prior cards' "mechanism built, not yet wired to every caller" notes (e.g. D020's audit-logging gap).

`HoldExpirySweeper.ts`'s two sweep functions (`sweepExpiredHoldsSqlite`, `sweepExpiredHoldsPg`) gained an optional `onAbandoned?: AbandonmentReporter` callback, fired with the `SweepResult` only when something actually expired (never on an empty tick, to avoid alert noise on a job that runs every minute) — the "abandonment monitored" half of the acceptance criteria. No cron/job runner invokes the sweeper in this repo yet (confirmed by search — it's still test-only, same pre-existing gap noted nowhere before now), so this hook is the monitoring mechanism ready for whatever wires the sweeper up, not a live alert today.

Test-first throughout: 4 new `ReservationRepository` tests (including two tenant-isolation cases, required by D021's isolation-coverage generator — confirmed zero gaps afterward), 3 new `BookingService` tests, 1 new route test, and 2 new sweeper tests, all confirmed failing (`is not a function` / assertion failures) before their implementations existed.

## Security check answer

**THREAT: DoS by reserving all inventory without paying.** Three caps now sit in front of every hold: `perAccountLimit` (an authenticated caller cannot hold more than 5 concurrent slots), `perIpLimit` (20, a looser shared ceiling — e.g. several staff behind one office IP), and `anonymousLimit` (3, the strictest, applied when there's no account at all — the actual attacker shape: no auth required, so the only signal is source IP). All three are counted against `reservations` directly (`state = 'HELD' AND expires_at > asOf`), the same lazy-expiry predicate the overlap checker already trusts, so the cap is never stale waiting on the sweeper and self-heals the moment a hold's TTL passes — an attacker cannot "bank" capacity by holding past expiry. Breaching a cap returns a generic `429` with a fixed detail string; no cap threshold, current count, or any other caller-specific number is disclosed in the response, so an attacker cannot binary-search the exact limit. The existing short hold TTL (`DEFAULT_HOLD_MINUTES = 15`, D059) remains the first line of defense; these caps are the second.
