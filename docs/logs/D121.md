## Security check answer

"Public endpoint — rate limited, no internal IDs exposed" — **met**. Both `GET /v1/m/:slug` and `GET /v1/m/:slug/listings` are unauthenticated and share a `SlidingWindowRateLimiter` keyed by `ip:{request.ip}` (default 30 requests/60s, tighter than nothing and configurable per deployment) — proven by `publicStorefront.test.ts`'s two "rate limits repeated requests from the same IP" cases, which force a 429 with a 2-request limit. "No internal IDs exposed" is enforced by construction, not by convention: the route never returns a repository row directly — it always maps through `publicMerchantProfileSchema`/`publicListingSchema`-shaped literals (`name`/`slug`/`defaultCurrency` for the merchant; `id`/`mode`/`name`/`slug`/`description` for a listing) — so the merchant's DB-internal `id`, `taxId`, `legalName`, business address, and `connectAccountId` can never reach a storefront visitor, proven by "never exposes internal id, tax id, legal name, or address"; and a listing's `merchantId` (redundant once the caller already has `slug`), `status`, and lifecycle timestamps are dropped the same way, proven by "never exposes merchantId or listing status on any listing." The listing `id` itself (a UUIDv7) is deliberately still returned — `docs/design/06`'s own contract names `GET /v1/m/{merchantSlug}/listings/{id}` as the next endpoint in this surface (D122), so that id is the public identifier by design, not an internal leak; only `PUBLISHED` listings are ever reachable through `listPublished`, so a draft/archived catalog's existence is never revealed either way — proven by "never returns DRAFT or ARCHIVED listings."
