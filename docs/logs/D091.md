## What happened

Added Stripe-style webhook signature verification, reimplemented with Node's built-in `crypto` (same "native now, real provider later" pattern as `HmacMediaUploadProvider`, D073) rather than the `stripe` SDK, since no Stripe account is wired up yet. `verifyStripeWebhookSignature` (`packages/db/src/payments/WebhookSignatureVerifier.ts`) parses the `t=<timestamp>,v1=<hex>[,v1=...]` header format, recomputes the HMAC-SHA256 over `${timestamp}.${rawBody}` with the webhook secret, compares with `timingSafeEqual`, and enforces a 300s replay-tolerance window — it only calls `JSON.parse` on the body after the signature has already matched. A new `POST /webhooks/stripe` route (`apps/api/src/routes/webhooks.ts`) wires this in: `app.ts` now captures the exact raw request bytes via a custom `application/json` content-type parser (`request.rawBody`) so the signature is checked against the real wire bytes, not a re-serialized copy. An unverified request (missing header, wrong signature, tampered payload, or expired timestamp) gets a generic 400 and a `warn`-level log line tagged `securityEvent: "webhook_signature_verification_failed"`; its body is never parsed or acted on beyond that raw string. No event-handling/deposit-release logic was added — this card's scope is the verification gate only, per the calendar's later D092 (idempotency) and D093 (ordering tolerance) cards, plus deposit authorization/capture itself lands in D094/D095.

## Acceptance criteria check

- "Unsigned and wrongly-signed events rejected" — **Met.** `WebhookSignatureVerifier.test.ts` (7 tests): correctly-signed event accepted and parsed; missing header rejected without parsing; wrong-secret forgery rejected; tampered-payload-under-valid-header rejected; malformed header rejected; expired timestamp outside tolerance rejected; multiple non-matching `v1` candidates rejected. `apps/api/test/webhooks.test.ts` (4 tests) proves the same at the HTTP layer: a correctly signed `POST /webhooks/stripe` returns 200; an unsigned one returns 400; a wrongly-signed one returns 400 and the generic error response never echoes back any field from the forged body; an unverified request produces the `webhook_signature_verification_failed` log line.

## Security check answer

**"CRITICAL threat: forged webhook triggering deposit release."** The route has no other guard — it is deliberately unauthenticated (Stripe calls it, not a logged-in user) — so signature verification is the entire trust boundary. `verifyStripeWebhookSignature` runs before any `JSON.parse`: an attacker who posts a forged or replayed body without the correct HMAC (computed only from the real Stripe webhook secret, never derivable from the request itself) gets rejected at 400 before the payload is ever deserialized, matched to an order, or capable of reaching any deposit-state-machine transition. The failure is also logged as a security event (`securityEvent: "webhook_signature_verification_failed"`, with a `reason` but never the raw body) so a sustained forgery attempt is observable. This card does not yet wire the route to `applyDepositEvent`/`releaseCompletedDepositsSqlite` — that wiring is later in this phase (D094/D095) — so today the practical effect is "no code path exists yet for a forged webhook to reach a deposit," and this card's job is to make sure that when that wiring lands, it can only ever be fed a verified event.
