## What happened

New `PayoutProvider` port (`packages/domain/src/payments/PayoutProvider.ts`), same "callers depend on the interface only" seam shape as `PaymentIntentProvider`/`RefundProvider` — it models Stripe Connect's payout report as a list of `PayoutTransaction`s, each traceable back to a `payments.provider_ref` this platform already recorded, carrying the provider's own gross/fee/net breakdown. The actual reconciliation rule is pure domain math in `packages/domain/src/payments/reconcilePayout.ts`: for every provider-reported transaction, compare its `grossAmountMinor` against this platform's own recorded amount for the same `providerRef` (`null` if we have no matching record at all), flag a per-line `mismatch`, and roll up gross/fee/net totals plus an overall `hasMismatch`. Kept deliberately apart from any repository access so the comparison itself is testable without a database (4 tests, 100% coverage). `SimulatedPayoutProvider` (`packages/db/src/payments/SimulatedPayoutProvider.ts`) is the only implementation — no live Stripe account provisioned, same precedent as every other `Simulated*Provider` in this codebase — test-seeded via `registerPayout` since a payout report isn't something this platform requests the creation of. `PayoutReconciliationService` (`packages/db/src/services/PayoutReconciliationService.ts`) is the card deliverable ("merchant-facing payout and fee breakdown"): it fetches the provider's payout report, looks up this platform's own recorded amount per transaction via `PaymentRepository.findByProviderRef` (already tenant-scoped), runs `reconcilePayout`, and — this card's security check — appends a `payout.reconciliation_mismatch` row to the merchant's own append-only, hash-chained audit log (`AuditLogRepository`) whenever `hasMismatch` is true, before returning. Gated by the existing `payouts:manage` RBAC action (`docs/design/07`'s role table already restricts payout figures to `OWNER` alone; `ADMIN` explicitly has "no payout... changes") rather than adding a new action for a financial-data view that table already scopes. 4 new `PayoutReconciliationService` tests (clean reconciliation, STAFF/READ_ONLY/ADMIN all rejected, mismatch triggers exactly one audit-log entry with the expected shape, cross-tenant isolation reads as a mismatch rather than leaking merchant A's payment into merchant B's view) and 2 new `SimulatedPayoutProvider` tests.

## Acceptance criteria check

- "Figures reconcile against provider records" — **Met.** `PayoutReconciliationService.reconcilePayout` compares every provider-reported transaction's gross amount against this platform's own `payments` ledger entry for the same `providerRef`, proven by a test where the two agree (`hasMismatch: false`, correct net/fee totals) and by three tests where they deliberately don't (amount disagreement, a missing record, and a cross-tenant lookup), all correctly flagged.

## Security check answer

**"Reconciliation mismatch is an escalation trigger (T3)."** `docs/design/14`'s risk register lists "Any deposit reconciliation mismatch" as T3's own escalation trigger. `PayoutReconciliationService.reconcilePayout` checks `result.hasMismatch` after running the comparison and, if true, appends a `payout.reconciliation_mismatch` entry (`actorType: "SYSTEM"`, `entityType: "payout"`, `entityId: <payoutId>`, the full reconciliation result as `afterJson`) to the merchant's own hash-chained `audit_log` before returning — the same append-only, tenant-scoped ledger every other sensitive action in this system writes to, so a mismatch becomes a durable, timestamped record rather than a value a caller could silently discard. Proven by a dedicated test: a deliberately mismatched payout produces exactly one audit-log entry with that shape; the clean-reconciliation test proves the converse — zero entries when figures agree, so the audit log isn't spammed on the happy path.
