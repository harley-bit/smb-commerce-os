## What happened

Implemented the `capacity > 1` fungible-resource admission logic `docs/design/05` "Fungible capacity" describes and D050/D051/D053's logs flagged as an open gap, for both dialects, then proved the three edge cases the card names.

**SQLite:** generalized `ReservationRepository.createGuarded` (`packages/db/src/repositories/ReservationRepository.ts`) with an optional `capacity` parameter (default 1). Inside the existing `BEGIN IMMEDIATE` transaction it now sums `quantity` across `findBlocking`'s overlapping blocking reservations and only conflicts once admitting the new request would exceed `capacity`, instead of conflicting on any overlap unconditionally. Default `capacity = 1` reduces to exactly D050's original any-overlap-blocks behavior, so every existing D050/D052/D053 call site and test is unaffected (verified — no existing test needed a change).

**PostgreSQL:** D051's `EXCLUDE USING gist` constraint is a binary any-overlap check and cannot express "sum of overlapping quantities ≤ capacity" — as originally written it would incorrectly reject a valid concurrent booking within a `capacity > 1` resource's limit. New migration `0011_reservations_exclusion_inventory_unit_only.sql` narrows the constraint's `WHERE` clause to `subject_type = 'INVENTORY_UNIT'` only (rental units — always serialized, one row per physical unit, capacity implicitly 1 per `docs/design/05`'s "Rental assets are always serialized" split). New class `PgReservationRepository` (`packages/db/src/repositories/PgReservationRepository.ts`) now guards all `RESOURCE` subjects (capacity 1 included, since that's just this check's boundary) at the application level: `SELECT id FROM resources ... FOR UPDATE` inside a transaction serializes concurrent bookings for that resource, then the sum-of-overlapping-`quantity` check runs against fully-committed data before the insert.

This is a real, deliberate narrowing of D051's original "even from a console session" guarantee for `RESOURCE` subjects specifically — a raw SQL insert bypassing `PgReservationRepository` can now double-book a `RESOURCE`, where before the DB-level constraint caught it unconditionally. `INVENTORY_UNIT` keeps the stronger DB-level guarantee unchanged. This tradeoff is inherent to Postgres exclusion constraints (no sum expression, no cross-table predicate) and is what the design doc's own SELECT-FOR-UPDATE recommendation implies; flagged here explicitly rather than left implicit.

Existing D052/D053 PostgreSQL concurrency-harness tests (`ReservationRepository.pg-concurrency.test.ts`, `ReservationRepository.pg-identical-race.test.ts`) and D051's `reservations-exclusion.test.ts` raw-inserted `RESOURCE`-typed reservations to exercise the exclusion constraint directly — switched to `INVENTORY_UNIT` so they keep proving the constraint they were written to prove (still real, still N=10/N=50 genuinely parallel connections, still passing at 1 winner). The equivalent proof for the new capacity-checked `RESOURCE` path is `PgReservationRepository.test.ts`'s own dedicated multi-case suite (not concurrency-level parallel workers — this card's scope was correctness of the admission logic itself, not a new N=50 race harness).

Wrote failing tests first in all cases: 4 new cases appended to `ReservationRepository.test.ts` (adjacent-succeeds, 1-second-overlap-rejected, capacity-3-admits-exactly-3, quantity-aware capacity check) confirmed failing against the un-generalized `createGuarded` before the change; `PgReservationRepository.test.ts` (5 cases, including a tenant-isolation case) confirmed failing with "module doesn't exist" before `PgReservationRepository.ts` was written.

## Security check answer

"Capacity path uses SELECT FOR UPDATE on the resource row": confirmed directly for PostgreSQL — `PgReservationRepository.createGuarded` issues `SELECT id FROM "resources" WHERE id = $1 AND merchant_id = $2 FOR UPDATE` as the first statement inside its transaction, before the sum-of-quantity check runs, so a second concurrent caller for the same resource is blocked at that lock until the first caller's transaction commits or rolls back — the check it then runs is always against fully-committed data, never a stale read. For SQLite, the equivalent row-lock role is played by `BEGIN IMMEDIATE` (unchanged from D050): it takes the database's single write lock before the same sum-of-quantity check runs, which is SQLite's version of the same serialization guarantee — there is no per-row `FOR UPDATE` because SQLite has exactly one writer, the mechanism D050's log already established. One explicit caveat, not glossed over: this SELECT-FOR-UPDATE / BEGIN-IMMEDIATE guarantee only holds for callers going through `PgReservationRepository`/`ReservationRepository.createGuarded`. Unlike D051's exclusion constraint (still true for `INVENTORY_UNIT`), a `RESOURCE` reservation inserted via raw SQL outside those repositories is not capacity-checked at the database level — see "What happened" above for why (exclusion constraints can't express a sum), and this is a real, intentional narrowing of D051's original console-session guarantee for `RESOURCE` subjects specifically.
