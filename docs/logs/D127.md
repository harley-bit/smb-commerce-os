## What happened

Found a real gap while tracing where a `HELD` reservation actually gets confirmed: `ReservationRepository.confirm` (called by `BookingService.confirmServiceBooking`, wired to `POST /bookings/:id/confirm`) transitioned `HELD` → `CONFIRMED` via `applyReservationEvent` with no awareness of `expiresAt` at all. `docs/design/05`'s "Hold expiry and the sweeper" already guarantees an unswept expired `HELD` row never *blocks* a new reservation (the lazy filter) and gets swept to `EXPIRED` within a minute (the active sweeper, `HoldExpirySweeper.ts`) — but nothing stopped the *original* holder from confirming that same stale row in the window before the sweeper runs, which would either silently double-book the slot (if someone else's reservation had already been confirmed in the meantime, since the expired hold stopped blocking) or hand the customer false confidence that their payment secured a slot that was actually gone. Added `HoldExpiredError` and a check in `ReservationRepository`'s shared `transition` method: `confirm(ctx, id, asOf?)` now rejects with `HoldExpiredError` when the row is still `HELD` but `expiresAt <= asOf`, leaving the row untouched (still `HELD`, not silently transitioned). `asOf` is optional so every pre-existing caller (tests that never pass a confirm-time) is unaffected; `BookingService.confirmServiceBooking` now requires `confirmedAt` and passes it straight through — the "payment time" instant this card's security check is about. `apps/api/src/routes/bookings.ts`'s confirm route now supplies `new Date().toISOString()` and maps `HoldExpiredError` to a 409 with a clear, actionable message ("This hold has expired. Please create a new booking.") instead of letting it bubble as an unhandled error. For the visible half of the deliverable, added a pure `computeHoldCountdown(expiresAt, now)` (`packages/domain/src/reservations/holdCountdown.ts`, no I/O — same posture as `expandIntervalForBuffer`) and wired a live countdown into `CalendarView.tsx`'s new "Hold" column: `CalendarService`/`GET /calendar` now also returns each entry's `expiresAt`, and a new `HoldCell` component ticks the countdown every second, shows "This hold has expired. Please create a new booking." and disables the Confirm button the instant the client-side clock reaches zero (no crash, no dead click), and renders the same message inline if the server's clock disagrees and returns the 409 anyway. `CalendarView` is the only real, already-wired UI surface today where a `HELD` reservation is both visible and confirmable — the storefront's own `ServiceDetailView`/`RentalDetailView` "Reserve" buttons still only toggle local state (no anonymous hold-creation endpoint exists yet, see `IMPROVEMENTS.md`'s new D127 entry), so a customer-facing countdown on the storefront itself is out of this card's reach until checkout (D128–D131) adds that endpoint.

## Acceptance criteria check

- "Expired hold produces a clear recoverable error" — **met**. `packages/db/src/repositories/ReservationRepository.test.ts`'s new `confirm() throws HoldExpiredError when asOf is past the hold's expiresAt` case proves the typed error at the repository layer and that the row is left `HELD`, not silently transitioned. `packages/db/src/services/BookingService.test.ts`'s new case proves the same through the service layer. `apps/api/test/bookings.test.ts`'s new "hold countdown (D127)" describe block proves the HTTP boundary: confirming an already-expired booking returns 409 with a `detail` matching `/expired/i`, and a follow-up `GET` shows the reservation is still `HELD` — recoverable, not a lost/corrupted state. `CalendarView.test.tsx`'s new cases prove the client never crashes on an expired hold either client-detected or server-detected, always rendering the same clear message.

## Security check answer

"Prevents silent loss of a slot at payment time" — **met**. Before this card, `applyReservationEvent`'s `HELD → CONFIRMED` transition had no idea `expiresAt` existed, so an unswept expired hold could be confirmed exactly as if it were still active — the customer would believe their payment secured the slot while, per `blockingStatePredicate`, that same expired hold had already stopped blocking anyone else from taking it in the meantime, a genuine silent-double-booking / silent-loss path. `ReservationRepository.confirm`'s new `asOf` check closes it: a confirm attempt against an expired `HELD` row now fails loudly and specifically (`HoldExpiredError`, not a generic error or a silent success), inside the same `BEGIN IMMEDIATE` transaction `transition` already uses, so the check and the write are atomic — no race between reading `expiresAt` and deciding to confirm. The API layer turns that into an explicit, actionable 409 rather than a 500 or a misleading 200. The client-side `HoldCell` countdown is the first line of defense (never even attempts the confirm once its own clock says expired), and the server-side check is the one that actually can't be bypassed by a stale client clock or a direct API call.
