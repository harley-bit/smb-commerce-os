## What happened

Added `packages/domain/src/utils/availabilityExceptions.ts`: an `AvailabilityException` type (`kind: "BLACKOUT" | "EXTRA"`, `interval: Interval`) matching the `availability_exceptions` table shape from `docs/design/03`, and `applyAvailabilityExceptions(baseIntervals, exceptions)`, which takes D046's `expandAvailabilityRule` output and overlays one-off overrides. `BLACKOUT` exceptions are subtracted from the base intervals first — `subtractOne` handles all four cases (no overlap, full cover, mid-interval split into two, trim-only-start/trim-only-end) using plain instant comparisons on D045's half-open `Interval`. `EXTRA` exceptions (one-off openings) are unioned in afterward via `mergeSorted`, which sorts by start and merges any intervals that overlap or abut. Every exception's `interval` is validated through D045's `makeInterval` up front so a malformed instant throws immediately rather than silently producing a wrong result via `NaN` comparisons. Wrote the failing test first (`availabilityExceptions.test.ts`, confirmed it failed on a missing module before implementing), covering: no-op with no exceptions, full/partial/trim-only BLACKOUT subtraction, a non-overlapping BLACKOUT leaving the base untouched, a disjoint EXTRA addition, an EXTRA that merges into an adjacent interval, BLACKOUT-then-EXTRA ordering (a one-off opening on a different day survives a blackout elsewhere), and a malformed-interval rejection.

## Acceptance criteria check

- "Exception overrides base rule correctly" — **Met.** `availabilityExceptions.test.ts` proves both override directions against the base rule's expanded intervals: a `BLACKOUT` removes time the base rule would otherwise grant (full removal, mid-interval split, and start/end trimming all covered separately), and an `EXTRA` grants time the base rule would not otherwise have (both as a disjoint addition and merged into an adjacent base interval). The ordering test confirms exceptions are evaluated independently of each other's kind, not just against the base.

## Security check answer

"Merchant-controlled, tenant-scoped" — `availability_exceptions` (D025) already carries `merchant_id` and is read/written exclusively through `TenantScopedRepository` per D017/D021's isolation-coverage generator, same as every other tenant-owned table; this card adds no new repository, so no new cross-tenant surface is introduced. `applyAvailabilityExceptions` itself is pure domain math with no I/O and no `merchant_id` parameter — tenant scoping is the calling repository/service's job (a future card wiring this into an `AvailabilityService`), not this function's; it operates purely on the caller-supplied interval lists, so it cannot itself leak or merge data across merchants. Every exception interval is validated via `makeInterval` before use, so a malformed row can't silently corrupt another merchant's or another resource's computed availability through a NaN-comparison bug.
