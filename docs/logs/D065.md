## What happened

Implemented `docs/design/05` line 111's "Allocation policy": rental assets are always serialized (one `inventory_units` row per physical unit per line 96), so booking a rental means picking one free unit out of however many satisfy the request, and the policy is to choose deterministically by **least recently returned first** rather than "lowest ID," which would hammer unit #1 and produce uneven wear. Added a pure domain function `selectUnitForAllocation(candidates)` (`packages/domain/src/reservations/unitAllocator.ts`, same style as D064's `bufferExpansion.ts` — no I/O) that takes a list of `{ unitId, lastReturnedAt }` candidates already narrowed down to units free for the requested interval, and returns the one with the oldest `lastReturnedAt`. A unit that has never been used (`lastReturnedAt = null`) is treated as infinitely long ago and is always preferred over any unit with a concrete return timestamp, so new fleet additions get worked into rotation immediately. Ties are broken by `unitId` ascending, which is what makes the function deterministic under test rather than just "usually" deterministic. Throws `NoAvailableUnitError` on an empty candidate list. Exported from `packages/domain/src/index.ts` alongside `bufferExpansion`.

As with D064, no rental-booking service exists yet to call this for real (that remains D066's job — "Rental reservation creation" — which will narrow `inventory_units` down to free ones via the overlap check and pass them here). This card proves the selection policy itself: correct, deterministic, and fleet-spreading.

## Acceptance criteria check

- "Allocation spreads across fleet" — **Met.** A dedicated test simulates 6 successive rental cycles over a 3-unit fleet (allocate → "return" with a fresh timestamp → allocate again) and asserts every unit is used exactly once before any unit is reused, i.e. the round-robin order `[unit-1, unit-2, unit-3, unit-1, unit-2, unit-3]` — the least-recently-returned rule naturally produces even rotation rather than favoring one unit.
- "Deterministic under test" — **Met.** A dedicated test calls `selectUnitForAllocation` twice with the identical input and asserts identical output; a separate test proves ties among multiple never-used units resolve by `unitId` ascending, not by input array order or `Array.prototype.sort`'s unspecified-for-equal-keys behavior.

## Security check answer

"Even wear and even utilization data" — yes: the allocator never returns the same unit repeatedly while a less-recently-used sibling is available, by construction of the sort key (`lastReturnedAt`, oldest first). This is the mechanism the design doc calls out by name (line 111) as the reason to avoid "lowest ID" allocation, which would concentrate wear and produce misleading per-asset utilization numbers (one kayak looking constantly rented, eleven others idle, even though demand was spread evenly). The fleet-rotation test above demonstrates the property directly rather than asserting it only for a single pair of units.
