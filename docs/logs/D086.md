## What happened

New `packages/db/src/services/gate-g4.e2e.test.ts` — the Phase 4 gate: a rental's full lifecycle (reserve → checkout → use → return → settle) driven entirely through the real service layer built across D064–D085 (`RentalReservationService`, `OrderRepository`, `ReservationRepository`, `ConditionReportRepository`/`ConditionReportService`, `FulfillmentEventService`, `DepositAuthorizationRepository`, `ProductSaleService`), with no direct schema writes standing in for any step, matching the shape of the existing `gate-g2.e2e.test.ts`.

Wrote the failing test first — the file didn't exist, so the first run failed on `Cannot find module`, then failed twice more for real reasons before going green: (1) `RentalReservationService.createRentalReservation()` had no `orderLineId` field to thread through to `ReservationRepository.createGuarded` (`CreateReservationInput` already supported it, but the rental service never exposed it), so the reservation created in the "reserve" step couldn't be the same row `FulfillmentEventService.findByOrderLineId` looks up in the "use"/"return" steps — fixed by adding an optional `orderLineId` to `CreateRentalReservationInput` and passing it through unchanged (`packages/db/src/services/RentalReservationService.ts`); (2) the test's first draft tried to exercise I3 by calling `ProductSaleService.sellProduct` against the RENTAL-mode variant's own unit — `ProductSaleService` is scoped to `PRODUCT`-mode variants only (it throws before ever reaching the reservation check), so that isn't a real path in this system today. Rather than change `ProductSaleService`'s scope (out of this card, and no card in the current sequence asks for "sell a rental asset off the fleet" as a feature), the test proves I3's underlying predicate (`ReservationRepository.isSubjectCurrentlyBlocked`) true mid-rental and false after return inside the rental flow itself, and proves the actual `ProductSaleService.sellProduct` → `UnitCurrentlyRentedError` path end to end in a second test against a `PRODUCT`-mode listing with a unit under a blocking reservation — the same invariant, the real service, just not artificially forced onto a variant mode that was never built to support it.

Two tests, both green:
- `"reserve -> checkout -> use -> return -> settle holds I4 and I7 end to end"` — retires one of two rental units first (I4: the allocator's candidate pool excludes RETIRED units, so the guarded reservation lands on the remaining unit, never the retired one); creates the order + rental line; reserves (linked via the new `orderLineId` field); authorizes a deposit; confirms checkout; proves pickup is refused with `MissingCheckoutConditionReportError` before any CHECKOUT condition report exists (I7) and that neither the reservation nor the fulfillment-event log moved; records the CHECKOUT report and pickup (reservation → `IN_USE`); confirms the unit is currently blocking (I3's predicate, true); records CHECKIN + return (reservation → `COMPLETED`); releases the deposit (`RELEASED`); confirms the unit is no longer blocking (I3's predicate, false); retires the unit; and proves the allocator now throws `NoAvailableUnitError` for that variant (I4 again, post-retirement) since both units are gone. Ends by verifying the tamper-evident audit chain (`verifyAuditChain`) is still valid across every write the lifecycle made.
- `"invariant I3 — ProductSaleService rejects selling a unit with a blocking reservation, end to end"` — a separate `PRODUCT`-mode listing/unit with a `CONFIRMED` blocking reservation: `sellProduct` throws `UnitCurrentlyRentedError`, no stock movement, unit stays `AVAILABLE`; after the reservation is cancelled, the identical `sellProduct` call succeeds, decrements stock, and moves the unit to `SOLD`.
