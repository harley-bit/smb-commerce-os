## Acceptance criteria check

Server-side: `POST /damage-claims/:claimId/capture` reads the order line's own `DepositAuthorizationRepository.findByOrderLineId` result and 400s any `amountMinor` above that hold's `amountMinor` before the provider is called (`apps/api/test/damageClaims.test.ts`, "400s a capture amount above the authorized deposit amount"). ## Security check answer

**"Capture requires explicit confirmation — one attempt only."** Two independent layers, matching this card's own phrasing exactly: (1) *one attempt only* is enforced at the provider layer, not the UI — `SimulatedDepositHoldProvider.captureManualCaptureHold` (D095) throws `DepositHoldAlreadyResolvedError` on any second attempt against an already-resolved intent, mapped by the route to `409 Conflict`, proven in `apps/api/test/damageClaims.test.ts`'s "409s a second capture attempt on the same deposit hold" — a UI bug or a replayed request can never cause a double capture regardless of what the browser does. (2) *explicit confirmation* is the UI's own contribution: `DamageClaimView`'s capture button stays `disabled` until a merchant checks an "I confirm this capture amount is correct" checkbox (a separate, affirmative step from typing the amount), and the button disables again the instant it's clicked — before the request resolves, not after — so a second click cannot physically fire a second request while the first is in flight. Both are proven directly in `DamageClaimView.test.tsx`.
