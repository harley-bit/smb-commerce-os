## What happened

Closed the persistence gap D077 deliberately left open. New `packages/db/src/repositories/DepositAuthorizationRepository.ts`, tenant-scoped persistence for `deposit_authorizations`, mirroring `DamageClaimRepository`'s shape (D076): `create`/`findById` plus a single private `transition()` that is the only write path for any state change — it reads the current row and hands its state, the requested `DepositEvent`, and `{ authorizedMinor: row.amountMinor }` to D077's `applyDepositEvent`, never setting `state` directly. `capture`/`release`/`expire` are thin named wrappers over `transition`, same pattern as `notifyCustomer`/`dispute`/`resolveCaptured`/`resolveWaived` on `DamageClaimRepository`.

This makes the card's deliverable ("one capture attempt; amount bounded by authorization") real at the database layer, not just in the pure domain function: `capture()` re-reads the row on every call, so a first successful capture leaves the row in a terminal state (`CAPTURED`/`PARTIALLY_CAPTURED`), and any second `capture()` call on the same id re-reads that terminal state and throws `IllegalDepositTransitionError` before any write — there is no window where a race or a repeated request reaches a second UPDATE. A capture amount above `row.amountMinor` is rejected the same way, by the domain function, before the write.

Wrote the failing test first (`DepositAuthorizationRepository.test.ts`, 10 cases) — confirmed it failed on the missing repository class before implementing, then implemented until green. Covers: create + read-back, full capture → `CAPTURED`, second capture on an already-captured row rejected (row unchanged), over-authorized capture rejected (row stays `AUTHORIZED`, `capturedMinor` stays `null`), capture attempted on an already-released row rejected, partial capture → `PARTIALLY_CAPTURED`, release, expire, and one cross-tenant isolation test (merchant B cannot create-as/read/capture/release/expire merchant A's authorization; merchant A's row is provably untouched by merchant B's rejected calls) — required by the D021 isolation-coverage generator, which initially flagged all five new methods until the isolation test was rewritten to call each method with two distinct named `ctxA`/`ctxB` contexts in one `it()` block.

No service-layer/RBAC or HTTP-route wiring in this card — the deliverable and acceptance criteria are the capture-attempt/bounds persistence guarantee itself ("One capture attempt; amount bounded by authorization" / "Second capture rejected; over-capture rejected"), matching the repository-only scope D076's first pass drew before a later pass added `DamageClaimService`. An RBAC-gated `DepositService` (`bookings:manage`, mirroring `DamageClaimService`) and an HTTP capture/release endpoint are natural follow-on work, not required by this card's text.

## Acceptance criteria check

- "Second capture rejected" — **Met.** `capture()` on an id already in a terminal state (`CAPTURED`, `PARTIALLY_CAPTURED`, `RELEASED`, `EXPIRED`) throws `IllegalDepositTransitionError`; tested explicitly for a second capture after a full capture, and for a capture attempted after a release.
- "Over-capture rejected" — **Met.** `capture(ctx, id, amountMinor)` with `amountMinor > row.amountMinor` throws `IllegalDepositTransitionError` and leaves the row at `AUTHORIZED`/`capturedMinor: null`; tested.

## Security check answer

**"THREAT: deposit amount tampering. Critical control."** `docs/design/07`'s stated control is "Capture amount bounded by the authorized amount; single capture; audit-logged." This card makes the first two parts structural at the persistence layer: `capture()` cannot write any amount the domain function (D077) hasn't already checked against `row.amountMinor` — the authorized amount as actually stored, not a client-supplied or in-memory value — and cannot write a second time once the row has left `AUTHORIZED`, because `transition()` always re-reads the current row from the database before deciding whether the event is legal. There is no path from an HTTP handler or service caller to an UPDATE that skips this read-check-write sequence, since `transition` is private and every public mutator (`capture`/`release`/`expire`) routes through it. The "audit-logged" third of the control is **not yet operational** — same honest gap D077 flagged: there is no repository or service in this card that writes to `audit_log`. The structural precondition is in place (one choke-point method, `transition`, is the only place a deposit's state ever changes), so audit-log wiring is a small addition to that one method whenever a future card requires it — not a redesign.
