## What happened

Added invariant I5 ("stock never goes negative") as a real, transaction-enforced guard rather than an application-level check-then-write. `InventoryMovementRepository.guardedDecrement` (`packages/db/src/repositories/InventoryMovementRepository.ts`) wraps the read-current-stock + insert-negative-movement sequence in `sqlite.transaction(...).immediate()` — `BEGIN IMMEDIATE` rather than the default deferred transaction, so the write lock is acquired *before* the SELECT runs. A concurrent caller blocks at `BEGIN IMMEDIATE` until the first transaction commits and therefore always reads the post-commit stock, closing the classic read-check-write race where two callers both read the same stale total before either commits. Rejects an out-of-range decrement via a new `InsufficientStockError`, and rejects a non-positive/non-integer quantity or a non-decrement `kind` before ever opening a transaction. Single-process tests (`InventoryMovementRepository.test.ts`) cover the method's business logic: success, rejection without a row being inserted, bad-input rejection, and cross-tenant isolation.

The card's named deliverable — a real N=50 concurrent test — is `InventoryMovementRepository.concurrency.test.ts`, a genuinely multi-threaded test using `node:worker_threads`, not `Promise.all` over synchronous same-thread calls (which would just be sequential, since better-sqlite3 is synchronous and JS is single-threaded — a same-process "concurrent" test could never actually race). 55 real OS threads, each holding its own `better-sqlite3` connection to the same file-backed SQLite database (WAL mode, per D013's `createConnection`), attempt `guardedDecrement(quantity: 1)` against a seeded stock of 50. A `SharedArrayBuffer` start-gate (`Atomics.wait`/`Atomics.notify`) holds every worker until all 55 have loaded and reported ready, then releases them at once, so the 55 attempts genuinely overlap rather than trickling in first-thread-wins order. Because worker threads run outside Vitest's TS transform pipeline, the worker script (`guardedDecrementWorker.mjs`, plain JS) imports the *built* `dist/` output of `@smb-os/domain`/`@smb-os/db` rather than TS source — the test's `beforeAll` runs `pnpm --filter @smb-os/domain --filter @smb-os/db build` first so it's never exercising a stale artifact from a prior session. Result, confirmed over three consecutive runs: exactly 50 succeed, exactly 5 fail with `InsufficientStockError`, and the post-run stock (read via a fresh connection) is exactly 0 — never negative at any point.

## Acceptance criteria check

- **Stock never negative** — Met. Structurally guaranteed by `BEGIN IMMEDIATE` serializing the read-check-write, not just true by luck in this run; the concurrency test's final-stock assertion (`0`, and `>= 0`) is the direct proof.
- **Exactly N succeed** — Met. With N=50 real stock and 55 real concurrent attempts, exactly 50 succeed and exactly 5 are rejected, verified across repeated runs (no flakiness observed).

## Security check answer

**"Real parallel transactions, not sequential calls."** Answered directly: the concurrency test spawns 55 real `worker_threads` (separate V8 isolates, separate OS-schedulable threads, separate `better-sqlite3` connections to the same file), synchronized to fire simultaneously via a `SharedArrayBuffer` start-gate, not 55 sequential or same-thread `await`ed calls. A same-process "concurrent" test would be misleading here — better-sqlite3 is synchronous and Node is single-threaded, so any same-process loop of calls is actually strictly sequential and can never exercise the race a naive (non-`IMMEDIATE`) transaction is vulnerable to. Real OS-thread parallelism was necessary to prove the guard, and is what this test uses.
