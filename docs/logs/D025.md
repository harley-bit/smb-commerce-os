## What happened

Added `resources`, `availability_rules`, and `availability_exceptions` (`packages/db/src/schema/{sqlite,pg}.ts`) per `docs/design/03`'s "Service capacity" section, with real `drizzle-kit`-generated migrations for both dialects (`packages/db/migrations/{sqlite,pg}/0004_*`). `resources` carries the `capacity` column (usually 1, >1 for a class/room with seats) that a future reservation service will check concurrent bookings against. `availability_rules` is deliberately weekday + `HH:MM` time window rather than a full RRULE, using `docs/design/04`'s portability mapping (`TEXT` in SQLite, `time`/`date` types in PostgreSQL). `availability_exceptions` covers one-off `BLACKOUT`/`EXTRA` deviations as a real half-open UTC interval. Test-first via `packages/db/src/schema/capacity.test.ts` (8 cases, confirmed failing with `Cannot find module`/undefined-table errors before the schema existed), including a real local PostgreSQL 16 run (`DATABASE_URL`-gated), not just SQLite. ## Security check answer

**"Resource capacity bounds concurrent bookings."** At this schema-only stage, the bound exists as data, not yet as enforcement: `resources.capacity` (`NOT NULL integer`) is the number a future reservation/capacity service must check the count of concurrent `HELD`/`CONFIRMED`/`IN_USE` reservations against before allowing a new booking, per `docs/design/03`'s reservation-state table and `docs/design/05`'s exclusion-constraint design. No reservations table exists yet (that is `D026`, the next card) and no service-layer check exists yet — flagged honestly as a deferred gap rather than silently assumed, the same pattern D022 used for mode immutability and D024 used for stock never going negative. This schema card's job was to make the bound representable and durable; enforcing it against real concurrent writes is `D026`+'s job and will need the non-negotiable Gate G3 (no-double-booking under concurrency) treatment before it ships.
