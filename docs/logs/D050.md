## What happened

Added `ReservationRepository.createGuarded` (`packages/db/src/repositories/ReservationRepository.ts`), the real check-then-insert write path per `docs/design/05` C1: `sqlite.transaction(...).immediate()` opens with `BEGIN IMMEDIATE`, taking the write lock before running the overlap check (`findBlocking`, D049) so a second concurrent caller cannot begin its own write transaction until the first commits, and therefore always evaluates the overlap check against post-commit data. A conflict throws the new typed `ReservationConflictError`; `create()` (D049) and `createGuarded()` now share one private `insertRow` helper.

Wrote the failing tests first: three new isolation-relevant cases in `ReservationRepository.test.ts` (no-conflict insert, overlap rejection with proof nothing was written, and a cross-tenant case with two distinct `ctx*` identifiers calling `createGuarded`, satisfying the D021 isolation-coverage scanner) — all confirmed failing (`createGuarded is not a function`) before implementation existed. A new file, `ReservationRepository.write-path.test.ts`, directly demonstrates the card's acceptance criterion using two real `better-sqlite3` connections against the same on-disk file with statements interleaved by hand (no worker threads needed — that harness is D052's separate job): a deferred-transaction variant and the real `createGuarded` path, both driven through the identical interleaving.

One real finding along the way: under `journal_mode = WAL` (mandatory since D013), a deferred transaction that already read stale data does **not** silently let a second writer double-book the way classic rollback-journal SQLite would — WAL's snapshot isolation detects the staleness and refuses the write. But it refuses with a raw, untyped `SQLITE_BUSY_SNAPSHOT` engine error, not a business-level rejection — a caller cannot tell "someone already booked this" from "the database is momentarily busy," and which of the two racing writers gets the error is an accident of statement order, not a designed guarantee. That is the concrete form "the deferred variant demonstrably fails" takes in this codebase: not silent double-booking, but an unusable, non-deterministic failure mode. `createGuarded`'s `BEGIN IMMEDIATE` fixes this by blocking the second writer at `BEGIN`, before any read, so its subsequent overlap check always runs clean and yields the typed `ReservationConflictError` every time — verified directly in the second test of `ReservationRepository.write-path.test.ts`. Also exported `ReservationRepository`/`ReservationConflictError`/its supporting types from `packages/db/src/index.ts` (they were left off the barrel in D049).

## Acceptance criteria check

- "Deferred-transaction variant demonstrably fails" — **Met**, in the form the real engine actually produces: `ReservationRepository.write-path.test.ts`'s first case proves a deferred check-then-insert throws an opaque `SQLITE_BUSY_SNAPSHOT` (asserted by `error.code`, and asserted *not* to be the typed `ReservationConflictError`) under the exact read-then-concurrent-write interleaving the design doc describes.
- "IMMEDIATE passes" — **Met.** The same file's second case runs the identical interleaving through `createGuarded`: the second writer's `BEGIN IMMEDIATE` is blocked while the first's transaction is open (`toThrow(/database is locked/)` against a short `busy_timeout`), and once the first commits, the second writer's retry through `createGuarded` cleanly detects the now-committed reservation and throws `ReservationConflictError` — never a raw engine error, never a second overlapping row.

## Security check answer

"BEGIN IMMEDIATE is load-bearing — deferred allows the race": confirmed directly, with a correction to the naive framing. Under this repo's mandatory `journal_mode = WAL`, a deferred transaction doesn't let the race manifest as a silent double-booking — WAL's snapshot isolation catches the staleness. But it still "allows the race" in the sense that matters operationally: it produces an untyped, non-deterministic engine failure (`SQLITE_BUSY_SNAPSHOT`) that the application cannot distinguish from transient contention and cannot safely retry-and-succeed against (retrying doesn't help — the snapshot is fixed, so the failing writer must abandon its transaction and restart from a fresh read). `BEGIN IMMEDIATE` closes this by acquiring the write lock before the overlap check runs at all, so every caller's check is always against fully-committed data and the outcome is always one of two things: a clean insert, or a clean, typed `ReservationConflictError`. No third, ambiguous outcome is possible.
