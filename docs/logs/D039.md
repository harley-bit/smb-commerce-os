## What happened

Built the first application code on top of the `inventory_movements` ledger table (schema already existed from earlier schema build-out cards; no migration needed). `packages/db/src/repositories/InventoryMovementRepository.ts` is a tenant-scoped, append-only repository (`record`/`listByVariant`/`sumStock` — no update/delete, matching `docs/design/03`'s "never a mutable counter" design) where `sumStock` derives stock on every call via `COALESCE(SUM(quantity), 0)`, scoped to a variant and optionally narrowed to one location. `packages/db/src/services/InventoryService.ts` adds `receiveStock` (records a `RECEIPT` movement, gated on `inventory:manage` via D037's `assertCan`, rejects a non-positive quantity or a blank note) and `getStock`. `receiveStock` also appends a hash-chained `audit_log` entry (D030's `AuditLogRepository`) carrying the same reason in `afterJson` — this card's security check, answered below. This is also the first application code to actually call `AuditLogRepository.append`, closing a gap D030's log flagged as future wiring work.

Test-first throughout, confirmed failing (`Cannot find module`) before either implementation file existed: `InventoryMovementRepository.test.ts` (6 cases, including the acceptance criterion directly — stock summed across mixed RECEIPT/SALE/ADJUSTMENT movements matches the ledger, plus location-scoping and cross-tenant isolation) and `InventoryService.test.ts` (7 cases — receipt reflected in stock, receipt on top of prior mixed-kind movements, STAFF/READ_ONLY forbidden from receiving stock, non-positive quantity rejected, blank note rejected, and the audit-log entry assertion).

## Acceptance criteria check

- **"Stock matches ledger sum across mixed movements"** — Met. `InventoryMovementRepository.test.ts`'s "stock is the sum of the ledger across mixed movement kinds" test records RECEIPT(+20), SALE(-3), ADJUSTMENT(-1), RECEIPT(+5) and asserts `sumStock` returns 21 — the literal sum, not a cached/derived value. `InventoryService.test.ts` proves the same at the service layer: a `receiveStock` call lands correctly on top of a pre-existing SALE movement.

## Security check answer

**"Adjustments are audit-logged with a reason."** Every `inventory_movements` row already requires a non-null `note` at the schema level (`docs/design/03`), and this card's service layer additionally requires it be non-blank before a RECEIPT is recorded (`InventoryService.test.ts`'s "rejects a RECEIPT with a blank note" case). Beyond the ledger row itself, `receiveStock` appends a separate, hash-chained `audit_log` entry (`action: "inventory.receipt"`, `entityType: "inventory_movements"`, `entityId` = the movement's id, `afterJson` carrying `quantity`/`note`/`variantId`/`locationId`) via D030's `AuditLogRepository.append` — verified directly by `InventoryService.test.ts`'s "this card's security check" test, which reads the audit log back and asserts the actor, action, and reason are all present. Scope note: this card only wires the audit call for `RECEIPT` movements (the card's stated deliverable); `ADJUSTMENT`-kind movements exist in the schema/repository but have no dedicated service method yet — that's D040+'s job as the SALE/adjustment paths get built, and they should call the same `auditLogRepo.append` pattern established here rather than re-deriving it.
