## What happened

Built the HELD → CONFIRMED service-booking flow on top of D050-D058's already-existing `reservations`/`resources` machinery. A "service booking" is a `reservations` row with `subjectType: "RESOURCE"`; no separate `bookings` table exists or was needed. Added a new `BookingService` (`packages/db/src/services/BookingService.ts`) with `createServiceBooking` (creates a `HELD` reservation via `ReservationRepository.createGuarded`, occupying the resource up to its `capacity`, defaulting the hold to 15 minutes per `docs/design/05`) and `confirmServiceBooking` (drives `HELD → CONFIRMED` through `packages/domain`'s `applyReservationEvent` — this is the first real caller of that state machine outside its own unit tests). Authorization reuses the RBAC matrix's existing `bookings:manage` action (`packages/domain/src/auth/rbac.ts`, already defined but previously unused) — OWNER/ADMIN/STAFF can book, READ_ONLY cannot — a deliberately different gate than `ResourceService`'s catalog-management `assertCanManageCatalog` (OWNER/ADMIN only), since booking a resource is a routine operational action, not catalog editing.

Idempotency (this card's security check) is implemented at the `reservations` table itself rather than a side table: added a nullable `idempotency_key` column plus a partial unique index (`merchant_id, idempotency_key`, `WHERE idempotency_key IS NOT NULL`) to both the SQLite and PostgreSQL schemas (migrations `sqlite/0010`, `pg/0012`, generated via `drizzle-kit generate`). `ReservationRepository.createGuarded` (SQLite) and `PgReservationRepository.createGuarded` (Postgres) both now check for an existing row with the caller's key *inside* the same serialized transaction (`BEGIN IMMEDIATE` / `SELECT ... FOR UPDATE`) that guards the conflict check, and short-circuit to the original row's id on retry instead of re-running the conflict check or inserting a duplicate — so a retried request for the same resource is provably safe under real concurrency, not just best-effort. `BookingService.createServiceBooking` throws `MissingIdempotencyKeyError` if the caller omits the key or passes an empty string.

Also added `ReservationRepository.findById` and `.confirm` (the actual HELD→CONFIRMED write, guarded the same way `createGuarded` is) and `.findByIdempotencyKey`. Zod contract added at `packages/contracts/src/booking.ts` (`createServiceBookingInputSchema`, `idempotencyKey` required non-empty). Test-first throughout: `BookingService.test.ts` and the new `ReservationRepository.test.ts` cases (idempotent replay, cross-tenant `findById`/`confirm`, illegal-transition) were written and confirmed failing (`Cannot find module`/missing methods) before the implementation existed. `findIsolationCoverageGaps` (D021/G1) initially flagged the two new arrow-function `RepositoryMethod`s (`findById`, `confirm`) for lacking a real two-tenant-context test — fixed by adding explicit cross-tenant tests for both, and the gate now reports zero gaps again.

No API routes were added — consistent with D058's precedent (`ResourceService` also has no HTTP layer yet) and confirmed against `docs/BUILD_CALENDAR.md`, which schedules the HTTP surface for `D060` (Availability API endpoint) and `D061` (Service booking endpoints), both still `Not started`.

## Acceptance criteria check

- **Booking occupies the resource** — Met. `BookingService.createServiceBooking` inserts a `HELD` reservation with `subjectType: "RESOURCE"`, `subjectId: resource.id`, checked against `resource.capacity` inside `createGuarded`'s serialized transaction; proven by `BookingService.test.ts`'s "occupies the resource with a HELD reservation" test reading the row back via `ReservationRepository.findById`.
- **Conflict rejected** — Met. `BookingService.test.ts`'s "rejects a conflicting booking on the same resource" test proves an overlapping booking on a capacity-1 resource throws `ReservationConflictError`, reusing the concurrency-safe conflict check already proven under real concurrency by D052-D054's harness — this card didn't have to re-prove G3, only wire a SERVICE-mode caller onto it.

## Security check answer

**Idempotency-Key required on creation.** `BookingService.createServiceBooking` throws `MissingIdempotencyKeyError` if `input.idempotencyKey` is missing or empty (`BookingService.test.ts` "security: createServiceBooking() requires an Idempotency-Key"), and `createServiceBookingInputSchema` (`packages/contracts/src/booking.ts`) makes the field non-optional and non-empty at the contract layer too. Beyond just requiring the header, a *retried* request carrying the same key is provably idempotent, not just rejected-if-missing: `ReservationRepository.createGuarded`/`PgReservationRepository.createGuarded` look up the key inside the same serialized transaction that guards the resource-conflict check (`BEGIN IMMEDIATE` / `SELECT ... FOR UPDATE`), so a network-retry of an already-succeeded booking request returns the original reservation id instead of either erroring or double-occupying the resource — proven by `BookingService.test.ts`'s "retrying ... replays the original booking" test asserting exactly one blocking reservation exists after two identical-key calls. The partial unique index (`reservations_merchant_idempotency_key_unique`) is the DB-level backstop if a caller ever reuses a key across genuinely different subjects.
