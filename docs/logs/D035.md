## What happened

`apps/api/src/app.ts`'s `buildApp()` now configures Fastify with structured JSON logging (pino, `level: "info"`, with a `redact` list covering `Authorization`/`Cookie` headers and any password/token/code body fields as defense in depth), an `X-Request-Id` correlation id (accepted from the client via `requestIdHeader`/`genReqId` when present, otherwise generated with `randomUUID()`, and echoed back on every response via an `onSend` hook), and RFC 9457 `application/problem+json` error responses for both a 404 (`setNotFoundHandler`) and any unhandled error (`setErrorHandler`) — extracted into `apps/api/src/problemDetails.ts` (`ProblemDetails`, `problemType`, `sendProblem`). Added `GET /health` and `GET /ready`, both returning `200`. A new `loggerStream` build option lets tests capture and assert on real emitted JSON log lines without touching production behavior (which still logs to stdout). One surprise: Fastify's default request/response log serializers don't include headers or body at all, so the "no PII/tokens in logs" property held even before the explicit `redact` config — the redact list is still worth keeping as defense in depth against a future call site that logs `request.body` directly.

## Acceptance criteria check

## Security check answer

**"No PII, tokens, or stack traces in logs or responses"** — verified directly, not assumed:
- Responses: the `setErrorHandler` never includes `error.message` or `error.stack` for a `>=500` error — the client gets a fixed `"Internal Server Error"` detail regardless of what the underlying error said. A test throws an error containing a fake secret (`"db password is hunter2"`) and asserts the string never appears anywhere in the JSON response body.
- Logs: the same handler logs only `error.name`/`error.code` to `request.log.error`, deliberately excluding `error.message`/`error.stack`, since an application error's message text is developer-written and not guaranteed to be secret-free. A test captures real emitted log lines (via the new `loggerStream` option) for a `/auth/login` call carrying a real email and password, asserts every line parses as JSON (structured logging), and asserts none of them contain the submitted email or password — true today mostly because Fastify's default request/response serializers don't log headers or body, reinforced by an explicit `redact` config on `Authorization`/`Cookie` headers and password/token/code body fields for the day a future log call does include them.
- Known gap, not fixed here: no route currently logs `request.body` explicitly, so the redact list is currently unexercised in practice — flagged so a future card adding body logging doesn't assume it's automatically safe without checking this config still covers the new fields.
