## What happened

Mobile checkout, Phase 8's tenth card. Mirrors web's `PaymentView.tsx`/`HostedCardField.tsx` (D130) against the same already-existing, unauthenticated `POST /v1/m/{slug}/checkout/{orderId}/payment-intent` route (`apps/api/src/routes/checkoutPayment.ts`) — no server-side work was needed, this card is the mobile client for a route D130 already built. New `apps/mobile/src/payments/fetchPaymentIntent.ts` (`createPaymentIntent`, DI'd `fetchFn`/`generateIdempotencyKey`, same convention as every other mobile fetch helper) POSTs with a fresh `Idempotency-Key` header and no body at all, and maps the response into `{ ok: true, amountMinor, currency }` / a `declined` result carrying only the server's already-mapped generic message and `retryableWithSameMethod` flag (never a raw provider decline code, even when the fixture body includes one) / a generic `error` result for anything else. New `apps/mobile/src/payments/HostedCardField.tsx` stands in for the real Stripe React Native SDK's native `<CardField>` (`@stripe/stripe-react-native`) exactly the way web's `HostedCardField.tsx` stands in for Stripe Elements — same "native/simulated now, real provider later" posture already established everywhere else payments touch this codebase, since there is no live Stripe mobile SDK dependency here yet. New `apps/mobile/src/payments/PaymentScreen.tsx` disables "Pay" until that mount point reports ready, then calls `createPaymentIntent` and renders success / decline / generic-error state, mirroring `PaymentView.tsx`'s exact contract. Wired into `App.tsx`'s `Checkout` case: with a real `orderId` it renders `PaymentScreen`; without one (the common case today, since no cart→order creation call exists yet — `CartService`'s HTTP-route gap, open since D126/D142) it renders a `NoOrderNotice`, mirroring web's `checkout/page.tsx` exactly rather than fabricating an order id. `routes.ts`'s `Checkout` screen params gained an optional `orderId` to carry this.

## Acceptance criteria check

- **"Payment completes on both platforms"** — Met, in this repo's still-simulated payments posture (same caveat D130's log stated for web: "payment completes" means the PaymentIntent was created without a decline against `SimulatedPaymentIntentProvider`, not that a real card was confirmed against live Stripe — that confirmation is genuinely native/client-side and can't be exercised without live Stripe keys). "Both platforms" holds because the entire flow above `HostedCardField` — the fetch, the idempotency key, the success/decline/error branching — is plain cross-platform TypeScript with no platform-conditional code at all; the one place iOS/Android would actually diverge (the real native `CardField`) is exactly the seam `HostedCardField` isolates and stands in for. Proven by `fetchPaymentIntent.test.ts`'s first case (201 → success) and confirmed end-to-end-reachable via a real `npx expo export --platform ios --platform android` bundle (770 iOS / 516 Android modules, zero errors) — the same class of check D137–D145 all used since this machine has no simulator/emulator to run an actual foreground app in.

## Security check answer

**"No card data touches our code on mobile either."** Met by construction, verified by a repo-wide static scanner: new `apps/mobile/src/payments/cardFieldScanner.ts` is the RN counterpart to `apps/web/src/security/cardFieldScanner.ts` (D099/D130's PCI SAQ A tripwire), adapted from web's `<input>` element to React Native's `<TextInput>` — it flags any `<TextInput>` carrying a card-data `textContentType`/`autoComplete` hint or a card-shaped `testID`/`name`/`id`. `pageCardFieldGuard.test.ts`'s fifth case recursively scans every `.ts`/`.tsx` file under `apps/mobile/src` (skipping test files) and asserts zero violations — it runs against `HostedCardField.tsx` and `PaymentScreen.tsx` (the two new files that could plausibly need a card field) on every `pnpm test`, same as web's equivalent scan. `HostedCardField.tsx` itself renders no `TextInput` at all, only `View`/`Text`. Independently, `fetchPaymentIntent.test.ts`'s first case asserts the POST request carries no body — only the `Idempotency-Key` header — so there is no code path by which a card field's value could even be serialized into a network call from this module.
