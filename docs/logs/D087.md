## What happened

First Phase 5 (Payments — Stripe Connect) card. Added a `ConnectAccountProvider` port (`packages/domain/src/payments/ConnectAccountProvider.ts`) — same seam shape as `AuthProvider` (D010) and `MediaUploadProvider` (D073): `createAccount`, `createOnboardingLink`, `retrieveAccount`, so every caller depends on the interface only and a real Stripe-backed implementation can swap in later without touching any consumer. `deriveConnectAccountStatus` (`packages/domain/src/payments/connectAccountStatus.ts`) is pure domain math, no I/O, mapping Stripe's three account flags (`detailsSubmitted`, `chargesEnabled`, `payoutsEnabled`) to a merchant-facing `ONBOARDING | ACTIVE | RESTRICTED` status. No Stripe platform account has been provisioned for this project yet, so the first (and, for now, only) implementation is `SimulatedConnectAccountProvider` (`packages/db/src/payments/SimulatedConnectAccountProvider.ts`) — an in-memory stand-in that models the real onboarding shape (a new account starts with nothing enabled; only a hosted onboarding link moves it forward; `simulateOnboardingCompleted` stands in for the `account.updated` webhook a real integration would receive) without holding or transmitting any real underwriting data. `ConnectOnboardingService` (`packages/db/src/services/ConnectOnboardingService.ts`) is the actual card deliverable — `startOnboarding` creates the connected account and returns a hosted onboarding link; `checkStatus` reports back the derived status. No merchant -> connected-account mapping is persisted yet; that's explicitly D088's job ("Payments schema wiring"), so this card proves the onboarding mechanics only, the same scoping precedent D073's log set for its own follow-on card.

## Security check answer

**Provider holds funds — reduces money-transmitter exposure.** Every step of onboarding happens through `ConnectAccountProvider`'s hosted-link flow (`createOnboardingLink` returns a provider-hosted URL the merchant completes on Stripe's own domain) — this codebase never collects bank account numbers, SSNs, or other underwriting data itself, and `SimulatedConnectAccountProvider` upholds that same property today even though no live Stripe account exists yet (it never stores or transmits anything beyond a boolean-flag account record). Funds custody and the money-transmitter-license burden stay with the provider, not the platform, which is the entire point of using Connect rather than building payment processing directly. One honest limit: since no real Stripe account is provisioned, this only proves the *shape* of that property — the real guarantee is verified once a concrete Stripe-backed `ConnectAccountProvider` exists behind this same interface.
