## What happened

Built `packages/domain/src/auth/rbac.ts` per `docs/design/07`'s "Authorization" section: `MerchantRole` (`OWNER`/`ADMIN`/`STAFF`/`READ_ONLY` — the merchant-role axis only, not the separate platform-role axis that doc also defines), a closed `MerchantAction` union covering the four roles' documented scopes (catalog/inventory view+manage, bookings view+manage, condition-report management, reports view, payouts management, role assignment), a `ROLE_ACTIONS` matrix, a pure `can(role, action)` predicate, and `assertCan(ctx, action, resource?)` — the exact signature the design doc names — which throws a new `ForbiddenActionError` (carrying `role`/`action`/`resource`) for anything `can()` doesn't explicitly allow. Placed in `packages/domain` (no I/O, pure domain logic) rather than `packages/db`, since `MerchantUserRole` already lives in `packages/db` and domain code can't depend the other way — the two role types are structurally identical but independently declared; flagged as a real duplicate-source-of-truth gap in `IMPROVEMENTS.md` (new file this card) rather than fixed here, since unifying them is a cross-package refactor the acceptance criteria didn't ask for. Also flagged, same file: `ListingService`/`VariantService`/`ProductListingService`'s existing `assertCanManageCatalog` (D023) duplicates a small role check instead of calling this new `assertCan` — not migrated here for the same reason.

Test-first via `packages/domain/src/auth/rbac.test.ts` (8 cases), confirmed failing (`Cannot find module './rbac.js'`) before `rbac.ts` existed: every role's full permitted/forbidden action list is asserted individually (the card's acceptance criterion, directly), plus two default-deny cases — an action string entirely outside the `MerchantAction` union is denied for every role via both `can()` and `assertCan()` (the card's security check, directly) — and a case proving `assertCan` throws `ForbiddenActionError` carrying the exact role/action/resource that was denied.

## Acceptance criteria check

- **Each role's permitted and forbidden actions tested** — Met. Four dedicated test cases (one per role) each assert the full permitted list and the full forbidden list from `docs/design/07`'s role-scope table: OWNER gets everything including `payouts:manage`/`roles:assign`; ADMIN gets operations but not those two; STAFF gets bookings/condition-reports but not catalog/inventory management, reporting, payouts, or roles; READ_ONLY gets only the `*:view` actions.

## Security check answer

Card's stated check: "Default deny — unlisted actions are forbidden." True by construction, not by a fallback branch: `ROLE_ACTIONS` is the only source of "allow" (`can()` is `ROLE_ACTIONS[role].has(action)`, nothing else), so any action that was never added to a role's set — including one that isn't even a member of the `MerchantAction` type at all, tested directly by casting an arbitrary string through it — resolves to `false`/throws. There is no `else return true` path anywhere in the module. Verified directly: `can(role, unlistedAction)` is `false` for all four roles, and `assertCan({ role }, unlistedAction)` throws `ForbiddenActionError` for all four roles, including `OWNER` — the highest-privilege role is not treated as an implicit wildcard.
