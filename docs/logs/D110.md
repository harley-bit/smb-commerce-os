## What happened

D041's `InventoryUnitRepository`/`InventoryUnitService` already existed (`create`, `findById`, `listByVariant`, and a fully state-machined `updateStatus`/`transitionStatus` with `AVAILABLE`→`SOLD`/`MAINTENANCE`/`RETIRED`/`LOST` terminal-state rules and audit logging), but — the same gap category as D106–D109 — nothing exposed it over HTTP and no merchant-facing UI existed to list, add, edit, or retire a unit. New `packages/contracts/src/inventoryUnit.ts` adds `createInventoryUnitInputSchema` (making `acquisitionCostMinor`/`acquiredAt` *mandatory* at the contract boundary — this card's security check, mirroring D103's `onboardMerchantInputSchema` pattern of being stricter than the nullable DB column beneath it) and a `.strict()` `updateInventoryUnitInputSchema` that has no `acquisitionCostMinor`/`acquiredAt`/`status` member at all, so a caller cannot backfill or alter acquisition data or smuggle a status change through an edit. `InventoryUnitRepository` gained a new `update` method (`packages/db/src/repositories/InventoryUnitRepository.ts`), typed against a narrow `UpdateInventoryUnitFields` interface that structurally excludes acquisition fields — the same "can't backfill" property enforced again at the TypeScript layer, not just the Zod layer. `InventoryUnitService` gained `create`/`update`, both re-asserting `inventory:manage` (`ADMIN`/`OWNER` only) via `assertCan`, mirroring `transitionStatus`'s existing RBAC posture.

New `apps/api/src/routes/inventoryUnits.ts` (`registerInventoryUnitRoutes`, wired into `app.ts`) adds `GET`/`POST /listings/:listingId/variants/:variantId/units`, `PUT .../units/:unitId`, and `POST .../units/:unitId/retire` — mirroring `./variants.ts`'s `requireAction`/lazy-migration pattern exactly. Every route re-resolves the variant under the URL's `listingId` and the unit under the URL's `variantId` before acting, 404ing on a cross-listing or cross-tenant mismatch rather than 403/200 (`VariantService.findById` is already tenant-scoped, so another merchant's variant/unit is invisible, not merely forbidden). `POST .../units` forces `variantId` from the already-resolved variant, never trusting a client-supplied value, the same "don't trust the client to name its own parent" rule `./variants.ts` applies to `mode`/`listingId`. `/retire` calls the existing `transitionStatus` with `newStatus: "RETIRED"`, a server-generated `occurredAt`, and the caller's own `request.auth.identity.userId` as actor — an illegal transition (e.g. retiring an already-`SOLD` unit) surfaces as 409, not a silent no-op.

New `apps/web/src/app/dashboard/catalog/InventoryUnitsView.tsx` (routed at `/dashboard/catalog/[listingId]/variants/[variantId]/units`, linked from each `VariantTable` row via a new "Manage units" link) is the deliverable: lists every unit on a variant with its status, lets a merchant bulk-edit `unitCode`/`expectedLifeMonths`/`conditionGrade` in one "Save changes" action (mirroring `VariantTable`'s dirty-row-tracking pattern), retire a non-terminal unit via a per-row button, and add a new unit through a form that requires acquisition cost and acquisition date up front — the UI never exposes an acquisition-cost/date field anywhere except that one-time add form, since the server's own update schema would reject them anyway.

Wrote failing tests first throughout: `packages/contracts/src/inventoryUnit.test.ts` (11 cases, confirmed the schemas' shape before wiring anything else); `packages/db/src/repositories/InventoryUnitRepository.test.ts` and `.../services/InventoryUnitService.test.ts` gained new `update()`/`create()` describe blocks, confirmed red (`repo.update is not a function` / `service.update is not a function`) before implementing; `apps/api/test/inventoryUnits.test.ts` (22 cases, full RBAC matrix across all four routes, the mandatory-acquisition-data 400, the client-supplied-`variantId`-ignored proof, cross-tenant 404s, and the terminal-state 409 on retiring a `SOLD` unit); `InventoryUnitsView.test.tsx` (6 cases, including a dedicated assertion that a PUT request body never contains the strings `acquisitionCostMinor`/`acquiredAt`).

## Security check answer

**"Acquisition data captured now — impossible to backfill"** — enforced at two independent layers, not asserted once: (1) `createInventoryUnitInputSchema` requires `acquisitionCostMinor`/`acquiredAt` — omitting either 400s before a unit is ever created (`inventoryUnit.test.ts`, `inventoryUnits.test.ts`'s dedicated 400 case); (2) `updateInventoryUnitInputSchema` is `.strict()` with no member for either field, and `InventoryUnitRepository.update`'s own `UpdateInventoryUnitFields` type has no such member either — so even a bug in the Zod schema alone couldn't let a later edit smuggle a cost/date change through, since the repository method the route calls is typed to reject it before compilation. `apps/api/test/inventoryUnits.test.ts` proves the runtime side of this (a PUT carrying `acquisitionCostMinor` 400s and leaves the original value on record); `InventoryUnitsView.test.tsx` proves the client never even constructs such a request body.
