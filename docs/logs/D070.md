## What happened

Added `FulfillmentEventRepository` (`packages/db/src/repositories/FulfillmentEventRepository.ts`), the first repository over D029's `fulfillment_events` table: `record` (insert) and `listByOrderLine` (read) only, no update/delete — an append-only ledger of pickup/return history, matching `AuditLogRepository`/`InventoryMovementRepository`'s existing precedent. On top of it, `FulfillmentEventService` (`packages/db/src/services/FulfillmentEventService.ts`) exposes the card's two named handlers, `recordPickup`/`recordReturn`, both routing through a shared private `recordEvent`: `assertCan(role, "bookings:manage")` first (same RBAC action `RentalReservationService`/`BookingService` already gate operational booking actions on), then a non-empty-note check (`MissingFulfillmentNoteError`), then a tenant-scoped order-line lookup via a new `OrderRepository.findLineById(ctx, lineId)` method (`OrderLineNotFoundError` if the line doesn't exist or belongs to another merchant), and only then the repository write. Deliberately does not transition the underlying reservation's state — `docs/cards/D071.md` ("Event-driven state transitions") is the next card and owns that; this card only records the events.

## Acceptance criteria check

- "Events recorded append-only with actor" — **Met.** `FulfillmentEventRepository` exposes no update/delete method (structurally append-only, same shape as the audit log), every row requires a non-null `actorUserId` (schema-enforced, D029), and `FulfillmentEventRepository.test.ts`'s "records multiple events in append order — never mutates a prior event" proves two events for the same order line both persist independently rather than one overwriting the other. `FulfillmentEventService.test.ts` proves the actor is carried through faithfully (`actorUserId: userA` asserted on the persisted row) and that no write happens at all when authorization, the note, or the order line fails validation.

## Security check answer

"Event log is repudiation defence": the whole point of an append-only ledger with a mandatory, non-empty `actorUserId` and `note` on every row is that "who did what, when, and why" can't be edited after the fact — no method on `FulfillmentEventRepository` can alter or remove a row once written. This card adds one enforcement point beyond the schema: `MissingFulfillmentNoteError` rejects a blank/whitespace-only note before any write, since a repudiation record with no substantive content ("customer picked up trailer at store" vs. "") isn't actually evidence of anything if a pickup or return is later disputed. Known gap, same class as D030/D069's tracked caveat: this repository's `record` write is not itself hash-chained (unlike `audit_log`) and isn't wrapped in the same transaction as any future reservation-state write (D071), so it's an honest, tamper-resistant-by-structure log, not a cryptographically tamper-evident one — a future card could additionally mirror each fulfillment event into `audit_log` if that stronger guarantee is ever required.
