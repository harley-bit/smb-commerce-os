## What happened

Orders already existed as a unified concept (`orders`/`order_lines` tables, D0xx-era schema, `packages/db/src/repositories/OrderRepository.ts`) — `order_lines.mode` already carries `PRODUCT`/`SERVICE`/`RENTAL` per line, so a single order can genuinely mix all three. `OrderRepository` had `create`/`findById`/`addLine`/`listLines`/`findLineById`/`updateTotals` but no list-all-orders method, so I added `listByMerchant` (tenant-scoped, most recently placed first). Added a new `OrderService` (`packages/db/src/services/OrderService.ts`) with `listOrders` (returns an `OrderSummary` per order, including the distinct set of `modes` present across its lines) and `getOrderDetail` (returns every line with its listing name resolved via `ListingRepository`, since order lines only carry `listingId`/`variantId` lineage references, not a display name). New `GET /orders` and `GET /orders/:orderId` routes (`apps/api/src/routes/orders.ts`), gated by a new `orders:view` RBAC action (`packages/domain/src/auth/rbac.ts`) granted to every merchant role including `READ_ONLY` — the same staff-wide-view rationale D114 used for `bookings:view`. Both routes are `GET`-only; this card adds no order-mutation endpoint. New `apps/web/src/app/dashboard/orders/OrderListView.tsx` (table of orders, each row showing its full `modes` set) and `OrderDetailView.tsx` (per-line table showing mode, listing name, quantity, price, and start/end for SERVICE/RENTAL lines), with `page.tsx`/`[orderId]/page.tsx` routes and an "Orders" cross-link added to `CatalogView.tsx` next to the existing "Calendar" link. Wrote failing tests first throughout: `OrderRepository.test.ts` (1 new `listByMerchant` case, confirmed `repo.listByMerchant is not a function` before implementation), `OrderService.test.ts` (5 cases, new file), `apps/api/test/orders.test.ts` (8 cases, new file, `it.each` over all four roles), `OrderListView.test.tsx` (4 cases, new file), `OrderDetailView.test.tsx` (3 cases, new file) — all confirmed red (missing module / missing method / 500s from the stale `@smb-os/domain` and `@smb-os/db` dist builds) before green. Had to rebuild `@smb-os/domain` and `@smb-os/db` (`tsc`) mid-run since `apps/api`/`packages/db` import each other's compiled `dist/` output, not source, and the new `orders:view` action / `listByMerchant` method weren't visible across the package boundary until rebuilt.

## Security check answer

"Role-gated: READ_ONLY cannot mutate" — this card's feature (order list + detail) exposes only `GET /orders` and `GET /orders/:orderId`, both gated by the new `orders:view` RBAC action. No mutation route exists in `apps/api/src/routes/orders.ts` for any role, so the gating holds structurally rather than by a per-role check on a write path. Proven by a dedicated test (`apps/api/test/orders.test.ts`, "this card's security check") that sends `PUT`/`DELETE` to `/orders/:orderId` as `READ_ONLY` and confirms both 404 (no route registered) rather than reaching any handler. `it.each` over all four roles (`OWNER`/`ADMIN`/`STAFF`/`READ_ONLY`) confirms every role can view, matching `orders:view`'s grant in `rbac.ts`.
