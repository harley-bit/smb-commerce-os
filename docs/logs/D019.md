## What happened

Built the first two real tenant-scoped repositories on top of D017's `TenantScopedRepository` base class and D018's `merchants`/`locations` tables: `packages/db/src/repositories/MerchantRepository.ts` and `LocationRepository.ts`. `merchants` has no `merchant_id` column of its own — its own `id` *is* the tenant boundary — so `MerchantRepository` scopes on `merchants.id` itself: `create` sets `id` from `ctx.merchantId` rather than trusting caller input, and `findOwn`/`update`/`archive` all filter through `this.scope(ctx)`, so a caller can only ever create, read, or write their own merchant row. `LocationRepository` follows the more conventional pattern from D017's `WidgetRepository` example: `create` sets `merchantId` from `ctx.merchantId`, and `list`/`findById`/`update`/`archive` all AND `this.scope(ctx)` with any row-id predicate. Test-first via two new test files (10 cases total), confirmed failing on `Cannot find module` before the repository files existed. Both packages exported from `packages/db/src/index.ts`. Postgres-dialect repository variants were not built this card — matches the existing `WidgetRepository` precedent of testing the runtime-scoping pattern against SQLite only; the schema layer (D018) already proved both dialects enforce FKs/uniqueness identically, and this card's job was the repository/scoping pattern, not a second dialect implementation.

## Acceptance criteria check

- **CRUD works** — met. `MerchantRepository`: create/findOwn/update/archive, all tested. `LocationRepository`: create/list/findById/update/archive, all tested.
- **Scoping predicate present in every query** — met. Every method takes `TenantContext` as its first parameter (compile-time layer, inherited from `RepositoryMethod`) and every query (`insert`/`select`/`update`) either sets the merchant-owning column from `ctx.merchantId` directly or ANDs `this.scope(ctx)` into its `where` clause — verified behaviorally, not just by inspection: 6 of the 10 new tests assert merchant A's context cannot read, update, or archive merchant B's row (or vice versa).

## Security check answer

**Layer 3 — runtime scope injection.** Per `docs/design/07` Control #1, the runtime layer is: "Repository base class injects the `merchant_id` predicate; raw query construction is banned outside `/packages/db`." Both new repositories only ever construct their `WHERE` predicate through `TenantScopedRepository.scope(ctx)` (or, for `MerchantRepository.create`, by setting the primary key directly from `ctx.merchantId`) — there is no code path in either class that accepts a caller-supplied merchant id and uses it to build a predicate or an insert value. The `local/no-raw-sql` ESLint rule (D003) additionally prevents any raw SQL from bypassing this inside `packages/db` at all, everywhere except the migration/connection layer itself.
