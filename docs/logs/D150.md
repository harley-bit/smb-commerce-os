## What happened

Built the mobile app's condition-photo capture and upload, reusing the API surface Phase 6 already built for the web dashboard (`apps/api/src/routes/fulfillment.ts`'s `/condition-reports/:id/media/upload-url` + `/media/confirm` pair, D073) rather than adding anything server-side. `apps/mobile/src/merchant/conditionPhotoUpload.ts` is the pure, DI'd core (`baseUrl`, `fetchFn`, `accessToken`, `merchantId`, an injected `sha256Hex` adapter, an injected `now()`): it requests an upload grant, hashes the exact bytes about to be sent, then confirms with `storageKey` + `contentType` + `bytesBase64` + `declaredSha256` + `capturedAt` — mirroring `apps/web/src/app/dashboard/rentals/RentalCheckoutView.tsx`'s flow but over `Authorization: Bearer` + `x-merchant-id` headers instead of web's session cookie, the same mobile-vs-web auth split `../account/fetchOrderHistory.ts` (D147) already made. A hand-rolled `base64ToBytes` decoder (no `Buffer`/`atob` dependency, same reasoning as `../auth/pkce.ts`'s own base64 encoder) turns the picker's base64 output back into bytes for hashing. `apps/mobile/src/merchant/expoConditionPhotoCapture.ts` is the real, untested on-device wiring (same posture as `../auth/expoPkceAdapter.ts`): `expo-image-picker`'s `requestCameraPermissionsAsync` + `launchCameraAsync({ base64: true })` for capture, `expo-crypto`'s `Crypto.digest` for the real SHA-256 hash. Added the `expo-image-picker` dependency (`npx expo install expo-image-picker`, resolved to `~57.0.16` for this app's Expo SDK 57) and wired its camera-permission purpose string into `app.json`'s plugin config.

## Acceptance criteria check

- "Photos upload with hash and metadata" — **Met.** `conditionPhotoUpload.test.ts`'s first case asserts the confirm request body carries `declaredSha256` computed from the exact captured bytes and `capturedAt` metadata, and that the upload-url request precedes it with the correct byte count; the second and third cases assert a failed grant or a failed confirm (e.g. a server-side hash mismatch) is surfaced as a reported error rather than silently swallowed.

## Security check answer

"Camera permission requested with clear purpose string." The purpose string itself lives in `app.json`'s `expo-image-picker` plugin config (`cameraPermission: "Staff use the camera to photograph an item's condition at rental checkout and check-in. Photos are attached to the order's condition report only."`) — this is the exact string iOS's `NSCameraUsageDescription` and Android's runtime permission dialog show the user, generated by the Expo config plugin at build time, so there's no separate string to keep in sync. `expoConditionPhotoCapture.ts` calls `requestCameraPermissionsAsync()` fresh on every capture attempt (never assumes a prior grant), so a mid-session revocation via device settings is caught before `launchCameraAsync` is invoked, and a denial returns a distinct `permission-denied` status the caller can show a clear message for rather than the camera silently never opening.
