## What happened

Investigated what this card actually requires before writing code: "Internal testers can install both builds" via TestFlight and Play internal testing needs a provisioned Apple Developer Program membership + App Store Connect access, a provisioned Google Play Console developer account, and an EAS (Expo Application Services) project/account to actually produce and sign the builds. Confirmed none of these exist in this environment: `eas` CLI is not installed (`npx eas --version` fails to resolve an executable), there is no EAS project id anywhere in `apps/mobile`, and `app.json`'s bundle identifiers were still Expo's default placeholder (`com.anonymous.mobile`, never registered with either store). Built the piece of this card's deliverable that *is* code-shaped and answers the security check directly: `apps/mobile/eas.json`, with every build profile (`development`/`preview`/`production`) and both platforms (`ios`/`android`) set to `credentialsSource: "remote"` — EAS's own encrypted credential store, which holds the actual signing certificates/provisioning profiles/keystores and injects them at build time; nothing signing-related is ever written to this repo or a build machine's disk. The `submit.production` block references only environment-variable names (`$EXPO_APPLE_ID`, `$EXPO_ASC_APP_ID`, `$EXPO_APPLE_TEAM_ID`, `$EXPO_GOOGLE_SERVICE_ACCOUNT_KEY_PATH`) that a real CI run would resolve from its secrets manager — no literal credential ever appears in the file. New `apps/mobile/src/distribution/signingCredentials.ts` provides `validateRemoteCredentials` (structurally rejects any profile that isn't `"remote"` on either platform) and `findLocalSigningArtifacts` (recursively scans a directory, skipping `node_modules`/`.git`/the gitignored generated `ios`/`android` folders, for key-shaped file extensions — `.jks`/`.p8`/`.p12`/`.key`/`.mobileprovision`/`.pem`/`.keystore`). Wrote the failing test first (`signingCredentials.test.ts`, 8 cases, confirmed failing on the missing module before implementation), including two cases that assert against the *real* `eas.json` and the *real* `apps/mobile` tree, not just fixtures — so this isn't just a config file that looks right, it's continuously enforced. Also set `app.json`'s `ios.bundleIdentifier`/`android.package` to a real-looking namespaced id (`os.smbcommerce.mobile`) instead of the Expo default, since a placeholder can't be registered with either store when the account work eventually happens.

Confirmed `.gitignore` already blocks every signing-artifact extension (`*.jks`/`*.p8`/`*.p12`/`*.key`/`*.mobileprovision`/`*.pem`) plus the entire generated `/ios`/`/android` folders, and that D009's repo-wide `gitleaks` scan (`packages/config/test/secret-scanning.test.ts`) runs on every `pnpm test` as defense in depth — this card's new scanner is mobile-specific and additive to that, not a replacement.

## Security check answer

"Signing keys in Secrets Manager, never in the repo." Every build profile in `apps/mobile/eas.json` sets `credentialsSource: "remote"` for both `ios` and `android` — EAS's own encrypted remote store holds the actual private keys/certificates/provisioning profiles/keystores, uploaded once via `eas credentials` outside this repo, and injects them into the build environment at build time; they never touch git history or local disk. The `submit` block's App Store Connect / Google Play values are all `$ENV_VAR` references resolved from CI's own secrets store, never literal. This is enforced, not just asserted: `signingCredentials.test.ts`'s `validateRemoteCredentials` fails any profile that isn't `"remote"` on either platform (including against the real `eas.json` itself, so a future edit that regresses this fails the test suite), and `findLocalSigningArtifacts` scans the real `apps/mobile` tree for committed key-shaped files and asserts it finds none — backed by `.gitignore` (which already excludes every relevant extension and the generated native folders) and D009's repo-wide gitleaks scan as independent, overlapping defense.
