## Security check answer

**"Portability failure is caught the day it is written"** — addressed structurally, not just described: the `test-postgres` CI job runs the exact same `packages/db` test suite as the SQLite path, against a real PostgreSQL service container, on every PR. A change that works on SQLite but violates a PostgreSQL constraint (or vice versa) fails that job immediately, the same PR it's introduced in — not discovered later when the app is actually pointed at production Postgres. The behavioral FK test in `pg-connection.test.ts` is the concrete proof this works today: it exercises the one divergence D013's log already flagged (`foreign_keys` defaults off in SQLite, on in PostgreSQL) from the PostgreSQL side, so both halves of that portability rule now have a real regression test, not just a pragma read-back on one side.
