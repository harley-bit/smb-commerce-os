## What happened

Added `orders` and `order_lines` (`packages/db/src/schema/{sqlite,pg}.ts`) per `docs/design/03`'s "Orders" section. `orders`: `id`, `merchant_id`, `customer_user_id` (FK `users`), `status` (`CART | PENDING_PAYMENT | CONFIRMED | FULFILLED | CANCELLED | REFUNDED`), `currency`, `subtotal_minor`, `tax_minor`, `total_minor`, `placed_at`, `cancelled_at`. `order_lines`: `id`, `merchant_id`, `order_id`, `listing_id`, `variant_id`, `mode` (`PRODUCT | SERVICE | RENTAL`), `quantity`, `unit_price_minor`, `line_total_minor`, `deposit_minor`, `starts_at`, `ends_at` — `mode`, `unit_price_minor`, and `line_total_minor` are copied from the listing/variant at write time, exactly as `03` specifies ("Prices copied, never referenced"); `listing_id`/`variant_id` remain as plain lineage FKs, but the row they point to is no longer the source of truth for price or mode once the order line exists. One index per `03`'s "Indexing" section: `order_lines_merchant_order_idx` on `(merchant_id, order_id)`. Real `drizzle-kit`-generated migrations for both dialects (`packages/db/migrations/{sqlite,pg}/0006_*`). Test-first via `packages/db/src/schema/orders.test.ts` (6 cases, confirmed failing with `TypeError: Cannot read properties of undefined (reading 'Symbol(drizzle:Columns)')` before the schema existed — the columns didn't exist to insert into), including a real local PostgreSQL 16 run (started via `brew services start postgresql@16` for this session, stopped again afterward — not left as a persistent background service, matching D014/D015's convention) that inserts a full order/order-line row and checks `pg_indexes` for the merchant/order index directly. No repository/service layer yet, same split as D022→D023, D024→(pending), D025/D026 before it — that's a future card's job.

## Acceptance criteria check

- "Archiving a listing does not alter historical orders" — **Met.** A dedicated test (`orders.test.ts`, "archiving a listing does not alter a historical order line's copied price and mode") writes an order line, then updates the listing variant's price and archives the parent listing, then re-reads the order line and asserts its `mode`, `unit_price_minor`, and `line_total_minor` are unchanged from what was written at order time. This is possible precisely because those columns are copies, not computed via a join to `listings`/`listing_variants` at read time.

## Security check answer

**"Prices copied not referenced — history must not mutate."** Confirmed at the schema level: `order_lines.unit_price_minor` and `line_total_minor` are plain integer columns populated once, at write time, from the listing variant's then-current price — there is no view, generated column, or join-on-read back to `listing_variants.price_minor` anywhere in this schema, so a later price edit or archive on the listing has no path to reach an existing order line. The remaining gap, flagged honestly rather than silently assumed: nothing yet *enforces* that a future service-layer write path actually copies the price correctly (e.g. a buggy `OrderService.create` could theoretically write the wrong number) — that's I8 ("order line totals equal quantity × unit price") from `03`'s invariant table, explicitly listed there as a domain invariant "asserted on write," which is a future service-layer card's job, not this schema-only one's. This card guarantees immutability of whatever was written; it does not yet guarantee correctness of the write itself.
