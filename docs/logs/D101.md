## What happened

`apps/web` had no Next.js in it at all — just a leftover `@smb-os/contracts` wiring smoke test (D034) and D099's card-field scanner. This card adds a real Next.js 15 App Router scaffold (`next`, `react`, `react-dom` — none previously installed anywhere in the repo) with server-side session verification and role-gated routing, built around the actual `apps/api` auth surface that already exists (`apps/api/src/app.ts`, native `AuthProvider` per ADR-002): a single opaque, httpOnly, `Secure`, `SameSite=Strict` `session` cookie, verified via `GET /auth/me`.

Auth logic is three small, independently tested modules under `apps/web/src/auth/`: `access.ts` (`evaluateAccess` — pure default-deny decision: no session → redirect `/login`; session present but role not in the route's required set → redirect `/403`; otherwise allow), `session.ts` (`fetchSession` — forwards the incoming request's raw `Cookie` header to `apps/api`'s `GET /auth/me`, never reads/decodes the token itself), and `routeRules.ts` (which path prefixes require which `MerchantRole`s — `/dashboard/admin` requires `OWNER`/`ADMIN`, plain `/dashboard` requires only an authenticated session). `src/middleware.ts` wires these together against Next's request pipeline (`matcher: ["/dashboard/:path*"]`).

Wrote failing tests first for every one of these (`access.test.ts`, `session.test.ts`, `routeRules.test.ts`, `middleware.test.ts` — the last imports and calls the actual exported `middleware` function against a real `NextRequest`, not a hand-rolled stand-in), confirmed each failed for the expected reason (missing module) before writing the implementation, then confirmed green. Pages added: `/` (public), `/login` (client component posting credentials straight to `apps/api`, `credentials: "include"`, never touching the token itself), `/dashboard`, `/dashboard/admin`, `/403`.

Adding `next` pulled in a vulnerable transitive `postcss@8.4.31` (two high-severity advisories, GHSA-6g55-p6wh-862q and GHSA-r28c-9q8g-f849) that broke `packages/config`'s real `pnpm audit`/pre-push-hook tests — fixed with a `pnpm-workspace.yaml` override pinning `postcss: "^8.5.18"` across the workspace; `pnpm audit --audit-level=high` is clean again (3 remaining moderate advisories, below the gate's threshold).

`apps/web`'s tsconfig needed its own `moduleResolution: "bundler"` / `jsx: "preserve"` override (the shared `NodeNext` base conflicts with both Next's webpack resolution of relative imports and JSX) — this is scoped to `apps/web` only, every other package is untouched. `package.json`'s `build`/`dev` scripts now point at `next build`/`next dev` instead of the old bare `tsc`; the stale `dist/` output and `main` field (nothing ever imported `@smb-os/web` as a library) were removed. `turbo.json`'s `build` task output list gained `.next/**` alongside the existing `dist/**`.

## Security check answer

**"Tokens in memory + httpOnly refresh cookie, never localStorage."** The card's phrasing describes the generic access-token-in-memory / refresh-token-in-cookie split; the repo's actual, more recent authority is [ADR-002](../adr/ADR-002-authentication-provider.md), which deliberately supersedes that pattern with a single opaque, server-revocable session token — no JWT, no refresh token at all, because a JWT "invites the how-do-we-revoke-it problem." What this card actually implements is stricter than the card's own phrasing in one respect and equivalent in the part that matters: `apps/web` never holds the token in *any* JavaScript-reachable memory, client or server. `src/auth/session.ts`'s `fetchSession` forwards the browser's raw `Cookie` header straight through to `apps/api`'s `GET /auth/me` on every request and returns only the resolved identity (`userId`/`email`/`roles`) — the token value itself is never parsed, stored in a variable that outlives the request, or sent to the browser in any HTML/JSON payload. The login page (`src/app/login/page.tsx`) posts credentials directly to `apps/api` with `credentials: "include"`; the `Set-Cookie` response header (httpOnly, `Secure`, `SameSite=Strict`, per `apps/api/src/app.ts:252-258`) is handled entirely by the browser's cookie jar — this page's own JavaScript never sees the token. `localStorage`/`sessionStorage` are not used anywhere in this app. Net effect: zero token exposure to any JS context (browser or server component), re-verified against the API on every protected request rather than cached — a stronger property than "in memory," which is still technically JS-readable within its own execution context.
