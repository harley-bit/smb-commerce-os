## What happened

New `packages/db/src/jobs/DepositAutoReleaseJob.ts` — the deposit-side complement to `HoldExpirySweeper` (D062), implementing `docs/design/05`'s "Hold expiry and the sweeper" rule: "A scheduled job releases holds whose rental has completed with no claim filed, before expiry. Never let a hold silently expire on a customer's card; release it deliberately and notify." Where `HoldExpirySweeper` reacts to a *reservation* hold expiring before fulfillment, this job reacts to a rental actually finishing — signaled by a `CHECKIN` condition report existing for the order line (`docs/design/03`, D075) — with no damage claim ever filed against that order line (D076's `damage_claims`, any state, since even a resolved claim means a claim was on file).

`releaseCompletedDepositsSqlite(conn, onReleased?)` selects every `AUTHORIZED` deposit authorization whose order line has a `CHECKIN` condition report and zero rows in `damage_claims`, and moves each through `DepositAuthorizationRepository`'s same `RELEASED` transition path (via a direct, `state = 'AUTHORIZED'`-guarded `UPDATE`, matching `HoldExpirySweeper`'s batch-update shape) inside a single `BEGIN IMMEDIATE` transaction, so a second concurrent run serializes behind the first and then finds nothing left in `AUTHORIZED` state — idempotent under real concurrency, same discipline as the D062 sweeper. `releaseCompletedDepositsPg` is the PostgreSQL twin, using `SELECT ... FOR UPDATE SKIP LOCKED` so two concurrent runs never contend for the same row.

This card's deliverable — "customer notified" — is an injected `DepositReleaseCustomerNotifier` callback (default no-op), same shape as `DamageClaimCustomerNotifier` (D076) and `FutureReservationCancelledNotifier` (D069), fired once per deposit actually released (not once per sweep tick, since here every fire is meaningful — a real dollar amount moving off a real card) with the released deposit's id, order line, amount, and currency.

Wrote the failing test first (`DepositAutoReleaseJob.test.ts`, 5 cases, confirmed failing on `Cannot find module` before the job file existed): a deposit whose rental hasn't checked in yet is left untouched; a deposit whose rental checked in with no claim is released and the notifier fires exactly once with the right payload; a deposit with a damage claim on file (even though the rental checked in) is left untouched; a second run after release is a no-op with no re-notification; and a deposit already `CAPTURED` (not `AUTHORIZED`) is left untouched even when the rental completed cleanly with no claim, since the state machine's terminal-state rule (D077) still governs — this job only ever acts on `AUTHORIZED` rows.

## Acceptance criteria check

- "Hold released before expiry" — **Met.** The job releases as soon as a deposit becomes eligible (rental checked in, no claim filed) rather than waiting for `expires_at`; run on a schedule well ahead of any realistic authorization window, it never lets an eligible hold ride out to expiry.
- "Customer notified" — **Met.** `onReleased` fires once per released deposit with enough detail (id, order line, amount, currency) for a real delivery channel to compose a notification; verified by test that it fires exactly once per release and not on a no-op re-run.

## Security check answer

**"Never let a hold silently lapse on a customer's card."** This job is the deliberate-release half of that guarantee: instead of waiting for the payment provider's authorization window to lapse on its own (D079's 30-day ceiling, D077's `EXPIRE` transition), it actively finds every deposit that no longer needs to be held — rental checked in, no claim on file — and releases it, with a notifier that fires on every real release so the customer is told, not left to notice a silent hold disappear from their statement. The "silently" part is enforced structurally, not just by convention: `onReleased` fires from inside the same function that performs the release, driven off the actual set of rows the transaction just updated, so a release can't happen without the notifier being invoked for it. What is **not yet closed**: like D078/D079, there is still no real delivery-channel implementation behind the notifier (default no-op) and no scheduler actually invoking this job on an interval yet — both are infrastructure/wiring work for a later card, the same gap `HoldExpirySweeper` (D062) has carried since it was built. The `EXPIRE` path (a deposit that genuinely does ride out to its provider window with an unresolved claim situation) is deliberately untouched by this job — that's D077's state machine's job, not this one's.
