## What happened

Second Phase 5 card. Two pieces, both behind ports so no concrete Stripe SDK is depended on anywhere: `computeApplicationFeeSplit` (`packages/domain/src/payments/applicationFeeSplit.ts`) is pure domain math — splits a server-computed order `Money` total into a platform `applicationFee` and `merchantProceeds` at a caller-supplied basis-point take rate, rounding the fee and deriving proceeds by subtraction so the two pieces always sum back to the total exactly (no rate is hardcoded in domain code — that's a business decision outside this card's scope, so the rate is an explicit input every caller must supply). `PaymentIntentProvider` (`packages/domain/src/payments/PaymentIntentProvider.ts`) is the same seam shape as D087's `ConnectAccountProvider`. `SimulatedPaymentIntentProvider` (`packages/db/src/payments/SimulatedPaymentIntentProvider.ts`) is the only implementation, same "native/simulated now, real provider later" precedent as D087/D010/D073 — no live Stripe account is provisioned. `CheckoutPaymentService.createCheckoutIntent` (`packages/db/src/services/CheckoutPaymentService.ts`) is the card's actual deliverable: given a tenant context and an order id, it reads the order's server-recomputed `totalMinor`/`currency` from `OrderRepository` (the same total `CartService`, D0xx, maintains on every cart mutation), computes the split, and calls the provider with the full amount and the fee carved out for the platform, destined at a caller-supplied connected-account id. No merchant → connected-account mapping is persisted yet (D087/D088's known open gap), so `connectedAccountId` stays a caller input for now — unchanged scope, not this card's job to close.

## Acceptance criteria check

- **Split lands correctly on a test transaction** — Met. `CheckoutPaymentService.test.ts`'s `"D089 acceptance criteria: the application-fee split lands correctly on a test transaction"` test checks out a $100.00 cart at a 2.5% (250 bps) take rate and confirms the service reports back `applicationFeeAmountMinor: 250` / `merchantProceedsMinor: 9750`, and separately that the `SimulatedPaymentIntentProvider` actually recorded that same split on the created PaymentIntent (`provider.getRecordedIntent`) — not just that the service claimed it. `applicationFeeSplit.test.ts` additionally proves the split never loses or gains a minor unit to rounding (999 minor units at 250 bps: fee rounds to 25, proceeds 974, sum still 999) and rejects an out-of-range or non-integer take rate.

## Security check answer

**Amounts computed server-side only — met by construction.** `CreateCheckoutIntentInput` carries no amount field at all, so a conforming caller cannot supply one; `createCheckoutIntent` reads the charge amount exclusively from `OrderRepository.findById(ctx, orderId).totalMinor` — the same server-recomputed total `CartService` maintains from scratch on every line mutation (D0xx), never trusting a stored or incoming value. The `"computes the amount from the server-recorded order total, not a client-supplied amount"` test proves this directly: it casts a tampered input carrying `amountMinor: 1` past the type system (the same "raw/untyped payload with extra keys" attack `CartService.test.ts` exercises) and confirms the resulting PaymentIntent is still created for the real `$100.00` order total, not the injected `$0.01`. The fee split itself is pure domain math run against that same server value, so no amount in the created PaymentIntent — charge or fee — ever originates from caller input.
