## What happened

Built order confirmation end to end: a new pure-domain `buildOrderReceipt` (`packages/domain/src/payments/orderReceipt.ts`) assembles an `OrderReceipt` — itemized line items (mode, quantity, unit price, line total, and each line's own deposit hold or `null`) plus the order's own server-recomputed `subtotalMinor`/`taxMinor`/`totalMinor` and a summed `depositHoldsTotalMinor` — entirely from `OrderRepository`'s `Order`/`OrderLine` records, never from client input. New `OrderConfirmationService.confirmOrder` (`packages/db`) wraps that with the "emailed receipt" deliverable: an injectable `ReceiptEmailNotifier` (same optional, default-no-op callback shape as every other notifier in this codebase — D069/D076/D094/D120) fires once, with the same receipt, whenever the order has a `contactEmail` on file (D128's `CheckoutDetailsService.submitDetails`); it stays silent when there's none yet. New unauthenticated, self-rate-limited HTTP route `POST /v1/m/{slug}/checkout/{orderId}/confirmation` (`apps/api/src/routes/orderConfirmation.ts`), same posture as D130's payment route — including its current lack of a `customerUserId` ownership check, since no storefront customer session exists yet for any Phase 7 checkout route. Wired into `buildApp` via a new injectable `onReceiptEmail` option (default no-op). New web page `OrderConfirmationView.tsx`, routed at `/m/[slug]/checkout/confirmation?orderId=...` (`page.tsx`, same query-string-carried-`orderId` posture as D130's `page.tsx` — `CartService` still has no HTTP route, D126's unchanged open gap), renders every line item with its own quantity/unit price/line total, a deposit-hold line per rental line that has one, and a "Deposit holds (not charged)" summary distinct from "Total charged" — this card's acceptance criterion made visible, not just present in the API payload. `PaymentView.tsx`'s success state now links to this page.

## Acceptance criteria check

**"Receipt itemizes charges and any deposit hold"** — Met. `buildOrderReceipt`'s 5 unit tests prove every line is itemized (quantity/unit price/line total) and that deposit holds are summed correctly across zero, one, and multiple rental lines, treating a zero `depositMinor` the same as no deposit (`null`, not `0`). `OrderConfirmationService.test.ts`'s first case proves the same end-to-end against real `OrderRepository` rows (a mixed PRODUCT + RENTAL order: 2 line items, the rental line's `depositHoldMinor` is 20000, `depositHoldsTotalMinor` is 20000). `apps/api/test/orderConfirmation.test.ts`'s first case proves it again over real HTTP (201, `lineItems.length === 1`, correct `totalMinor`). `OrderConfirmationView.test.tsx`'s first case proves the itemization and the deposit-hold total are both actually rendered on the page, not just present in JSON the UI never surfaces.

## Security check answer

**"No card details in the receipt"** — By construction, not by filtering: `OrderRepository`'s `Order`/`OrderLine` types (the only inputs `buildOrderReceipt` ever reads) carry catalog and money fields only — id, currency, mode, quantity, prices, deposit, dates — no card number, CVC, or expiry has ever been read or stored anywhere in this codebase (`docs/design/07`'s "card data never touches our servers", already structurally enforced since D089's `CheckoutPaymentService` never accepted one either). There is therefore no field on `OrderReceipt` a caller could populate with card data even by mistake. Verified at three layers, not just asserted: `OrderConfirmationService.test.ts`'s security-check case asserts `JSON.stringify(receipt)` never matches `/card|cvc|pan|expiry/i`; `orderConfirmation.test.ts`'s first case asserts the same over the real HTTP response body; `OrderConfirmationView.test.tsx`'s security-check case asserts the rendered page has zero `<input>` elements and no card-shaped text anywhere in its `textContent`. `pageCardFieldGuard.test.ts`'s repo-wide scan (D099) also covers both new `apps/web` files as part of its normal full-tree sweep.
