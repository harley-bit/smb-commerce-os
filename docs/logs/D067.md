## Security check answer

"The invariant no competitor implements": most off-the-shelf rental/POS software treats rental inventory and sale inventory as separate systems (or separate SKUs) that don't cross-check each other in real time, so a unit checked out to a renter can still get rung up as a sale at the register if a staff member scans its barcode — a real, common failure mode in dual product/rental shops. This card closes that gap at the domain-invariant level: `ProductSaleService` now consults the *same* reservation ledger the rental booking path writes to, at the moment of sale, using the identical blocking-state predicate (`CONFIRMED`/`IN_USE`/unexpired `HELD`) the concurrency-safe reservation write path (D050/D054) already enforces — so there is exactly one source of truth for "is this unit currently spoken for," not a second, driftable copy. The check is best-effort against races with a *concurrent* reservation write (it reads outside `ProductSaleService`'s own transaction and the sale's stock decrement has its own separate guard), which is an honest, narrower promise than the reservation path's own `BEGIN IMMEDIATE` serialization — flagged in `IMPROVEMENTS.md` as a gap to close if it ever needs the same hard concurrency guarantee I3's sibling invariant (D068, sold unit cannot be reserved) will need on the other side of this pair.
