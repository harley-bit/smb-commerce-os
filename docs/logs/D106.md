## What happened

`packages/db`/`packages/contracts` already had a full PRODUCT-mode-locked listing service (D032) and a mode-conditional-validated variant service (D033), but no HTTP route ever exposed variant create/list, and `apps/web` had no editor UI at all — this card closed both gaps. New `apps/api/src/routes/variants.ts` (`registerVariantRoutes`, wired into `app.ts` alongside the existing listing routes): `GET /listings/:listingId/variants` and `POST /listings/:listingId/variants`, both behind `catalog:view`/`catalog:manage` respectively, mirroring `./listings.ts`'s `requireAction`/lazy-migration pattern exactly. The POST route never trusts a client-supplied `mode` or `listingId` on the variant body — it looks up the parent listing first (404 if missing or cross-tenant) and forces both fields from that listing's own row before running `@smb-os/contracts`'s `createVariantInputSchema`, so a caller cannot attach a variant to a different listing or smuggle a mode-forbidden field (e.g. a RENTAL `depositMinor`) past validation by lying about `mode`. New `apps/web/src/app/dashboard/catalog/ProductEditor.tsx` (client component) is the actual "listing editor" deliverable: a form for name/slug/description plus a repeatable variant-row editor (sku/name/price/currency), which on save POSTs the listing then each variant, then re-fetches both from the server (`GET /listings/:id`, `GET /listings/:id/variants`) and renders the read-back result — proving persistence, not just optimistic client state. `apps/web/src/app/dashboard/catalog/new/page.tsx` mirrors D105's `Suspense`/`?merchantId=` page shape; `CatalogView.tsx` gained a "New product" link into it. Wrote failing tests first at both layers: `apps/api/test/variants.test.ts` (11 cases, red — every request 404'd before the route existed) covering the full RBAC matrix, the 400/404 paths, and the client-supplied-mode-smuggling rejection; `ProductEditor.test.tsx` (3 cases, red — unresolved import before the component existed) covering the full save-then-render-back flow, client-side rejection of an incomplete form with zero fetches, and a surfaced server rejection. Hit and fixed a real build-breaking bug while wiring the client form: importing any *value* (not just a type) from `@smb-os/contracts`'s barrel (`index.ts`) forces Next's client webpack bundle to load `variant.ts`, which validates money through `@smb-os/domain`'s `Money.of`, and that package's own barrel unconditionally pulls in `node:crypto` (for `generateUuidV7`) as a module-graph side effect — confirmed live via a real `next build` failure (`UnhandledSchemeError: node:crypto`) before the fix. Fixed by never importing a *value* from `@smb-os/contracts` inside `ProductEditor.tsx` (only `type Listing`/`type Variant`, fully erased at build) and instead defining two small local Zod schemas (`listingDraftSchema`/`variantDraftSchema`) that mirror the contracts package's structural field rules without depending on `@smb-os/domain`. Added `zod` as a direct `apps/web` dependency (previously only reachable transitively through `@smb-os/contracts`) at the same pinned version contracts already uses.

## Security check answer

"Server-side validation mirrors client Zod schema" — answered on both sides of that phrase. Server-side: `POST /listings` and `POST /listings/:listingId/variants` both parse the request body with `@smb-os/contracts`'s real `createListingInputSchema`/`createVariantInputSchema` (unchanged from D034/D038 for listings; now wired for variants by this card), and `ListingService`/`VariantService` re-run their own field/price/mode checks on top — a client bypassing this UI entirely and posting straight to the API still gets full server-side validation, since none of it lives only in the browser. Client-side: `ProductEditor.tsx`'s `listingDraftSchema`/`variantDraftSchema` are Zod schemas that mirror the contract schemas' structural rules (required name/slug/sku/variant-name, integer price, non-empty currency) closely enough to give the merchant fast, honest feedback — but are deliberately *not* the literal same schema objects, because importing any value from `@smb-os/contracts` in a "use client" bundle transitively pulls in `@smb-os/domain`'s `node:crypto` dependency and breaks the build (see "What happened" above). This is a real, load-bearing distinction from D105's `CatalogView`, which only ever imports `@smb-os/contracts` *types* (fully erased, no bundling impact) — the first time this repo's web app has had to write actual submission logic against a mutating endpoint, not just render a `GET` response.
