## Security check answer

**Q: Frozen lockfile prevents dependency substitution — how?**
A: The workflow's only install step is `pnpm install --frozen-lockfile`, which fails the job outright if `pnpm-lock.yaml` doesn't exactly match `package.json` across all workspaces, instead of silently re-resolving and rewriting it. That means CI can never install different (e.g. maliciously substituted or newer/compromised) package versions than what's actually committed to the lockfile — any drift between manifest and lockfile is a hard CI failure, not a silent upgrade. Verified locally by running `pnpm install --frozen-lockfile` against the current lockfile, which succeeded exactly because the two are in sync.
