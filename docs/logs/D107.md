## Security check answer

**Resource assignment respects tenant scope.** `ResourceService.assignListingResource` looks up both `input.listingId` (via `ListingRepository.findById`) and `input.resourceId` (via `ResourceRepository.findById`) under the *acting* `TenantContext` before `ListingResourceRepository.assign` is ever called; either lookup returning `undefined` (because the id belongs to another merchant, or doesn't exist) throws `CrossTenantResourceAssignmentError` and no row is written. This is deliberately a second check on top of the repository's own `merchantId`-scoping guarantee: `ListingResourceRepository.assign` alone would happily record a join row under the caller's own `merchantId` even if the *referenced* `listingId`/`resourceId` belonged to a different tenant — the repository's `merchantId` guarantee says nothing about what the referenced ids point to. Proven at both layers: `ResourceService.test.ts`'s two cross-tenant tests (merchant B's resource assigned to merchant A's listing, and the reverse) both assert `CrossTenantResourceAssignmentError` and zero rows written; `apps/api/test/resources.test.ts`'s "404s assigning a resource id that belongs to another merchant" test proves the same thing at the HTTP layer over a single shared connection, where `otherResourceId` genuinely exists — this is a real cross-tenant IDOR attempt, not merely an unknown id, and the route correctly answers `404` (not `403` or `200`), the same generic-not-found posture `variants.ts`/`bookings.ts` already established for cross-tenant reads.
