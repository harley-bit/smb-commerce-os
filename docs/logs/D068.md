## What happened

Investigated invariant I4 ("sold unit cannot be reserved"), the mirror of D067's I3. Before writing anything, probed the current behavior directly against `RentalReservationService.createRentalReservation`: transitioned a variant's only unit(s) to `SOLD` (then separately to `RETIRED`) via `InventoryUnitService.transitionStatus`, then attempted a reservation. Both cases already threw `NoAvailableUnitError` with zero production changes, because D066's candidate-building step (`RentalReservationService.ts`) filters `listByVariant(...)` down to `unit.status === "AVAILABLE"` before ever calling `selectUnitForAllocation` — a SOLD or RETIRED unit was never a candidate to begin with, and `InventoryUnitService`'s state machine (D0xx) already makes both statuses terminal (`ALLOWED_TRANSITIONS.SOLD`/`RETIRED` are empty sets), so there's no path back to `AVAILABLE` to race against. Given the invariant was already structurally enforced, the "smallest change" here is a permanent regression test rather than new logic: added a parameterized `it.each(["SOLD", "RETIRED"])` block to `RentalReservationService.test.ts` under "invariant I4 — sold or retired unit cannot be reserved (D068)", and added one clarifying comment at the filter site in `RentalReservationService.ts` naming which card and invariant that line satisfies. Logged the finding (no code change needed beyond tests/comment) in `IMPROVEMENTS.md` for traceability, cross-referencing D067's existing concurrency caveat.

## Security check answer

"Prevents renting an asset the merchant no longer owns": once a unit is `SOLD`, the merchant has transferred title to a customer — it is legally no longer the merchant's asset to rent out. `RETIRED` units (write-offs, end-of-life) are similarly not available for use. `InventoryUnitService`'s status-transition state machine already makes both statuses terminal (no transition out of `SOLD` or `RETIRED` back to `AVAILABLE` exists), and `RentalReservationService` only ever allocates from the `AVAILABLE` subset of a variant's units — so a sold or retired unit can never re-enter circulation as a rentable candidate, closing the same class of "system doesn't cross-check itself" gap D067 closed for the sale side. As with D067, this is a sequential-read guarantee (unit status is read before the reservation's own guarded write), not a hard concurrency guarantee against a sale committing in the same instant as a reservation attempt for the same unit — tracked as a shared, not-yet-required gap in `IMPROVEMENTS.md`.
