## What happened

Added a new `checkout_consents` table (both SQLite and PostgreSQL dialects, migrations `0020_left_living_lightning.sql` / `0022_reflective_photon.sql`) plus `contact_name`/`contact_email`/`contact_phone` columns on `orders`. New `CheckoutDetailsService.submitDetails` is the single entry point: it requires a non-empty `termsVersion`, confirms the order exists under the acting tenant, confirms the acting customer actually owns the order (`NotOrderOwnerError` otherwise — no consenting on someone else's cart), confirms the order is still `CART`/`PENDING_PAYMENT` (`OrderNotCheckoutableError` otherwise), writes the contact details onto the order, records the consent row, and mirrors the same consent (terms version + timestamp) into the merchant's existing hash-chained `audit_log` via `AuditLogRepository.append`. No API route was wired in this card — like `CartService`/`CheckoutPaymentService` before it, this is the service-layer piece; nothing in the storefront yet calls a checkout endpoint at all (`BUILD_STATE.md`'s D127 note on this gap still applies), so wiring a route is left for whichever later card in this epic adds the storefront checkout flow itself. 6 new service tests + 2 new repository tests (cross-tenant isolation evidence for `record`/`findLatestForOrder`) + 2 new `OrderRepository.updateContactDetails` isolation tests, all passing; full local gate green (`InventoryMovementRepository.concurrency.test.ts`'s N=50 worker-thread test failed once under full-suite parallel load and passed cleanly standalone — a pre-existing load-sensitive flake unrelated to this card's change, not touched).

## Security check answer

"Repudiation defence: consent is evidenced" — every consent is written twice: once to `checkout_consents` (queryable, one row per consent event, never updated/deleted) and once mirrored into the merchant's hash-chained `audit_log` (`action: "checkout.consent_recorded"`, `afterJson` carries `termsVersion`/`consentedAt`). `checkout_consents` alone would still be a plain row a privileged actor with DB access could quietly edit or delete after the fact; the audit-log mirror is what makes a later "the customer never agreed to this" claim checkable against a chain that would visibly break if the entry were altered — proven in `CheckoutDetailsService.test.ts`'s "mirrors the consent into the tamper-evident audit log" test, which asserts the entry exists with a real `prevHash`/`rowHash`.
