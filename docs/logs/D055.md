## What happened

Added `packages/domain/src/reservations/reservationStateMachine.ts`, a pure domain state machine for `docs/design/03`'s reservation `state` column (`HELD | CONFIRMED | IN_USE | COMPLETED | CANCELLED | EXPIRED`). `applyReservationEvent(currentState, event)` is the single entry point for moving between states — it looks the event up in a per-state transition table and throws `IllegalReservationTransitionError` for anything not explicitly listed, which covers both genuinely illegal transitions (e.g. `HELD` receiving a `RETURNED` event) and every event on a terminal state, since `COMPLETED`/`CANCELLED`/`EXPIRED` have empty transition entries. Also exports `BLOCKING_RESERVATION_STATES` (`HELD`/`CONFIRMED`/`IN_USE`, matching `docs/design/03` line 130) and `TERMINAL_RESERVATION_STATES` as named, reusable constants rather than ad hoc set literals. No I/O, no tenant parameter — same shape as D046–D049's other pure-domain reservation math. `packages/db`'s `ReservationRepository.ts` still declares its own structurally-identical `ReservationState` string union (pre-dates this card); not unified here since doing so would touch already-shipped repository code beyond what this card's acceptance criteria required — flagged in `IMPROVEMENTS.md` alongside the existing `MerchantRole`/`MerchantUserRole` duplicate from D037.

## Acceptance criteria check

- **Illegal transitions rejected:** met. Every state/event pair not in the transition table throws `IllegalReservationTransitionError` (carrying the offending `fromState`/`event` for callers), proven directly for `HELD`→`RETURNED`, `CONFIRMED`→`EXPIRE`, and `IN_USE`→`CONFIRM`.
- **Terminal states enforced:** met. `COMPLETED`, `CANCELLED`, and `EXPIRED` each have an empty transition entry; a parameterized test loop proves all three reject all seven event types (21 cases), so no code path can move a reservation out of a terminal state.

## Security check answer

"State is never written directly — events drive transitions." `applyReservationEvent` is the only exported function that produces a next state, and it only accepts a `ReservationEvent` (a `{ type: ... }` discriminated union), never a bare target state string — there is no exported setter or `setState`-shaped function a caller could use to assign `state` directly, so any transition necessarily goes through an explicit, named event and the guard table above. This module is domain-only (no I/O): the actual persistence of a transitioned state into the `reservations` table, and wiring real triggers (payment confirmation → `CONFIRM`, the hold sweeper → `EXPIRE`, fulfillment events → `PICKED_UP`/`RETURNED`/`NO_SHOW`/`COMPLETED`/`CANCELLED`) to call this function, is a future service-layer card's job — not yet built, so today nothing in the codebase persists a reservation state transition at all (D050–D054 only ever create new `HELD`/blocking rows, never transition an existing one). Flagging that honestly rather than assuming it.
