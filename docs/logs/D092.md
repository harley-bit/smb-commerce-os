## What happened

Added the idempotency anchor for raw webhook deliveries themselves, distinct from `PaymentRepository`'s existing `(provider, provider_ref)` anchor (D088) for payment records — a raw Stripe event id (`evt_...`) is not the same key as a payment/intent id, and no handler exists yet to match an event to an order/merchant, so this couldn't reuse the `payments` table. New `webhook_events` table (`packages/db/src/schema/sqlite.ts`, `pg.ts`; migrations `0015_careless_diamondback.sql` / `0017_motionless_power_man.sql`) with a `(provider, event_id)` unique index, plus `WebhookEventRepository.record`/`findByProviderEventId` (`packages/db/src/repositories/WebhookEventRepository.ts`) — a plain, non-tenant-scoped repository (same reasoning as `UserRepository`: a raw event hasn't been matched to a merchant at the point it's persisted). `record` relies on the unique index rather than check-then-insert, translating a constraint violation into a new `DuplicateWebhookEventError` (`packages/domain/src/payments/DuplicateWebhookEventError.ts`) rather than racing concurrent deliveries.

`POST /webhooks/stripe` (`apps/api/src/routes/webhooks.ts`) now runs this after signature verification: pulls `id` off the verified event body, calls `webhookEvents.record(...)` with the raw body as `payloadJson`, and on `DuplicateWebhookEventError` logs an info line and answers `200 { received: true, duplicate: true }` without any further processing — the first delivery's effects (once handler logic exists in D093+) never run twice. A verified event missing an `id` field is rejected with 400 rather than crashing. `registerWebhookRoutes` now takes the app's `Connection` (wired from `app.ts`, same connection instance already shared with `./listings.ts`/`./bookings.ts`) and lazily runs migrations on first call, matching those routes' existing pattern.

Still no deposit-release or order-matching logic here — that's D094/D095, per D091's log note. This card's scope is exactly the calendar's "Dedupe by provider event id; persist raw event."

## Security check answer

**"Providers retry aggressively."** Stripe's own webhook delivery guarantee is at-least-once with retries on anything short of a fast `2xx`, so every handler this route will ever grow (deposit capture/release, D094/D095) must be safe to receive the same event more than once. The `(provider, event_id)` unique index is the actual enforcement mechanism, not a check-then-insert — a second concurrent delivery of the same event racing the first one still can't both win, because the second `INSERT` hits the constraint and is caught, not a separate `SELECT` that could pass before the first insert commits. A duplicate is answered `200` immediately (not a 4xx/5xx that would make Stripe retry it as if it failed), so a retried-but-already-processed event stops retrying without ever reaching the not-yet-built processing logic a second time.
