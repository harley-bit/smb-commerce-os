## Security check answer

**"Hash chain makes tampering detectable, not merely difficult."** Answered directly by `verifyChain.test.ts`'s design: `row_hash` binds a row to its own content, and the *next* row's `prev_hash` independently commits to that same value. An attacker who edits a row's content and even recomputes that row's own `row_hash` to hide the edit (`verifyChain.test.ts`'s "resealed" test) still can't make the chain verify, because the following row's `prev_hash` was captured before the edit and no longer matches — the only way to hide a single-row edit is to rewrite every row after it, which is the property `docs/design/07` calls out as the reason to choose a hash chain over write-only permissions. One honest limitation, not concealed: `append`'s read-then-write (fetch the latest `seq`/`rowHash`, then insert) is not lock-protected, so concurrent audit writes for the *same* merchant could race and compute against a stale `prevHash`/`seq` — flagged in the repository's own doc comment as a known gap, not a G3-class concurrency guarantee like reservations. No caller in this repository yet calls `AuditLogRepository.append` from application code (that wiring — role changes, deposit captures, inventory adjustments — is future cards' job per `docs/design/03`'s "mandatory for" list), so this gap has no live exposure today.
