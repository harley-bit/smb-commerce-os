## What happened

Implemented the future-reservation sale override in `ProductSaleService.sellProduct`. Added `ReservationRepository.findFutureBlocking(ctx, subjectType, subjectId, asOf)` — a sibling of D067's `isSubjectCurrentlyBlocked`, but returning every still-blocking (CONFIRMED/IN_USE/unexpired HELD) reservation whose `startsAt` is *after* `asOf`, i.e. bookings that haven't started yet and would otherwise be silently orphaned by the sale. When a sale specifies a `unitId` and `findFutureBlocking` returns any rows, `sellProduct` now throws `FutureReservationsExistError` (the "warn" half of the deliverable) unless the caller passes `overrideFutureReservations: true`, and further requires a non-empty `overrideReason` string (throwing `MissingOverrideReasonError` otherwise) — this is what makes the security check's "audit-logged with actor and reason" possible, since a reason is mandatory input, not an afterthought. On a valid override, the sale proceeds as normal (stock decrement + unit transitioned to SOLD), then each future reservation is cancelled via a new `ReservationRepository.cancel(ctx, id, releasedAt)` method (routes through `applyReservationEvent`'s `CANCELLED` transition, so an already-terminal reservation throws `IllegalReservationTransitionError` instead of silently no-opping), an injected `FutureReservationCancelledNotifier(reservation, reason)` callback fires once per cancelled reservation (same optional, default-no-op shape as the native auth provider's `ResetTokenNotifier` — no delivery channel exists yet, this is the seam a later card wires an actual notification service into), and a dedicated `inventory.sale.override_future_reservations` audit-log entry is appended with `actorId` and the reason/cancelled-reservation-ids in `afterJson`, kept separate from the plain `inventory.sale` entry so the override reason is never buried inside a routine sale record.

## Acceptance criteria check

- "Override path cancels affected bookings and notifies customers" — **Met.** New test `ProductSaleService.test.ts` > "cancels future reservations, notifies, and audit-logs actor + reason when overridden (D069)": sells a unit with one future CONFIRMED reservation using `overrideFutureReservations: true` + a reason, then asserts the reservation's state is `CANCELLED`, the injected notifier was called exactly once with that reservation's id and the reason, and the unit transitioned to `SOLD`. A second test, "rejects selling a unit with a future reservation unless overridden (D069)", proves the warn path: no override → `FutureReservationsExistError`, zero writes (stock unchanged, unit still `AVAILABLE`, reservation still `CONFIRMED`, notifier never called).

## Security check answer

"Override is audit-logged with actor and reason": `sellProduct` refuses to treat an override as valid unless `overrideReason` is a non-empty string (`MissingOverrideReasonError` otherwise), so a reason cannot be omitted at the call site. The override writes its own `audit_log` row (action `inventory.sale.override_future_reservations`, `actorId: input.actorUserId`, `afterJson` carrying the reason and the exact list of cancelled reservation ids) through the same hash-chained, tenant-scoped `AuditLogRepository.append` every other privileged action in this codebase uses — verified directly in the new test by parsing that entry's `afterJson` and asserting both the actor and the reason match what was passed in. This is a real, non-bypassable trail of "who decided to sell out from under a future booking and why," which is exactly the kind of unilateral operator decision that competitor rental software tends to let happen silently (or blocks entirely with no override path at all, pushing staff to work around the system instead of through it).
