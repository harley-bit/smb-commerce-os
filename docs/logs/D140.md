## Security check answer

"Public endpoints rate-limited per device" — **Already true, no change needed by this card.** `apps/api/src/routes/publicStorefront.ts` (which this screen's two new fetches are the mobile client of — no new API endpoints were added) already wraps `GET /v1/m/:slug` and `GET /v1/m/:slug/listings` in a `SlidingWindowRateLimiter` keyed `ip:${request.ip}` (30 req/60s default), independent of any session/auth state — a mobile device hitting these endpoints is rate-limited exactly the same way the web storefront's requests already are, since it's the same unauthenticated route, not a device-aware exemption. Verified live in this run: `apps/api/test/publicStorefront.test.ts`'s three "rate limits repeated requests from the same IP" cases (`GET /v1/m/:slug`, `/listings`, `/listings/:listingSlug`, plus the availability route's tighter 3/60s budget) are part of the 377 passing `@smb-os/api` tests in this session's `pnpm test` run. This mobile screen adds no new public endpoint and no bypass of that limiter.
