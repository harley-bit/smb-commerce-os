## What happened

`docs/design/06`'s "Webhook handling" note — "Providers retry aggressively and deliver out of order. Idempotency and ordering-tolerance are requirements, not refinements" — split idempotency to D092 and left ordering-tolerance to this card. New pure domain function `applyOrderedEvent` (`packages/domain/src/payments/orderedEventApplication.ts`, same shape as `depositStateMachine.ts`): folds a `{ status, occurredAt }` provider event onto a `{ status, lastAppliedAt }` state, and is a no-op if the incoming event's own `occurredAt` (the provider's event timestamp, e.g. Stripe's `created`) is not strictly newer than what's already applied. Folding a set of events through this function in any arrival order therefore converges on the same final state regardless of delivery order — proven directly by an exhaustive-permutation test over a 3-event sequence, plus explicit "later event arrives first" and "duplicate/identical timestamp" cases.

Wired into persistence: `payments` gained a new `last_event_at` column (`packages/db/src/schema/sqlite.ts`/`pg.ts`, migrations `0016_jittery_trauma.sql`/`0018_faithful_surge.sql`) recording the provider-event timestamp of whichever event last actually updated `status` — distinct from `webhook_events.received_at` (D092's raw-arrival record) and from `payments.created_at` (the payment row's own creation time). `PaymentRepository.applyProviderEvent(ctx, id, { status, occurredAt })` reads the current row, delegates the decision to `applyOrderedEvent`, and only issues an `UPDATE` when the resolved state actually differs — an out-of-order/stale event changes nothing, not even a redundant write.

No route wires this yet: there is still no handler that maps a parsed Stripe event to a specific `payments` row (that requires matching `event.data.object.id` to `provider_ref`, which is real business logic belonging to D094/D095's deposit-capture/release work, per D091/D092's carried notes). This card's scope, per the calendar ("Out-of-order handling; async processing; fast 200"), is proving the ordering-tolerance mechanism itself is correct — `POST /webhooks/stripe` already returns a fast 200 after verify+dedupe (D091/D092), with no slow synchronous work in the request path, so "fast 200" was already satisfied; nothing changed in `apps/api/src/routes/webhooks.ts` this card.

## Security check answer

**"Ordering is not guaranteed by the provider."** Stripe explicitly does not guarantee webhook delivery order — retries, multiple endpoints, and infrastructure-level fanout can deliver an earlier event after a later one. If a handler simply overwrote `payments.status` with whatever event arrived most recently, a late-arriving stale event (e.g., a delayed `payment_intent.processing` retry landing after `payment_intent.succeeded` already updated the row) could silently regress a payment's state — the exact "deposit/payment state corruption" risk `docs/design/14`'s risk register calls out. `applyProviderEvent` closes this by keying the decision on the event's own `occurredAt` timestamp rather than call/arrival order: an event whose timestamp is not strictly newer than `last_event_at` is discarded as a no-op before any write, so a provider's out-of-order retry can never move state backward, and the row's final status is always whichever event is chronologically last — not whichever event happened to arrive last.
