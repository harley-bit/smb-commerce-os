## Security check answer

**Staff resources contain personal data — classified in `docs/design/08`.** A `resources` row with `kind = "STAFF"` carries a staff member's name under `docs/design/08`'s "Merchant staff" classification (Confidential — name/email/role), not the stricter customer-identity "Personal data" class the reservation/condition-media rules apply to. This card's handling is proportionate to that classification: standard tenant-scoped access control plus the same OWNER/ADMIN authorization gate `ListingService`/`VariantService` already use for catalog management — every mutating `ResourceService` method (create/update/archive a resource, or its rules/exceptions) asserts `assertCanManageCatalog` before touching the repository, so a `STAFF`- or `READ_ONLY`-role caller can never write or read-back-and-modify another staff member's resource record via this service. No stricter GDPR-style erasure/retention path is implied by this classification, and none was built here — that would be over-scoping the card's actual security check, which named the "Confidential" row, not the "Personal data" one. Reads are intentionally left unrestricted by role (any authenticated tenant member can `list`/`find`), matching `ListingRepository`'s existing read posture — availability data (who's working when) is operationally useful to `STAFF`, not something to lock behind ADMIN.
