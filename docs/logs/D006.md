## What happened

Installed `gitleaks` (8.30.1, via `brew install gitleaks` — no real npm package exists under that name) and wired it into three places: a repo-local pre-commit hook, the CI pipeline, and a regression test. Wrote the test first — `packages/config/test/secret-scanning.test.ts` — which (1) shells out to the real `gitleaks` binary against a scratch directory containing a planted fake AWS key and asserts a non-zero exit plus a "leaks found" message, (2) asserts a clean scratch directory exits 0, and (3) greps `.github/workflows/ci.yml` for a gitleaks install step ordered before `pnpm test`, a `gitleaks detect ... --exit-code 1` step, and `fetch-depth: 0` on checkout (needed for gitleaks to see full history, not just the shallow default). All 5 assertions failed before the workflow was updated (confirmed: `-1` not `> -1`, missing `fetch-depth`, etc.) and passed once `.github/workflows/ci.yml` was edited — a real red-to-green cycle, not a test written to match the implementation.

Implementation: `.githooks/pre-commit` runs `gitleaks protect --staged --redact --exit-code 1` (refusing to commit if the binary is missing, rather than silently skipping the scan), wired up automatically via a new root `package.json` `"prepare": "git config core.hooksPath .githooks"` script (same mechanism Husky uses, no extra dependency). `.github/workflows/ci.yml` now installs gitleaks straight from the GitHub release tarball (pinned to v8.30.1, matching the locally-installed version) before the test step, and adds a final "Secret scan" step running `gitleaks detect --source . --redact --exit-code 1` over the whole repo (full history, via `fetch-depth: 0`). Ran `gitleaks detect --source . -v` against the current repo (with and without `--no-git`) before wiring this in — zero pre-existing findings, so this doesn't retroactively break the build on old commits.

## Security check answer

**Q: Any finding fails build; rotation procedure documented?**
A: Yes on both counts. Every gitleaks invocation wired in here uses `--exit-code 1` (already gitleaks' default, made explicit): the pre-commit hook aborts the commit on any match, and the CI "Secret scan" step fails the job on any match — there's no threshold or allowlist that lets a real finding through quietly. Rotation procedure: if gitleaks ever does catch a real secret (in CI, since it scans full history — a `git log` rewrite doesn't erase it from a already-pushed remote), the procedure is (1) treat the leaked credential as compromised the moment it's found, regardless of whether it was ever used, (2) rotate/revoke it at the source (the provider or service that issued it — Stripe, cloud IAM, DB credentials, etc.) before doing anything else, (3) only then remove it from history if required, and (4) note the incident in `docs/BUILD_STATE.md`'s carried-over notes so it isn't lost. No secrets exist in this repo yet (Phase 0, no live integrations), so this is process documentation for future phases, not a response to an actual incident.
