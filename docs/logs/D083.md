## What happened

New `packages/domain/src/rentals/lateFeePolicy.ts`, implementing step 5 of `docs/design/05`'s "Late returns" section: "Apply late fees per the variant's policy, on merchant confirmation." Pure domain math, no I/O — same shape as `authorizationWindow.ts` (D079) and `depositStateMachine.ts` (D077). A `LateFeePolicy` is `{ perDayMinor, graceHours?, capMinor? }`. `computeLateFeeProposal(policy, overdueHours)` prices an overdue return — grace hours subtracted first, remaining hours rounded up to full billable days, multiplied by the per-day rate, capped if a cap is configured — and can *only* ever return a `PROPOSED` fee; there is no code path in this module from a policy straight to a charge. `confirmLateFee(proposal, confirmedByUserId, confirmedAt)` is the only function that can turn a `PROPOSED` proposal into an `APPLIED` fee, and it requires a real, non-empty `confirmedByUserId` — the merchant taking the action — as an explicit argument; it also refuses to run against anything that isn't currently `PROPOSED`, so a fee can't be double-confirmed.

This makes "no automatic charge without merchant action" a structural property, not just a documented convention: pricing (`computeLateFeeProposal`) and applying (`confirmLateFee`) are two separate functions, and the second one cannot be reached without a caller supplying an actual merchant user id. Wrote the failing test first (`lateFeePolicy.test.ts`, 11 cases, confirmed failing on `Cannot find module` before the file existed): zero fee within the grace window; one day's charge for a partial day past grace; multiple full+partial days rounding up; amount capped at the policy's `capMinor`; uncapped when no cap is configured; negative overdue duration rejected; invalid policy (non-positive `perDayMinor`) rejected with `InvalidLateFeePolicyError`; a bare proposal never carries a `confirmedByUserId` (proves it isn't a charge); `confirmLateFee` with a real user id produces `APPLIED` with the same amount; `confirmLateFee` with an empty user id is rejected; and confirming an already-`APPLIED` fee a second time is rejected — the direct proof of "no double charge." Exported from `packages/domain`'s `index.ts`.

## Acceptance criteria check

- "No automatic charge without merchant action" — **Met.** `computeLateFeeProposal` (the only function invoked from overdue-detection data) never produces anything beyond `PROPOSED`. The only function capable of producing an `APPLIED` fee, `confirmLateFee`, requires a real `confirmedByUserId` argument and throws `InvalidLateFeeConfirmationError` if it's empty or if the proposal is already applied — proven directly by the "refuses to confirm without a merchant user id" and "refuses to confirm an already-applied fee" tests.

## Security check answer

**"Automatic charging without review invites chargebacks."** Addressed structurally: this module has no function that both computes a fee amount and marks it chargeable in the same call — `computeLateFeeProposal` only prices, `confirmLateFee` only applies, and the latter is unreachable without an explicit actor id representing the merchant reviewing the case. There is no default, no timer, and no code path anywhere in this module that reaches `APPLIED` on its own; a caller (a future service/route layer) has to make a deliberate call with a real user id after a human has looked at the case. What is **not yet closed**: no repository/service/route wires this to a real overdue reservation or persists an applied fee anywhere yet (same domain-only scope split as D077's deposit state machine before D078 added persistence) — a future card would need to connect `LateReturnDetector`'s overdue hours to a stored `LateFeePolicy` per variant (no such column exists in `listing_variants` yet; `attributes_json` is the closest fit today, undecided) and record `confirmLateFee`'s result as an actual capture/charge, likely against the deposit authorization the same way `DamageClaimService` does. No follow-on card in the current sequence (`D084`–`D086`) is scoped to close this gap, so it stays open until surfaced explicitly.
