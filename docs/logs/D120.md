## What happened

Closed the tracked gap `MerchantUserRepository.ts`'s own file comment had flagged since D030: role assignment existed (OWNER-only, enforced by a runtime check) but had no audit trail, no owner notification, and no HTTP route. New `packages/db/src/services/MerchantUserService.ts` wraps `MerchantUserRepository`, asserting `packages/domain`'s `roles:assign` action (OWNER-only per the RBAC matrix) before doing anything, then on a successful `assignRole` call: writes an `AuditLogRepository.append` entry (`merchant_user.role_changed`, `entityId` = the target user, `beforeJson`/`afterJson` capturing the previous and new role) and invokes an injectable `RoleChangeNotifier` callback once per current OWNER of the merchant — same optional, default-no-op injected-callback shape as `DamageClaimCustomerNotifier`/`FutureReservationCancelledNotifier` used throughout this codebase, no opinion on delivery channel. A rejected (non-OWNER) attempt writes nothing and notifies no one — proven directly. New `apps/api/src/routes/team.ts` (`GET /team`, `POST /team/role-assignments`) is the first HTTP surface either the repository or the new service ever had, wired into `app.ts` via a new `onRoleChanged` option (defaults to a no-op, same pattern as every other payments/notification seam in this codebase). New `apps/web/src/app/dashboard/settings/TeamSettingsView.tsx` (routed at `/dashboard/settings`) lists the merchant's team and lets an OWNER change a member's role via a `<select>`, re-fetching the server's own read-back after a successful change rather than optimistically updating local state — the same "what's on screen is what was persisted (and therefore audit-logged)" pattern every prior Phase 6 view uses. Wrote failing tests first throughout: `MerchantUserService.test.ts` (6 cases, confirmed red on `Cannot find module` before the service existed), `apps/api/test/team.test.ts` (8 cases, hit a real `500` before rebuilding `@smb-os/domain`/`@smb-os/db` — same stale-`dist/` freshness snag D104/D108 already documented — then went green), `TeamSettingsView.test.tsx` (5 cases).

## Security check answer

"Role changes audit-logged and notified to owners" — **met**. Every successful `POST /team/role-assignments` call goes through `MerchantUserService.assignRole`, which (1) writes an `AuditLogRepository` entry — part of the same hash-chained, tenant-scoped `audit_log` table every other sensitive write in this codebase appends to — before returning, and (2) calls the injected `onRoleChanged` notifier once for every user currently holding `OWNER` on that merchant (not just the acting owner), after the audit entry and the underlying role write are both durable. A rejected (non-OWNER-attempted) change writes no audit entry and fires no notification — proven by `MerchantUserService.test.ts`'s "does not notify anyone, and writes no audit entry, when the assignment is rejected" and `team.test.ts`'s "a non-OWNER cannot assign a role — 403, no write, no audit entry".
