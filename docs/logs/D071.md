## What happened

Closed the gap D070's log flagged: fulfillment events now actually drive reservation state, still exclusively through `packages/domain`'s `applyReservationEvent` state machine. `ReservationRepository.confirm`/`.cancel` were refactored to share one private `transition(ctx, id, eventType, releasedAt?)` helper instead of each hand-rolling the same read/apply-event/write sequence, and two new siblings were added on top of that same helper: `markPickedUp` (CONFIRMED → IN_USE, via the `PICKED_UP` event) and `markReturned` (IN_USE → COMPLETED, via `RETURNED`, stamping `releasedAt` the same way `cancel` does). There is still exactly one place in the repository that ever writes the `state` column — every public method names one `ReservationEventType`, none of them accept a state value directly. A new `findByOrderLineId` lookup resolves the reservation (if any) linked to an order line, since `reservations.orderLineId` was a real schema column (D026) that no caller had ever actually populated on write.

`FulfillmentEventService` (D070) now takes a third constructor argument, `ReservationRepository`, and `recordPickup`/`recordReturn` look up the order line's linked reservation and call `markPickedUp`/`markReturned` on it *before* recording the fulfillment event — not every order line has one (e.g. a product-sale line), in which case the lookup returning `undefined` is a no-op, not an error. Running the transition before the event write means an illegal transition (a RETURNED event on a reservation that was never picked up) throws `IllegalReservationTransitionError` and the event is never appended — the append-only log never records an operation that didn't actually happen.

Test-first throughout: 8 new `ReservationRepository.test.ts` cases (`markPickedUp`/`markReturned` happy path, illegal-transition rejection, tenant-scoping for both, plus `findByOrderLineId` happy path / not-found / tenant-scoping) confirmed failing (`repo.markPickedUp is not a function`, etc.) before the methods existed, and 4 new `FulfillmentEventService.test.ts` cases (pickup transitions CONFIRMED→IN_USE, return transitions IN_USE→COMPLETED with `releasedAt` stamped, an out-of-order return is rejected and neither the reservation nor the event log moves, and a reservation-less order line's pickup is a state no-op that still records the event) confirmed failing (`ReservationRepository` not wired into the constructor) before the wiring existed.

## Acceptance criteria check

- **Direct state write is rejected by the service layer** — Met. There is no method on `ReservationRepository` that accepts a `state` value and writes it verbatim; the only path is the private `transition()` helper, reached exclusively through `confirm`/`cancel`/`markPickedUp`/`markReturned`, each of which names one fixed `ReservationEventType` and delegates the legality question to `applyReservationEvent`. Proven concretely by `ReservationRepository.test.ts`'s "throws IllegalReservationTransitionError when the reservation is not CONFIRMED" (`markPickedUp`) and "an out-of-order RETURNED event cannot skip IN_USE" (`markReturned`) cases, and end-to-end by `FulfillmentEventService.test.ts`'s "the service layer cannot skip straight to a direct state write" case, which asserts both the reservation's state and the event log are unchanged after a rejected call.

## Security check answer

**Single path for state change simplifies audit.** Every reservation state transition in the codebase — `HELD→CONFIRMED`, `HELD/CONFIRMED→CANCELLED`, `HELD→EXPIRED` (via the sweeper), and now `CONFIRMED→IN_USE`/`IN_USE→COMPLETED` — funnels through the same two things: `packages/domain`'s `applyReservationEvent` (the one function that knows which transitions are legal) and, inside `ReservationRepository`, the one private `transition()` helper that reads the current row, calls it, and writes back the result inside a `BEGIN IMMEDIATE` transaction. An auditor reviewing "how can a reservation's state ever change" has exactly one method and one state machine to read, not five independent read-modify-write call sites that could each drift out of sync with the transition rules or with each other. `FulfillmentEventService` reinforces this at the next layer up: it never touches `state` itself, it only ever calls `markPickedUp`/`markReturned` and lets the repository enforce legality — so the fulfillment event log and the reservation state machine can never silently disagree about whether a pickup or return actually happened.
