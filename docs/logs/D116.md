## What happened

Most of a rental checkout's domain/db layer already existed from Phase 4 (D070–D075): the reservation state machine's `PICKED_UP` transition, `ConditionReportRepository`/`ConditionMediaRepository`, `FulfillmentEventService.recordPickup` (already refuses pickup with `MissingCheckoutConditionReportError` when no `CHECKOUT` report is on file — this card's acceptance criterion), and `ConditionMediaUploadService`/`ConditionMediaConfirmService` (signed-upload-grant + hash-verified confirm, D073/D074). What was missing was the write path for the CHECKOUT report itself and any HTTP/dashboard surface at all — `ConditionReportService` only had `recordCheckin` (D075, for D117's future check-in flow); nothing in `apps/api` or `apps/web` referenced any of these services. So D116's actual scope was: (1) add `ConditionReportService.recordCheckout`, gated on `bookings:manage` and validated against the caller's own `orderLineId` (via `OrderRepository.findLineById`, throwing the existing `OrderLineNotFoundError` on a cross-tenant or nonexistent line — tenant isolation, Gate G1); (2) a new `apps/api/src/routes/fulfillment.ts` exposing that plus the media upload/confirm pair and `POST /order-lines/:orderLineId/pickup` over `FulfillmentEventService`, wired into `buildApp` (`apps/api/src/app.ts`) with a new `HmacMediaUploadProvider` instance (same "native now, real provider later" placeholder pattern as the Stripe webhook secret); (3) a new dashboard flow, `apps/web/src/app/dashboard/rentals/RentalCheckoutView.tsx` + `[orderLineId]/checkout/page.tsx`, gating its own "Complete checkout" button on a report already being on file, with a "Check out" cross-link added from `OrderDetailView.tsx` on RENTAL lines. Wrote the failing domain test first (`ConditionReportService.test.ts`'s three new `recordCheckout` cases — confirmed `service.recordCheckout is not a function` / a missing `OrderLineNotFoundError` throw before implementing), then updated the Gate G4 rental-lifecycle E2E test (`gate-g4.e2e.test.ts`) to route its CHECKOUT baseline through the new service method instead of writing the repository directly. New route and UI tests followed the same test-first order.

## Acceptance criteria check

- "Cannot complete checkout without a report" — **Met**, at two layers. Server-side: `POST /order-lines/:orderLineId/pickup` maps the pre-existing `MissingCheckoutConditionReportError` to `409 Conflict` — proven by `apps/api/test/fulfillment.test.ts`'s dedicated acceptance-criterion test (pickup attempted with no CHECKOUT report on file, asserts 409) and by the updated Gate G4 E2E test (pickup refused, reservation/event log both untouched, until a CHECKOUT report exists). UI-side: `RentalCheckoutView`'s "Complete checkout" button is `disabled` until `recordCheckout`'s response sets local report state — proven by `RentalCheckoutView.test.tsx`.

## Security check answer

"Photograph the asset, not the customer — guidance in UI" — there is nothing to enforce server-side here: `condition_reports`/`condition_media`'s schema (D072/D074) has no field that could hold a person's identity, only `orderLineId`/`inventoryUnitId`, so a "customer photo" isn't a distinguishable case the server could reject even if it wanted to. This is answered entirely in the UI: `RentalCheckoutView`'s photo-capture section renders "Photograph the rented item itself — its condition, any existing wear or damage. Never photograph the customer or any other person." directly above the file input, and `RentalCheckoutView.test.tsx` asserts that copy renders.
