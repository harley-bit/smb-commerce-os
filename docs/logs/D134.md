## What happened

Built the four transactional notification types the card names — confirmation, reminder, return-due, deposit release — as pure content builders plus the two missing real trigger points. New `@smb-os/domain` module `notifications/transactionalNotifications.ts` exports `buildOrderConfirmationNotification`/`buildReservationReminderNotification`/`buildReturnDueNotification`/`buildDepositReleasedNotification`, each a pure `{ type, subject, body }` function with no I/O, mirroring `depositDisclosure.ts`'s shape. Of the four trigger points, two already existed as injectable notifier callbacks from earlier cards — D131's `OrderConfirmationService.notifyReceiptEmail` (confirmation) and D080's `releaseCompletedDepositsSqlite`/`Pg`'s `onReleased` (deposit release) — so this card wires the new content builders into those existing hooks rather than duplicating them. The other two had no trigger point at all: new `packages/db/src/jobs/ReservationReminderJob.ts` (`detectUpcomingReservationsSqlite`/`Pg`) detects `CONFIRMED` reservations whose `starts_at` falls within a caller-supplied window ahead of `asOf` — the pre-checkout-time complement to D081's `LateReturnDetector`, which only ever looks at reservations already in progress or overdue; new `packages/db/src/jobs/ReturnDueJob.ts` (`detectReturnsDueSqlite`/`Pg`) detects `IN_USE` reservations whose `ends_at` falls within a window ahead but hasn't passed yet — the not-yet-overdue complement to that same `LateReturnDetector`, which only fires once `ends_at < asOf`. Both new jobs are read-only and re-derived on every call, same posture as `LateReturnDetector`/`DepositAutoReleaseJob` — no persisted "already reminded" flag, `windowHours` is the caller's own open judgment call (same category as D119's `DEPOSIT_EXPIRING_SOON_WINDOW_HOURS`). New `packages/db/src/services/transactionalNotifications.e2e.test.ts` proves all four fire end-to-end, each through its real trigger point (`OrderConfirmationService`, the two new jobs, `releaseCompletedDepositsSqlite`), carrying content actually built by the new domain module — this is the card's acceptance-criterion evidence.

## Acceptance criteria check

**"All four delivered in test"** — Met. `packages/domain/src/notifications/transactionalNotifications.test.ts` proves each builder's content in isolation (4 cases). `packages/db/src/services/transactionalNotifications.e2e.test.ts` proves each of the four actually fires through its real trigger point end-to-end (4 cases, one per type): order confirmation via `OrderConfirmationService.confirmOrder`, reservation reminder via `detectUpcomingReservationsSqlite` against a `CONFIRMED` reservation inside the window, return-due via `detectReturnsDueSqlite` against an `IN_USE` reservation inside the window, deposit release via `releaseCompletedDepositsSqlite` against a checked-in, unclaimed deposit. `ReservationReminderJob.test.ts` (6 cases) and `ReturnDueJob.test.ts` (5 cases) separately prove each new job's own boundary conditions (window edges, wrong state, re-derivation on repeat calls) — same test shape as `LateReturnDetector.test.ts`.

## Security check answer

**"Transactional only — no marketing, so no consent management"** — Met by construction, documented directly in the new domain module's file comment: every one of the four notifications is triggered either by the customer's own action (placing an order → confirmation) or by the state of their own order/reservation/deposit (an upcoming start, an approaching due date, a hold release) — never by a merchant-initiated campaign — so none of it is marketing communication requiring opt-in/opt-out consent tracking. This is a different category from `checkout_consents`/`deposit_consents` (D128/D129), which exist to evidence terms/deposit-disclosure agreement, not marketing consent — no new consent table or opt-out mechanism was added or is needed for this card.
