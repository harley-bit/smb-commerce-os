## What happened

`@smb-os/contracts`'s `createVariantInputSchema` and `apps/api/src/routes/variants.ts` (D033/D063/D106) already accepted a RENTAL variant's `ratePeriod`/`depositMinor`/`bufferMinutes`, and the lower-level services that make those fields *do* something (`RentalReservationService.createRentalReservation`, D066; `DepositAuthorizationService.placeHold`, D094) already existed unmodified — this card's actual gap, mirroring D106/D107's precedent exactly, was that no merchant-facing editor UI existed to configure a RENTAL listing at all. New `apps/web/src/app/dashboard/catalog/RentalEditor.tsx` (routed at `/dashboard/catalog/new-rental`, linked from `CatalogView.tsx`) saves a RENTAL listing plus a rate/deposit/buffer variant through the exact same `POST /listings`/`POST /listings/:listingId/variants` routes D106/D107's editors call, then renders the server's own read-back — mirroring `ProductEditor.tsx`/`ServiceEditor.tsx`'s save-then-render-back pattern. It also carries a UI-only "typical rental term (days)" field (never sent to the server — no such column exists on `listing_variants`, a term belongs to a specific booking's start/end, not the catalog item) that shows an advisory warning when the entered term exceeds the 30-day product ceiling, duplicating `packages/domain/src/payments/authorizationWindow.ts`'s `AUTHORIZATION_WINDOW_CEILING_DAYS` locally rather than importing it — same reason `ProductEditor.tsx`/`ServiceEditor.tsx` keep local structural mirrors of `@smb-os/contracts`'s schemas: any value import from `@smb-os/domain` pulls in `node:crypto` as a module-graph side effect that a "use client" bundle can't include (`docs/logs/D106.md`).

The acceptance criterion ("deposit and buffer persist and apply") is proven end-to-end, not just asserted, in new `apps/api/test/rentals.test.ts`: a RENTAL variant is saved through the editor's own HTTP routes with `ratePeriod`/`depositMinor`/`bufferMinutes`, read back to confirm exact persistence, then that *same read-back variant* drives (a) a real `RentalReservationService.createRentalReservation` call whose resulting reservation's `endsAt` is expanded by exactly the variant's own `bufferMinutes` (D064's `expandIntervalForBuffer`, buffer "applies"), and (b) a real `DepositAuthorizationService.placeHold` call against an order line carrying that same variant's `depositMinor`, whose resulting hold amount matches exactly (D094's provider seam, deposit "applies") — proving the persisted configuration is what a real reservation/hold actually uses, not a hardcoded number in either service. `DepositAuthorizationRepository` was previously built (D078) but never exported from `@smb-os/db`'s public index — a real oversight, not something this card invented — so it was added there to let this end-to-end test compose the deposit path from `apps/api` the same way `resources.test.ts` composes `BookingService`.

Wrote the failing tests first: `apps/api/test/rentals.test.ts` (4 cases) initially failed with `TypeError: DepositAuthorizationRepository is not a constructor` — confirmed red because `@smb-os/db`'s compiled `dist/` output (which `apps/api` resolves against, same freshness snag D104 hit) predated the new index export — before rebuilding `@smb-os/domain`/`@smb-os/db` and going green. `RentalEditor.test.tsx` (4 cases) covers the save-then-render-back flow (including the deposit/buffer values appearing in the rendered read-back), an incomplete-form client-side rejection with zero fetches, and both the warning-shown and warning-absent states of the window-ceiling check.

## Security check answer

**Window-ceiling warning shown for long rental terms.** `docs/design/05`'s C4 rule ("surface this in the merchant UI when a rental period is configured beyond the [30-day authorization] ceiling — do not discover it in production") is answered by `RentalEditor.tsx`'s "typical rental term (days)" field: entering a value above `AUTHORIZATION_WINDOW_CEILING_DAYS` (30, mirroring `packages/domain/src/payments/authorizationWindow.ts`'s hard product ceiling) renders a `role="status"` banner with the same guidance text `RentalTermExceedsAuthorizationWindowError` carries server-side ("...use a captured deposit up front or a contractual claims process instead"), while a term at or under the ceiling shows nothing — proven by `RentalEditor.test.tsx`'s two dedicated cases (45 days → warning present; 14 days → warning absent). This is an advisory UI echo, not the enforcement itself: the real, throwing gate is `recordProviderAuthorizationWindow`/`validateRentalTermAgainstAuthorizationWindow` (`packages/domain`, D094's `SimulatedDepositHoldProvider` already calls the former), which this card does not modify and which cannot be bypassed by skipping this form.
