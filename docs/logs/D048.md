## What happened

Added `packages/domain/src/utils/freeIntervals.ts`: `computeFreeIntervals(baseIntervals, exceptions, blockingReservations)`, implementing the card's deliverable literally — "rules minus exceptions minus blocking reservations" — by composing D047's `applyAvailabilityExceptions` (base rule intervals with BLACKOUT/EXTRA overlaid) with a subtraction pass over `blockingReservations`. Refactored `availabilityExceptions.ts` to extract and export `subtractIntervals(intervals, subtrahends)` (folds the existing `subtractOne` over a list of subtrahends, order-independent since set difference against a union of removals doesn't depend on removal order) so both `applyAvailabilityExceptions`'s BLACKOUT handling and this card's blocking-reservation subtraction share one interval-removal implementation instead of two. `blockingReservations` is typed as bare `Interval[]`, not reservation rows — per `docs/design/05`, only `HELD`/`CONFIRMED`/`IN_USE` reservations (and only non-expired holds) block, so the caller (a future `AvailabilityService`) is responsible for pre-filtering reservations to that set and mapping each to its effective `[starts_at, ends_at)` (including any `buffer_minutes` expansion already applied at write time) before calling this pure function. Every blocking interval is validated via `makeInterval` up front, same malformed-input guard as D047. Wrote the failing test first (`freeIntervals.test.ts`, confirmed `Cannot find module` before implementing), 10 cases: no-op with nothing to subtract, exceptions-only (matches D047 exactly), full/partial/non-overlapping reservation subtraction, multiple reservations subtracted regardless of list order, a reservation trimming an EXTRA-added opening (not just the base rule), a combined BLACKOUT+EXTRA+reservation scenario, malformed-reservation rejection, and a direct assertion that a free-interval result object carries only `start`/`end` keys — no reservation identity. Exported from `packages/domain/src/index.ts`.

## Acceptance criteria check

- "Computed free set matches fixtures across edge cases" — **Met.** `freeIntervals.test.ts`'s 10 cases cover the composition's edge cases specifically (not just re-testing D047's exception logic or plain interval subtraction in isolation): a reservation blocking an EXTRA-added window, multiple reservations in reverse order, and a three-way BLACKOUT/EXTRA/reservation combination, on top of the base full/partial/non-overlap/malformed-input cases already proven for interval subtraction.

## Security check answer

"Never returns who booked a slot — free/busy only" — enforced by the function's type signature, not by a runtime redaction step: `blockingReservations` is `readonly Interval[]` (just `{ start, end }`), so `computeFreeIntervals` never receives a reservation id, customer id, or any other booking metadata in the first place — there is nothing to leak. The output is likewise always `Interval[]`. The last test case in `freeIntervals.test.ts` asserts this directly: every interval in the result has exactly `start`/`end` keys. The real security-relevant obligation this pushes onto the caller — stripping reservation identity down to a bare interval before calling this function, and correctly filtering to only `HELD`/`CONFIRMED`/`IN_USE` (and non-expired holds) per `docs/design/05` — is not yet exercised by a real repository/service call, since no `AvailabilityService` exists yet; that wiring is a future card's job, flagged honestly rather than assumed done here.
