## What happened

A PRODUCT line gets `expiresAt: null` — stock isn't time-bound, so there's nothing to count down. `selectCartLineStatuses(cart, now)` reuses `@smb-os/domain`'s existing `computeHoldCountdown` (D127) and is a pure function of its two arguments — no `Date.now()`, no storage read, no network call anywhere inside it — which is what makes "handled gracefully offline and online" true by construction: `CartScreen` ticks `now` every second via `setInterval` for the online/live case, but a cart re-opened after the device was offline for an hour renders the exact same `expired: true` state through the same code path, not a special offline branch. `App.tsx`'s `onBuy` (PRODUCT) and `onReserveRental` (RENTAL) now add a line to the cart and push the new `Cart` screen instead of going straight to `Checkout`; `onBook` (SERVICE) is unchanged, still pushing `Checkout` directly, because `ServiceDetailScreen`'s `onBook(interval: FreeInterval)` callback (D143) only carries a time interval, not a variant id or price — `PublicServiceDetail` exposes no price/variant data at all for a service listing, so there is nothing to build a priced cart line from without extending that contract, which is out of this card's scope.

## Acceptance criteria check

"Hold expiry handled gracefully offline and online" — met. `selectCartLineStatuses`/`computeHoldCountdown` are pure functions of `(cart, now)`; `cartStore.test.ts` proves the expired/active/no-hold states directly against fixed `now` values with no I/O involved, and `CartScreen.tsx` never performs a network call to compute or refresh the countdown — the "offline" and "online" cases are literally the same code path, not two implementations that could drift.

## Security check answer

"Idempotency keys on all creation calls" — every `CartLine` is issued a non-empty `idempotencyKey` (via injected `CartLineGenerators`, real implementation `expoCartLineGenerators` wrapping `expo-crypto`'s `Crypto.randomUUID()`) at the moment it's added to the cart, generated once and carried unchanged from then on — `cartStore.test.ts` asserts every line has a key and that two lines never collide. No line is ever added without one: `addLine` has no code path that skips key generation. This key is what a future checkout call forwards as `Idempotency-Key`/`idempotencyKey` (the same field `createServiceBookingInputSchema`, `packages/contracts/src/booking.ts`, already requires) — because it's minted at add time rather than at submit time, a retried submission reuses the same key instead of minting a fresh one, so a network retry can't produce a duplicate creation.
