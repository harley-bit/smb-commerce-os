## What happened

New `RefundProvider` port (`packages/domain/src/payments/RefundProvider.ts`), same seam shape as `PaymentIntentProvider`/`DepositHoldProvider` — `SimulatedRefundProvider` (`packages/db/src/payments/SimulatedRefundProvider.ts`) is the only implementation, no live Stripe account provisioned, with the same idempotency-key replay behavior as the other simulated providers. `RefundService.refundOrderLine` (`packages/db/src/services/RefundService.ts`) is the card deliverable: it reuses D084's `CancellationPolicySet`/`resolveCancellationPolicy`/`computeCancellationRefund` — the domain math that already keeps PRODUCT/SERVICE/RENTAL refund rules structurally separate via an exhaustive switch with no default — deriving `hoursBeforeStart` from the order line's own `startsAt` (0 for lines with none, i.e. products) and pricing the refund against the line's server-recorded `lineTotalMinor`, never a caller-supplied amount. It looks up the order's original succeeded `CHARGE` payment via a new `PaymentRepository.listByOrderId` (throwing `NoChargeToRefundError` if none exists), calls the provider, and writes a `REFUND` payment row — checking for an existing row by the provider's returned `refundId` first, so a replayed idempotency key doesn't hit `DuplicatePaymentReferenceError`. New `payments:refund` RBAC action (`packages/domain/src/auth/rbac.ts`) granted to `OWNER`/`ADMIN` only, not `STAFF`/`READ_ONLY` — `assertCan` is the first thing `refundOrderLine` calls. 8 new service tests (one per mode's tiered refund proving the policies are genuinely different for the same `hoursBeforeStart`, no-charge rejection, STAFF/READ_ONLY rejection with no payment row written, OWNER success, cross-tenant rejection, and idempotency replay not minting a second payment), 5 new `SimulatedRefundProvider` tests, 2 new `PaymentRepository.listByOrderId` tests, and RBAC matrix tests extended for the new action across all four roles.

## Acceptance criteria check

- "Product, service, and rental refund paths" — **Met.** `RefundService.refundOrderLine` works against order lines of all three `OrderLineMode` values, routed through `resolveCancellationPolicy` keyed on the line's own mode.
- "Each mode's policy applied correctly" — **Met.** Three tests use policies with deliberately different tier thresholds/percentages per mode and prove the same `hoursBeforeStart` input produces a different refund under SERVICE's policy (50%) than under RENTAL's policy (25%) — not just that some refund happens.

## Security check answer

**"Refund authority restricted by role."** `RefundService.refundOrderLine` calls `assertCan({ role: actingRole }, "payments:refund")` before touching any repository or the provider. The new `payments:refund` action is granted only to `OWNER` and `ADMIN` in `ROLE_ACTIONS` — `STAFF` (which already holds `bookings:manage` and handles the rest of the rental-return flow) and `READ_ONLY` are both rejected with `ForbiddenActionError`, proven end-to-end by a test that attempts a refund as each forbidden role and then confirms zero `REFUND` payment rows exist afterward — the rejection happens before any write, not just before the HTTP response.
