## What happened

Built offline-tolerant read caching for the mobile app: new `apps/mobile/src/offline/offlineAwareFetch.ts` exports `createOfflineAwareFetch`, a higher-order wrapper around the same `fetchFn: typeof fetch` seam every existing mobile `fetch*` module already takes as an injected dependency (`fetchMerchantHome.ts`, `fetchCatalogPage.ts`, `fetchProductDetail.ts`, etc. — see `docs/cards/D140.md` onward). For a `GET`, a successful response's body is cached by URL via an injected `KeyValueCache`; when the underlying `fetchFn` throws (this codebase's existing DI convention for a network failure), the wrapper replays the last cached body for that URL instead of propagating the error, and rethrows only if nothing has ever been cached for that URL. For every other method (`POST`/`PUT`/`PATCH`/`DELETE` — writes), the cache is never read or written in either direction, and a thrown network error is converted into a distinct `OfflineWriteError` rather than an ambiguous raw network error, so a write that can't reach the server fails immediately and identifiably instead of being queued, retried, or silently dropped. Because the wrapper is composed into `deps.fetchFn` at the DI root, none of the existing fetch modules need to change to become offline-tolerant.

## Acceptance criteria check

- "Cached reads work" — **Met.** `offlineAwareFetch.test.ts`'s second case does a successful `GET`, then a second `GET` where `fetchFn` throws a `TypeError` (simulated offline), and asserts the wrapper returns the first response's cached body/status instead of throwing.
- "writes fail clearly when offline" — **Met.** The fourth case asserts a `POST` whose underlying `fetchFn` throws rejects with `OfflineWriteError` specifically (not a raw/ambiguous error), and the fifth case asserts a write never touches the cache (`cache.set` not called) even when it succeeds — confirming no offline write queueing exists to accidentally trigger.

## Security check answer

"Offline writes explicitly out of scope (accepted risk)." Confirmed by construction: `createOfflineAwareFetch` has no code path that stores a failed write for later retry — a write's cache interaction is zero in both directions, and a network failure on a non-`GET` request is converted straight into a thrown `OfflineWriteError` with no queue, no local mutation, and no silent success. This is enforced by the fifth test case (`cache.set` not called for a write) and the fourth (write failure surfaces immediately as a typed, catchable error a screen can show to the customer rather than pretending the write succeeded).
