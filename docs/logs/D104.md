## What happened

Built the Connect onboarding UI end to end, which required closing D087/D088's carried-forward gap first: no merchant → connected-account mapping existed anywhere. Added a nullable `merchants.connect_account_id` column (both dialects, `migrations/sqlite/0018_productive_mikhail_rasputin.sql` / `migrations/pg/0020_special_edwin_jarvis.sql`) and threaded it through `MerchantRepository`'s existing `Merchant`/`UpdateMerchantInput` types — no new repository method needed, `update` already took an arbitrary patch. New `apps/api/src/routes/connect.ts` (`registerConnectRoutes`, wired into `buildApp` via a new `connectAccountProvider`/`webBaseUrl` option, defaulting to D087's `SimulatedConnectAccountProvider`): `POST /connect/onboarding` reads the merchant's own `businessCountry` (400 if D103's onboarding never completed the business address), calls D087's `ConnectOnboardingService.startOnboarding`, and persists the returned `accountId`; `GET /connect/status` reports `NOT_STARTED` when no account is on file yet, or the derived `ONBOARDING | ACTIVE | RESTRICTED` status (D087's `deriveConnectAccountStatus`) once one is. Both routes are gated by the existing `payouts:manage` RBAC action (OWNER-only, D097's precedent) rather than adding a new one — starting/checking Connect onboarding is a payouts concern. `apps/web/src/app/dashboard/payments/PaymentsView.tsx` is the actual UI deliverable: fetches status on mount scoped by `X-Merchant-Id`, renders a "Connect payouts" button when `NOT_STARTED`, a "Continue payouts setup" button while `ONBOARDING`/`RESTRICTED` (clicking either starts/resumes onboarding and redirects the browser to the hosted flow's URL), and a plain "Payouts are enabled" message with no action once `ACTIVE`. `page.tsx` wraps it in a `Suspense` boundary reading `merchantId` from the query string via `useSearchParams` (required by Next's static-export rules, confirmed by a real `next build`). D103's onboarding page now redirects to `/dashboard/payments?merchantId=...` instead of a bare `/dashboard`, so a brand-new merchant is walked straight into payouts setup.

Wrote the failing test first for both new layers: `apps/api/test/connect.test.ts` (5 cases) started red against the unregistered routes (404s), and a Vitest run before wiring `connectAccountProvider` into `BuildAppOptions` would have failed to type-check. `apps/web/src/app/dashboard/payments/PaymentsView.test.tsx` (5 cases) exercises the full state machine against a mocked `fetch`, including the acceptance-criterion case: after starting onboarding, calling the simulated provider's `simulateOnboardingCompleted` directly (the same test-only seam D087's own tests use — there is still no real Stripe account to complete a hosted form against) and re-fetching status returns `ACTIVE`/`chargesEnabled: true`/`payoutsEnabled: true`, which the component renders as "Payouts are enabled." One implementation snag: `apps/api` resolves `@smb-os/db`/`@smb-os/domain` through their published `dist/` output, not `src/` directly, so the new schema column and `MerchantRepository` types had to be rebuilt (`pnpm --filter @smb-os/domain build && pnpm --filter @smb-os/db build`) before the route test could see them — the first run failed with a raw `SqliteError: near "where": syntax error`, which turned out to be Drizzle's `UPDATE ... SET` clause silently going empty because the stale compiled schema had no `connect_account_id` column to map the patch onto.

## Security check answer

"No bank details stored by us" — structural, same shape as D094's "expires_at mandatory" answer: neither `apps/api`'s new route nor `apps/web`'s new page has any field, parameter, or column for an account/routing number, SSN, or other underwriting datum.
