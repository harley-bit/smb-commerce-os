## What happened

D089's `CheckoutPaymentService` (packages/db) has existed since Phase 5 but had never been given an HTTP route or any UI — every Phase 7 checkout card since D126 ("no storefront checkout endpoint exists at all yet") called this out as an open gap. D130 closes it for the payment step specifically. New API route `apps/api/src/routes/checkoutPayment.ts` — `POST /v1/m/{slug}/checkout/{orderId}/payment-intent` — is unauthenticated and self-rate-limited (same posture as `./publicStorefront.ts`, since a storefront customer has no staff session), resolves the merchant by slug, requires the merchant to have a `connectAccountId` on file (409 if not), and requires an `Idempotency-Key` header, then delegates straight to `CheckoutPaymentService.createCheckoutIntent`. Wired into `buildApp` via new injectable `paymentIntentProvider` (default `SimulatedPaymentIntentProvider`, same "native/simulated now, real provider later" precedent as every other payments seam in this codebase) and `checkoutTakeRateBasisPoints` (default 250bps — no commission rate has been finalized by `docs/design/15` yet, so this is a documented placeholder, not a silently invented business decision). `PaymentDeclinedError` is now exported from `@smb-os/db`'s public index (it wasn't before — no route had ever needed it) so the route can map it to a 402 carrying only the already-mapped generic customer message and `retryableWithSameMethod` flag, never the provider's raw decline code.

New web UI: `apps/web/src/app/m/[slug]/checkout/HostedCardField.tsx` is a mount-point stand-in for Stripe Elements' `<CardElement>` — a real integration would mount Stripe's own iframe here; this repo has no live Stripe.js dependency yet (same simulated posture as the API side), so it's a labelled `<div>`, never our own `<input>`. `PaymentView.tsx` orchestrates the flow: "Pay" stays disabled until the hosted field reports ready, then POSTs to the new endpoint with a fresh `Idempotency-Key` (via `crypto.randomUUID()`) and renders either a success message (amount charged) or, on a 402, the decline's generic message plus a retry hint — never a raw decline code. `page.tsx` routes this at `/m/[slug]/checkout?orderId=...` — `orderId` comes from the query string rather than a session-bound cart, since `CartService` itself still has no HTTP route (D126's open gap, unchanged by this card — out of scope).
