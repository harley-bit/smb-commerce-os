## Security check answer

"Deposit disclosed before any commitment" — **met**. There is no code path in `RentalDetailView` that reaches a "commitment" action (the "Reserve" button, itself only a client-side selection toggle — this codebase has no rental-line checkout endpoint yet, same tracked gap D108's log left open) without the deposit line having already rendered: the deposit paragraph is unconditional on `variant` alone, not on `startDate`/`endDate`/`available`, so it always precedes the Reserve button in both render order and the state machine (dates must be picked and found available *after* the deposit is already visible). Server-side, `depositMinor` is carried through `toPublicRentalVariant` (`apps/api/src/routes/publicStorefront.ts`) unconditionally from `VariantRepository`'s own value (never defaulted, never omitted) — a merchant who configured a deposit can't have it silently dropped from the public response, and one who didn't correctly renders "no deposit required" rather than a misleading blank. No unit id, unit count, or reservation identity is ever exposed by either new route — `rentalAvailabilityResponseSchema` is a bare boolean (`.strict()`-tested to reject an extra `unitId` field) and `publicRentalVariantSchema` carries no `unitsAvailable`/`unitsTotal` field (also `.strict()`-tested).
