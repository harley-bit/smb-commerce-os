## Acceptance criteria check

- "Query uses the index" — **Met.** `ReservationRepository.test.ts`'s last case runs `EXPLAIN QUERY PLAN` on `findBlocking`'s exact predicate and asserts the plan references `reservations_subject_interval_idx`.
- "Returns only HELD/CONFIRMED/IN_USE" — **Met.** The `COMPLETED`/`CANCELLED`/`EXPIRED` exclusion test and the expired-HELD test both confirm the returned set is exactly the blocking-state set, not the full state enum — and that "HELD" alone isn't sufficient without the expiry check (see security check below).

## Security check answer

"Blocking-state filter is security-relevant: expired holds must not block" — a `HELD` reservation's `state` column does not flip to `EXPIRED` until a separate sweeper process runs (not yet built as of this card); in between the hold's `expires_at` passing and the sweeper's next run, a naive `state IN ('HELD','CONFIRMED','IN_USE')` filter would still treat it as blocking, holding a slot indefinitely for a checkout the customer never completed — an availability-starvation bug, not just a display glitch. `findBlocking` closes this by taking an explicit `asOf` parameter and requiring `state = 'HELD' AND expires_at > asOf` in addition to state membership; `CONFIRMED`/`IN_USE` have no expiry and are unconditionally blocking. Two tests exercise this directly: a HELD row with `expiresAt` before `asOf` returns empty, and the same row with `asOf` before `expiresAt` returns the row — proving the boundary, not just one side of it.
