## What happened

Added `apps/web`'s first design-system layer. Design tokens live as CSS custom properties in `src/styles/tokens.css` (color, spacing, typography, radius, focus-ring), consumed by `src/styles/globals.css`, which is now imported once from `src/app/layout.tsx` — no inline `style` attributes anywhere in the new code, verified directly by tests. Two accessible base components: `Button` (`src/components/Button.tsx`, a real `<button type="button">` by default so it never accidentally submits a form) and `TextField` (`src/components/TextField.tsx`, label/input linked by a real `htmlFor`/`id` pair via `useId()` so two instances on one page never collide, with `aria-invalid`/`aria-describedby` exposing a validation error to assistive tech rather than color alone). `src/app/login/page.tsx` — the one real form in the app — was rewritten to use both, proving the components in a live accessible form rather than only in isolation. Wrote failing tests first for all new modules (`Button.test.tsx`, `TextField.test.tsx`, `csp.test.ts`, plus new middleware assertions), confirmed red, then implemented. Adding component tests required wiring `apps/web` for the first time with a real DOM test environment: `@testing-library/react`, `@testing-library/user-event`, `@testing-library/jest-dom`, `jsdom`, and `@vitejs/plugin-react` (pinned to `^4.7.0` — the installed `vite@6.4.3` in this workspace doesn't satisfy `@vitejs/plugin-react@6`'s `vite@^8` peer requirement, confirmed by a real `ERR_PACKAGE_PATH_NOT_EXPORTED` failure before downgrading), plus a `vitest.setup.ts` registering `@testing-library/jest-dom/vitest` matchers and `cleanup()` in `afterEach` (without it, a second component render in the same file collided with the first's leftover DOM). Keyboard navigation was verified for real, not simulated: `user.tab()` + `user.keyboard("{Enter}"/" ")` for `Button` (including a disabled-button-is-skipped-by-tab case), `user.tab()` + typed input for `TextField`, both via `@testing-library/user-event`.

For the security check, `middleware.ts` now sets a strict, nonce-based `Content-Security-Policy` header on every response (broadened its route matcher from `/dashboard/:path*` to everything except `_next` static assets and the favicon, so unprotected routes like `/login` get the header too), built by a new pure function `src/security/csp.ts:buildCspHeader(nonce)`. The nonce is generated fresh per request (`crypto.randomUUID()`) and forwarded two ways: as the response's CSP header (`script-src 'self' 'nonce-<n>' 'strict-dynamic'`) and as an `x-nonce` request header, which `app/layout.tsx` reads via `headers()` and applies as `<html nonce={nonce}>` — Next's documented strict-CSP pattern, letting the framework's own injected scripts inherit trust from the nonce'd root without needing `unsafe-inline`. `style-src 'self'` has no `unsafe-inline` either, which is why every new component uses CSS classes against `globals.css`, never a `style` prop — proven directly by a dedicated test on both `Button` and `TextField` asserting no `style` attribute is ever rendered. Verified live, not just in tests: ran `next build` (succeeds) and `next dev`, then `curl -sD -` against `/login` and confirmed the real response headers (`content-security-policy` with a live nonce, no `unsafe-inline` anywhere in the string) and real markup (`<label for="...">Email` correctly paired with the generated input id, `<button type="submit" class="btn btn--primary">` with no inline style).

## Security check answer

**"Output encoding by default; strict CSP, no unsafe-inline."** Output encoding: unchanged from React/Next's baseline — every new component renders through JSX (auto-escaped), nothing uses `dangerouslySetInnerHTML`. Strict CSP: `middleware.ts` now sets `Content-Security-Policy` on every response via `security/csp.ts:buildCspHeader`, restrictive on every directive (`default-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'none'`), with `script-src` trusting only `'self'` plus a fresh per-request nonce (`'strict-dynamic'` lets the framework's nonce-trusted scripts load their own child chunks) and `style-src 'self'` with nothing else — no `'unsafe-inline'` on any directive, checked by an explicit test (`csp.test.ts`) asserting the string never contains `unsafe-inline` or `unsafe-eval`, and confirmed against the real live response headers.
