## What happened

Built invariant I7 ("a rental cannot reach `IN_USE` without a `CHECKOUT` condition report", `docs/design/03`): a new `ConditionReportRepository` (`packages/db/src/repositories/ConditionReportRepository.ts`), the first repository/service-layer code on top of D029's `condition_reports` schema table, with `create` (append a report, CHECKOUT or CHECKIN), `listByOrderLine`, and `hasCheckoutReport` (the read the guard actually uses). `FulfillmentEventService.recordPickup` (D070/D071) now takes `ConditionReportRepository` as a fourth constructor argument; when an order line's `PICKED_UP` event would drive its linked reservation from `CONFIRMED` to `IN_USE`, the service checks `hasCheckoutReport` first and throws the new `MissingCheckoutConditionReportError` before touching the reservation or writing the fulfillment event — so a rejected pickup leaves neither the reservation state nor the append-only event log moved, the same all-or-nothing shape D071 established for `IllegalReservationTransitionError`. Order lines with no linked reservation (e.g. a product sale) are unaffected — the guard only fires on the path that would actually reach `IN_USE`.

Test-first throughout: `ConditionReportRepository.test.ts` (4 cases, confirmed failing on `Cannot find module` before the file existed) covers create/read, a CHECKIN report not satisfying the CHECKOUT check, and two cross-tenant isolation cases (`hasCheckoutReport` and `listByOrderLine`, both required by the Gate G1 isolation-coverage generator). `FulfillmentEventService.test.ts` gained a CHECKOUT-report fixture in its existing CONFIRMED→IN_USE success case (previously it transitioned with no report at all — that gap is exactly what I7 closes) and a new case asserting the transition is rejected with `MissingCheckoutConditionReportError`, with the reservation still `CONFIRMED` and the event log still empty afterward, confirmed failing before the guard existed.

## Security check answer

**Without a baseline, a damage claim is unwinnable.** A merchant's damage claim after a rental return only holds up if there's a documented, timestamped condition record from *before* the customer took the item — otherwise "you damaged this" is just the merchant's word against the customer's for wear that could have existed at checkout. This card makes that baseline structurally mandatory rather than a process the front desk can forget: `FulfillmentEventService` now refuses to let a reservation leave `CONFIRMED` for `IN_USE` — the state that represents the item being in the customer's hands — unless a `CHECKOUT`-phase `condition_reports` row already exists for that order line, enforced in the same service-layer guard that already owns every other reservation-state transition (`ReservationRepository`'s single `transition()` path, D071), so there is no route to `IN_USE` that bypasses it. The remaining honest gap: this card doesn't yet build the endpoint/UI staff actually use to *write* a condition report (`ConditionReportRepository.create` exists and is tested, but nothing calls it from an HTTP route yet), and `condition_media` (the photo evidence D029 also modeled, with its `sha256` tamper-evidence column) isn't wired to condition reports at all — that's D073's job per the card sequence.
