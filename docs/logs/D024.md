## What happened

Added `inventory_units` and `inventory_movements` (`packages/db/src/schema/{sqlite,pg}.ts`) per `docs/design/03`'s "Inventory — products and rentals" section, real `drizzle-kit`-generated migrations for both dialects. `inventory_units` has no stock/quantity column — it's a per-unit row (always `SERIALIZED` for rentals, `SERIALIZED` or `FUNGIBLE` for products) carrying lifecycle/utilization fields (`acquisition_cost_minor`, `acquired_at`, `expected_life_months`, `condition_grade`, `retired_at`). `inventory_movements` is append-only: current stock is always `SUM(quantity)` over the ledger, never a stored counter; `quantity` is a signed integer (inbound kinds positive, outbound kinds negative) so summing gives net stock directly. `unit_id` is nullable (FUNGIBLE stock moves at the variant/location level with no single unit to reference); `order_line_id` is a plain column, not a FK, since `order_lines` doesn't exist yet. `actor_user_id` (FK to `users`) and `note` are both `NOT NULL` — the schema-level enforcement of "every change has actor and reason." Test-first via `packages/db/src/schema/inventory.test.ts` (11 cases, confirmed failing on `Cannot find module`/table-not-found before the schema existed): migration application, a structural check that `inventory_units` carries no `stock`/`quantity`/`stock_quantity` column, round-tripping a unit, summing a mixed RECEIPT/SALE/ADJUSTMENT sequence to the correct net total, proving a correction is done by appending a new row (not mutating an old one) and the sum reflects it, rejecting a movement missing `actor_user_id` or `note`, FK enforcement on both tables, and a unique `(merchant_id, unit_code)` constraint. A `DATABASE_URL`-gated case was also run for real against a local PostgreSQL 16 instance this session — full round-trip, correct sum, and the mandatory-actor rejection all passing against real Postgres, not just SQLite.

## Acceptance criteria check

- "Movement ledger sums correctly" — **Met**. `computes current stock as the sum of signed movement quantities, not a stored counter` inserts RECEIPT(+10)/SALE(-3)/SALE(-2)/ADJUSTMENT(-1) and asserts the summed total is 4; the real-Postgres case does the same with RECEIPT(+10)/SALE(-4) summing to 6.
- "no mutable counter" — **Met**. `has no stock/quantity counter column on inventory_units` asserts via `PRAGMA table_info` that no `stock`/`quantity`/`stock_quantity` column exists on `inventory_units`; `appending a correcting movement changes the sum; nothing is ever updated in place` proves stock changes only by inserting a new ledger row (movement-1 stays untouched; a second row corrects the total from 5 to 3).

## Security check answer

"Ledger is auditable — every change has actor and reason" — **enforced at the schema level, not deferred to a service layer.** `inventory_movements.actor_user_id` is `NOT NULL` with a real FK to `users.id` (a movement must name a real, existing identity, not just any string), and `inventory_movements.note` is `NOT NULL` (a movement must state why). Both are proven by direct rejection tests: `rejects a movement with no actor` and `rejects a movement with no note` each attempt an insert omitting the field and assert the database itself throws — this isn't a convention a future caller could accidentally skip. This is narrower than the full `audit_log` table (`docs/design/03` "Audit" — append-only, hash-chained, a separate future card, same tracked gap already noted for D020/D023's role and catalog changes) — this card only guarantees the inventory ledger itself always carries actor+reason, not that a rejected/denied inventory action gets recorded anywhere.
