## What happened

Built the deposit management view end to end. `DepositAuthorizationRepository.listAll` (`packages/db`) is a new merchant-wide, tenant-scoped read ordered soonest-`expiresAt`-first. A new pure-domain classifier, `classifyDepositForDashboard` (`packages/domain/src/payments/depositDashboard.ts`), buckets a deposit into `HELD | EXPIRING_SOON | CAPTURED | RELEASED | EXPIRED`; there's no design-doc-mandated threshold for "expiring soon" (unlike the 30-day authorization-window ceiling), so I picked 72 hours ahead of `expiresAt` as a documented judgment call — comfortably inside the shortest real provider window (~7 days) — and exported it as `DEPOSIT_EXPIRING_SOON_WINDOW_HOURS` rather than inlining it. An `AUTHORIZED` hold whose `expiresAt` has already passed (sweeper hasn't run yet) buckets as `EXPIRING_SOON`, not `HELD` — fails closed rather than hiding an overdue hold. New `GET /deposits` route in `apps/api/src/routes/damageClaims.ts` (reusing that file's existing deposit-service wiring) returns every deposit for the merchant with the bucket computed server-side, gated `bookings:view` like the other deposit reads in that file. New `apps/web/src/app/dashboard/deposits/DepositManagementView.tsx` (routed at `/dashboard/deposits`) renders one section per bucket, "Expiring soon" first, each row linking to `DamageClaimView.tsx` (D118) for that order line — the one place a claim can be filed or the hold can still be released ahead of the auto-release job. Wrote failing tests first throughout: `depositDashboard.test.ts` (9 cases, including the exact window-boundary case), `DepositAuthorizationRepository.test.ts` (2 new `listAll` cases including a merchant-B isolation case), `damageClaims.test.ts` (7 new `GET /deposits` cases: empty list, HELD, CAPTURED, RELEASED, EXPIRING_SOON via a short provider window, READ_ONLY readability, and cross-merchant isolation), `DepositManagementView.test.tsx` (4 cases: empty state, expiring-soon section, held/captured/released grouping, load error).

## Acceptance criteria check

- "Expiring holds surfaced before they lapse" — **met**. `classifyDepositForDashboard` computes `EXPIRING_SOON` server-side from `expiresAt` against a documented 72h window (before the hold would otherwise lapse via provider expiry or `DepositAutoReleaseJob`), and `DepositManagementView` renders that section first, ahead of "Held" — proven by `damageClaims.test.ts`'s short-provider-window case (1-day window from `CREATED_AT` buckets as `EXPIRING_SOON`, not `HELD`) and `DepositManagementView.test.tsx`'s "surfaces an expiring-soon hold in its own section" case.

## Security check answer

"Prevents silent expiry on customer cards" — answered structurally, not by this view alone: `DepositAutoReleaseJob` (D080) already releases a hold deliberately, with notification, before expiry whenever a rental completes with no claim filed. This view is the merchant-facing complement — it surfaces any hold that job hasn't caught yet (still `AUTHORIZED` and inside the 72h expiring-soon window, including one already past its recorded `expiresAt`) so a merchant can act — release, capture, or resolve a claim — before it lapses silently on a customer's card, rather than discovering it only after the fact. The bucket computation itself never trusts client state: it's derived server-side from the deposit's own persisted `state`/`expiresAt` on every `GET /deposits` call, so a merchant always sees the current, real classification.
