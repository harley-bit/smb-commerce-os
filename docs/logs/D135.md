## What happened

Surveyed the storefront (`apps/web/src/app/m/**`) before changing anything: the shared `Button`/`TextField` components and existing pages were already in good shape — real `<button>`/`<label>` elements, `role="alert"` error text, `:focus-visible` outlines, no leaked server error detail. Two concrete gaps were found and fixed. First, `RentalDetailView`'s date-range picker used bare `<input type="date">` with no shared `TextField` wiring, so an invalid range (end date before start date) failed completely silently — no visible or accessible feedback at all; fixed by switching both inputs to the shared `TextField` and surfacing a `role="alert"` message tied to the end-date field via `aria-describedby`/`aria-invalid` when the range is inverted. Second, the app had no `viewport` meta at all (`apps/web/src/app/layout.tsx`) — mobile browsers would render the page at desktop width and zoom out regardless of any CSS, which is the actual root cause a "mobile-web layout" pass needs to fix; added the Next 15 `viewport` export plus a one-place `main` max-width/padding rule and `min-height: 2.75rem` touch-target sizing on `.btn`/`.field__input` (WCAG 2.5.8) in `globals.css`. Also added an explicit keyboard-only test (`Tab` + `{Enter}`, no mouse click) to `ServiceDetailView.test.tsx` proving the slot picker's keyboard path, since prior tests only exercised `userEvent.click`.

## Security check answer

"Accessible error messaging does not leak detail" — confirmed by audit, not new code: every error path in the storefront (`MerchantPageView`, `ProductDetailView`, `RentalDetailView`, `ServiceDetailView`, `OrderHistoryView`, `PaymentView`) renders a fixed, generic user-facing string (e.g. "Could not find that rental.") never `error.message`, a stack trace, or a raw server response body. The new range-validation message ("The end date must be after the start date.") follows the same pattern — it's a client-side-computed string, not anything echoed from the network. `PaymentView`'s decline messaging (from D130) was re-checked and still only surfaces the server's mapped `decline.detail` category, never a raw processor code.
