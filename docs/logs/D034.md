## What happened

Added Zod schemas + inferred types to `packages/contracts`: `listing.ts` (`listingModeSchema`, `listingStatusSchema`, `listingSchema`, `createListingInputSchema`, `updateListingInputSchema`) and `variant.ts` (`variantModeSchema`, `variantRatePeriodSchema`, `variantSchema`, `createVariantInputSchema`, `updateVariantInputSchema`), both exported from `packages/contracts/src/index.ts`. Each mirrors the corresponding `packages/db` repository type (`ListingRepository`/`VariantRepository`, D023/D033) field-for-field. `updateListingInputSchema`/`updateVariantInputSchema` use `.strict()` so a patch carrying an extra `mode`/`listingId` key is rejected at parse time, not just omitted from the TS type — the runtime half of the immutability guarantee those repository update types already have at compile time. Variant price validation (`assertValidMoney`) calls the real `Money.of` from `@smb-os/domain` inside a `superRefine`, rather than re-implementing "integer minor units, non-empty currency" as a second rule; the mode-conditional forbidden-fields matrix (`FORBIDDEN_VARIANT_FIELDS_BY_MODE`) is defined once and used by both the create schema's `superRefine` and (implicitly, by construction) anywhere else in this package that needs it. `packages/contracts` gained its first real test suite (`vitest`, matching `packages/domain`'s 95%-threshold coverage pattern; actual result 100% across statements/branches/functions/lines) — previously `test`/`test:isolation` were both `echo` stubs. `apps/web/src/index.ts` was extended with `parseListingDraft(input: unknown): CreateListingInput`, a real (not merely declared) usage of the contracts package's schema and generated type, to make the "web...compile[s] against generated types" criterion a fact checked by `pnpm typecheck`, not an assumption from the existing dependency edge.

## Acceptance criteria check

- **Web and mobile compile against generated types** — Met for web: `pnpm typecheck` passes with `apps/web/src/index.ts` importing and calling `createListingInputSchema`/`CreateListingInput` from `@smb-os/contracts`. **Mobile does not exist yet** — Phase 8 (`docs/design/01`) explicitly defers all mobile work until after the web MVP gate (G7), so there is no `apps/mobile` package for this criterion to apply to today. Nothing about this card's schema design is web-specific (plain Zod + inferred types, zero DOM/web dependencies), so there's no reason to expect it wouldn't compile identically once a mobile package exists — but that is a forward-looking claim, not a verified one, and is recorded honestly as such rather than marked Met.

## Security check answer

**"One validation definition, enforced everywhere."** Within this package, yes: `createVariantInputSchema` and `updateVariantInputSchema` both validate price through the single `assertValidMoney` helper, which itself defers to `@smb-os/domain`'s `Money.of` rather than re-declaring "integer + non-empty currency" as a separate rule — the same function `VariantService` (D033) calls server-side. The mode-conditional forbidden-fields rule is defined once in this package as `FORBIDDEN_VARIANT_FIELDS_BY_MODE` and reused by `createVariantInputSchema`'s `superRefine`. **Known remaining gap, flagged honestly and not fixed in this card:** `packages/db/src/services/VariantService.ts` still carries its own separately-declared `FORBIDDEN_FIELDS_BY_MODE` object (identical values, different definition) rather than importing this package's copy — unifying that would mean adding a new `@smb-os/db` → `@smb-os/contracts` dependency edge and touching D033's already-shipped, already-tested service file, which is beyond this card's stated deliverable ("Zod schemas for listings and variants; generated types"). Tracked as follow-up work for whichever future card next touches `VariantService`.
