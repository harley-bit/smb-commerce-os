## Security check answer

**Media integrity hash verified on display.** Two layers, matching what's actually possible given `condition_media` never stores raw bytes (only `sha256`, the D074 gap this repo has carried since D073/D074 — confirmed again this session): (1) every media item served by `GET .../condition-reports` carries the `sha256` `ConditionMediaConfirmService` independently recomputed and verified against the declared hash at upload time — the check-in view only ever reads that server-persisted value, never a client-supplied one, for both the CHECKOUT baseline photos and any CHECKIN photos. (2) For freshly captured CHECKIN photos specifically, `RentalCheckinView.handlePhotoSelected` goes one step further: it computes the SHA-256 of the file's bytes client-side (as `RentalCheckoutView` already did before upload), then after `/media/confirm` succeeds, re-fetches the comparison and refuses to add the photo to the on-screen list unless the server's confirmed record echoes back that exact same digest — a genuine display-time integrity check, not just a repeat of the upload-time one, since it would catch a response that got corrupted or reordered in transit between confirm and display.
