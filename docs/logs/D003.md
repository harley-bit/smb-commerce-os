## What happened

Added a new shared package, `@smb-os/eslint-config`, holding a flat ESLint 10 config factory (`createConfig({ allowRawSql })`) built on `@typescript-eslint/{parser,eslint-plugin}` plus `eslint-config-prettier` (to keep stylistic rules out of ESLint's way once Prettier owns formatting). The factory wires in a custom local rule, `local/no-raw-sql`, which flags: string/template literals whose content starts with a SQL statement keyword (`SELECT`/`INSERT INTO`/`UPDATE`/`DELETE FROM`/`CREATE|DROP TABLE`/etc.), tagged-template calls using a `sql` tag (the common raw-SQL escape hatch in query builders like Drizzle), and `.query()`/`.execute()`/`.raw()`/`.unsafe()` calls passed a literal SQL string. The rule is `error` by default and only turned `off` via `allowRawSql: true`, which is set solely in `packages/db/eslint.config.js` — the one package allowed to speak the dialect directly.

## Security check answer

**Rule enforces the dialect + tenant-scoping boundary.** `packages/db` is the only package with a working connection to the actual SQL dialect (Postgres today, portable per `docs/design/04`) and is where tenant-scoping predicates (e.g. `WHERE tenant_id = ...`) are meant to be enforced structurally, not left to each call site's discipline. `local/no-raw-sql` makes it a lint error — not a convention — for any other package (`apps/api`, `apps/web`, `packages/{domain,contracts,config}`) to hand-write SQL, whether as a bare string, a `sql\`...\`` tagged template, or a `.query()`/`.execute()` call with a literal. That closes off the most common way tenant scoping gets silently bypassed: a developer reaching for a raw query to work around the query builder instead of extending it, which routes the query outside whatever tenant-isolation guarantees `packages/db` provides. The rule is off only in `packages/db` itself (`eslint.config.js: createConfig({ allowRawSql: true })`), which is exactly where that responsibility is meant to live.
