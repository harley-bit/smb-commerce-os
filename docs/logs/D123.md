## What happened

Built the service listing detail page and slot picker — Phase 7's third card, extending D122's `GET /v1/m/{slug}/listings/{listingSlug}` route to also serve `SERVICE` listings (previously PRODUCT-only; it now 404s only for RENTAL, D124's scope). The route composes the existing `listing_resources` join (`ListingResourceRepository.listByListing`, from D107) into a new `@smb-os/contracts` `publicServiceDetailSchema`/`PublicServiceDetail` — the listing plus a bare `resourceIds: string[]`. Exposing `resourceId` publicly adds no new surface: it was already public via `GET /v1/m/{slug}/availability?resourceId=...` (`apps/api/src/routes/availability.ts`, D046/D047-era), which this detail response points the storefront at. New `apps/web/.../ServiceDetailView.tsx` fetches the service detail, then (if a resource is assigned) fetches that resource's free intervals over the next 14 days from the same public availability endpoint, and renders each returned interval as a selectable `<button>`. `page.tsx` (previously `ProductDetailView`-only) now does a small mode-dispatch fetch first and renders `ServiceDetailView` or `ProductDetailView` accordingly, so both modes share the one `/m/[slug]/l/[listingSlug]` route. `MerchantPageView.tsx` now links SERVICE listings to their detail page too (RENTAL stays plain text). Wrote failing tests first throughout: `packages/contracts`'s `publicStorefront.test.ts` (+3 for `publicServiceDetailSchema`), `apps/api/test/publicStorefront.test.ts` (updated the old "404s all non-PRODUCT" case to be RENTAL-specific, +4 new SERVICE-detail cases), `MerchantPageView.test.tsx` (split the old combined "does not link service or rental" case into a SERVICE-links / RENTAL-doesn't-link pair), new `ServiceDetailView.test.tsx` (7 cases: name/description render, only free intervals render as slots, a slot can be selected, empty-availability state, no-resource-assigned state skips the availability call entirely, no busy-slot/booker text ever appears, 404 error state).

## Acceptance criteria check

- "Only free slots selectable" — **met**. `ServiceDetailView` renders exactly one `<button>` per entry in the availability endpoint's `free: Interval[]` array and nothing else is ever clickable on the page — proven by `ServiceDetailView.test.tsx`'s "renders only the free intervals as selectable slots" (two free intervals in the mock response → exactly two buttons) and "shows no selectable slots when nothing is free" (empty `free` array → zero buttons, a text fallback instead). There is structurally no busy-slot data for the component to render as disabled-but-present, since `computeFreeIntervals` (`packages/domain/src/utils/freeIntervals.ts`, unchanged by this card) never returns one.

## Security check answer

"Availability shows free/busy only, never who booked" — **met**, and mostly inherited rather than newly built. `GET /v1/m/{slug}/availability` (D046/D047) already answers this one layer down: its `Interval` type (`packages/domain/src/utils/interval.ts`) carries only `start`/`end`, and `AvailabilityService.getResourceAvailability`'s own doc comment notes it "has no way to leak who booked a slot because it never asks `ReservationRepository.findBlocking` for anything but `startsAt`/`endsAt`." This card's new pieces don't add any reservation-identity data: `publicServiceDetailSchema` (`packages/contracts/src/publicStorefront.ts`) carries only `resourceId`s — a resource's own `name`/`kind` (a `STAFF` resource's name is "Confidential" per `docs/design/08`, per `ResourceService.ts`'s doc comment) is never included, proven by `apps/api/test/publicStorefront.test.ts`'s "never exposes merchantId, listingId, or the resource's own name" (asserts the fixture's staff name "Jamie" never appears anywhere in the JSON response). `ServiceDetailView.test.tsx`'s "never renders who booked a busy slot" asserts no "booked by"/"customer" text appears anywhere in the rendered slot picker.
