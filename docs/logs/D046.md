## What happened

Added `packages/domain/src/utils/availabilityRule.ts`: an `AvailabilityRule` type (`weekday` 0–6, local `startTime`/`endTime` as `"HH:MM"`, IANA `timezone`) matching the `availability_rules` table shape from `docs/design/03`, and `expandAvailabilityRule(rule, rangeStart, rangeEnd)`, which walks local calendar dates in the rule's timezone across `[rangeStart, rangeEnd)`, and for each date matching the rule's weekday converts the local start/end wall-clock time to a concrete UTC `Interval` (D045's half-open type). The core correctness piece is `zonedTimeToUtcMs`: it resolves the UTC offset for a local date/time using `Intl.DateTimeFormat` with `timeZone`, then re-resolves at the corrected instant and uses that if it differs — because the offset itself is a function of the instant near a DST transition, a single lookup at the wrong side of the transition gives the wrong answer. Wrote the failing test first (`availabilityRule.test.ts`, confirmed it failed on a missing module before implementing), covering: a plain non-DST weekday window, multiple occurrences across a date range, validation (bad time format, start ≥ end, out-of-range weekday), a spring-forward case (`America/New_York`, 2024-03-10, clocks jump 02:00→03:00 — a wall-clock 01:00–03:30 window resolves to exactly 1.5h of real UTC duration, not the 2.5h wall-clock difference), a fall-back case (2024-11-03, clocks repeat 01:00–02:00 — a wall-clock 00:30–02:30 window resolves to exactly 3h of real UTC duration, not 2h), and a half-hour-offset DST zone (`Australia/Lord_Howe`) to rule out an implementation that assumes whole-hour transitions. All expected UTC instants were independently verified against Node's `Intl` output before being hard-coded into the test.

## Acceptance criteria check

- "DST transition cases produce correct local windows" — **Met.** `availabilityRule.test.ts` — "spring-forward: a window crossing the DST gap reflects real elapsed time, not wall-clock diff" and "fall-back: a window crossing the DST repeat reflects real elapsed time, not wall-clock diff" both assert exact UTC start/end instants and exact elapsed duration (1.5h and 3h respectively), proving the expansion uses the correct offset at each endpoint independently rather than a single offset for the whole window.

## Security check answer

"Timezone errors are a correctness risk (T23)" — addressed directly: all instant math is delegated to the platform `Intl.DateTimeFormat` timezone database (no hand-rolled offset tables to drift out of date), every output interval is constructed via D045's `makeInterval` (which itself validates UTC-ISO shape and `start < end`, so a malformed or zero-length interval can never leave this function silently), and the DST-transition test cases assert exact instants and durations rather than "doesn't throw" — a wrong-by-one-hour bug would fail the test, not just an outright crash. Weekday day-of-week is computed from the already-localized calendar date, not from an instant, so it can't be skewed by the timezone conversion itself. Malformed input (bad `HH:MM` format, `startTime >= endTime`, out-of-range `weekday`) is rejected with explicit errors rather than producing a silently-wrong interval.
