## What happened

The raw `payments` table with its `(provider, provider_ref)` unique index already existed from D028 (schema-only, no repository/service layer — confirmed by reading D028's log, which explicitly deferred "capture/release/expiry logic and Stripe webhook handling" to Phase 5). This card is that wiring: new `PaymentRepository` (`packages/db/src/repositories/PaymentRepository.ts`), tenant-scoped, mirroring `DepositAuthorizationRepository`'s shape — `create`, `findById`, and `findByProviderRef` (the lookup a webhook handler will use before deciding whether to reprocess an event). `create` does not check-then-insert (that would race under two concurrent webhook deliveries for the same event); it always attempts the insert and lets the schema's own unique index be the single source of truth, catching the resulting `SQLITE_CONSTRAINT_UNIQUE` driver error and translating it into a new domain error, `DuplicatePaymentReferenceError` (`packages/domain/src/payments/DuplicatePaymentReferenceError.ts`, exported from `packages/domain`'s `index.ts`), so a caller sees a typed, catchable domain condition rather than a raw `better-sqlite3` exception. 6 new tests in `PaymentRepository.test.ts`: create/read round-trip, `findByProviderRef` lookup (hit and miss), the duplicate-`provider_ref`-rejected case (asserting `DuplicatePaymentReferenceError` and that the rejected duplicate wrote nothing), same `provider_ref` accepted across two different providers (constraint is scoped to the pair, matching D028's schema test), and a single isolation test exercising `create`/`findById`/`findByProviderRef` across two distinct tenant contexts in one `it()` block (required by the D021 isolation-coverage generator, which initially flagged all three methods as gaps until this was added). `PaymentRepository` and its types also now exported from `packages/db`'s `index.ts`. Full local gate green: lint, typecheck, `pnpm test` (10/10 tasks; `@smb-os/db` 486/486 passing, up from 480; one `@smb-os/api` `/health` test timed out on an unrelated load-flake, confirmed passing in isolation on a clean re-run of just that package, same category of flake noted in D079's log), `pnpm test:isolation` (the D021 generator embedded in `pnpm test` itself reports zero gaps including the new repository; the standalone `test:isolation` script remains the known pre-existing stub `echo`, unchanged by this card).

## Acceptance criteria check

- "Duplicate provider_ref rejected" — **Met.** `PaymentRepository.create` rejects a second insert with the same `(provider, provider_ref)` pair by throwing `DuplicatePaymentReferenceError`, proven in `PaymentRepository.test.ts`'s "rejects a duplicate (provider, provider_ref) with a domain error" test, which also confirms the rejected duplicate wrote nothing (only the first row exists afterward). The underlying DB-level guarantee (a real unique index, not an app-level race-prone check) was already proven at the schema layer in D028's `payments.test.ts`; this card proves the same guarantee surfaces correctly through the new repository as a typed domain error.

## Security check answer

**"provider_ref is the idempotency anchor."** Confirmed and made concrete at the repository layer this card adds: `findByProviderRef(ctx, provider, providerRef)` is the exact lookup a future webhook handler calls before deciding whether an incoming event has already been recorded, and `create`'s reliance on the schema's real unique index (rather than a check-then-insert) means that guarantee holds even if two webhook deliveries for the same event arrive concurrently — there is no window between a lookup and a write where a second delivery could slip through and create a duplicate payment record. The DB constraint, not application logic, is the actual anchor; the repository's job is only to translate its violation into something a caller can catch by type.
