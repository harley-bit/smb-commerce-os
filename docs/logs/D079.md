## What happened

New `packages/domain/src/payments/authorizationWindow.ts` — pure domain math, same shape as D077's `depositStateMachine.ts` — implementing `docs/design/05`'s C4 rule: "The 30-day ceiling is a product constraint... Rentals longer than the provider's window cannot rely on a hold... Surface this in the merchant UI when a rental period is configured beyond the ceiling — do not discover it in production" (same risk as T11 in `docs/design/14`).

Two functions, deliberately the only two entry points: `recordProviderAuthorizationWindow(providerWindowDays)` is the sole way to produce a `ProviderAuthorizationWindow` value ("provider window recorded") — it rejects non-positive/non-integer inputs and, critically, rejects any window above the hard 30-day `AUTHORIZATION_WINDOW_CEILING_DAYS` product ceiling even if a provider or caller claims a longer one, so the ceiling can never be silently bypassed by passing through unvalidated provider data. `validateRentalTermAgainstAuthorizationWindow(rentalTermDays, window)` is the sole way to check a rental term against a recorded window ("rental term validated against it") — it throws `RentalTermExceedsAuthorizationWindowError`, carrying both the offending term and the window, with a message written to be surfaced verbatim in a merchant UI (e.g. "Rental term of 10 day(s) exceeds this payment provider's 7-day authorization hold window... use a captured deposit up front or a contractual claims process instead").

Wrote the failing test first (`authorizationWindow.test.ts`, 13 cases) — confirmed both imports failed on the missing module before implementing. Covers: recording a standard 7-day window, recording the extended 30-day lodging/vehicle-rental MCC window, rejecting zero/negative/non-integer windows, rejecting a window above the 30-day ceiling (31 days), accepting a term within and exactly at the window boundary, rejecting a term one day beyond a standard window and beyond an extended window, the error carrying `rentalTermDays`/`window` fields and a message that names the actual window size and both remediation options (captured deposit, contractual claims process), and rejecting a non-positive term. Exported from `packages/domain/src/index.ts` alongside the other payments exports.

No service-layer or HTTP wiring in this card — like D077, this is domain-only. There is no existing "rental term" field anywhere in the schema/variant contracts to hook a live configuration check into yet (variant `ratePeriod` is a billing cadence — HOUR/DAY/WEEK — not a fixed term length; the actual term lives on a booking's `starts_at`/`ends_at`), so wiring this validation into an actual configuration flow (variant setup, booking creation, or a merchant-facing deposit-policy screen) is follow-on work for whichever future card owns that surface.

## Security check answer

**"Product constraint surfaced in UI, not discovered in production."** This card makes the constraint impossible to bypass silently at the point a caller checks it: `recordProviderAuthorizationWindow` refuses to record a window above the 30-day product ceiling regardless of what a provider or upstream config claims, so no caller can construct a `ProviderAuthorizationWindow` that would let a too-long rental term slip through. `validateRentalTermAgainstAuthorizationWindow` throws rather than returning a boolean a caller could ignore, and the thrown error's message is written as end-user/merchant-facing guidance (states the actual window size in days and both valid remediations) rather than a generic "invalid" message — the intent is that a UI layer can display `error.message` directly rather than needing its own copy. What is **not yet done**: no route or form in this repo currently calls this function, so the constraint is enforced in the domain layer but not yet actually surfaced in any UI — that wiring is the natural next step once a rental-term configuration surface exists, flagged in "Notes for next session" rather than left silent.
