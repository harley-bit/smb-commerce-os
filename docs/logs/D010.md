## What happened

This card ran across two sessions on the same day. Session 1 built the `AuthProvider` interface (`packages/domain/src/auth/AuthProvider.ts`, no I/O) and `NativeAuthProvider` (`apps/api/src/auth/NativeAuthProvider.ts`) per ADR-002: Argon2id password hashing (`@node-rs/argon2`), an opaque revocable session-cookie model, hashed single-use password-reset tokens, per-IP-and-per-account rate limiting, progressive account lockout, and an Origin-header CSRF check — but was Carried because TOTP MFA for `OWNER`/`ADMIN` (an explicit ADR-002 requirement) was not yet built.

Session 2 (this run) closed that gap. Added `otpauth` (9.5.2, pure-JS, single well-known dependency `@noble/hashes`, no native build step) and implemented mandatory TOTP MFA:

- `packages/domain/src/auth/AuthProvider.ts`: new `MfaEnrollmentRequiredError`, `MfaCodeRequiredError`, `InvalidMfaCodeError`, and an `MfaEnrollment` type (`{ secret, otpauthUrl }`); `AuthProvider.authenticate` now takes an optional `mfaCode`; two new interface methods, `enrollMfa(email, password)` and `confirmMfaEnrollment(email, password, code)`.
- `apps/api/src/auth/repositories.ts`: `UserRecord` gained `mfaSecret: string | null` and `mfaEnabled: boolean`; `UserRepository` gained `setPendingMfaSecret` and `enableMfa`.
- `apps/api/src/auth/NativeAuthProvider.ts`: `authenticate` now checks role against `MFA_REQUIRED_ROLES = {OWNER, ADMIN}` after password verification — if MFA isn't enrolled yet it throws `MfaEnrollmentRequiredError` (password was correct, so this doesn't count as a login failure against the account-lockout backoff); if enrolled but no code was given it throws `MfaCodeRequiredError`; if the code is wrong it throws `InvalidMfaCodeError` and does count as a failure. `enrollMfa`/`confirmMfaEnrollment` re-verify the password (no session exists yet at enrollment time) before issuing/confirming a base32 TOTP secret (`otpauth`'s `Secret`/`TOTP`, SHA1/6-digit/30s period, ±1 step clock-drift window).
- `apps/api/src/app.ts`: `/auth/login` now accepts an optional `mfaCode` and maps the three new error types to `409` (enrollment required, `mfaEnrollmentRequired: true`), `401` (code required, `mfaCodeRequired: true`), and `401` (wrong code); two new routes, `/auth/mfa/enroll` and `/auth/mfa/confirm`, both re-verifying the password and both consuming the same per-IP/per-account rate limiter as login (they accept a password guess, so they need the same protection).
- Every registered account defaults to `OWNER` (unchanged from session 1), so in practice **every** account must complete MFA enrollment before its first successful login now — this was confirmed deliberately, not discovered as a side effect, since ADR-002 says MFA "does not get to slip just because auth is native now" and doesn't carve out an exception for the only role registration currently assigns.
- Updated the existing acceptance-criteria test (`apps/api/test/auth-flow.test.ts`) to enroll+confirm MFA as part of the register→login→...→password-reset flow (password reset preserves the MFA secret; re-enrollment isn't required after a password change). Added `apps/api/test/mfa.test.ts` (5 endpoint-level tests: enrollment-required login block, enroll→bad-code→good-code confirm, code-required/wrong-code/right-code login, wrong-password rejection on both MFA endpoints, missing-field validation) and extended `apps/api/test/native-auth-provider.test.ts` with 3 provider-level tests (enrollment gate, full enroll→confirm→code-gated-login cycle, and a non-privileged role bypassing MFA entirely via a directly-injected `STAFF` record, since role assignment beyond auto-`OWNER` isn't in scope yet). Extended `packages/domain/src/auth/AuthProvider.test.ts` and `apps/api/test/repositories.test.ts` for the new interface surface.

## Security check answer

- Passwords are hashed with Argon2id, never bcrypt/SHA/plaintext, and never appear in logs/audit/error responses: **Yes** — unchanged from session 1, still tested.
- Login and reset-request endpoints are rate-limited from this card: **Yes** — unchanged, and the two new MFA endpoints (`/auth/mfa/enroll`, `/auth/mfa/confirm`) reuse the same per-IP/per-account limiter since they also accept a password guess.
- Session tokens are opaque and revocable server-side, not a long-lived unrevoked JWT: **Yes** — unchanged.
- **MFA for `OWNER`/`ADMIN` (ADR-002, the reason this card was Carried): Yes, now implemented.** TOTP via `otpauth` (standard algorithm, SHA1/6-digit/30s, not SMS, per `docs/design/07`); enrollment is gated behind a password re-check (no session exists yet at that point); the secret is only usable after `confirmMfaEnrollment` verifies a real code, so a leaked-but-unconfirmed secret can't silently enable MFA bypass; login enforces the code for every subsequent authentication once enrolled, and a wrong code counts toward the same account-lockout backoff as a wrong password (an enrollment-required response does not, since the password was correct).
- CSRF: unchanged, still an Origin-header check per ADR-002's allowance.

All of ADR-002's requirement table is now implemented and tested: Argon2id, session revocation, rate limiting, account lockout backoff, reset-token hashing/expiry, CSRF origin-check, and TOTP MFA for `OWNER`/`ADMIN`.
