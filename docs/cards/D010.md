## Task

Implement the `AuthProvider` interface (`packages/domain/auth/AuthProvider.ts`) natively: `NativeAuthProvider` backed by our own database, no external identity provider yet.

## Deliverable

- `AuthProvider` interface in `packages/domain` (no I/O, per the domain-package rule in ADR-001).
- `NativeAuthProvider` implementation in `apps/api`: Argon2id password hashing, a `users` + `sessions` schema (session table, not a bare JWT — see ADR-002), httpOnly/Secure/`SameSite=Strict` session cookie issuance and verification.
- Login, logout, and password-reset-initiation endpoints wired through this provider, with per-IP and per-account rate limiting on login and reset-request.
- Nothing outside `packages/domain/auth` references `NativeAuthProvider` by name — only the `AuthProvider` interface, so a future `Auth0Provider` is a swap.

## Acceptance criteria

A test user can register, log in, receive a session cookie, access an authenticated route, log out (session revoked), and request a password reset — all against `NativeAuthProvider`, with a passing test for each step. A test asserting no other module imports `NativeAuthProvider` directly (only the interface) passes.

## Security check

Passwords are hashed with Argon2id (never bcrypt/SHA/plaintext) and never appear in logs, audit `before_json`/`after_json`, or error responses. Login and reset-request endpoints are rate-limited from this card, not a later one. Session tokens are opaque and revocable server-side (not a long-lived unrevoked JWT). See `docs/adr/ADR-002-authentication-provider.md` for the full requirement set this card must satisfy — it is materially more than the original "no password storage" security check this card carried before ADR-002.
