## Task

Backend: Google and Apple OAuth sign-in

## Deliverable

New `AuthProvider` methods verifying a Google ID token and an Apple identity token respectively (correct `aud`/`iss` verification against each provider's JWKS — never trusting client-supplied profile data), find-or-create the `users` row by verified email (linking to an existing native account on email match), and issue the same session/PKCE-mobile-token shapes D138 built. New `POST /auth/mobile/oauth/google` and `POST /auth/mobile/oauth/apple` routes. Per `docs/adr/ADR-003-social-login.md`: these paths do **not** route through `NativeAuthProvider.authenticate()`'s `MFA_REQUIRED_ROLES` check — OAuth-authenticated sessions skip this app's own TOTP MFA.

## Acceptance criteria

A verified Google or Apple identity token produces a real session/token pair; a token with the wrong audience or a tampered signature is rejected; signing in with the same email a native account already uses links to that account rather than creating a duplicate.

## Security check

Confirm token verification checks signature, audience, issuer, and expiry against each provider's own public keys — not just that a token merely parses as a JWT. Confirm Apple's private-relay email and first-authorization-only name are handled without assuming either is always present.
