## What "charges, splits, deposits, and refunds all correct" means here

Every individual piece of the payments surface was already built and unit-tested by its own card: `CheckoutPaymentService`/application-fee split (`D089`), idempotency (`D090`), webhook signature verification and idempotency (`D091`/`D092`), ordering tolerance (`D093`), deposit hold placement (`D094`), capture/partial-capture/release (`D095`), refunds per mode (`D096`), payout reconciliation (`D097`), decline handling (`D098`). No prior card had exercised charge → split → refund for PRODUCT and SERVICE, or hold → capture/release for RENTAL, together in one continuous run per mode — the same "compose, don't just unit-test in isolation" bar `G2`/`G4` set for their own domains.

## Verification performed this session

`packages/db/src/services/gate-g5.e2e.test.ts` (3 cases, new this card) wires the real service classes together for each fulfillment mode — no direct repository/schema writes standing in for any service call itself (repository classes are only used to construct services, to seed merchant/user fixture rows, and to persist the `payments` rows that no service in this codebase yet writes automatically — an open gap already flagged by every prior payments card's log):

1. **PRODUCT mode** — `CartService` → `CheckoutPaymentService.createCheckoutIntent` charges the cart's server-recomputed total ($100.00), the application-fee split ($2.50 platform / $97.50 merchant at 250bps) sums back to the charge exactly, then `RefundService.refundOrderLine` (product policy: 100% refund at any notice) refunds the full $100.00 — two distinct, correctly-typed `payments` rows (`CHARGE` then `REFUND`) against the same order.
2. **SERVICE mode** — a service order line with a future `startsAt` is charged ($80.00, 5% take rate, split verified to sum exactly), then cancelled 30 hours before the appointment — inside the service policy's 24–48h tier, not the 0–24h (0%) or 48h+ (100%) tiers — and refunds exactly 50% ($40.00), proving the per-mode policy (not a shared one) actually governs the outcome.
3. **RENTAL mode** — two independent rentals on the same variant: rental A's $200.00 deposit hold is partially captured for $75.00 (damage), leaving `PARTIALLY_CAPTURED` with `releasedRemainderMinor` of $125.00 correctly reported by the provider; rental B's deposit hold is released in full on a clean return, reaching `RELEASED`. Asserts the two holds never cross-contaminate — rental A's capture leaves rental B's hold untouched, and vice versa.

## Known gaps, honestly stated

- No service in this codebase yet writes a `payments` row itself — `CheckoutPaymentService.createCheckoutIntent` and `DepositAuthorizationService.captureHold`/`releaseHold` all still leave the `CHARGE`/`DEPOSIT_HOLD` row's initial persistence to the caller (this test does it explicitly, the same pattern every prior payments-service test already uses). A future card should decide whether that write belongs inside the service itself.
- No HTTP route exposes checkout, refund, or deposit placement/capture/release yet — every payments card to date has been service-layer-only; wiring to `apps/api` is tracked as an open gap since `D087`, unchanged by this gate.
- No merchant → connected-account mapping is persisted (`connectedAccountId` is still caller-supplied) — unchanged from `D087`/`D088`.
- Payments writes are not yet appended to the merchant's hash-chained audit log the way inventory/reservation/condition-report writes are (`AuditLogRepository` is never constructed in this test) — `verifyAuditChain` is therefore not asserted here, unlike `G4`'s record. This is a real, pre-existing gap across every payments card (`D087`–`D099`), not introduced by this gate; a future card should decide which payment events warrant an audit-log entry.
- As with every gate to date, "PASSED" here means the full local command sequence, not a fresh GitHub Actions run — the standing gap already documented in `G0`'s own record.

## Verdict

**PASSED.** Charges, application-fee splits, deposit holds/captures/releases, and per-mode refunds are all correct — proven by a real, passing, service-layer-only end-to-end test exercising all three fulfillment modes (PRODUCT, SERVICE, RENTAL), not by inspecting each piece separately. Phase 5 (`D087`–`D100`) is closed.
