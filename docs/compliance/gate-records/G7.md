# Gate G7 — Acceptance Record (MVP GATE)

**Gate criterion (`docs/design/01_phasing_and_mvp_definition.md`):** "MVP GATE. Pilot-capable, web only"
**Phase:** 7 — Customer Storefront (Web) (`D121`–`D136`)
**Date closed:** 2026-09-09
**Closed by card:** [`D136`](../../cards/D136.md)

## What "pilot-capable, web only" means here

Every prior Phase 7 card built and unit/service-tested its own slice: public merchant page (`D121`), product/service/rental listing detail with real availability (`D122`–`D124`), the availability calendar UI (`D125`), a mixed-mode cart (`D126`), hold-expiry enforcement (`D127`), checkout consent/deposit-disclosure (`D128`/`D129`), payment (`D130`), order confirmation (`D131`), order history with IDOR protection (`D132`), cancellation (`D133`), transactional notifications (`D134`), and an accessibility/responsive pass (`D135`). No prior card had ever run the whole customer journey through a real browser against a real, listening `apps/api` process — every test in this repo to date is either `app.inject()` (bypasses the network stack entirely) or a jsdom component test (never loads a real script or makes a real cross-origin request). This card is that missing proof, the same "compose, don't just unit-test in isolation" bar `G2`/`G4`/`G5` set for their own domains — and, being the MVP gate, the first time this codebase's `apps/api` has ever been started as a real, listening process at all.

## Verification performed this session

Five Playwright specs (`e2e/tests/*.spec.ts`, new this card) drive a real Chromium instance against a real `next build && next start` (`apps/web`) and a real `tsx watch src/serve.ts` (`apps/api`, new this card — see "New infrastructure" below), sharing one real SQLite file:

1. **`product-purchase.spec.ts`** — browse a PRODUCT listing (real stock-status render), pay through the real hosted-card-field UI (`PaymentView.tsx`), land on an itemized confirmation receipt with no card data anywhere in the DOM.
2. **`service-booking.spec.ts`** — browse a SERVICE listing, interact with the real free/busy slot picker (D123/D125) against real server-computed availability, pay, confirm the SERVICE line and price on the receipt.
3. **`rental-booking.spec.ts`** — browse a RENTAL listing, verify the deposit is disclosed *before* any date is entered (D124's security check, now proven in a real browser), pick an available date range (real availability check), pay, confirm the deposit hold appears on the receipt.
4. **`order-history.spec.ts`** — a customer authenticated via the real `/auth/register` → MFA-enroll → MFA-confirm → `/auth/login` sequence (see "Known gaps" — no UI exists for this yet) sees their own order in "Upcoming"; a second customer's order id returns a real 404 over real HTTP (D132's IDOR defense, proven end to end, not just at the service layer).
5. **`cancellation.spec.ts`** — a customer cancels an upcoming order by clicking a real "Cancel" button (new this card — see below) in `OrderHistoryView.tsx`; the row updates to `CANCELLED` with no page reload, and the button itself disappears (server-side `OrderAlreadyFinalizedError` guard's UI-side twin).

## New infrastructure this card had to build to make E2E possible at all

None of the following were this gate's original scope on paper, but "pilot-capable" cannot be verified — or be true — without them; each was a real, previously-undiscovered gap, found only because this was the first time a real browser and a real listening server were used together:

- **`apps/api/src/serve.ts`** — `apps/api` had never had a real process entrypoint; `index.ts` was a placeholder marker and `dev`/`start` were `echo` stubs. New `serve.ts` opens one real, migrated SQLite connection, wires a real `DbMerchantMembershipResolver` to it (closing the exact disconnect `app.ts`'s own doc comment on `connection?: Connection` had flagged: "Real end-to-end DB wiring for `apps/api` is still a future card"), and listens.
- **CORS (`apps/api/src/app.ts`, `@fastify/cors`)** — no CORS response headers existed anywhere; every one of `apps/web`'s cross-origin `fetch(..., { credentials: "include" })` calls would have been silently blocked by the browser itself in any real multi-origin deployment. `app.inject()` never surfaces this (it bypasses the network stack). Fixed by reflecting the same `allowedOrigins` allowlist the CSRF origin-check already uses, with `credentials: true`. New `apps/api/test/cors.test.ts` (3 cases).
- **CSP `connect-src` (`apps/web/src/security/csp.ts`)** — the strict CSP's `connect-src 'self'` silently blocked every cross-origin API fetch in a real browser; jsdom component tests never load a real script and so never hit this. `buildCspHeader` now takes an optional `apiOrigin` argument, wired from `middleware.ts`'s existing `API_URL`. New `csp.test.ts` cases (2).
- **`next dev`'s CSP-vs-`unsafe-eval` conflict** — webpack's dev-mode `eval(...)`-based devtool violates this app's own no-`unsafe-eval` CSP; `e2e/playwright.config.ts` runs `next build && next start` instead (also more representative of the real deployment target).
- **Cross-process SQLite path bug (this suite's own infrastructure, not app code)** — `playwright.config.ts` is re-evaluated in each Playwright worker process, not just the orchestrator that spawns `webServer`; an unconditional `mkdtempSync` at module scope minted a second, different temp-file path in the worker, silently disconnected from the one the API server was actually given. Fixed with a `??=` guard so the path is computed once and inherited.
- **"Cancel" button in `OrderHistoryView.tsx`** — D133 built cancellation at the service/HTTP layers only (its own acceptance criteria named no UI); no prior card added one. A pilot-capable storefront needs a customer to be able to actually cancel through the product, not just via a raw HTTP call, so this card added it (new `OrderHistoryView.test.tsx` cases).

## Known gaps, honestly stated

- **No customer-facing login, registration, or MFA-enrollment UI exists anywhere in `apps/web`.** `apps/web/src/app/login/page.tsx` is email/password only, no MFA step — and MFA is mandatory for *every* account, not just merchant staff (`NativeAuthProvider.register` always assigns the global `roles: ["OWNER"]`, and `MFA_REQUIRED_ROLES` checks exactly that field). `order-history.spec.ts`/`cancellation.spec.ts` authenticate via real HTTP calls against the real running API (register → enroll → confirm → login) and inject the resulting session cookie directly into the browser context — proving the *server* and the *authenticated pages* work correctly, but not that a customer can reach that state through the product today. This is a real, separate gap this gate does not close, tracked in `IMPROVEMENTS.md`.
- **`CartService`, `CheckoutDetailsService`, and `CheckoutDepositConsentService` still have no HTTP route** — open since `D126`/`D128`/`D129` respectively, still open as of this gate. A customer cannot add a line to a cart, submit contact details, or record deposit consent through any HTTP endpoint; `e2e/fixtures/seed.ts` seeds cart/order state directly through `@smb-os/db`, the same pattern every vitest fixture in this repo already uses internally (e.g. `gate-g4.e2e.test.ts`). What *is* real, HTTP- and UI-wired, and what these specs actually drive through a real browser: listing detail pages (with live availability/slot-picker/deposit-disclosure), payment, order confirmation, order history, and cancellation.
- **The `secure: false` cookie-injection workaround** in `e2e/fixtures/auth.ts` is a test-fixture-only concession for running over plain `http://127.0.0.1` (no local TLS is configured, out of scope for this card) — the real API still sets `secure: true` on its actual `Set-Cookie` response, correct for a real HTTPS deployment. No production code was changed by this.
- As with every gate to date, "PASSED" here means the full local command sequence, not a fresh GitHub Actions run — the standing gap already documented in `G0`'s own record. CI does not yet run `pnpm test:e2e` (browser install + two built servers is a meaningfully heavier CI job than the existing lint/typecheck/test/test:isolation steps) — a follow-up card should decide whether/how to wire it in.

## Verdict

**PASSED, with gaps stated above carried forward honestly.** Five critical customer journeys — product purchase, service booking, rental booking with deposit disclosure, order history with IDOR protection, and cancellation — all pass end to end through a real browser against real, listening `apps/web` and `apps/api` processes, not through `app.inject()` or component-level mocks. Three previously-undiscovered, real gaps (no CORS headers, a CSP that blocked every cross-origin fetch, and an `apps/api` with no real process entrypoint) were found and fixed as a direct result of this being the first real end-to-end run this codebase has ever had — exactly the kind of gap a gate like this exists to catch. The storefront is pilot-capable for the flows a customer reaches through built UI; cart/checkout-consent HTTP wiring and customer login/MFA UI remain open, tracked gaps for a following card, not silently assumed closed. Phase 7 (`D121`–`D136`) is closed.
